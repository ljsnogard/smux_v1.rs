# `bind_async(unspecified)`：由连接自行安排一个空闲 dock

> 主题：`connection` 的**绑定期**——`unspecified` 从「参数错误」改为「请连接自行安排」。
> 本文记录需求裁决、算法形状，以及实现中一次真实撞上的分配基线回归（`alloc_count`）
> 及其最终处理。中间结论已按「文档先清理」删掉，只留最终链条。

---

## 1. 需求与裁决

`MuxConnection::bind_async(local_dock)` 原来对 `Dock::unspecified()`（数值 `0`）报
`BindError::ReservedDock`。新语义：**它不是参数错误，而是让连接自行挑一个空闲 dock 并
在其上完成同样的独占绑定**——同 `bind(2)` 传入端口 `0` 由内核挑临时端口的传统。

四条裁决（用户确认）：

| 议题 | 裁决 | 理由 |
| --- | --- | --- |
| 候选范围 | **只给 `1024` 及以上**（`[1024, wildcard)`） | 仿 UNIX 特权端口约定：`0..1024` 留给调用方显式指定，自动分配不去争调用方惯用的低号段 |
| 候选耗尽 | **复用 `BindError::DockInUse`**，不新增变体 | 与「这一个 dock 被占」共用：调用方在两种情形下能做的事没有区别；同时不动公开错误枚举 |
| `wildcard` | **仍然报 `ReservedDock`** | 它的既有语义是「任意 remote」（listener 的哨兵，见 §4.3），不能充当**本端**身份；把它也算作「请自行安排」会丢掉「保留值不可作身份」这条可检测性 |
| 契约位置 | **写进 `abs_smux`** 的 `TrConnection::bind_async` 文档 | 这是所有实现都该遵守的约定，只在 `smux_v1` 里成立就等于没约定；只改文档、不改签名 |

调用方如何知道分到了哪个 dock：**不新增 API**。`DockBinding::local_dock()` 本来就有，
自动分配路径同样返回 `DockBinding`，值从那里读回。

---

## 2. 为什么必须落在注册表里，而且必须是一次临界区

「找一个空闲的」与「占住它」如果写成 API 面的两步（先查、再 `bind_dock_`），两个并发
`bind_async(unspecified)` 会选中同一个 dock。而 dock 一旦被选中就是**身份的一半**
（§4.1「dock 对即身份」），没有事后反悔的余地——先占的那个 binding 已经把身份发出去了。

因此分配落在 `ChannelRegistry_::bind_any_dock_`：**同一个写锁临界区内完成找与占**，
返回选中的值。API 面（`mux_bind_async_`）只负责把 `unspecified` 路由到这条路径、把
`wildcard` 拒掉，两条路径共用同一次「先 drain 释放邮箱」与同一套错误映射。

并发原子性由 `tests/thread_safety.rs::mux_auto_dock_allocation_is_atomic_tokio_` 钉住：
两条线程同时自动分配，双方都必须成功且 dock 互不相同。

## 3. 算法：两个互不重叠的来源

候选范围是 `[K_FIRST_AUTO_DOCK, wildcard)`。分配**不扫表**，只用两个来源：

| 来源 | 含义 | 单次代价 |
| --- | --- | --- |
| `reusable_docks_: VecDeque<Dock, A>` | 自动分配**曾发出、现已归还**的 dock（先进先出） | 出队一项，O(1) |
| `next_fresh_dock_: Dock` | 从未被自动分配过的**单调游标** | 取游标并前进，O(1)；只被「调用方显式占住的 dock」挡时才多走几步 |

### 3.0 复用池的形状与顺序（用户裁决）

- **容器**：`VecDeque` 而不是 `BTreeSet`。回收池不需要有序性，「取最小号」既多付
  O(log n)，也只是一个偏好；队列的入队 / 出队都是 O(1)。
- **顺序**：**先进先出**——`push_back` 收新归还的，`pop_front` 取（用户裁决）。
- **不做中间摘除**：调用方显式绑定恰好走了池里的某个值时，那一份留在池里，直到它
  出队那一刻被 `bound_` 复核拦下、**取出即消费**地丢弃，再试下一个。

代价（已知、接受）：池里会滞留「此刻已被显式绑定」的条目，于是
「池里的值一定未绑定」这条强不变量不再成立，只剩「值都在候选范围内」与「同一个 dock
至多一份」两条（都钉在 `assert_index_consistent_` 里）。后者由「取出即消费」与「只有
自动归还才入池」共同保证——池里一个值要被取出后才能再次入池，所以**不会出现同一 dock
的两份候选**，也就不会把它发两遍。

> **被推翻的中间结论**：一度按「FILO（后进先出）」实现为 `push_back` + `pop_back`，
> 并在 `bind_dock_` 里用 `retain` 就地摘除以保住「池里一定未绑定」。用户裁决改为
> **先进先出 + 出队时过滤**：顺序上「最早归还的最先复用」，实现上省掉线性摘除。
> 两者在稳态（绑一个放一个，池里只一项）下行为完全一致，只有批量归还后才看得出差别。

### 3.1 为什么不是一个纯游标

纯游标（只增不减、跳过已占用的）看着更省，但**永远不回收低位空洞**：游标一旦越过某个
值就不再回头，于是频繁 bind/unbind 的长跑连接会一路把游标推到 `wildcard` 才失败——而
实际上有大量空闲 dock。所以必须有回收路径。

### 3.2 为什么两个来源天然不重叠

- 游标**只增不减**：同一个值不会被它发出去第二次；
- 只有**自动分配发出过**的 dock 才进复用池，而它们全部已被游标越过。

于是「同一个 dock 被自动分配两次」在两个来源上都无从发生，也不需要「哪些 dock 分配过」
的额外记录。池里取出的候选仍会复核 `bound_`：这一步不是多余的防御性检查，而是「不做
中间摘除」换来的**正常路径**——滞留项正是在这里被丢弃的，绝不把「已被占用的 dock」发
出去。

### 3.3 候选耗尽

游标走到 `wildcard` 且复用池为空 ⇒ `ReserveErr_::DockInUse`（映射到
`BindError::DockInUse`）。单测用「直接把游标推到 `wildcard`」构造这个边界——真去绑
2^32 次当然不可能。

## 4. 复用池只收「自动分配发出的归还」

最初实现是「凡曾绑定、现已解绑的 dock 都进池」，最符合「空闲」的字面意思。它在
`tests/alloc_count.rs` 上撞了一次回归：**首次解绑多出一次注入分配**（11 → 12 次），
因为复用池的第一次入队要为它建缓冲区。

因果链：该用例在循环里每轮丢弃一个 `DockBinding`，`Drop` 投递释放消息；下一轮
`bind_async` 先 drain → `unbind_dock_` → 插入复用池 → 首次插入分配。功能是对的，但
「只用手动绑定的连接」因此要为一个它从不使用的特性付一次分配。

最终形状：`DockCtx_` 增加一个**随每次绑定重置**的标记 `auto_`

- `bind_dock_`（调用方显式指定）置 `false`；
- `take_free_dock_`（自动分配）置 `true`；
- `unbind_dock_` 只在 `was_bound && was_auto` 时归还进池。

三条推论：

1. **纯手动绑定的连接在解绑路径上零额外分配**（`alloc_count` 基线不变）；
2. 语义更准：复用池 = 「自动分配发出的 dock 的归还集合」，调用方显式绑定的值由调用方
   自己管理；
3. 「同一个 dock 先被自动分配、归还后被显式绑定、再解绑」不会误把那次解绑当成自动分配
   的归还——标记随绑定量置。

代价（已知、接受）：调用方显式绑定的 dock 释放后**不**进池。若游标已越过它，它就成为
一个再也用不到的空洞。这只浪费编号，不影响正确性；而混用两种绑定风格的连接本就少见。

## 6. 验证

- 注册表单测 7 条（每条在 tokio / compio 两个装配下各跑一遍）：分配互不相同且从 1024
  起、优先复用归还的、**先进先出**（最早归还的最先复用）、**滞留项出队即被丢弃**、跳过
  被显式占住的、低号段不参与、耗尽后靠复用池继续服务；
- 集成场景：B 侧自动分配一个 dock 并**在其上监听**，A 侧自动分配一个 binding 后向它
  发起子流，完成一次双向收发 + 半关闭——证明自动分配的值是**对端可寻址的真实身份**，
  而不是「报了一个数」；随后验证显式重绑报 `DockInUse`、丢弃后复用到同一个值；
- 线程安全：两条线程并发自动分配，两条都成功且 dock 不同；
- `tests/alloc_count.rs` 基线**保持不变**（复用池对纯手动绑定的连接零成本）。
