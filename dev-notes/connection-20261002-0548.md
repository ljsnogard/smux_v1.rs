## 2. 差距清单（按「不解决就写不下去」排序）

### 2.1 【阻塞·协议】冒烟测试的「同一 dock 上 64 条并发子流」与身份规则冲突

- `connection/mod.rs` §4.1 与 §11.7 已定稿：**`(local_dock, remote_dock)` 就是子流
  身份，同一 dock 对同一时刻至多一条活动子流**；要并发多条，发起方必须为每条分配
  **互不相同**的 `local_dock`（临时 dock，类比 TCP 临时端口）。
- 但 `tests/common/mod.rs` 的 §「关于同一 dock 上 64 条子流」明确采用「同一 dock 内
  按 FIFO 配对」的约定：发起侧对每个 `dock` 反复 `bind_async(Dock::new(dock))`，
  64 条并发 `open_channel_async(Dock::new(dock), ..)` 全部落在同一个 dock 对上。
- 这两条不能同时成立：
  - 按 §4.1 严格实现，第 2 条并发 `OPEN` 在同一个 dock 对上必须被
    `MuxError::Duplicate` 拒绝（而 `reserve_channel_` 目前**连重复检测都没有**，
    见 §2.5）；
  - 按测试的约定实现，就必须放弃「dock 对即身份」，给 dock 对加一条隐含的
    FIFO 顺序——这正是 §6「不引入 channel id」时论证过要避免的那类状态。
- 另外 `tests/common/mod.rs` 的断言
  `assert_eq!(handle.remote_dock(), Dock::new(dock))`：在「被动方镜像」语义下，
  被动方的 `local_dock` 是监听 dock、`remote_dock` 是发起方的临时 dock。该断言只在
  「两侧用了同一个 dock 取值」时才碰巧成立；一旦改用临时 dock 就会失败，必须改成
  `handle.local_dock() == Dock::new(dock)`。
- **结论**：要么改测试（推荐，协议不动），要么改协议。见 §5 Q2。

### 2.2 【阻塞·架构】「谁来唤醒写路径」——N 条发送环无法同时 park

这是本轮**最硬的技术问题**。事实核对：

- 每条子流发送环的应用侧（`ChannelTx`）与会话侧（写路径）各持一个 `buffex` 半部；
  应用提交（段 drop → `advance_write`）时，环**只**会唤醒「已在本环登记 park 的
  消费者」——`ring_core_.rs::advance_write` 先看 `CONSUMER_STNDBY` 位，再调
  `consumer_.wake(&state)`。
- 每个环**只有一个** consumer 等待槽（`half_.rs::RingHalf_` 单槽 + 单 STNDBY 位），
  且 `RingReader::read_async` 借用半部本身。因此「一个写循环同时 park 在 N 条环上」
  在现有 buffex API 下**不可行**；「每条环一个 park 任务」又会退化成 N 个任务。
- 于是需要一个**连接级**的「某条子流有数据可发」通知。它必须在**提交之后**触发，
  否则「通知 → 写循环查看（还没提交）→ 写循环重新 park → 提交无通知」会丢唤醒，
  表现就是**某条 channel 永久卡住**（冒烟测试会直接超时）。

现有可用的零件：

- `signal_.rs` 的 MPSC 通道已经是「多生产者 → 单消费者」的连接级通知通道，但语义
  定的是「应用**读走**接收环数据之后发窗口通知」；要复用它承载「发送环有数据」，
  需要扩展（内部扩展，不是公开 API）。
- 「提交后通知」的落点：`ChannelTx` 的 `TrBuffTryWrite::try_write` /
  `TrBuffWrite::write_async` 返回的**段**由应用 drop，drop 即提交。`abs_buff` 的
  `TrBuffSegmView` / `TrBuffSegmMut` 是公开 trait、`SegmMut::new` 是 public const，
  因此可以把段包一层，**在包裹类型的 `Drop`（字段声明顺序保证在内层段 commit 之后）
  发通知**；`write_async` 那条路可以用本项目已有的
  `gen_may_cancel_future` 生成具名 future 来映射段的类型（`TrBuffWrite::WriteAsync`
  本身就要求实现 `TrMayCancel`）。代价：约 100–150 行 + 要逐个实现段的 trait 方法。
- 备选（便宜但**不健全**）：`try_write` / `write_async` **进入时**就发通知，写循环在
  「收到通知但查不到数据」时 park 到**刚刚通知的那条环**上（让该环的 commit 兜住
  这次丢唤醒）。残留漏洞：若两条环都通知且都在持有段、都不提交，写循环 park 在第
  二条上，第一条的提交就没有任何事件；这是真实可构造的挂起。
- 备选（改上游）：给 `buffex` 增加「提交时回调 / 可由第三方登记的唤醒句柄」，或让
  `Ring` 支持多个订阅者。要动 `buffex` 自己的协议与测试，属跨仓库改动。

见 §5 Q4。**我倾向：包裹段 + 提交后通知**，因为它是唯一在现有 API 下既健全又不动
上游的做法，而且复用了项目已有的宏与 trait。

### 2.3 【阻塞·架构】一个循环还是两个循环（既有文档自相矛盾）

- `connection/mod.rs` §2 / `session_.rs` 说：内部只有**一个**中心循环（同时持
  `Rx` 与 `Tx`，「两条路径之间不靠大锁」）。
- 但 `sync_.rs` 的注册表里是 **`loops_: [CancelToken_<A>; 2]`**，且注释写明
  「`0` = 读循环，`1` = 写循环」；`MuxConnection::new` 的文档也写「spawn **读 / 写
  两个**循环」。`sync_` 比 `session_.rs` 晚写，更可能是真实意图。
- 技术差别是实打实的：
  - **单循环**：需要在同一个任务里 `select`「网络读」与「事件通道」两个 future，
    退出路径要同时处理两者的取消；
  - **双循环**：读循环只 park 在网络读上、写循环只 park 在事件通道上，两者通过
    注册表 + 事件通道协作，取消各自一个令牌——正好对上 `sync_` 已有的两个令牌与
    `mark_failed_` 的「一起触发」。
- 这一点还牵连 §2.2：只有写循环需要「发送环有数据」的通知；读循环只产事件，不消费
  该通知。

见 §5 Q3。**我倾向双循环**（与 `sync_` 的现成结构一致，且省掉 `select`），并把
`session_.rs` / 模块文档 §2 的「唯一中心循环」改写成「读 / 写两个循环，共享注册表」。

### 2.4 【阻塞·资源】`TrMuxConfig` 造不出 `Buff`，也没有帧暂存缓冲

- `TrMuxConfig` 目前只有 `allocator()` / `policy()` / `channel_capacity()`。建一条
  子流环需要「按容量分配一块 `Self::Buff`」，但 trait 里**没有**这个入口；集成测试
  只能自己写 `Owned::new_uninit_slice(capacity, CoreAlloc)`，泛型代码无法这么做。
- 读路径还需要一个「帧暂存缓冲」：`read_header_async_` 只解析帧头，载荷由调用方读
  （最多 `max_packet_size`，默认 4096）。这块内存同样没有出处。
- 因此需要给配置层补一个**公开**的构造入口（新增公开 trait 方法），例如
  `fn make_buff(&self, len: usize) -> Self::Buff`；帧暂存缓冲复用它
  （`Buff: BorrowMut<[MaybeUninit<u8>]>` 正好够用）。
- 顺带：`C` 的**所有权**要定。`policy()` 返回引用、trait 没有 `Clone` 约束，而
  「建流」发生在 API 侧、「窗口策略判定」发生在循环侧。最省事的做法是在
  `MuxConnection::new` 时把策略**展开成数值**（初窗、收缩/扩张水位、最小帧间隔、
  epoch）存进共享状态，之后运行时不再访问 `C`；`Alloc` 由 `AllocatorClone` 克隆；
  `capacity` 是 `usize`。这样 `C` 本身不需要 `Clone`，也不需要进共享单元。
- 这属于**公开 API 变更**（AGENTS.md §1），需要人类点头。见 §5 Q8。

### 2.5 【阻塞·控制面】注册表缺少承载子流实体的能力

`ChannelRegistry_` 现在只有「dock 链 + `remote_dock` 单链表 + 计数」，要变成能支撑
并发子流的索引，至少缺：

1. **节点要挂 owner**：`ChannelNode_` 目前只有 `remote_dock_`，需要按 §11.5 升级为
   持有 `Shared<ChannelOwner_<B, A>>`（`RegistryInner_<A>` 因此变成
   `RegistryInner_<B, A>`，`ChannelRegistry_` 同理）。
2. **按 dock 对查询**：写循环收到通知后要「由 (local, remote) 找到 owner」，现在
   没有这个入口（只有增删）。
3. **重复检测**：`reserve_channel_` 允许同一 dock 对上重复登记，`MuxError::Duplicate`
   目前**没有任何落点**。按 §2.1 的裁决，需要在这里拒绝第二个并发子流。
4. **入向待决队列**：被动方同一 dock 上可能有多条已 `OPEN`、尚未 `accept`/`reject`
   的子流，`income_async` 要按序取；现在 `DockNode_` 里只有 `inbound_waker_`。
5. **响应路由**：主动方的 `open_channel_async` 要等对端的 `OPEN`（更新发送窗口）与
   `ACCEPT`/`REJECT`；这些帧到达时必须能找到并唤醒对应的等待者。现在没有任何
   「等待建流结果」的槽位。
6. **遍历**：若采用「事件通道可能丢通知」的旧方案，需要全表扫描；若采用无界事件
   通道（见 §2.6），可以不需要遍历。

### 2.6 【阻塞·并发】事件通道的定容契约与「不丢」负担

`signal_.rs` 的实现（`flume::bounded`）与 §11.4 的契约绑定：**定容 + 每条子流一个
「已入队」位 + 队列满时置连接级「全扫」标志**。这套契约成立的前提是「所有通知都是
可重建的提示」。但在本轮的用法下：

- 「发送环有数据」的通知**不可重建**：丢了就是那条 channel 卡死；
- 控制帧（`OPEN` / `ACCEPT` / `REJECT`）若也走这条通道，**更不能丢**。

两个方向：

- **(a) 保持定容 + 认真实现「已入队位 + 全扫标志」**：契约完整，但要处理
  「置标志」与「消费者检查标志后 park」之间的竞态；
- **(b) 换成无界事件通道**：借助「每条子流至多一条待处理通知（owner 里的已入队
  位）」+「控制帧数量本来就有配额上限」两条约束，队列长度天然上界是
  `O(活跃子流数 + 控制帧数)`，`try_send` 不会失败，于是「全扫标志」整个机制可以
  不要。代价是与 §11.4 的定容结论不一致（要改决策记录），且失去内存上界的显式
  保证。

见 §5 Q6。**我倾向 (b)**：本轮优先要「不丢」，而内存上界由配额
（`max_channel_count`）间接保证；「定容 + 全扫」留到有内存预算诉求时再做。

### 2.7 【阻塞·所有权】会话侧环半部放哪：`Shared` 还是循环的本地表

- §11.3 写「注册时把**会话侧**两个半部交给 `MuxConnection`，`MuxConnection` 把它们
  放进**自己的会话本地表**」。
- 但 `abs_art` 的 `spawn` / `spawn_local` 要求 future `'static`，循环不能借用
  `MuxConnection`；而且子流是**运行时动态创建**的，创建时循环早已在跑，「本地表」
  必须能被循环实时看到。
- 因此实际只有两种落点：
  - **(a) 放进 `Shared<ChannelOwner_>`（注册表节点）**：循环用
    `SyncCell_::{with_, with_mut_}` 短闭包访问，**闭包内绝不能 `await`**，所以
    `try_read` / `try_write` 这类同步操作可以在锁内做，但「把数据搬上网」的 await
    必须挪到锁外（也就是要**先拷进循环自己的暂存缓冲**）；
  - **(b) 创建时通过事件通道把半部移交给循环**：循环本地持有，可自由 park/await，
    但事件通道要能承载「带类型的半部」，会把它变成泛型通道，且循环要做本地表管理。
- 另外 `buffex` 的段借用生命周期绑定在半部上：**半部不能藏在会跨 await 的锁后面**。
  这条是 (a) 必须「锁内取段 → 锁内 copy 出来 → 锁外 await 写网络」的原因。

见 §5 Q7。**我倾向 (a)**：不需要泛型事件通道、不需要循环本地表；代价是每帧一次
copy（对冒烟测试的几百字节到 2KB 载荷无所谓）。

### 2.8 【阻塞·流控最小集】窗口到底执不执行

`flow_ctrl` 的实现是完整的，但「接线到什么程度」是本轮的裁量点：

- **发送侧**：是否按 `SendWindow::available()` 切片、窗口为 0 就 park？若执行，就
  必须有接收侧的 `WINDOW_UPDATE` 来回补，否则「发满初窗 → 双方互等」。
- **接收侧**：`RecvWindow::on_data` 能判越权；但若发送侧不守规矩，读路径往接收环里
  写就会遇到 `Stuffed`。此时：(i) 判为流控违例、连接失败（`MuxError::FlowCtrl`）；
  (ii) 把剩余载荷暂存在循环的帧缓冲里，park 等应用消费（队头阻塞），不判违例。
- 两端都是本实现时，**只要发送侧守窗口，接收环在数学上不会溢出**（窗口 = 环容量，
  在途量已被 `W = W₀ − (S − R₀)` 扣掉），所以 (i) 在自洽实现下不会误触发，且能
  把「对端违约」变成显式错误；但调试期一旦算错就会整条连接失败，风险更高。
- 「流控不完全完善」的最小自洽集，我建议：
  - 建流时按 §4.2 通告 `(R, W)`（**已由线格式强制**，不做也发不出去）；
  - 发送侧**执行**额度（含窗口为 0 时 park），这是「多 channel 并发」下避免大
    channel 饿死/打死连接的关键；
  - 接收侧应用消费后经事件通道回补并**按 `should_report` 发 `WINDOW_UPDATE`**；
  - 接收侧遇到 `Stuffed` 先按 (ii) 暂存重试，**不**判违例（把严格判定留到流控轮）。

见 §5 Q5。

### 2.9 【阻塞·关闭与拆流】谁发 FIN/CLOSE、谁释放配额

- 关闭态已经定为「直读环两端」（§9）：应用 drop `ChannelTx` → 环的 producer 关闭；
  会话关掉接收环 producer → 应用读到 EOF。
- 但**拆流触发**没有定：应用 drop `ChannelTx` 之后，写循环要发 `Close`（`FIN`）并
  释放注册表配额；`ChannelTx` 的 drop 本身不会产生任何事件（环的 `close()` 只在
  「本环有 park 者」时唤醒，而写循环按 §2.2 **不 park 在环上**）。因此要么：
  - 给 `ChannelTx` / `ChannelRx` 加 `Drop`，在 drop 时发一条事件（推荐，简单可靠）；
  - 或者写循环额外 park 在环上（与 §2.2 冲突）。
- 还有「两侧半部都消失后，注册表条目与环内存何时归还」：读循环与写循环都可能先
  发现半边关闭，需要一份原子计账（或规定「谁发现谁释放，release 幂等」）。

### 2.10 【阻塞·保活】`PULSE` 与 `IdleTimeout` 的运行时部分

- 线格式、字段与「收到只刷新不回复」都已定稿并实现；缺的是：
  - 每条子流的**活跃时间戳**（owner 里加一个 `Instant` 或等价的 tick）；
  - 一个**计时源**（`abs_art::TrDelay`；缺省 feature 下没有 `Rt: TrDelay` 约束，
    要加 bound 或开额外 feature）；
  - 超时判定与 `MuxError::IdleTimeout` 的回传路径。
- 这依赖循环已经跑起来（没有循环就没有「闲置」可言）。见 §5 Q9，**我倾向本轮
  不做**计时，只把活跃时间与 `PULSE` 的**收发处理**挂上（收到 `PULSE` 能刷新窗口
  与活跃时间；本端不发或只在显式条件下发），把 `IdleTimeout` 留给下一轮。

### 2.11 【非阻塞·支线】telegraph 与「开场消息」

- `Telegraph` 整条支线（`open_telegraph_async` / `send_async` / `recv_async`）仍是
  `todo!()`。本轮目标只提 channel，可以留 `todo!()`。
- **发现一处 API 缺口**：`TrChannelHandle::accept_async` 只返回 `(Tx, Rx)`，没有
  任何出口能读到主动方 `OPEN` 携带的「开场消息」；按现有 trait，这条载荷只能**收下
  即丢弃**。要不要在 `abs_smux` 补一个出口，属跨仓库公开 API 变更，本轮先记遗留。
- `connection/mod.rs` §3 文档仍写 `flags::K_NO_PAYLOAD`（该位已在 §11.2.3 删除、位 3
  改作 `K_TOTAL_RESET`），文档待清理。

### 6.5.1 Q4 裁决的已知残留风险与必须遵守的实现契约

Q4 选的是「提交前通知 + park 兜底」，**不是**健全方案。必须把风险与契约写在代码旁：

- **残留漏洞**（真实可构造）：两条子流 A、B 各持有一个已借出但未提交的写段；两者
  都发了事件；写循环醒了、扫了一遍（都还没提交），于是 park 到**最后通知的**
  B 环上。之后 A 提交（A 的事件已被消费掉、A 的环没有被 park），B 一直不提交 ⇒
  **A 的数据永久发不出去**。
- **为什么在目标场景下大概率不触发**：单线程执行器下，应用从拿到段到 drop 提交
  之间**不经过 await 点**就不会把控制权交回调度器；冒烟测试的
  `write_channel_all_` / `try_write_all_` 正是这种形态。
- **实现必须遵守的契约**（把概率压到最低，且出问题时可见）：
  1. 「刚通知」按**最近一次收到事件的那条环**解释，且写循环在**每次醒来后先全扫
     一遍本地表**，再决定 park 到哪条环；
  2. 写循环**只在表内确实有环可 park** 时才 park；表为空时 park 在事件通道上；
  3. 每条子流的「已入队」位由**应用侧写路径置位、写循环在开始排空前清零**（顺序
     与 §11.4 一致：先清位、再读数据），因此重复事件无害；
  4. 该漏洞作为**已知限制**写进 `session_.rs` 与模块文档；若后续出现「channel
     卡住」类问题，**第一嫌疑就是它**，届时再升级为「包裹段提交后通知」（Q4 的
     建议方案），改动点集中在 `channel_.rs` 的段类型。

### 6.5.2 Q7 裁决带来的连带设计（与 §2.7 不同）

因为会话侧半部交循环本地持有，所以：

- **环不再经过 `SyncCell_`**：循环可以直接在环上 `read_async` / `write_async`
  （park 是被允许的），也**不需要**每帧一次 copy；
- 两个循环各自维护一张**按 dock 对索引的本地表**，节点用调用方注入的分配器分配
  （沿用 `ChannelRegistry_` 的侵入式单链表写法），表项 = `Shared<ChannelOwner_>`
  + 会话侧环半部；
- 移交通道必须承载**带类型的环半部** ⇒ 事件通道类型变成连接的内部泛型类型；
  读循环与写循环各一条通道（写循环通道带 `AttachTx` / 控制帧 / `TxReady` /
  `RxConsumed` / `Release`；读循环通道带 `AttachRx`）；
- `ChannelOwner_` 因此**只承载标量共享状态**（`FlowCtrl`、活跃时间、各类标志），
  环半部不在里面 —— 这也顺带消掉了 §11.3 里「半部藏在共享实体的锁后面」那条硬
  约束的冲突。
- **策略 `P` 的访问**：`RecvWindow::should_report<P>` 需要 `&P`，而 `C` 的
  `policy()` 只返回引用。做法是在共享上下文里存 `C` 本身，用
  `SyncCell_::with_(|c| …)` 的**短闭包**（不 await）在构造 `FlowCtrl` 与判定
  `should_report` 时就地取用；多线程配置下给 spawn 的那个 `impl` 补
  `C: Send + Sync` 的**实现级 bound**（不改公开 trait）。

## 6. 本轮已核对、会影响决策的硬事实（备查）

1. **环的 park 是单槽单位**：`buffex/src/ring/half_.rs` 的 `RingHalf_` 单槽 +
   `RingState` 的 `CONSUMER_STNDBY` / `PRODUCER_STNDBY`；`advance_write` /
   `advance_read` / `close_*` 只在兴趣位有效且登记被认领时 `wake()`。⇒ 一个写循环
   无法同时 park N 条环（§2.2）。
2. **段的提交点在段 drop**：`try_write` 只借出区间、不推进 wp；`advance_write`
   在段回收时执行。⇒ 「进入时通知」是提交前通知（§2.2）。
3. **`abs_art` 的 spawn 要 `'static`**，且 `TrJoinHandle` 无 `abort`、只有 `detach`
   ⇒ 循环必须自持状态、spawn 后 detach、靠取消令牌退出（§2.3 / §2.7）。
4. **`atomic_sync` 只有 preemptive（同步自旋）mutex**，没有 async mutex；
   cooperative rwlock 自带等待队列但需要 `alloc`。⇒ 「跨 await 持锁」在本项目里
   没有现成原语，`SyncCell_` 的闭包里不能 await（§2.7）。
5. **`TrBuffSegmView` / `TrBuffSegmMut` 公开、`SegmMut::new` 是 public const**；
   `TrBuffWrite::WriteAsync<'f>: TrMayCancel`；本项目已有
   `gen_may_cancel_future` 生成具名 future。⇒ 「包裹段 + 包裹 write_async」可行
   （§2.2）。
6. **`read_header_async_` 只解析帧头**，载荷由调用方按 `payload_len` 读；每帧都
   必须带非保留值的 dock 对；`max_packet_size` 默认 4096（`BasicOpts::DEFAULT`；
   `max_channel_count` / `max_dock_chan_count` 默认 `1<<28`；
   `max_channel_timeout` 默认 30s）。
7. **`ChannelRegistry_` 现状**：dock 链 + 每 dock 的 `remote_dock` 单链表、
   `inbound_waker_`、配额计数、两个循环令牌、`FailKind_`；**没有** owner 挂载、
   没有按 dock 对查询、没有重复检测、没有入向待决队列、没有建流响应槽。
8. **握手交付物**：`HandshakeDelivery { opts, tx, rx }`；`MuxConnection::new` 收
   `HandshakeDelivery<W, R>` 与 `C`，目前只把它俩存成字段（`Rx`/`Tx` 由连接独占）。
9. **基线验证**（本轮实测）：`cargo test --all-targets` = 58 passed + 2 ignored；
   文档记录的两 feature 配置 `check` / `clippy` / `doc` 全绿。

### 7.2 顺带落地的基础设施

- `flow_ctrl::ReportThresholds_`（`pub(crate)`）：把策略里的「通告阈值 / 最小帧间隔」
  在连接建立时展开一次，读写循环因此不需要持有 `C` / `P`；`RecvWindow::should_report`
  改为委托给 `should_report_with_`。
- `MuxError::cast_`：把 `MuxError<(), ()>`（注册表等只有类别、没有载荷的路径）搬成
  目标错误类型。
- `ChannelRegistry_` 升级：节点挂 `Shared<ChannelOwner_>`、入向待决表
  （`Pending` → `HandedOut` + 对端窗口快照）、`Duplicate` 检测、`find_channel_`、
  `allocator_()`；`mark_failed_` 现在会唤醒**所有**等待中的 API future
  （dock 入向等待者 + 每条主动子流的建流等待者）。
- `ChannelOwner_` / `ChannelState_`（`owner_.rs`）：`FlowCtrl` + 建流状态 + 活跃时间 +
  拆流记账，全部经 `SyncCell_` 短闭包访问（**闭包内不 `await`**）。

### 7.3 实施阶段查出的三个真实缺陷（值得记下）

1. **通告的窗口快照没有记账** ⇒ 对端第一帧被误判为 `FlowCtrl::PeerViolation`。
   `RecvWindow` 的越权判定以「最近一次通告」为准；建流时只用策略算了个数写进
   `OPEN`，却没有调用 `report()` 把它记进去。修法：建 `FlowCtrl` 之后立刻
   `recv_window_mut().report()`（两处：主动方 `open_channel_async`、被动方
   `accept_async`）。
2. **只读不消费地看待环段** ⇒ 同一段数据被反复上线（对端读到重复载荷）。
   写循环最初用 `segm.as_segm_ref().iter_slices()` **只读**段再写网络，段的已消费量
   没有推进，drop 提交时环的读指针不动。修法：改成 `move_items_to_buff` 把字节
   **搬进循环自有的暂存**（`scratch: Vec<u8>`，每条连接分配一次），搬出即消费。
3. **在「排空数据」里用了会 park 的 `read_async`** ⇒ 多子流直接死锁。
   `drain_one_` 原本用 `read_async(Demand::no_more_than(..))`；`no_more_than` 的最小
   需求是 0，但 park 的判定按「至少 1」算，于是空环上它会 park——而这一步一旦
   park，事件通道里的事件就再也送不进来。修法：`drain_one_` 改用**非阻塞的
   `try_read`**；等待新数据只由写循环第 2 步（与事件通道竞争）负责。

### 7.4 Q4 兜底的实现 refinement（与原裁决的差异，需知悉）

原裁决是「park 到刚通知的那条环兜底」。实现时发现：**只 park 在环上会在多子流下
死锁**——写循环睡在 A 环上，B 子流入队的 `TxClosed` 排在事件队列里没人取，而 B 的
对端正等它的 `FIN`。因此第 2 步改成「**同时轮询环与该环的数据 + 事件通道**」：
事件先到就处理事件并回到循环顶部（顶部会先非阻塞排空事件），环先到就回到顶部正式
取走数据。这仍然满足「覆盖提交前通知的竞态」，同时消掉了死锁。

### 7.5 未完成 / 已知问题

1. **`multi-thread` 配置的驱动未实现**（`MuxConnection::new` 仍是 `todo!()`）。
   原因：`Rt::spawn` 要求循环 future `Send`，而 `abs_buff` 的 trait 没给关联 future
   加 `Send`；把该约束在「共享字节游标」`wire_io_` 这一层补齐，会**连带要求握手模块**
   （它也复用 `ReadCursor`）以及若干测试辅助一起改成 `Send` 版本。该改动与
   「多 channel 并发」无关，故推迟。缺省配置（compio 首要）不受影响。
   连带：`channel_.rs` 的 `#![allow(unused_imports)]`（多线程 `new` 用不到那些导入）
   属于**临时**，实现多线程时应移除。
2. ~~**socket 传输（调用方驱动的泵 + 全被动环）在并发下丢读唤醒**~~：**已复查证伪**，
   见 §8.2。原记录（「一侧的 `pump_input_` 停在 `input.read_async` 不再被唤醒」）在
   当前修订上从 2×2 到 16×64、两个运行时各重复 3 次都无法复现，且其证据「连接层在

3. ~~**`tests/common/mod.rs` 的 1024 条冒烟场景仍是旧的「同 dock 并发」写法**~~

## 8. 后续复查：冒烟测试「无法完成」的真正原因（2026-10-02）

> 人类指示：调查 `tests/smoke_{tokio,compio}` 无法完成的原因，判定是**协议设计问题**
> 还是**通信底座（socket 装配）实现问题**；已知事实是 `buffex_sock_uds_demo` 中双方
> 能完成通信。

### 8.1 结论：都不是，是「测试场景 vs 协议身份规则」不一致

失败的唯一直接原因是：`tests/common/mod.rs` 的 1024 条冒烟场景仍按「同一 dock 内
FIFO 配对」在**同一个 dock 对上并发 64 条子流**，与 `src/connection/mod.rs` §4.1
「dock 对即身份」冲突。发起侧第 2 条 `open_channel_async` 被
`ChannelRegistry_::reserve_channel_` 正确拒绝为 `MuxError::Duplicate`：

```text
panicked at tests/common/mod.rs:733:
向对端 dock 发起子流应当成功: Duplicate
```

注意 panic 发生在 `open_channel_async` 处——也就是说**握手、`MuxConnection::new`、
`bind_async` / `listen_async` / `income_async` 都已在真实 socket 上跑过**，根本还没
走到并发数据传输。这正是 §6.5 **Q2** 已裁决的冲突（「改测试、协议不动」），只是当时
1024 条场景没有跟着改。

### 8.2 socket 底座在全规模下是好的（实测）

用临时探针把「socket + 调用方驱动的泵 + 全被动环」按 Q2 的正确形态（每条子流不同
临时 `local_dock`、载荷按 `(dock, index)` 自洽校验、带半关闭）从 2×2 放大到 16×64：

| 实验 | tokio | compio |
| --- | --- | --- |
| 未改的 smoke（`--ignored`） | ❌ Duplicate（同步） | ❌ Duplicate（同步） |
| 进程内直连环 2×2（`inmem_mux`） | ✅ | ✅ |
| socket 探针 2×2 / 4×8 / 8×16 / 16×64 | ✅ | ✅ |
| 真实 smoke 1024 条（仅改 dock 分配） | ✅ 6.1s，3/3 稳定 | ✅ 21.5s，3/3 稳定 |

两条推论：

1. **§7.5 第 2 条（socket 丢读唤醒）在当前修订上无法复现**：2×2 到 16×64、两个运行时、
   各重复 3 次都没有挂起。该现象很可能是「`reserve_channel_` 还没有 Duplicate 检测」
   时期的产物——当时 64 条子流共用同一个 dock 对，登记表被互相覆盖，表现为挂起；
   现在同一现场被显式拒绝成 `Duplicate`。
2. **`buffex_sock_uds_demo` 的「能通」不能用来推断 smux**：那个 demo 不跑 smux，用的
   是 buffex 的**主动环适配器**（`BuffRead` / `BuffWrite`）；smux 测试用的是**设备级
   适配器 + 全被动环 + 调用方泵**，是另一套装配。本轮已把这套装配单独验证到满规模。

## 9. 后续复查：`bind_async` 的 dock 绑定独占性（2026-10-02）

> 人类指示：「`bind_async` 的实现完全没有尊重设计协议——一个 dock 被绑定之后，后续
> 再对同一个 dock 绑定应该在返回结果上报错而不是允许。调查它是否约等于百分百允许
> 绑定不检测，并写测试钉住这个原则。」

### 9.1 调查结论：修复前确实是「除保留值外 100% 允许」

`mux_bind_async_` 修复前只有两道检查：

1. `local_dock.is_special()` ⇒ `ReservedDock`。而 `TrDock::is_special` 只覆盖
   `unspecified`（0）与 `wildcard`（`u32::MAX`）两个值；
2. `ChannelRegistry_::reserve_dock_(local_dock, DockUse_::Channel)`，其语义是
   「**用途种类**标记」而非绑定凭据：

```rust
match dock.use_ {
    None => { dock.use_ = Some(use_); Ok(()) }
    Some(existing) if existing == use_ => Ok(()),   // 同一种用途：幂等放行
    Some(_) => Err(MuxError::DockInUse),            // 只有跨种类才拒绝
}
```

而且 `use_` 在生产路径上**只会**被置成 `Channel`（`bind` 自己、`reserve_channel_`），
`Telegraph` 分支在 `open_telegraph_async` 仍是 `todo!()` 的情况下**不可达**。此外
`release_channel_` 会在该 dock 子流清零时把 `use_` 抹成 `None`，所以它连「种类」都
不是持久状态。

⇒ 除 dock 取 `0` / `u32::MAX` 外，**同一个 dock 反复 `bind_async` 永远成功**；没有任何
路径会检测「这个 dock 已经被绑定过了」。用户判断成立。

### 9.2 为什么必须新加一个字段，而不是改 `reserve_dock_`

`use_` 已经被两件事共用（种类标记 + 被 `release_channel_` 随子流清零），既不能表达
「绑定」的持久性，也会在剪枝 `is_empty_` 时把状态一起丢掉。因此：

- `DockNode_` 新增 `bound_: bool`，**并计入 `is_empty_`**（绑定期间节点不可被 prune）；
- 新增 `ChannelRegistry_::bind_dock_(dock)`：`bound_` 已置位或该 dock 已作 telegraph
  ⇒ `MuxError::DockInUse`；否则置 `bound_ = true` 与 `use_ = Channel`；
- 新增 `ChannelRegistry_::unbind_dock_(dock)`，由 `DockBinding` 的 **`Drop`** 调用；
- `mux_bind_async_` 改调 `bind_dock_`（不再调 `reserve_dock_`）；
- `reserve_dock_` 保留为「种类标记」，文档明确它**不**承担绑定独占性。

语义取「**绑定期间独占、drop 即解绑**」：`bind d` → 再 `bind d` 报 `DockInUse`；
`drop(binding)` 之后可重绑。已由该 binding 建出的 `ChannelTx` / `ChannelRx` 不借用
binding，解绑不会动它们。

### 9.3 钉住原则的测试

| 层 | 用例 | 断言 |
| --- | --- | --- |
| 注册表单测 | `sync_::tests_::dock_binding_is_exclusive_and_persistent` | 同 dock 二次绑定 `DockInUse`；不同 dock 互不影响；telegraph 占用的 dock 不能绑定；**子流清零后绑定仍有效**（`use_` 做不到这条）；解绑后可重绑 |
| 集成（tokio） | `inmem_mux::mux_bind_is_exclusive_tokio_` | 经公开 `TrConnection::bind_async`：二次绑定 `DockInUse`；解绑后重绑成功；对端同名 dock 不受影响 |
| 集成（compio） | `inmem_mux::mux_bind_is_exclusive_compio_` | 同上，跑 compio 运行时 |

反向验证：把 `bind_dock_` 里的 `bound_` 检查临时短路后，上面 3 条用例全部失败
（单测 + 两条集成），说明它们确实钉住了这条行为，而不是恒真。

### 9.4 连带影响

- `DockBinding` 新增 `Drop`（公开类型的行为变化，已随人类指示一并落地；其字段本就
  私有，不引入新的可观察限制）；
- `MuxError::DockInUse` 的文档与 `Display` 从「已被 channel 或 telegraph 占用」改为
  「已被绑定或已作其他用途占用」；
- `crate::connection` 模块文档 §4.1 增补「绑定层独占」一段；
- 现有全部收发场景（2×2 / 4×8 / 8×16 / 16×64）每个 `local_dock` 都只绑定一次，因此
  不受影响、无需修改。
