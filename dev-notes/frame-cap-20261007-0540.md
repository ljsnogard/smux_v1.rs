# 发送路径的帧上限收敛：一次积压超过一个帧不再让连接失败

- 日期：2026-10-07
- 状态：**已修复**（`src/connection/session_.rs` 的 `drain_one_`），带回归用例
- 发现路径：跨进程真机 demo（`smux_v1_sock_demo`）搬 8 MiB 时必挂 → 单一变量 A/B
  收敛到 `max_packet_size` → 读源码定位到 `drain_one_` 的帧总长检查

## 1. 现象

一条子流的发送环里**一次积压超过「一个帧装得下的量」**时，连接不再有字节流动：两端进程
**0 CPU、线程状态 `S`**，而且**没有**任何错误上报——应用侧停在 `open_channel_async` /
`accept_async_managed` / 子流读写上无期限等待（30 s 后才会被子流超时兜底报出
`IdleTimeout`）。同进程的验收用例抓不到：一端 park 时，另一端的活动会顺带把本端本地队列
推起来。

进程内的最小复现：子流环 8 KiB、**一次**写入 6 KiB → 稳定挂死（见 §4 的回归用例）。

## 2. 根因

写循环每次最多从一条子流搬走**一个逻辑读段**，搬之前检查帧总长，超限即返回协议错误：

```rust
// src/connection/session_.rs（修复前）
let want = core::cmp::min(available as usize, K_MAX_DATA_CHUNK);  // 只受 16 KiB 与额度约束
let demand = Demand::no_more_than(want);
let mut outcome = entry.reader_.try_read(&demand);
let take = segm.least_count();                 // ← 环里这一段的**逻辑长度**，可达 16 KiB
...
if take + K_MAX_FRAME_HEADER > shared.max_packet_size_ {
    return Result::Err(MuxError::FrameTooLarge);   // ← 一次正常的大写入被当成非法帧
}
```

缺省 `max_packet_size = 4096`、`K_MAX_FRAME_HEADER = 64`，因此**一次积压 > 4032 字节**
就会命中；应用只要一口气把发送环写满（`write_all` 在不阻塞的情况下会一次写完）就必然踩到。

为什么表现为「挂死」而不是报错：`FrameTooLarge` 让写循环走连接级失败，而**连接级失败
不唤醒在册子流上的等待者**（`src/metrics/mod.rs` 的「已知缺口」：`ChannelCloseReason::
ConnFailed` 只在文档层面表达）。两条叠加，应用侧看不到任何东西。

## 3. 修复

**只改一处**：把每轮的搬运量收敛到「一个帧装得下的量」，让 `FrameTooLarge` 退回它本来的
语义（应对真正的非法协商），而不是「应用一次写多了」的出口。

```rust
let payload_cap = shared.max_packet_size_.saturating_sub(K_MAX_FRAME_HEADER);
if payload_cap == 0usize {
    // 协商出的帧总长连一个帧头都装不下：这才是真正的非法协商。
    return Result::Err(MuxError::FrameTooLarge);
}
let want = core::cmp::min(available as usize, K_MAX_DATA_CHUNK.min(payload_cap));
```

不需要在 `drain_one_` 里写「拆帧循环」：写循环本来就是**轮转 drain** 的结构——
`drain_one_` 发完一帧返回 `Ok(true)`，主循环 `continue` 回到 `drain_once_` 再取下一段，
直到环排空或额度用尽。原实现只是把「一段」取大了，导致第一轮就撞上兜底检查。

## 4. 回归用例

- 场景：`tests/common/scenarios_/frame_cap_.rs`（`run_frame_cap_scenario_`）——
  环 8 KiB、**一次**写入 6 KiB、B 侧在「让出 4096 轮仍无进展即 panic」的看门狗里读满并
  逐字节比对，随后双向半关闭等 EOF。看门狗把「挂死」变成一条可读的 panic。
- 用例：`tests/inmem_mux.rs` 的 `mux_frame_cap_burst_dual_`（tokio / compio 各一格）。

修复前 / 后（compio 装配）：

```text
修复前：test mux_frame_cap_burst_dual_::compio_ ... FAILED
        看门狗：发送环里一次积压超过一个帧的容量之后，数据没有被拆帧送出
        （疑似撞上 FrameTooLarge 导致连接静默失败）        finished in 0.07s
修复后：test mux_frame_cap_burst_dual_::compio_ ... ok    finished in 0.01s
```

任何放大，帧上限回到协议缺省，吞吐只差约 5%（多出来的开销是每帧 4032 字节而不是 16 KiB
的成帧开销）。

## 6. 遗留（未修，待裁决）

**连接级失败不唤醒在册子流**：本次只消除了「正常写入被误判为失败」这条触发路径；一旦真
发生连接级失败（协议错误、传输中断），在册子流上的等待者仍然只会挂到超时。`smux_v1` 自己
把它记为已知缺口（`src/metrics/mod.rs`），修法是让 `ChannelCloseReason::ConnFailed` 从
「只在文档层面」变成真的回调。这属于失败传播语义的改动，需要单独裁决后再动。
