# 用 `mpmc-chan` 替换 `flume`（feat/mpmc-chan 试验）

- 分支：`feat/mpmc-chan`
- 日期：2026-10-26
- 状态：**已实施并通过三后端全量回归**
- 相关：`signal_` / `sync_` / `session_` / `owner_` / `Cargo.toml`

## 0. 结论先行

`flume` 的三处使用中，**两条事件通道与会话释放邮箱**换成 `mpmc_chan`（定容 MPMC
环）；**取消令牌**改用项目已有的零分配 `NotifySlot_`（理由见 §4，实测它才是性能
关键）。旧的 `flume` 实现保留在 `chan-flume` feature 下，便于同一提交内 A/B。

由于 `mpmc_chan` 没有无界模式，事件通道按「事件能否重建」拆成两条投递路径：

1. **可重建高频提示**（`TxReady` / `TgReady` / `RxConsumed`）：环满时丢弃，只置
   「需要全扫」标志；写循环直接进入全表排空，读循环按 `RX_CONSUMED` 位重算窗口。
2. **不可重建的一次性通知**（`Attach` / `Control` / `TgAttach` / 拆流 / 释放）：
   环满时进入自旋锁保护的 FIFO 暂存，**绝不丢**。

容量：`EVENT_CHAN_CAP = 1024`（首轮 256，跨线程压力测试后调大，见 §6）、
`MAILBOX_CHAN_CAP = 256`、令牌通知通道 `2`。事件类型实测 64 字节，
1024 容量约 64 KiB/通道。

## 1. 为什么不能「直接换掉」

`flume` 在本项目里承担的是**无界**语义：

| 使用点 | 原语义 | 为什么需要 |
| --- | --- | --- |
| `WriteEvent_` / `ReadEvent_` | 无界、单消费者 | `Attach` 携带环半部句柄；`Control` 携带控制帧；`TxReady` / `RxConsumed` 是水位提示 |
| `SessionMailbox_` | 无界、多消费者 | 句柄 `Drop` 投递释放消息，不能丢 |
| `CancelToken_` 通知 | 容量 1 | 取消信号的持久唤醒 |

`mpmc_chan` 的容量是编译期常量（2 的幂、`>= 2`），且连接配额默认是 `1 << 28`，
固定容量不可能覆盖「每子流事件数 × 子流数」。因此必须为「满」定义语义。

`signal_` 的旧文档早已预告过定容化的代价：需要「每条子流一个已入队位 + 队列满置
连接级全扫标志」。本轮把这个预案落成实现。

## 2. 事件分类与兜底

### 2.1 可重建事件（丢 + 全扫）

只有**高频提示**走这条路——它们的信息量只是「可能变了」，真正的事实来源是各子流
的状态位：

| 事件 | 重建方式 |
| --- | --- |
| `WriteEvent_::TxReady` | 写循环每轮 `drain_once_` 全表扫描，事件只负责唤醒；`Rescan` 直接进入本轮排空 |
| `WriteEvent_::TgReady` | 主循环 2.7 每轮全表排空所有 telegraph 端点 |
| `ReadEvent_::RxConsumed` | `RX_CONSUMED` 位 + 环内实际积压 → 读循环 `rescan_read_` 重算窗口 |

生产端用 `try_send_event_`：`Full` 时 `Overflow_::mark_()`（原子置位 + 单等待者
`NotifySlot_` 唤醒），然后丢弃事件。消费端 `try_take_event_` / `take_event_async_`
在取空后看到标志就返回 `EventTake_::Rescan`；读循环调用 `rescan_read_`，写循环
直接进入排空（`drain_once_` 本来是全表扫描，不需要额外状态位全扫）。

### 2.2 不可重建事件（暂存，不丢）

| 事件 | 为什么不能丢 |
| --- | --- |
| `WriteEvent_::Attach` / `ReadEvent_::Attach` / `TgAttach` | 携带环半部句柄，只能转移一次 |
| `WriteEvent_::Control` | 携带控制帧（`OPEN` / `ACCEPT` / `REJECT` / 窗口通告 / `CLOSE`） |
| `WriteEvent_::TxClosed` / `RxClosed` / `PeerClosed` / `LocalAbort` | 一次性拆流通知，且 timer 的 `Finalize` 只置 `GRACEFUL_FIN_REQUESTED`、不置 `APP_TX_CLOSED`，全扫无法可靠重建 |
| `ReadEvent_::Release` | 身份释放的一次性通知，丢了接收环写端不会关闭 |
| `WriteEvent_::TgTxClosed` | telegraph 发送半边的摘表通知 |

这些生产者改用固有方法 `EventSender_::try_send_durable_event_`：环满时把事件推进
`Overflow_::durable_`（`SpinningMutexOwned<VecDeque<E>>`），并置标志唤醒消费者。
消费端**先取暂存、再取环**，因此暂存事件不会被 `Rescan` 吞掉。

> 首版曾把 `TxClosed` / `PeerClosed` / `LocalAbort` / `Release` 也归入「可重建」，
> 后来发现 timer 的 `Finalize` 只置 `GRACEFUL_FIN_REQUESTED`、不置 `APP_TX_CLOSED`，
> 全扫无从恢复；`Release` 也没有可查询的「已释放」位能可靠区分「已处理 / 丢了」。
> 因此把低频的一次性通知全部改为 durable——它们每子流至多几条，暂存压力可忽略，
> 换掉了一整类恢复漏洞。

选同步暂存而不是 `send_async` 的理由：`ChannelHandle::Drop` / `TelegraphSender::Drop`
里的 `Control` / `TgTxClosed` 不能 `await`；而 `Attach` 的投递点虽然都在异步上下文，
统一成同步暂存可以保持「投递失败 = 消费者消失」这一条判据不变。

### 2.3 顺序

- 可重建事件与不可重建事件之间**没有严格顺序要求**：前者只是提示，状态位才是事实；
- 不可重建事件之间仍是 FIFO（`VecDeque`）；
- 正常路径（未满）仍是通道 FIFO。

## 3. `SessionMailbox_`

正常路径走 256 定容通道（多消费者可克隆）；`post_` 在 `Full` 时推进自旋锁保护的
`VecDeque` 溢出暂存，`try_take_` 先取环、再取暂存。`Drop` 里不 `await`、不取注册表锁。

这是唯一保留「无界兜底」的地方：释放消息无可重建的状态位（身份节点没有 `dropped_`
位），若改成全扫需要给每个句柄注入身份节点句柄。首轮先保证不丢，后续可再收敛。

## 4. `CancelToken_`（**未走通道**）

首版把容量 1 的 `flume` 换成 `mpmc_chan` 容量 2。功能正确，但实测它是性能热点：
每个循环每轮 park 都会新建一次 `cancellation()`，而 `mpmc_chan` 的 `recv_async` 在空
通道上进入慢路径、每次都要取**消费方向写锁**。1024 条子流的 `smoke_socket` 因此从
flume 的 13 s 退化到 **39 s**；把容量从 1024 调到 8192 仍是 39 s，证明与「满」无关，
就是每次 park 的慢路径开销。

改为复用本模块已有的 [`NotifySlot_`]（一个原子位 + 一个 waker 槽，零分配）：

- `cancel_`：`cancelled_` 的 CAS 成功后 `notify_`；
- `cancellation(self)`：`poll_fn` 每轮先查原子标志，未取消则 `poll_wait_` 登记；
- 单等待者契约与 `NotifySlot_` 的前提一致。

结果 `smoke_socket` 回到 **13.0 s**（flume 13.0 s）。因此取消令牌最终**不使用任何
通道**；`mpmc_chan` 只承担两条事件通道与会话邮箱。

## 5. 分配与容量

`mpmc_chan` 每个通道一次堆分配（`Arc<MpmcChan>` 包住 `Box<MpmcBuf>` + 两把方向锁的
`Arc`）。**缓冲区必须放 `Box`**：`MpmcChan` 在 `Arc::new_in` 里按值构造，owned
`MpmcBuf<E, N>` 会先在栈上生成 N 个槽；N=4096 时直接栈溢出（实测
`cross_thread_tokio_` SIGABRT）。改用 `Box<MpmcBuf<E, N>>` 后缓冲区落在堆上。

事件 enum 实测（`CoreAlloc`）：

```text
WriteEvent_=64 ReadEvent_=64 SessionEvent_=12 ControlFrame_=64
```

1024 容量 = 64 KiB/通道（两条事件通道 128 KiB/连接），对默认 `max_packet_size`
场景可接受；`MAILBOX_CHAN_CAP = 256` = 3 KiB。

与 `flume` 的差异：

- `flume` 无界：稳态不预分配固定槽位，但每入队一个节点分配一次；
- `mpmc_chan`：一次性预分配固定槽位，稳态入队不再分配。

因此 A/B 时既要看**总分配次数**，也要看**峰值 RSS**。`tests/alloc_count.rs` 的
注入分配器只统计全局 allocator 调用，`mpmc_chan` 的 `Arc`/`Box` 分配会计入；
`flume` 的节点分配也会计入。两边可直接对比。

- `cargo test -p smux_v1 --doc`：12 passed；
- `signal_` 新增单元测试：容量内 FIFO、可重建满时丢弃 + `Rescan`、不可重建满时暂存。

### 6.1 容量实测（`cross_thread_tokio_`，256 条并发子流）

| `EVENT_CHAN_CAP` | 结果 | 耗时 |
| --- | --- | --- |
| 256 | **超时失败**（20 s 看门狗） | >20 s |
| 1024 | 通过 | 3.66 s |
| 4096 | 通过 | 3.67 s |
| `chan-flume`（无界对照） | 通过 | 0.81 s |

256 不够：256 条子流各自要投 `Attach`×2 + `Control`（OPEN/ACCEPT）+ 水位事件，
突发量超过容量，可重建事件被大量丢弃并触发全扫；全扫本身 O(n) 且带注册表锁，
在 20 s 内没有收敛。1024 后跨线程用例通过。

> **注意**：上表的 1024/4096 计时是在 `CancelToken_` 仍走 `mpmc_chan` 时测的；此时
> 1024 条子流的 `smoke_socket` 无论容量 1024 还是 8192 都是 39 s，说明那 26 s 的差距
> 来自取消令牌而不是事件通道容量（见 §6.2）。取消令牌改为 `NotifySlot_` 后
> `smoke_socket` 回到 13.0 s。跨线程用例的最新计时见 §6.3。

### 6.2 性能定位：取消令牌是主因

| 版本 | `smoke_socket_compio_`（1024 子流） |
| --- | --- |
| `chan-flume`（对照） | 13.01 s |
| `mpmc_chan` + 取消令牌走 mpmc 通道（容量 2） | 39.32 s |
| `mpmc_chan` + 取消令牌走 `mpmc_chan`，事件通道 8192 | 39.56 s |
| `mpmc_chan` + 取消令牌走 `NotifySlot_` | **13.07 s** |

容量 8192 与 1024 同速，排除了「环满 / 全扫」；改取消令牌后立刻回到 flume 水平。
根因是每轮 park 都新建 `cancellation()`，`mpmc_chan::recv_async` 的空通道慢路径每次
取消费写锁。

### 6.2.1 尝试过但回退的优化

把 `take_event_async_` 从 `mpmc_chan::recv_async` 改成「`try_recv` + 自有
`NotifySlot_` 唤醒」后，`cross_thread_tokio_` 从 3.66 s **退化到 16.26 s**，已回退。
观察：事件通道只有一个消费者、park 次数远少于取消令牌，`recv_async` 的快路径
（读锁 + try_pop）比「每次 poll 都取 waker 槽 + 复检」更划算。

### 6.3 最新计时

| 用例 | 默认（mpmc） | `chan-flume` |
| --- | --- | --- |
| `smoke_socket_compio_` | 13.07 s | 13.01 s |
| `cross_thread_tokio_`（256 子流） | **0.83 s** | 0.81 s |

取消令牌改走 `NotifySlot_` 后，跨线程用例也从 3.66 s 回到 0.83 s——之前那 4.5 倍
同样主要是取消令牌的 `recv_async` 慢路径。事件通道本身的 `try_send` / `recv_async`
在 1024 子流 smoke 与 256 子流跨线程两个场景下都已与 `flume` 持平。

待做：

1. 用 `smux_v1_uds_bench` 对比 `chan-flume` / 默认的稳态吞吐与分配；
2. 给 `Rescan` 加计数（metrics 或 `#[cfg(test)]` 计数），确认 1024 下是否仍触发；
3. 若 `SessionMailbox_` 溢出频繁，再评估给身份节点注入 `dropped_` 位、彻底去掉
   无界暂存；
4. 评估把高频窗口通告（`WINDOW_UPDATE` / `PULSE`）改为可重建事件，进一步降低
   durable 暂存压力；
5. 补齐 tokio/smol 之外的后端全量回归（当前已跑默认 compio 与 tokio）。

## 7. 复现命令

```sh
# 默认（mpmc_chan + compio）
CARGO_HOME=<可写 cargo home> cargo test -p smux_v1 --all-targets

# 对照（flume）。注意：test-* feature 会顺带启用 chan-mpmc，`mpmc_chan`
# 依赖仍被编译（cargo 会报一条 unused dependency 警告），但 `signal_` 按
# `chan-flume` 选择 flume 分支，运行时行为是 flume。
CARGO_HOME=<可写 cargo home> cargo test -p smux_v1 --no-default-features \
  --features test-compio-runtime,chan-flume --all-targets

# 其它后端
CARGO_HOME=<可写 cargo home> cargo test -p smux_v1 --no-default-features \
  --features test-tokio-runtime --all-targets
CARGO_HOME=<可写 cargo home> cargo test -p smux_v1 --no-default-features \
  --features test-smol-runtime --all-targets
```

> 本机 `~/.cargo/git` 只读，`mpmc_chan` 的 git 依赖需要可写 `CARGO_HOME` 或已缓存
> 的 checkout；这与本次改动无关，是环境限制。
