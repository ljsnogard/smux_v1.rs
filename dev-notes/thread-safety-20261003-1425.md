## 1. 本轮要验的最小事实

同一个 `MuxCore` 的两个 `MuxConnection` 实例分处两条线程，在 compio 运行时上**并发**
对同一个 dock 调 `bind_async` 时，绑定独占性必须成立：恰有一个成功，另一个拿到
`BindError::DockInUse`。

## 2. 实测事实（本轮）

测试：`tests/thread_safety.rs::mux_bind_cross_thread_is_exclusive_compio_`。

装配方式：

- 两条被动内存环在主线程的 compio 运行时里完成握手并建出两个 `MuxConnection`；
  **读写循环因此留在主线程的本地队列**，跨线程的只有连接句柄（即「句柄可以走、
  reactor 不走」，outlook §3）；
- 逐轮（32 轮）起两条线程：各持一份 `MuxConnection` 克隆、各自新建一个 compio
  `Runtime`，用 `AtomicBool` 自旋对齐起跑线后立刻 `bind_async` 同一个 dock。

两条实测结论：

1. **该测试能够编译**，即 compio 作用域下 `MuxConnection` 已经是 `Send + Sync`
   （与 outlook §4 的编译期探针一致）。因此「跨线程移交句柄」这条边界在行为层面
   已被顺带钉住，不需要额外的手写 `Send` 断言才能成立。
2. **第 0 轮即失败**：一条线程拿到 `Ok(Bound)`，另一条在
   `src/connection/sync_.rs:62` panic `共享状态的临界区不可重入`。三次重跑结果一致
   （两条线程谁 panic 会换，但必然是「一成功一 panic」）。

## 3. 对原始假设的更正（因果链）

本轮开工时的假设是：「`MuxCore` 实质上没有 `CooperativeRwLock` 保护，所以跨线程
并发 `bind_async` 会 UB」。**这个前提不成立**：

- 身份表的字段就是
  `inner_: Shared<CooperativeRwLockOwned<RegistryInner_<A>>, A>`
  （`registry_.rs`）；
- `bind_dock_` 的「查 `bound_` → 置 `bound_ = true`」完整落在**一次**
  `with_mut_` 写锁临界区内（`registry_.rs:769-781`），跨线程下互斥由这把锁保证；
- 因此不存在数据竞争，**不是 UB**，也不存在「两个 binding 同时成功」的内存层面可能。

真正的缺陷在**争用策略**：`registry_.rs` 的 `with_` / `with_mut_` 只走
`try_read` / `try_write` 快路径，失败即 `on_lock_contended_()` → panic
（`sync_.rs:61-63`）。单线程时代「取不到锁只可能是重入」成立；句柄可跨线程之后
它**不成立**——另一条线程合法持锁同样让 `try_write` 失败。outlook §7 第 2 条与
§11 第 2 条早已预告「只改一半会得到一个既 `Send` 又会在合法竞争下 panic 的连接」，
本轮的行为测试把这句话变成了可执行的事实。

## 4. 测试自身的时序纪律（为什么这么写）

断言「恰好一个 `Ok` + 一个 `DockInUse`」只有在**赢家解绑之前，输家已经查过
`bound_`** 时才成立。否则赢家先丢弃 `DockBinding`（= 解绑），输家随后看到空闲 dock
而合法地绑定成功——那是本用例自己制造的时序假象，不是产品缺陷。因此：

1. 每条竞争线程两阶段汇合：先公布「本轮已出结果」，再自旋等对侧也公布完，
   **最后**才丢弃 binding；
2. `bind_async` 外面套 `catch_unwind`，把 panic 收成结果——否则 panic 的线程不会
   公布「已出结果」，对侧的自旋等待只能靠兜底上限超时；
3. 所有自旋等待都有界，保证「线程意外消失」表现为断言失败而不是挂死；
4. 起跑线用 `AtomicBool` 自旋而不是 `Barrier`：两条线程在同一 cache line 上自旋，
   放行后进入 `bind_async` 的时间差在纳秒量级，真正制造并发（而不是先后执行）。

## 5. 反向验证：这个测试确实可绿

把 `registry_.rs` 的 `with_` / `with_mut_` 临时改成「自旋等待锁」而不是 panic，
该测试 32 轮全部通过（`0.03s`）。**实验已还原**，工作区只留下新增的测试文件。

这条验证的意义是：测试编码的是「期望语义」，不是「当前 bug 的形状」；争用策略一旦
按 §7 改造，它应当直接转绿，而不需要再改测试。

## 6. 人类裁决：争用策略 = 无忙等的等待

本轮把 §5 的三支候选收敛成一条硬要求：

> 「两个 `bind_async` 尝试 bind **不同**的 dock，那么他们先后成功，后成功的那个
> 不应该有任何 **CPU 忙等**；如果尝试 bind **相同**的 dock，其中一个应该得到错误，
> 并且也不存在 CPU 忙等。」（并要求：这个要求**不是测试能检测到的**，属于实现品质）

推论（这是本轮最重要的一条技术结论）：**「不忙等」在 `atomic_sync` 里只有一条出路
——协作式读写锁的异步获取**。该 crate 的 `preemptive` 系列全是自旋锁；`cooperative`
系列的被动等待只经 `read_async` / `write_async`：拿不到许可时 future 返回 `Pending`
并登记 waker，由执行器把线程 park 掉，锁释放时唤醒。因此：

- 快路径仍然是 `try_read` / `try_write`（无争用时零等待、零调度）；
- 失败路径改为 `read_async().await` / `write_async().await`——**让出执行权**，
  CPU 不空转；
- 不再有 `on_lock_contended_()` 的 panic，也不再有任何自旋重试。

## 7. 人类裁决：`Drop` 不碰锁，只向 `MuxCore` 投递消息

> 「任何一个 `Drop` 按照协议设计，都不是马上释放 dock 而是进入 `WAIT_CLOSE` 或者
> `TIME_WAIT`，也即 `Drop` 本身不阻塞，只是向 `MuxCore` 投送一个 `Drop` 消息，然后
> 由 `MuxCore` 内部调度决定何时真正执行资源回收以及协议相关的动作（例如，向远端
> 通告 channel 关闭）。」

这条把 §5 里「`Drop` 不能 `await`」的死结解开了：**`Drop` 根本不需要锁**。
今天的四处 `Drop` 直改注册表（`DockBinding::drop` → `unbind_dock_`、
`ChannelListener::drop` → `release_listener_`、`Telegraph::drop` →
`release_telegraph_`、`ChannelHandle::drop`（发起方未裁决）→ `unreserve_channel_`）
是**偏离**：同一套纪律在 `ChannelTx::drop` / `ChannelRx::drop` 上已经是对的
——它们只 `try_send_event_` 投一条 `WriteEvent_`（`TxClosed` / `RxClosed`），
真正改状态、发协议帧的活由写循环做。本轮要做的是把上面四处也拉回同一条纪律。

`ChannelHandle`（响应方未裁决）已经是投递 `Control{Reject}` 的形状，可作模板。

同时 `MuxCore::drop` 里的 `reg_().cancel_loops_()` 也必须去掉：它是**同步读锁**，
同样会在合法竞争下 panic。改法是核心自己持有一份两个循环的取消令牌克隆
（`CancelToken_` 本身就是可克隆的共享句柄），`Drop` 直接 `cancel_()`，不碰注册表。

## 8. 落地记录（本轮已实施）

### 8.1 争用策略：协作式锁 + park（不是 `.await`）

新增 `sync_::TrBlockingAcquire_`（实现于 `CooperativeRwLockOwned<T>`）：

- 快路径 `try_read` / `try_write`，与改造前一致（无争用时零等待、零调度）；
- 慢路径把 `read_async` / `write_async` 的唤醒接到 `std::thread::park`：写一个
  「唤醒 = `unpark` 本线程」的 waker（`UnparkWake_`），手动 poll 获取 future，
  `Pending` 就 `park()`。许可释放时锁内部 `wake` 这个 waker → 线程被唤醒 → 重新
  poll。零 CPU 空转，也没有自旋的 cache line 乒乓。

**为什么不是 `.await`（把注册表整个异步化）**：取锁点分三类——async 上下文、
`Future::poll`（`income_async` 的 `poll_fn`）与 `Drop`。后两类无法 `await`，若只把
async 路径改成 `write_async().await`，同一把锁就有了两套等待语义（异步与同步等待
并存，极易写出活锁）。park 版同步获取把三类统一到一条策略上。
`tests/thread_safety.rs` 与 `tests/inmem_mux.rs` 的全部用例在这套策略下稳定通过。

采纳范围：

| 锁 | 改造前 | 改造后 |
| --- | --- | --- |
| 注册表（`registry_`） | 协作式锁 + `try_*` + panic | 协作式锁 + `TrBlockingAcquire_` |
| 取消令牌（`sync_::CancelToken_`） | **抢占式自旋**锁 + panic | 协作式锁 + `TrBlockingAcquire_` |
| 子流热状态（`owner_::ChannelOwner_`） | 抢占式自旋锁 + panic | 自旋锁 + **睡眠重试**（`TrBackoffAcquire_`，见 §9） |

取消令牌必须一起改：最后一个连接句柄可能在任意线程上被丢弃，`Drop` → `cancel_()`
与循环线程的 `cancellation()` 轮询会真正撞上。

### 8.2 `Drop` 只投消息：`SessionEvent_` + `SessionMailbox_`

- `signal_` 新增 `SessionEvent_`（`UnbindDock` / `ReleaseListener` /
  `ReleaseTelegraph` / `UnreserveChannel` / `ReleaseChannel`）与
  `SessionMailbox_`：无界 `flume` 通道，**可多消费者**——两个循环与任意 API 面都
  可以 drain，每条消息只会被其中一个取到。
- 邮箱放在 `ChannelRegistry_` 的**锁外字段**里（`Clone` 共享生产端、克隆消费端）。
- 四处 `Drop` 改为 `post_session_event_`（`DockBinding` / `ChannelListener` /
  `Telegraph` / `ChannelHandle` 的 `abort_pending_`）；`ChannelTx` / `ChannelRx`
  本来就只投 `WriteEvent_` / `ReadEvent_`，未动。
- **drain 点**：两个循环每轮开头各一次；会创建 / 认领身份的 API 操作
  （`bind` / `listen` / `open_telegraph` / `open_channel`）在动身份表之前各一次。
  `drain_session_events_` 自身只 `try_take` + 逐条落实（每条落实都重新取锁），
  因此**不得在持锁时调用**。

### 8.3 语义确认：binding 无定时宽限

人类裁决选 A：`DockBinding` 是纯本地身份（帧属于 channel，不属于 binding），因此
`UnbindDock` **消息落实即释放**，不设 `WAIT_CLOSE` / `TIME_WAIT` 宽限；「丢弃
binding 后立刻重绑」这条既有约定保持不变，确定性由「`bind_async` 先清空释放邮箱」
保证（§8.2 的 drain 点）。channel 一侧的宽限期（`release_channel_` → `WAIT_CLOSE`
→ 到期回收）本来就是既有实现，未动。

### 8.4 `MuxCore::drop` 不再取锁

核心新增字段 `loops_: [CancelToken_; 2]`（建连时从注册表克隆一次，见
`CoreBundle_::build_`），`Drop` 直接 `cancel_()`。`MuxConnection::new` 取循环令牌
也改走核心字段，不再经注册表读锁。

### 8.5 测试

- `tests/thread_safety.rs` 新增第二个用例
  `mux_rebind_after_cross_thread_drop_compio_`：线程 A 绑定并持有 → 主线程确认
  `DockInUse` → A 丢弃 → 主线程**立刻**重绑必须成功。这条把 §8.2 的「Drop 投消息 +
  bind 前清空」钉住。
- 全量回归：`cargo test` 全部通过（73 lib + 12 inmem + 2 layered_rpc + 2 + 2 smoke
  + 2 thread_safety + 4 doctest），`cargo clippy --all-targets` 无告警；
  `thread_safety` 连跑 20 次全绿。

### 8.6 尚未做的一项（本轮范围的边界）

**「不忙等」在 async 路径上仍是 park（占住运行时线程）而不是 `.await`。** 这是本轮
为了「三类取锁点一条策略」付出的代价；若实测发现某条纯 async 热路径因占线程而受害，
再为它单独引入 `*_async` 获取（`with_read_async_` / `with_write_async_`）即可，
两者语义互补、互不干扰。

## 9. `ChannelOwner_`：保留自旋锁，但争用改为睡眠重试（人类裁决 B）

`owner_::ChannelOwner_` 仍用抢占式自旋锁，但取锁路径从「`try_*` 失败即 panic」改成
[`TrBackoffAcquire_`](crate::connection::sync_::TrBackoffAcquire_)：失败时
`thread::park_timeout(50µs)` 后重试。

三个候选与本轮裁决的因果：

| 方案 | 不忙等 | 不 panic | 额外分配 | 争用延迟 | 裁决 |
| --- | --- | --- | --- | --- | --- |
| A 留到第 2 期 | ✗（自旋） | ✗（panic） | 无 | — | 否 |
| **B 睡眠重试** | ✓（线程睡眠） | ✓ | 无 | 受定时器粒度约束（约 50µs 起） | **采纳** |
| C 换协作式锁 | ✓（park/唤醒） | ✓ | **每条子流一次全局 `Arc`** | 无额外 | 否 |

否决 C 的理由：`ChannelOwner_` 按**子流**分配，协作式锁每次构造都要
`Arc::new(RwCore)`，与「不隐式分配、不隐藏内存预算」的纪律冲突，也把注册表那处
「每次连接一次」的已记录例外放大成每子流一次。B 的代价（争用时延迟下探到定时器
粒度）只落在**争用**路径上，正常快路径依旧是 `try_*` 一次 CAS，因此对数据面无影响。

正解仍是 outlook §5.5／第 2 期：把热状态钉在 reactor 线程（窗口记账、建流状态机、
去重位迁入循环本地，应用面只留环状态），跨线程只剩「身份 + 标量」的消息与回复；
届时这把自旋锁与整条退避路径一起消失。B 是那之前「不 panic 且不忙等」的最小代价
选择。

## 10. 原始待裁决项的现状

outlook §10 Q2 的 (i) / (ii) 两支**都被本轮裁决取代**：不再需要「运行时模式值」，
也不需要「持有者线程 id + 自旋」——因为等待本身不再是自旋（park / await），
而 `Drop` 也不再取锁。若将来仍要保留重入 fail-fast，应作为**调试断言**单独设计，
而不是争用策略的一部分：`TrBlockingAcquire_` 的重入后果从「panic」变成了「永久
park」，这是本轮的**已知代价**（当前代码没有重入，见 §5 的闭包检查）。

## 11. 最终架构（人类裁决：删掉阻塞式闭包取锁）

### 11.1 裁决原文与因果

> 「现在的代码所有尝试获取读写锁使用 `with_mut` 之类的写法全是错的，它强迫调用者
> 阻塞等待，但我们要实现的方法签名本来就是 async 且支持通过外部传入 cancel token
> 来取消等待。……必须改成直接通过 `acquire_session` 来取得锁，并且正确实现 async
> 和 cancel token 的语义。」

这条推翻了 §6–§9：park（§8）与 `park_timeout` 睡眠退避（§9）都是「为了复用旧闭包
API 而把等待塞进同步路径」的产物。同时裁决：
- 注册表**不对会话句柄公开**（不暴露 session/内部结构），访问收口到 `MuxCore`；
- 保留**唯一一把**注册表锁（不新增任何等待助手）。

### 11.2 取锁形状：`acquire_session` + 可取消异步获取

`sync_` 新增（取代 `TrBlockingAcquire_` / `TrBackoffAcquire_`）：

```rust
pub(crate) type CoopSession_<'a, T> = CooperativeAcqSession<'a, T, usize, AtomicUsize, StrictOrderings>;

pub(crate) async fn acquire_write_<'a, 'g, T, K: TrCancellationToken>(
    session: &'g mut CoopSession_<'a, T>, cancel: K,
) -> Result<CoopWriteGuard_<'a, 'g, T>, LockCancelled_>
{
    if let Result::Ok(guard) = session.try_write() { return Result::Ok(guard); }
    session.write_async().may_cancel_with(cancel).await.map_err(|_| LockCancelled_)
}
```

守卫能逃逸出这个 `async fn`（`acquire_guard_escapes_session` 探针钉住），因为它借用的
是**调用方自建的会话**。因此注册表的每个方法直接写：

```rust
pub(crate) async fn bind_dock_<K: TrCancellationToken>(
    &self, local_dock: Dock, cancel: K,
) -> Result<(), ReserveErr_> {
    let mut session = self.inner_.acquire_session();
    let mut guard = acquire_write_(&mut session, cancel).await?;   // 可被 cancel 掉
    let inner = &mut *guard;                                       // 临界区**不跨 await**
    ...
}
```

- **没有 `with_*` 闭包包装**：取锁语句就在每个方法体里；
- 失败路径**不再阻塞**：`write_async().may_cancel_with(cancel).await` 让出执行权，
  由执行器 park 线程、锁释放时唤醒；取消则返回 `LockCancelled_`
  （`ReserveErr_::Cancelled` → 各 API 面的 `Cancelled` 变体）；
- 临界区仍在 `await` 之后同步完成，**不跨 await 持锁**。

### 11.3 访问收口到 `MuxCore`

- `ChannelRegistry_` 的每个共享状态方法都 async + 收 cancel token；会话句柄
  （`DockBinding` / `ChannelListener` / `ChannelHandle` / `Telegraph`）不再直接触
  注册表，而是经 `MuxCore::{bind_dock_, reserve_listener_, reserve_channel_,
  drain_session_events_, attach_owner_, take_inbound_report_, failure_, ...}`；
- 两个循环是例外：它们持 `LoopShared_`（核心在循环侧的展开）直接访问注册表，
  理由仍是「循环不持核心强引用，否则核心永不析构」。

### 11.4 同步上下文清零（不能 `await` 的地方一律不再取锁）

| 位置 | 处理 |
| --- | --- |
| `CancelToken_`（`is_cancelled` / `cancel_` / `cancellation().poll` 都是同步） | 改**无锁**：`AtomicBool` 置位 + 构造时建立的 `flume` 通知通道（容量 1）。`cancel_` = 首次置位者投一条；`cancellation()` 返回 async 块（先查原子、再 `recv_async`）。通道持久 ⇒ 先取消后登记不丢 |
| `ChannelOwner_` 的 `tx_queued_` 去重位（`ChannelTx::try_write` 同步路径） | 移出锁成为 `Shared<AtomicBool>`，用一次 `swap` 表达「是否首个置位者」；同步路径完全不取锁 |
| `ChannelOwner_` 其余状态 | 换协作式锁 + `with_async_` / `with_mut_async_`（异步、可取消） |
| `Establish_` 的建流等待者 | `WakerSlot_` → **持久通知通道**：`notify_`（try_send）+ `wait_establish_` 里 `recv_async` 与取消竞争。不再需要 `cx`，因此不再有手写 `poll` |
| `ChannelListener::income_async` | 同上：per-listener 通知通道 + 真异步等待（`failure_` / `take_pending_inbound_` / 通知三路，全部可取消） |
| 注册表 `loop_token_` / `cancel_loops_` | 令牌移到**锁外字段**，构造与 `Drop` 都不取锁 |
| `accept_async` 的安装步骤 | 建环保持同步（不取锁）；`take_inbound_report_` / `apply report` / `attach_owner_` 移进**可取消的 step 函数**；环被拒时改投 `SessionEvent_::ReleaseChannel` 消息 |
| `WakerSlot_` | 两个用户都改成通知通道后**整体删除** |

### 11.5 公开 API（已获同意）

`BindError::Cancelled` 与 `BindingError::Cancelled` 新增，与已有的
`HandleError::Cancelled` / `ListenerError::Cancelled` 对齐：等锁期间被取消时如实上报。

### 11.6 测试适配

单元测试是单线程无争用场景，因此在 `#[cfg(test)]` 下加了**同步壳**（`_t_` 后缀方法 /
`ChannelOwner_::with_`），内部是「`NonCancellableToken` + `block_on`」；生产路径一律
异步可取消。监听相关单测按通知通道语义重写（取消/失败/待决三路）。
