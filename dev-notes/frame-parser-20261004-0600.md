# 帧头解析改为 sans-IO 逐字节状态机

日期：2026-10-04 06:00
主题：`connection` 模块的帧头（`FrameHeader`）解析算法。

## 1. 问题：环容量极小时现有解析器直接失败

现有入口 `frame_::read_header_async_` 用 `ReadCursor` 包住读半边，**按字段**索要字节：

```text
读 1 字节（帧首 / 字段头）          要求 Demand::exactly(1)
读 width 字节（字段值，1..=8）      要求 Demand::exactly(width)
```

`url` 这一层的约束来自 `buffex::ring`：`Ring::try_read_internal_` 在

```text
min_len > cap  ⇒  ConsumerError::Unsatisfiable
```

处直接失败（`buffex/src/ring/ring_core_.rs:260`），而 `Unsatisfiable` 是**终态**，
不会被 `BuffRead::read_async` 的 pump 循环重试。

于是一旦环容量 `cap < width`：

- `width = 1` 的字段没问题（容量 1 恰好够）；
- 任何一个 2 / 3 / 4 / 8 字节宽的字段（`RemoteDock` 取 `BeU16` 起、
  `RecvTotal` 取 `BeU16` 起、`PayloadLen` 超过 `0xFF`）都会把
  `Demand::exactly(width)` 变成不可满足，解析器把它当作「读方向传输错误」，
  **整条连接失败**。

即：`cap == 1` 时**任何**带 2 字节以上字段的帧都解析不了。容量本身是合法的
（`buffex` 的 `MIN_CAPACITY == 1`，见 `ring/tests_.rs` 的
`try_new_accepts_min_capacity_one_`），失败的是解析算法。

另注：`connection` 模块文档 §5 目前把「连接读环必须能整块驻留一个满帧」写成硬约束，
用来回避「环满 vs 解析器还差几字节」的互等。那是**帧暂存环**（`StageRing`）的容量
前提，与本条并不冲突：本条的动机是让**解析算法**不再对单次索取量提出下限，
从而在与传输直接打交道的环（例如 `ConnRx`，容量由调用方注入）上也能工作。

## 2. 决策

**把帧头解析重写成一个 sans-IO 的逐字节状态机**，它自带一个定长的内置字节数组，
随逐字节推进产生状态变化，直到帧头解析完成。

### 2.1 内部缓冲需要多大：9 字节足够

字段是**逐个串行**解析的：任意时刻只有一个字段「在途」。而一个字段在线上最多是

```text
1 字节自描述头 + 8 字节大端值（BeU64）
```

因此内置 `[u8; 9]` 的定长数组就足以覆盖所有情况——与帧长、字段数量都无关。
这与握手侧 `codec_` 的结论同源（模块文档「为什么可以『不保存整帧』」）：
宽度只由**该字段自己**的头字节决定，读到一条就能立刻解码。

**这块缓冲就是值字节的存放处**（`[0]` 是当前字段的自描述头字节、`[1..=width]` 是它的
值），不是「解析完就丢的临时区」：收到一条字段的最后一个字节后直接从本缓冲按大端解码，
既不额外申请长度、也不额外保存副本。状态里只留一个「已收到几个字节」的进度计数。

> 落笔时的教训：最初这版解码写成「把值拷进 `[u8; 8]` 后 `from_be_bytes`」，但用
> `Iterator::zip` 对拉两个**长度不等**的迭代器时，短的一侧耗尽即停，剩余高位槽不会被
> 赋值——结果被当成左移放大（宽度 1、值 `0x07` 解出 `0x0700_0000_0000_0000`）。
> 单元测试立刻钉住了它（`window_update_frame_requires_window_report` 等三条）。
> 修法是按宽度显式取字节切片，把值拷到 8 字节槽的**末尾**、高位留 0。

### 2.2 状态划分

```text
Start  --帧首字节-->  FieldHeader  --自描述头字节-->  FieldValue(width)
FieldValue --收满 width 字节-->  FieldHeader（或 Done）
```

- `Start`：等帧首字节，一次拆出 `kind`（低 4 位）与 `flags`（高 4 位）；
- `FieldHeader`：等自描述头字节，拆出 `field_id`（低 4 位）与 `val_type`（bit 4..=6，
  bit 7 按保留位忽略）；**在这里**完成「标识已知 + 宽度被该标识接受」的校验；
- `FieldValue`：把值字节按大端累加进一个 `u64` 累加器；收满即解码、按标识归位，
  然后回到 `FieldHeader`；
- 读到 `PayloadLen` 时头结束：此后做与旧解析器**逐条对应**的组合校验
  （dock 对必需、窗口通告成对且与 `kind` 匹配、`ReasonCode` 只在 `REJECT`、
  `K_TOTAL_RESET` 只对窗口通告帧），产出 `FrameHeader`。

### 2.3 对外接口

1. **逐字节推进**：`consume_byte_(byte) -> Consume_`，`Consume_` 三态
   （`Pending` / `Done(FrameHeader)` / `Failed(MuxError)`）。
   **「还需要更多输入时必定消费这 1 个字节」**——包括「这 1 字节正好让帧头完成」
   （`Done`）或「正好判定帧头非法」（`Failed`）两种情况；出了结论之后的重复喂入
   一律返回既成结论、不再消费。这条不变量让喂字节的循环不必回退或缓存，
   因此在字节流上不会丢字节。
2. **取结论**：`finish_() -> Option<Result<FrameHeader, MuxError>>`，供「先按需要喂
   字节、再统一取结果」的调用方收尾（帧头完成时最后一个字节已被消费），以及需要
   复核结论的场合。已出结论时幂等；未出结论返回 `None`。
3. **接受 `TrBuffRead` 的异步入口**：内部按**每次只索要 1 字节**
   （`Demand::exactly(1)`）循环喂入状态机，于是 `min_len == 1 ≤ 任意合法容量`，
   `Unsatisfiable` 这条路径**从构造上不再可能**。错误映射比旧入口更细：
   读失败 → `Transport { write: false }`、取消 → `Cancelled`、
   关闭语义（`PeerClosed` 或底层 `Closing` 标签）→ `PeerClosed`。

### 2.4 与旧实现的兼容面

`FrameHeader`、`MuxError`、`FieldId` / `FrameKind` / `flags` 等公开类型一律复用，
**不新增对外 API、不改动任何现有签名**。本轮实际改动只有三处：

- 新增 crate 私有模块 `src/connection/frame_parser_.rs`（含状态机、异步入口与单元测试）；
- `connection/mod.rs` 加一行 `mod frame_parser_;`（模块仍**不对外导出**）；
- `frame_.rs` **纯新增**一个 `pub(crate) fn decode_dock_field_`，让新状态机与旧入口
  共用唯一的 dock 校验出处；既有的项一律未动。

`session_.rs` 的调用点切换留待下一轮，届时可与旧入口做等价性对拍。

## 3. 落地与验证记录

实现即上述设计，无偏离。验证证据：

- `cargo test --lib`：**93 passed / 0 failed**，其中 `frame_parser_` 下 16 条（含
  「容量 1 的环」与「空输入判对端关闭」两条异步用例）；
- `cargo test --doc`：4 passed / 3 ignored（新模块的三段示例因模块尚未导出而标记
  `ignore`，接入后应改回可编译示例）；
- `cargo clippy`：新模块与改动文件**零告警**（仓库既有的 `allocator_api`
  stable-features 告警与本轮无关）。

**关键用例 `capacity_one_ring_parses_header_`** 直接钉住本 dev-note §1 的失败模式：
在容量 1 的环上，分别解析 7 / 9 / 13 字节的三个帧头（最后一个含 `BeU64` 的
`RecvTotal`，远超容量），并用「边写边读」的 `join!` 驱动——这正是旧入口会拿到
`Unsatisfiable` 而整条连接失败的场景。

  有了逐字节解析后，这条约束对**读环**已非必要（对写环的分块写入本就有别的理由）。
