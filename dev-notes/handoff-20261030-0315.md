## 3. P0：修复两个失败测试

### 3.1 `metrics_e2e`：帧长口径不一致（发送 24 / 接收 84）

- **断言位置**：`smux_v1/tests/metrics_e2e.rs:318`——
  `assert_eq!(snap.frame_bytes_sent, snap.frame_bytes_recv, ...)`；下一行还有
  `frames_sent == frames_recv` 的条数断言。
- **实测**：`发送 24 / 接收 84`（稳定，0.02 s 内失败）。
- **已知线索**：
  - 场景是「A/B 两条连接、一条子流、双向 4 字节 `ping`/`pong` + 半关闭」；
  - 发送侧计数点在 `main_loop` 组帧（`write_control_frame_async_` / `try_write_control_frame_`）
    与 `mux_loop` 的数据帧成帧；接收侧在 `demux_loop` 的 `on_frame(Recv, ..)`；
  - 24 与 84 的差额（60）很像「**控制帧（OPEN/ACCEPT/CLOSE/PULSE/WINDOW_UPDATE）
    只被一侧计数**」：R9 起控制帧由 main 写公共 TX，若 main 的写入点没有
    `on_frame(Send, ..)`、而 demux 收到时必计数，接收侧就会多出这些帧的长度。
  - 另一条同样可疑的路径：`mux_loop` 搬公共 chunk 时是否重复/漏报。
- **下一步**：
  1. 在 `DebugCounters` 的每个上报点打一张「谁在什么条件下报」的小表（帧种类 × 方向）；
  2. 用 `--nocapture` 打印 `snap` 的分桶计数（若 `DebugCounters` 没有分桶，先在测试里
     用 `on_frame` 的 `kind` 累加到临时 `BTreeMap`）；
  3. 定位是「发送侧漏报控制帧」还是「接收侧多报」，再决定改计数点还是改断言口径；
  4. **验收**：断言恢复；若确属设计上的口径变化（例如控制帧只在一侧计入），必须在
     测试注释里写明理由并同步 `src/metrics/mod.rs` 的文档。

### 3.2 `thread_safety`：三个用例全部挂起

- **现象**：三个用例都超过 60 s 无结果（`timeout 200` 内没有任何 `ok`/`FAILED`）；
  单跑 `mux_auto_dock_allocation_is_atomic_tokio_` 也 >2 min。
- **结构**：主线程建连：
  `tokio_rt.block_on(async { let scope = art_rt.local_scope(); scope.run_until(connect_pair_(..)).await; (a, b, scope) })`
  → 主线程的 `block_on` 返回后**不再驱动** `scope`；
  工作线程各自 `new_tokio_rt_()` + `block_on(bind_async(..))`。
- **根因假设（未验证）**：`bind_async` 走 `MainRequest_` → 请求队列 → `main_loop`；
  而 `main_loop` 是主线程 `LocalSet` 里的本地任务。主线程建连后不再 `run_until`，
  请求没有任何消费者 → 工作线程永久等待。也就是说这些用例**当前欠一个「持续驱动
  本地队列」的宿主**，不是产品逻辑挂死。
- **下一步（按代价从低到高）**：
  1. 在主线程留一个后台驱动：`std::thread::spawn(|| tokio_rt.block_on(async { scope.run_until(core::future::pending::<()>()).await }))`，
     工作线程完成后再用取消/`shutdown` 收回；先只改一个用例验证假设；
  2. 若 `run_until(pending)` 不能与「另一个线程的 `block_on` 同时使用同一个 `LocalSet`」
     共存，则这组用例在现架构下**不可测**——改为 `#[ignore]` + 文件头写明原因，并把
     「绑定独占性」的验证移到 compio 单线程（两个 `Task` 在同一 scope 内竞争）。
  3. **验收**：三例要么通过，要么显式 `#[ignore]` 且在 `thread_safety.rs` 与
     `sw-scope-20261028-2130.md` §7 写明「为什么不可测、替代验证在哪」。
- **注意**：`tokio` 的 `LocalSet` + `Handle` 模型决定了「连接的循环必须在建连线程上被
  持续 poll」；这与「句柄可跨线程」并不矛盾（跨线程的只是句柄），但**测试壳必须提供
  那个持续 poll 的宿主**。

## 5. P2：已知偏离、死代码与待拍板

### 5.1 `main_loop` 不是「完全同步」（设计稿 §6.3 的偏离）

`main_step_` / `handle_request_` / `tick_` 里仍有：

- `release_done_channels_` / `reap_retired_` / `reserve_channel_` / `take_pending_inbound_`
  等注册表异步取锁；
- `write_control_frame_async_` 的 `poll_tx_space_` park；
