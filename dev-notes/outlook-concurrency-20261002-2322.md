## 1. 结论速览

| 编号 | 事项 | 结论 | 一句话理由 |
| --- | --- | --- | --- |
| b | **连接与句柄可跨线程移交** | **必须做**（核心目标） | 服务器要让业务处理离开 reactor 线程；今天的公开类型连 `Send` 都不是 |
| a | 同一条连接的两个循环跑在不同核上 | **暂不做**（可选优化） | 收益上限 2 核/连接，对 compio 不适用，且与「热状态单线程钉住」直接冲突 |

| — | 身份表（`ChannelRegistry_`） | **它是高频共享结构**，不是「低频入口」（§5.3 更正） | 每建立 / 拆除一条子流都要改它，且改它的人横跨读循环、写循环与所有应用线程 |
| — | `ChannelOwner_` 一类「复制/记账重」的状态 | **永远单线程钉住**，不得被移交 | 它的字段被两个循环与建流路径共用，跨线程访问只会换来 cache line 乒乓 |
| — | 高频但无需上锁的行为（水位等） | 改为**消息直达业务核心**（`flume` 队列） | 消息传递天然单写者；不再为一次水位变化抢锁 |
| — | 上游 `abs_art` 提供 `SendSpawner` | **不指望**（见 §8） | 「Send 到哪条线程」不是薄封装能解决的语义，compio 与 tokio 形状无法统一 |
| — | 入向待决（`reserve_inbound_` → `income_async`） | **已裁决：改为 per listener 队列**，不再放全局身份表（§5.3） | 它是「读循环投递 → listener 取用」的单向流，天生适合消息队列 |
| — | 公开泛型参数 | **已裁决并落地：参数放传输类型 `R` / `W`，`MuxError` 自身也以传输为参数**（§5.7） | 错误是次要信息且常常不可命名；详见 `connection-…§18.7` |

## 2. 人类指示（本轮讨论，按原意记录）

> 1. 「跨线程访问，应该首先由 `MuxCore` 分发给不同业务线的不同 session 来控制并发同步
>    （因为只持有 session 编译器可以很大程度阻止相互死锁）。实现这一步之后，我们再去
>    考虑那些高频并发但实际上并不需要上锁的行为，改为用 `flume` 的消息队列来直达业务
>    核心。」
> 2. 「我们可能不做 a，但 b 是必须要做的，必须确保连接与句柄可以跨线程移交。并且必须
>    保证，对 `ChannelOwner_` 之类的内存复制重业务只能在一个线程上运行，永远不会被
>    转移。也即从逻辑上来说 b 才是核心目标，a 反而算是一种额外优化。」
> 3. 「上游 `abs_art` 支持一个 `SendSpawner` 我估计不是一个薄的封装层，因为无法解决
>    compio 的任务到底要 Send 到具体哪一个线程上，除非由业务自行决定，但这又是与
>    tokio 的形状无法吻合的。」

这三条构成本文的方向；§5 与 §7 是它们的展开，§8 是对第 3 条的逐后端核对（结论与人类
判断一致），§9 是建议的落地顺序。

## 3. 目标「b」的准确含义

「跨线程移交」很容易被读成「把连接搬到另一条线程继续跑」。这里要的是**更窄也更硬的
一条**：**句柄可以走，reactor 不走。**

| 条目 | 要求 | 说明 |
| --- | --- | --- |
| `MuxConnection` | `Send`（`+ Sync` 视为附带收益） | 它是**共享单元**（智能指针），跨线程共享也应当成立 |
| 四个会话句柄、两个半部 | `Send` | 它们是**所有权单元**（全部 `!Clone`，见 §5.1），只做**一次性移交** |
| `Rx` / `Tx` 与它们所在的本地队列 | **不迁移** | 读 / 写循环永远留在创建连接的线程与作用域上 |
| 循环 future | **不要求 `Send`** | 因此 **compio 也能用 b**：跨线程的只是句柄，`!Send` 的 socket 仍在原线程 |
| 热状态（`ChannelOwner_`、环、流控、帧暂存） | **单线程钉住** | 人类指示第 2 条；§5.5 给出拆分方案 |

### 3.1 为什么 a 是「额外优化」而不是目标

- **收益上限就是 2 核/连接**：一条 TCP 流只有两个方向，读写各自独立，没有第三个并行
  维度；跨连接并行度由「一线程一 scope + N 连接」已经给出。
- **对 compio 不成立**：compio 的 socket 半边是 `!Send`（`SharedFd` 内含 `Rc`，见
  `tests/common/mod.rs` 的模块文档），而 compio 是本项目首要目标。
- **与热状态钉住冲突**：读写两个循环都要碰同一份流控状态（读侧记「已收」，写侧记
  「已通告 / 已消费」）。把两个循环分到两个核上，等于把这份状态变成跨核共享——与
  §5.5 的「单线程钉住」直接矛盾。
- **换来的是 cache line 乒乓**：每帧都要碰的 `ChannelOwner_` / 窗口计数 / 环头尾一旦跨
  核，代价通常大于「多出来的那一个核」。

## 4. 今天的差距（实测）

用编译期探针实测（探针已撤，结论如下）：

| 类型 | compio 作用域（ZST） | tokio 作用域（`Rc<LocalSet>`） |
| --- | --- | --- |
| `MuxCore` | **`Send + Sync`** | `!Send + !Sync` |
| `MuxConnection` | **`Send + Sync`** | `!Send + !Sync` |
| `ChannelTx` / `ChannelRx` | `Send` | `!Send` |
| `BufferedRx/Tx`、`LoopShared_`、`CancelToken_`、`EventReceiver_`、`Owned<[u8]>` | `Send + Sync` | 同左 |

三条结论：

1. **唯一让连接 `!Send` 的是核心里的作用域保活槽**（`MuxCore::scope_`）：tokio 的
   `LocalScope` 内含 `Rc<LocalSet>`，编译器报错直指它；把作用域换成零大小的 compio
   作用域，`MuxCore` / `MuxConnection` / 两个半部**全部已经是 `Send(+Sync)`**。
2. **循环 future 是否 `Send` 只取决于传输**：其余组成部分（`LoopShared_`、
   `CancelToken_`、`Owned<[u8]>`、事件接收端、buffex 环端）全部 `Send + Sync`。
   tokio 的传输是 `Send`，compio 的 socket 不是。
3. **我们在为 `Sync` 付钱，却没有交付 `Send` 的能力**：`ChannelOwner_` 用自旋读写锁、
   注册表用 `Arc` 协作锁——这套原子/加锁成本是「状态可能被多线程访问」才需要的，而今天
   公开类型一个都过不了线程边界。这是当前形状最不划算的一处，也是 b 应当尽快落地的
   直接经济理由。

## 5. 并发模型：会话所有权 + 消息

### 5.1 会话是**所有权单元**（第一层，先做）

事实（已核对）：**只有 `MuxConnection` 是 `Clone`**；`DockBinding` / `ChannelListener` /
`ChannelHandle` / `Telegraph` / `ChannelTx` / `ChannelRx` 全部 `!Clone`，并且它们的操作
（`listen_async` / `open_channel_async` / `income_async` / `accept_async` / `send_async`
…）都取 `&mut self`。

于是「分发」这件事不需要新机制：**把句柄 `Send` 到另一条线程即可**。

- 任一时刻，一个会话在**恰好一条**线程上被持有；
- 同一会话不可能被两条线程同时使用——**编译器**阻止（`!Clone` + `&mut self`），
  不需要运行时检查；
- 因此**会话内部的状态不需要锁**，两个会话之间也天然不会互相等待（「我持有我的、你
  持有你的」），人类指示第 1 条所说的「很大程度阻止相互死锁」正是指这一层。

`MuxCore` 的职责因此被收窄为：**把会话分发给不同业务线**，而不是替业务线管理它们的
并发。分发单位有两类（见 §5.3 的线程布局表）：

- **每个 dock 的对象**（`DockBinding` / `ChannelListener` / `Telegraph`）：通常长期留在
  acceptor 线程上，一个连接上可以并存 O(端口数) 个；
- **每条子流的对象**（`ChannelHandle` → `ChannelTx` / `ChannelRx`）：一次性移交到处理该
  业务线的 worker 线程上。

### 5.2 仍然共享的：身份表与建流路径

会话内部状态不共享（§5.1），但**身份表 `ChannelRegistry_` 必须共享**：它同时被读循环、
写循环与**任意多条应用线程**访问。

> **更正（人类指出，本文档先前写错）**：`bind_async` / `listen_async` **不是「每连接
> 一次」**，而是 **(连接, dock) 级**的应用面对象——一个服务端在 16 个 dock 上监听，
> 就是同一条连接上 16 个并存的 `DockBinding` + 16 个 `ChannelListener`，而且通常
> **长期持有**（连接存活期间一直在）。所以它们的**调用次数**是「每个 dock 一次」，但
> **在册对象数**是 O(端口数)；更要紧的是，**listen 这条路径整体是高频道**，理由见 §5.3。

### 5.3 身份表是共享核心的热点（本节的更正）

**为什么 listen 路径必然高频碰核心状态**：每建立一条子流都要改一次身份表，而这一步跨
三个执行者。今天实现里的实际触点：

| 事件 / 调用 | 谁在改 | 频率 |
| --- | --- | --- |
| 对端 `OPEN` 到达 → `reserve_inbound_`（登记待决 + 配额计数 + 存窗口快照） | **读循环** | 每条入向子流一次 |
| `income_async()`（`take_pending_inbound_` / `has_pending_inbound_` / `register_inbound_waker_`） | 应用线程（listener 持有者） | 每条子流一次，且**每次 poll 都要取锁复检** |
| `accept_async` / `reject_async`（`take_inbound_report_` / `attach_owner_` / `release_channel_`） | 应用线程（handle 持有者） | 每条子流 1~2 次 |
| `open_channel_async`（`reserve_channel_` / `attach_owner_`） | 应用线程（binding 持有者） | 每条子流 2 次 |
| 拆流（`FIN` / `RESET` / 半部丢弃 / 宽限态登记与到期回收） | 读循环 + 写循环 + 应用线程 | 每条子流 1~3 次 |
| `bind_dock_` / `unbind_dock_` / `reserve_listener_` / `release_listener_` | 应用线程 | **每个 dock** 一次（在册数 O(端口数)） |
| telegraph 端点登记 / 释放 | 应用线程 | 每个端点一次 |

配套的是**线程布局**——它决定了争用的形状（也解释了为什么「会话所有权」不能顺带解决
身份表）：

| 线程（典型角色） | 长期持有什么 | 对身份表的动作 |
| --- | --- | --- |
| reactor（每条连接一条，或每核一条） | 两个循环、连接指针 | 每条入向 `OPEN` 一次（`reserve_inbound_`）+ 拆流若干次 |
| acceptor（可有多个） | `DockBinding` / `ChannelListener` | 每个 dock 一次（bind / listen）+ **每条子流若干次**（income / accept / reject） |
| worker（多条） | `ChannelTx` / `ChannelRx` | 基本不碰：半部 `drop` 只是**发消息**给循环，由循环代改身份表；若 worker 自己 `open_channel_async`，才各碰 2 次 |

三条结论：

1. **`ChannelOwner_` 被拆走之后（§5.5），身份表就是跨线程共享内存里唯一的竞争点**。
   它的临界区都很短（`BTreeMap` 增删查 + 计数），但**次数是每条子流数次**，因此在
   「大量短连接 / 大量子流」的服务器上必须实测竞争，而不能按「低频入口」对待。
2. **b 落地本身就是竞争的来源**：今天连接、句柄与循环同线程，身份表实际上没有并发；
   b 让句柄可以落到别的线程，身份表**立刻**变成真正跨线程的结构。所以「争用策略」
   （§7）与「身份表的临界区」必须在第 1 期一起处理，不能拖到后面。
3. **入向待决改为 per listener 队列（人类已裁决）**：它本质是「读循环投递 → listener
   取用」的单向流，天生适合消息队列，因此 `reserve_inbound_` 不再写全局身份表，而是
   投进**该 listener 自己的队列**（§5.4 的消息纪律在 accept 路径上的直接应用）。这样
   读循环每收一条 `OPEN` 只碰「该 dock 自己的队列 + 配额计数」，全局表退化为身份查询。

   需要一起设计的东西（不是小改动）：
   - **配额计数**：`max_channel_count` / `max_dock_chan_count` 的判定仍在**登记时刻**
     （读循环）发生，因此计数器必须独立于「身份表条目」存在（原子计数或每 dock 计数）；
   - **重复检测**：今天靠 `(local, remote)` 在全局表里的存在性；改成队列后需要队列内
     查重或每 dock 一张小集合；
   - **取用顺序**：今天 `take_pending_inbound_` 按 `remote_dock` 升序返回（§14.6 记录
     过这次行为变化），改成队列后变成**到达顺序**（对协议无要求，但要写进文档）；
   - **失败与取消**：`income_async` 今天每轮 poll 都复检 `failure_()`，改队列后必须
     与失败唤醒竞争（否则连接失败时 listener 会一直等）；
   - **宽限态 / 统一身份表**：释放路径（`release_channel_` → 宽限态 → 到期回收）仍在
     全局表上，保持不变；被移走的只是「待决集」；
   - **队列的分配**：`flume` 走全局分配（既有例外），自建队列则归
     `TrMaxAllocConfig`（§6）。
4. **仍然可选的缓解方向**：**按 `local_dock` 分片**——键是 `(local, remote)` 有序对，
   天然以 local 为前缀，而 `DockCtx_` 本来就按 local 组织；代价是全局计数
   （`max_channel_count`）与全局宽限态到期索引需要单独处理。

### 5.4 高频通路走消息（第二层，后做）

那些「高频但不需要上锁」的行为——发送环有数据（水位置位）、应用消费了接收数据（水位
回落）、两个方向的收尾——改为**经 `flume` 队列直达循环**。要落成的纪律（不是「随便发」）：

1. **每条需求一条消息**，载荷只有身份 + 少量标量（如已消费字节数）；
2. **每条子流至多一条待处理水位消息**，去重责任在**生产侧**（见 §5.5 的第 3 条，
   它顺带把去重位从共享单元搬到单线程域）；
3. 队列**定容**（建立时分配一次），满时的兜底是「置本连接重扫标志」而不是丢消息；
4. 任一消息**不可重建**：水位消息丢了就是那条 channel 卡住，因此「不丢」是硬约束。

现状对照：`signal_` 今天已经在做这件事（`WriteEvent_::TxReady` / `RxConsumed` /
`TxClosed` / `RxClosed` / 控制帧），差别是它把「去重位」和「水位判定」留在了共享单元
里。展望里的变化是**把判定与去重都挪到单线程一侧**，队列只承载「结果」。

### 5.5 `ChannelOwner_` 的单线程钉住与职责拆分

人类指示第 2 条要求「`ChannelOwner_` 之类的内存复制重业务只能在一个线程上运行，永远
不会被转移」。要满足它，就得把今天挤在同一个共享单元里的三件事拆开：

| 今天在 `ChannelOwner_` 里的东西 | 谁在用 | 展望中的归属 |
| --- | --- | --- |
| 收发窗口（`FlowCtrl`）、`should_report` 判定 | 读循环 + 写循环（**都碰**） | **循环本地**（两个循环同线程，见下） |
| 建流状态机（`Establish_`、对端窗口快照） | 读循环写、建流 future 读 | 读循环本地 + **回复消息**回传结果 |
| 活跃时间 `active_` | 两个循环 | 循环本地 |
| 「已入队」去重位 `tx_queued_` | 应用面置位、写循环清零（**跨线程**） | 写循环本地（`BTreeSet<(local, remote)>`），或用环的「空 → 非空」边沿去重 |
| 关闭位 `app_tx_closed_` / `peer_fin_` … | 半部与循环 | 已经是**环两端**的事实（`is_producer_closed` / `is_consumer_closed`），无需额外状态 |
| `released_`（只释放一次） | 写循环 | 循环本地 |
| 建流等待者 `WakerSlot_` | 建流 future | 由「回复消息 + 一次性 future」取代 |

两条直接后果（这才是性能收益所在）：

1. **「字节搬运 + 记账」全部留在 reactor 线程**：解复用 → 接收环、发送环 → 成帧 → 网络，
   以及窗口预留 / 回补 / 通告判定，都只由循环本地状态参与。跨线程剩下的只有
   「身份 + 标量」的消息与回复。
2. **热路径上的锁可以去掉**：今天每次写入要过一次 `ChannelOwner_` 自旋锁（`tx_queued_`
   去重）、每帧要过一次流控锁；拆分之后这些变成**单线程字段访问**，甚至可以退回非原子
   容器。注意这**只在「两个循环同线程」的前提下成立**——这正是 a 被排在后面的又一
   个理由（a 会把这份状态劈到两个核上）。

> 边界要说清：**应用面自己的 `memcpy` 留在应用线程**（`try_write` 是应用把字节写进
> 环，`try_read` 是应用把字节搬走）。这部分本来就不是 smux 的职责，也不受「会话移交」
> 影响；本文所说的「复制重业务不迁移」指的是 **smux 内部**的解复用投递与成帧上线。

### 5.6 一次移交的时序（目标形状）

```text
线程 A（reactor：scope + 两个循环）
   accept 入向连接 → MuxConnection（核心在 A 上、循环投在 A 的 scope）
   bind(dock) → DockBinding ──┐
   listen → ChannelListener   │  会话在 A 上创建
   income → ChannelHandle     │
   accept → (ChannelTx, ChannelRx)
                              │
                              └── 经业务自己的分发（channel / thread::spawn / 线程池）
                                  把**句柄**交给线程 B、C、D…（各一个）

线程 B：持有 ChannelTx，业务在此写数据
        ├─ 写 → 环（本地 memcpy）
        └─ 水位变化 → 一条消息 → 线程 A 的写循环
线程 A：写循环把环数据成帧上网；读循环把网络数据写进接收环
        所有窗口记账、去重、建流状态机都只在 A 上发生
线程 C：持有另一个 ChannelRx，读环（本地 memcpy），消费量经消息回报给 A
```

「谁碰什么」由此变成一条可检查的规则：**跨线程只有 `Send` 的句柄与消息；共享内存单元
一律属于 reactor 线程。**

### 5.7 公开泛型参数：传输为主、错误派生（人类已裁决）

同一轮讨论中的第二项裁决：`MuxConnection`（以及四个句柄、两个半部）的参数应当是
**传输类型 `R` / `W`**，而不是它们的错误类型：

```text
之前：MuxConnection<C, S, RE, WE>          // 参数是次要信息，且常常不可命名
现在：MuxConnection<C, S, R, W>            // 参数是「你手里有什么」
      TrConnection::Err = MuxError<R, W>   // 错误类型同样以传输为参数
      MuxError::Rx(<R as TrBuffTryRead<u8>>::Err)   // 载荷由传输派生
```

三条理由（详细记录见 `connection-20261002-0548.md` §18.7）：

1. **错误类型常常不可命名**：可能是私有类型、或只以
   `<T as TrBuffTryRead<u8>>::Err` 这样的投影存在。旧形状逼调用方在每一个类型别名里
   写投影——`tests/common/mod.rs` 上一轮就出现过
   `MuxConnection<SmokeMuxConfig, S, <R as TrBuffTryRead<u8>>::Err, …>`；改后是
   `MuxConnection<SmokeMuxConfig, S, R, W>`。
2. **参数应当是「你手里有什么」**：调用方手里是 `Rx` / `Tx`；错误类型他们从没见过。
3. **`MuxError` 自己也要这样**（否则问题只是从连接搬到错误类型上）：先试过「引擎枚举
   保持载荷参数 + 公开类型别名」的方案，实测**模式匹配推不出类型**
   （`MuxError::DockInUse` → `cannot infer type for type parameter R ... on the type alias`），
   于是改成**枚举自身以传输为参数**。内部「只碰一个方向」的层用一个 crate 内部的占位
   半边 `NoHalfway_`（不可构造）写成 `MuxError<R, NoHalfway_>`，把「另一侧不可能出错」
   变成类型事实。

对 b 的意义：会话句柄的类型别名因此可以只写传输（`ChannelTx<Cfg, S, Rx, Tx>`），
跨线程移交时用户不需要理解任何错误类型细节；而业务代码（错误分类、日志、重试判定）
可以直接 `match MuxError::Rx(e)`——`error_.rs` 的 doctest 与 `layered_rpc` 的 F9 探针
把这条能力钉在了编译期。

## 7. 争用策略：今天的 `panic` 要变成什么

今天的 `sync_::on_lock_contended_` 无条件 `panic!("共享状态的临界区不可重入")`，理由是
「连接与全部句柄都是单线程对象，取不到锁只可能是重入」。**b 一旦落地，这条推理不再
成立**：锁可能被另一条线程合法持有（例如线程 B 的 `bind_async` 与 reactor 上的循环
同时改身份表）。候选：

| 方案 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| (i) 运行时模式 + 失败路径分支 | 核心存一个 `Concurrency` 值（`Local` / `Shared`）；本地模式 panic、共享模式自旋 | 失败路径上一个 bool 分支（本来就罕见） | 共享模式下真重入变成**静默死锁** |
| (ii) 持有者线程 id | 我们自己的锁包装在获取时记一次持有者线程 id；失败时若等于当前线程 ⇒ 重入 panic，否则自旋 | 获取 / 释放各一次 relaxed store | 需要包一层 `atomic_sync` 的锁（读写两条路径） |
| (iii) 恢复编译期 feature | 回到 `multi-thread` 那套 | 与「用值区分能力」的方向相悖（§17.9 的教训） | 同一份代码两条 bound 路径 |

**建议 (ii) 为主、(i) 为默认值**：默认共享模式、自旋等待，但**同线程重入仍然 panic**，
把那半 fail-fast 保住；本地模式（确定单线程使用）则保持「失败即 panic」的最快路径。
不建议 (iii)。

## 8. 为什么不应指望上游 `abs_art` 提供 `SendSpawner`

人类指示第 3 条判断「不是一个薄的封装层」，逐后端核对后同意，且理由更硬：

| 后端 | `spawn`（`Send`）实际投到哪 | 能否「Send 到指定线程」 |
| --- | --- | --- |
| tokio | **全局注入队列 + 工作窃取**：任意 worker 线程 | 不能。要指定线程只能走 `LocalSet`（即「本地作用域」那条路） |
| smol | `async_executor::Executor`（多线程全局执行器） | 不能，同上 |
| compio | **线程本地队列**；`Runtime` 自身 `!Send` | **语义上不可能**：本线程无法把任务投到另一条 compio 线程；目标线程必须自己来取 |

由此得到三条结论：

1. 「Send 到哪条线程」**不是 `spawn` 这个动作能表达的东西**：对 tokio/smol 而言它没有
   意义（没有指定线程的概念），对 compio 而言它需要一个**跨线程可用的投递口**，而
   compio 的运行时句柄恰恰是 `!Send`。
2. 真要做「指定线程」，唯一的通用形状是**每线程一个 inbox（消息队列）+ 该线程自己
   本地 spawn**。这已经是**业务级**结构（谁来建 inbox、谁持有目标线程的句柄、线程如何
   命名与发现），不是「把 `spawn` 变成值」能覆盖的。
3. 因此：**不要等上游**。若将来真要做 a，正确做法是在 smux（或最终业务）里用一个**值**
   表达「线程亲和 / reactor 归属」——例如「每线程一个 reactor 注册表 + `Send` 的
   reactor 句柄」，由目标线程自己从 inbox 取任务并本地 spawn。这也解释了为什么 a 的
   前置条件比 b 多整整一层。

## 9. 建议的分期路线图

| 期 | 内容 | 验收（含反向验证） |
| --- | --- | --- |
| **第 1 期：b 的地基** | ① 去掉核心的作用域保活槽（作用域退回「只在 `new` 期间使用」）；② 争用策略按 §7 改造；③ 用编译期断言把 `MuxConnection` / 四个句柄 / 两个半部的 `Send`（`+ Sync`）钉住；④ **身份表的竞争实测与临界区收缩**——b 落地后它才第一次真正跨线程（§5.3），不能留到后面 | 断言测试编译通过；**反向**：故意给核心加回一个 `Rc` 字段，断言测试必须失败。行为回归：握手 + 2 dock × 2 channel 双向收发；新增「句柄跨线程移交、循环不迁移」的用例；新增「连接在另一线程被 drop 时循环正常收尾」的用例（复用 §18 的析构探针） |
| **第 2 期：拆 `ChannelOwner_`** | 按 §5.5 把窗口/建流/活跃时间/去重位迁入循环本地；建流结果改回复消息；应用面只留环状态 | 单线程钉住的**负向**探针：热状态类型必须 `!Send`（避免哪天被顺手塞进 `Send` 域）；`inmem` / `layered_rpc` / 两条 smoke 全绿 |
| **第 3 期：消息纪律** | 高频通路统一走定容队列（或自建队列，归 `TrMaxAllocConfig`）；把「每条需求一条消息、每条子流至多一条待处理、队列满则置重扫标志」写成不变量并测；**入向待决改为每 listener 一条队列**（§5.3 第 3 条），把身份表从「每条子流数次写」压回「身份查询」 | 队列满的兜底路径有专门用例（人工把队列压满）；分配次数与竞争数据的实测记录 |
| **第 4 期（可选）：a** | 仅当实测证明「单连接 > 单核」才做；前置是 §8 的「线程亲和值」先定义出来 | 需要新的实测矩阵；若 compio 无法参与，必须在文档里写明 a 是 tokio-only |

**先做第 1 期的三个理由**：它是 b 的全部前提；它顺带把 §4 第 3 条那笔「为 `Sync` 付钱」
的账变成收益；它的改动面小且可反向验证。

## 10. 未决问题（需裁决）

1. **保活槽去不去**：去掉 ⇒ `MuxConnection<C, RE, WE>`（少一个参数）且可 `Send`，代价是
   「调用方先丢作用域 ⇒ 队列消失」；保留 ⇒ tokio 下永远 `!Send`，b 无法达成。**本文的
   方向是去掉**，但它推翻了 §18.1 Q12 的原裁决，需要重新确认。
2. **争用策略**：§7 的 (i) / (ii) 选哪个（建议 (ii)，同线程重入仍 panic）。
3. **「会话」的粒度**：分发单位是 **dock 对（一条 channel）** 还是 **binding（一个业务
   逻辑，可含多条 channel 与 listener）**？粒度越粗，一条线程上的串行区越大、编译期
   排除死锁的覆盖越强；越细则并行度越高。
4. **身份表怎么分担竞争**：入向待决改为 per listener 队列**已裁决**（§5.3 第 3 条），
   剩下的问题是**其余身份表部分**保持单把锁（+ 实测收缩临界区）还是按 `local_dock`
   分片——后者要处理全局计数与全局宽限态到期索引。
5. **要不要 `Sync`**：只做「移交」只需要 `Send`（句柄 `!Clone`）；若还允许**共享**连接
   指针（`bind_async(&self)` 从两条线程调用），才需要 `Sync`。建议顺手做到 `Sync`。
6. **消息队列的分配归谁**：`flume` 不支持 `allocator_api`；自建队列的分配点归
   `TrMaxAllocConfig` 的哪个关联类型。
7. **`ChannelOwner_` 拆分后，被动方建流**（`accept_async` 才建环）需要一次
   「读循环 → 应用线程」的回复；这条回复路径的语义（超时、连接失败、取消）要与 §15 的
   宽限态、§16.3 F8 的关闭竞态一起设计，不能各写各的。

## 11. 对当前实现的即时启发（不依赖上述裁决）

1. **热路径成本清单**（第 2、3 期会解决，但今天就能测）：每次写入一次
   `ChannelOwner_` 自旋锁 + 可能一条 `flume` 消息；每帧一次流控锁 + 一次
   ring → scratch → transport 的搬运；`ControlFrame_::payload_` 是唯一的冷路径 `Vec`。
   先测「每核多少 Gbps / 多少 MPPS、CPU 花在哪」，再决定优化顺序。
2. **`!Send` 与 panic 目前是自洽的**：既然公开类型过不了线程边界，「取不到锁即重入」
   成立。**这也是为什么 b 与 §7 必须同批做**——只改一半会得到一个既 `Send` 又会在合法
   竞争下 panic 的连接。
3. **别急着把 `ChannelOwner_` 的锁降级为非原子容器**：那只有「确定长期不做 b」时才划算；
   按本文方向，正确的顺序是「先拆分职责（第 2 期）→ 热状态自然单线程化 → 届时再决定
   锁的形态」。
