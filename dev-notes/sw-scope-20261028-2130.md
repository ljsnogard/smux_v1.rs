## 1. 任务背景

`smux_v1` 之前在 `feat/conn-alloc` 分支上把连接内部用到的分配器拆成了
`TrConnAllocCfg`：每个“分配用途”一个关联类型 + 一个取实例的方法。它让“按用途注入
不同分配器”成为可能，但也把配置面撑得很大：

```text
TrMuxAllocConfig: RegistryAlloc, ChanOwnerAlloc
TrConnAllocCfg:   MpmcAlloc<'a>, TcsAlloc, AttachAlloc, LocalTableAlloc,
                  EventAlloc, ScratchAlloc, CoreAlloc, PublicAlloc
```

本次尝试换一个方向：引入 [`sw-scope`](../../sw-scope/) 来承载**临时性内存**。
本文的“临时性”采用需求方的定义：

> 生命周期短于一个子流（channel）或一个 Telegraph 的对象。

需要回答两个问题：

1. sw-scope 的原理是什么，它适合承载哪些对象？
2. `TrConnAllocCfg` 里哪些临时性用途能换成 Scope，哪些不能，为什么？

## 2. sw-scope 的原理

### 2.1 三个句柄，两种职责

| 类型 | 类比 | 生命周期 | 能做什么 |
| --- | --- | --- | --- |
| `Retain<T>` | GC handle | 无 `'a`，可随处传递 | 持有对象身份；可克隆；可升级成视图 |
| `Owning<'a, T>` | `Box<T>` | 绑定 `&Retain` 的借用 | 独占读写（`DerefMut`） |
| `Sharing<'a, T>` | `Arc<T>` | 绑定 `&Retain` 的借用 | 共享只读（`Deref`），可克隆 |

关键设计是**把“谁还能访问”和“什么时候销毁”拆开**：

- 访问受 Rust 借用检查约束：`Owning`/`Sharing` 的 `'a` 来自 `&Retain`，
  因此不会被随意塞进长期存活的结构里；
- 销毁由 Scope 兜底：即使对象之间形成环，`Scope::close` 也能在不追踪对象图的前提下
  把它们全部驱动到析构。

`Retain::try_owning()` / `try_sharing()` 会做一次状态 CAS。两者互斥：

- 已经有人在 `Owning` 时，`try_sharing()` 返回 `None`；
- 已经有人在 `Sharing` 时，`try_owning()` 返回 `None`；
- 只剩 `Retain`（状态 `Created`）时两者都能成功。

源码：`index_.rs` 的 `Retain::try_owning` / `try_sharing` 与 `Owning::drop` /
`Sharing::drop` 的状态转换。

### 2.2 存储与分配路径

```text
RootScope (进程级单例, static AtomicPtr)
  ├── scopes_: BPlusTree<ScopeKey, NonNull<ScopeInner>>
  ├── 实体池（WeakSlot + StrongChunk<ScopeEntity<A>>）
  └── type table（T / P 的类型擦除 vtable）

Scope ──► StrongChunk<ScopeEntity<A>>
            ├── ScopeLock（内含 ScopeInner）
            └── A（每域一份池分配器，内联在实体尾部）

ScopeInner
  ├── handles_ / closed_ / close_requested_
  ├── weak_head_ / weak_tail_   （弱槽位池链）
  └── strong_head_ / strong_tail_（强块池链）
```

一次 `put` / `emplace` 的顺序（`scope_inner_/alloc_.rs`）：

1. 先从本域**弱池链**摘一个 `WeakSlot`（对象身份 + 生命周期状态）；
2. 再从本域**强池链**按 `Layout` 做 bump 分配，拿到 `StrongChunk`；
3. 数据就地构造，槽位绑定强块，状态置 `Created`，弱计数置 1；
4. 强池分配失败时把弱槽位立刻还回去，不留半成品。

强块的实际布局：

```text
(StrongChunkBase, [meta 指针], [predrop 对象], data)
```

`T: Sized` 不占 meta 槽；`T: ?Sized` 的元数据写进强块头部。类型擦除析构所需的
vtable 按 `typeid::of::<T>()` 登记在 root 的类型表里，`finish_destroy_` 查表后先跑
`Predrop`、再跑 `T` 的析构（`index_.rs`）。

### 2.3 销毁的两条来源

1. **确定性析构（引用计数）**：最后一个 `Retain` 消失、且状态是 `Created` 时，
   弱计数归零直接认领析构；
2. **显式清盘（`Scope::close`）**：无视引用，强制析构本域所有 `Created` 对象；
   遇到仍存活的 `Owning`/`Sharing` 就跳过，等视图释放后由
   `try_flush_for_slot_` 重试。

`Scope` 的普通 `Drop` **只**打关闭标记，不强制清盘——这是为了保留“句柄先消失、
`Retain` 仍可继续使用”的语义。**需要回收循环引用或整域归还时必须显式
`close()`**，这也是“每连接一个 Scope”方案里连接关闭路径必须做的事。

### 2.4 锁与线程

- `Scope`：`Send + Sync`，每次 `put_async` 先 `write_async()` 拿域写锁；
- `RootScope`：`Send + Sync`，`scopes_` 是 B+ 树，创建 / 回收域要拿 root 锁；
- `Retain` / `Owning` / `Sharing`：源码里**没有任何** `unsafe impl Send/Sync`。
  它们含 `NonNull`，默认 `!Send + !Sync`。

`Scope::put_async` 是**异步**的，且只有异步入口（`put_async` / `emplace_*_async`）；
同步路径只有低层的 `ScopeInner` 方法，未对外导出。

## 3. smux_v1 的临时性内存需求清单

### 3.1 `TrConnAllocCfg` 各项的真实用途

| 关联类型 | 实际分配的对象 | 生命周期 | 跨任务共享 | 能否换 Scope |
| --- | --- | --- | --- | --- |
| `RegistryAlloc` | `RegistryRoot_`、四棵 `DockBPlusTree_`、`VecDeque`、`ControlStateInner_` | 连接 | `Shared` | **不能**：B+ 树要求 `Allocator`，非 Scope |
| `ChanOwnerAlloc` | `Shared<DockBinding_, A>`、`Shared<AtomicBool, A>` | 子流 | `Shared` 克隆 | **不能**：需 `Send`，且 `try_write` 热路径每次要 CAS |
| `MpmcAlloc<'a>` | `ControlState_` / `Attach` / 会话邮箱通道的外层 `Arc` 与等待 chunk | 连接 | `mpmc_chan` 句柄 | **不能**：`mpmc_chan` 要求 `AllocatorClone` |
| `TcsAlloc` | `Shared<TcsInner_<T>, A>`（一次请求一个） | 一次请求（短于子流） | `Shared` 克隆，进请求通道 | **能**（需补 `Send`、`new_` 异步化） |
| `AttachAlloc` | `WriteAttach_` / `ReadAttach_` inbox | 连接 | `mpmc_chan` 句柄 | **不能**：同 `MpmcAlloc` |
| `LocalTableAlloc` | `ReadTable_` / `WriteTable_` / `TgReadTable_` / `PendingFin_` | 子流 / 连接 | 循环本地独占 | **不能**：B+ 树要求 `Allocator` |
| `EventAlloc` | **无实际使用者** | — | — | **可删**（死配置） |
| `ScratchAlloc` | 循环内 `Owned<[u8]>` 暂存 | 连接（每循环一次） | 循环本地独占 | **能**（需 `emplace_async` 造 `[u8]`） |
| `CoreAlloc` | `MuxCore`、`CancelToken_` | 连接 | `Shared` / 令牌 | **不能**：连接核心跨任务、且是连接级 |
| `PublicAlloc` | `PublicChannelInner_`、两条公共 ring 的缓冲 | 连接 | `Shared` + ring | **不能**：ring 要求 `Allocator`，且是连接级 |

### 3.2 `registry_` 之外的隐式全局堆分配

这些不是 `TrConnAllocCfg` 的项，但同属“临时性”审查范围：

| 位置 | 对象 | 生命周期 | 备注 |
| --- | --- | --- | --- |
| `signal_::ControlFrame_.payload_: Vec<u8>` | 建流期 message / welcome / reason | 一次请求 | 走全局 `Vec`，可考虑迁入 Scope，但它随请求跨通道（需 `Send`） |
| `signal_::Overflow_.durable_: VecDeque<E>` | 事件通道满时的不可丢事件 | 连接 | 投递点可能在任意线程的 `Drop` 里，需 `Send` |
| `util_::read_available_into_vec_` 的 `Vec<u8>` | 握手期读缓冲 | 握手 | 一次性，收益小 |
| `signal_::EventTx_` 的 `Box<MpmcBuf<...>>` | 事件通道缓冲 | 连接 | 全局 `Box`，`mpmc_chan` 的 buffer 参数 |

## 4. 逐项判定与理由

### 4.1 为什么能

**（1）`TcsAlloc`：典型的“短于子流”对象。**
`Tcs_` 一次请求一个，句柄只在“提交请求 → 等待答复”这段存活，远短于子流。
它没有自引用、没有环，`Retain` 的确定性析构就足够；`Scope` 只是替它做一次
“同页 bump 分配”，避免每次请求一次 `Shared::new_in`。
需要三个前提：

- 给 `Retain` 补 `Send + Sync`（`T: Send + Sync`），否则 `Tcs_` 进不了
  `MainLoopRequest_` 的 mpmc 通道；
- `Tcs_::new_` 从同步改成 `async`（`Scope::put_async` 是异步的），调用点都在
  `async fn` 里，可改；
- 每次访问用 `try_sharing()` 取视图，并对 `None`（已清盘）给出“取消”语义。

**（2）`ScratchAlloc`：循环本地独占的字节缓冲。**
`Owned<[u8]>` 只被单个循环持有，不需要跨任务共享，也不需要 `Allocator` 接口。
用 `emplace_async` + `IntoEmplace<[u8]>` 在 Scope 里造一块零初始化 `[u8]`，
循环里 `try_owning()` 拿 `Owning<[u8]>` 即可读写。
前提只是 `emplace_async` 是 `unsafe`（调用方保证不越界），封装在 `connection::scope_`
里并写清安全注释。

**（3）`EventAlloc`：死配置。**
全仓除 `config_.rs` 外没有任何引用；事件通道实际用的是 `Box<MpmcBuf<...>>`。
直接删除不改变任何运行时行为。

### 4.2 为什么不能

**（1）Scope 不是 `Allocator`。**
`RegistryAlloc` / `LocalTableAlloc` 服务于 `bplus_tree_cmp` 的 `new_in`，
`MpmcAlloc` / `AttachAlloc` 服务于 `mpmc_chan::new_in`，`PublicAlloc` 的一半服务于
`buffex` ring。这些第三方结构要的是 `AllocatorClone` 或 `Allocator`，不是
“一个能放对象的域”。sw-scope 没有（也不应该）实现 `Allocator`：`Scope` 的分配是
`async` 的，而 `Allocator::allocate` 是同步 `&self` 接口，语义对不上。

**（2）`Retain` / `Owning` / `Sharing` 目前不是 `Send`/`Sync`。**
`ChanOwnerAlloc`（身份节点）、`CoreAlloc`（`MuxCore` / 取消令牌）、
`PublicAlloc`（公共子流元数据）都要求句柄能跨任务。`Retain` 含 `NonNull`，
源码没有条件 `Send`/`Sync` 实现，直接用会编译失败。补上条件实现后仍然有下面的
问题。

**（3）借用视图不能长期存进结构体。**
`Owning`/`Sharing` 的 `'a` 绑定 `&Retain`，不能存进 `ChannelOwner_`、`TcsInner_`
这类需要“自己活着、随时被访问”的结构。可行的写法只有“结构里存 `Retain<T>`，
每次访问 `try_sharing()`”。这对热路径是实打实的退化：

- 当前 `Shared::deref` 是裸指针解引用，零原子操作；
- `try_sharing()` 每次一次 CAS + 失败判空，`Sharing::drop` 再一次 CAS。

`ChannelOwner_` 的 `try_write` / `try_read` / 每帧流控记账都在这个路径上，
不适合迁移。

**（4）清盘语义与 smux 的对象图不完全兼容。**
`Scope::close` 会强制析构所有 `Created` 对象，指向它们的 `Retain` 立即失效。
smux 的子流对象之间有大量强引用（半部、窗口、身份节点、环），生命周期由协议状态
驱动，而不是由“域关闭”驱动。把身份节点放进 Scope 后，任何一次 `close` 都可能让
另一个仍被协议引用的对象变成“查到 `None`”，需要在每一个访问点补判空——这等于把
“生命周期正确性”从类型系统搬到运行期检查，收益为负。

**（5）每子流一个 Scope 的成本高于收益。**
`Scope` 的创建 / 回收要拿 `RootScope` 的全局锁，实体本身由 root 的分配器
（默认是 `Global`）分配一次。也就是说“每子流一个 Scope”会新增一次全局锁 +
一次全局堆分配，而它想省的只是子流身份节点的一次 `Shared::new_in`。净效果是更差。

**（6）默认 root 的分配器固定为 `Global`。**
`Scope::default_root_()` 用 `alloc::alloc::Global` 发布进程级 root；`Scope` 实体与
root 的 B+ 树节点都走全局堆。只有“每域池分配器”（`new_with_alloc_value` 传入的
`A`）走注入分配器。这与 smux “分配一律经注入分配器”的纪律有出入，需要在
`dev-notes/audit-heap-alloc-*` 的口径里单独记一笔。

## 5. 本次落地的范围（保守方案）

经评审确认，本次只做“能”的三项，其余保留：

1. **sw-scope 补齐**：给 `Retain` / `Owning` / `Sharing` 增加条件 `Send`/`Sync`
   （`T: Send + Sync`，`Owning` 用 `T: Send` / `T: Sync`），语义与 `Arc` / `Box`
   对齐；这是让 `Tcs_` 能跨任务的**前提**，本身不改变 sw-scope 的任何运行期行为。
2. **删除 `EventAlloc`**：关联类型、`event_alloc()` 方法与
   `SingleConnAllocCfg` 的转发一并删除。
3. **`TcsAlloc` 改为连接级 Scope**：`ChannelRegistry_` 持有一个 `Scope`（每域池
   分配器取 `RegistryAlloc`，页大小 64 KiB）；`Tcs_<T, C>` 收敛为 `Tcs_<T>`，
   内部字段 `Shared<TcsInner_<T>, C::TcsAlloc>` 换成 `Retain<TcsInner_<T>>`；
   `Tcs_::new_` 改为 `async fn new_(&Scope)`，返回 `Result`。
4. **`ScratchAlloc` 改为连接级 Scope**：循环暂存从
   `Owned<[u8], ConnScratchAlloc_<C>>` 换成 `Owning<'_, [u8]>`，辅助函数签名统一成
   `&mut [u8]`；`ScratchAlloc` 关联类型与 `ConnScratchAlloc_` 投影删除。

保留的项与理由见 §4.2。`TrConnAllocCfg` 因此从 8 个关联类型减到 5 个
（`MpmcAlloc`、`AttachAlloc`、`LocalTableAlloc`、`CoreAlloc`、`PublicAlloc`），
加上 `TrMuxAllocConfig` 的 2 个，合计 7 个。

### 5.1 已知代价（必须写进后续评审）

- **Scope 写锁成为新的串行点**：每次建 `Tcs_` 都要拿连接级 Scope 的写锁。临界区
  很短（bump 分配 + 槽位绑定），但它是跨线程共享的；高并发 API 请求下会与
  `Shared::new_in` 的无锁分配形成可观测差异，需要基准对比。
- **`Tcs_` 的每次访问多一次 CAS**：`set_` / `poll_wait_` / `abandon_` 都要
  `try_sharing()`。请求路径不是每帧热路径，暂接受。
- **连接关闭必须显式 `close` Scope**：否则对象内存要等进程结束。已在
  `MuxCore::drop` 的收尾路径处理（`close` 只做 `try_write`，不阻塞、不取注册表锁）。
- **Scope 实体与 root 树走全局堆**：每连接一次，非每请求。

## 6. 未决问题

1. 是否给 `Scope` 增加同步的 `try_put`（当前只有 async 入口）？如果以后要把
   `Drop` 路径上的临时对象也迁进来，需要它；但那要求分配器状态可无锁推进，改动大。
2. `ControlFrame_.payload_: Vec<u8>` 与 `Overflow_.durable_` 是否也迁入 Scope？
   两者都需要 `Send`，且投递点可能不在当前线程；等 `Tcs_` 的基准结果再定。
3. `RegistryAlloc` / `LocalTableAlloc` 是否合并？它们都是 B+ 树分配器，只差生命周期
   标注；本次不动，等下一轮配置收敛时讨论。
