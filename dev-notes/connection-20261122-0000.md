# 四循环 + 连接级环：裁决与踩坑（connection）

## 0. 本轮要解决的问题

`src/connection/mod.rs` §5 一直写着「子流收发环与协议帧的收发暂存**一律使用
`buffex::ring`**……中心循环持有一条**帧暂存环**」，但实现里从来没有那样一条环：
连接级暂存是两块裸 `Owned<[u8], _>`（读侧按 `max_packet_size`、写侧按
`K_MAX_DATA_CHUNK`），从 `b9229de` 起就是 `Vec<u8>`。也就是说 §5 是空头文档。

本轮把实现拉到文档上，并按人类指示把形状定成**四个循环 + 两条连接级环**。

## 1. 最终形状（已落地）

```text
网络 Rx ──读泵──▶ 连接读环 ──解复用──▶ 各子流接收环 ──▶ 应用
应用 ──▶ 各子流发送环 ──复用──▶ 连接写环 ──写泵──▶ 网络 Tx
```

| 令牌序号 | 循环 | 位置 | 搬运方向 |
| --- | --- | --- | --- |
| 0 | 读泵 | `session_pump_` | `C::ConnRx` → 连接读环 |
| 1 | 解复用 | `session_` | 连接读环 → 各子流接收环（解析帧、拉读事件） |
| 2 | 复用 | `session_` | 各子流发送环 → 连接写环（成帧、拉写事件） |
| 3 | 写泵 | `session_pump_` | 连接写环 → `C::ConnTx` |

要点：

- **两条连接级环的存储类型与子流环解耦**：`TrConnCfg::StageBuff` + `make_stage_buffs`。
  子流环容量是「逐条子流、由调用方在 `accept_async` 决定」的策略，而帧暂存是
  **连接级**策略，两者不该互相绑架。`MuxConnection::new` 多收两块 `C::StageBuff`。
- **`StageRingPair_`**（`ring_.rs`）：由两块缓冲建两条环，`into_halves_` 把
  「外侧（贴传输）」与「内侧（贴子流）」分发给四个循环。一条环的同一端不得被两个
  任务同时持有——环的 park / 唤醒状态是按端记的。
- **内侧循环不再 park 在传输上**：「对端不读导致写阻塞」这个必然状态被限制在写泵
  一个任务里，于是事件通道不会被饿死；网络调用次数也与帧数解耦。
- 取消令牌从 2 个扩到 4 个（`MuxCore` 与 `ChannelRegistry_` 各持一份 `[_; 4]`）。
  收尾链条不变：最后一个应用面对象 ⇒ 核心析构 ⇒ 取消四个令牌 ⇒ 循环在下个 await 点退出。

## 2. 容量约束（新的硬前提）

- **连接读环必须能整块驻留一个满帧**（帧头 + `max_packet_size` 载荷）。否则外侧读泵
  （环满而 park）与内侧解复用（还差几字节才判得完这一帧而 park）互等，而环的唤醒只
  由写入 / 读出触发。默认实现给
  `K_STAGE_RING_CAPACITY = 64 KiB`；文档明确要求「`max_packet_size` 超过它时要按自己的
  值放大」。
- **连接写环不要求整帧空间**：入环写入分块推进（见 §3.2）。

## 3. 本轮实际踩到的坑（都是真金白银）

### 3.1 把「环有空间」当唤醒条件 ⇒ 纯空转

复用循环最初把「写环有空间」做成 park 条件，用
`tx_stage.write_async(&Demand::at_least(1))` 轮询。**空环必然立刻满足 `at_least(1)`**，
于是 park 立即就绪、循环回到顶部、再次 park……变成纯空转（也会掩盖真正的死锁）。

**裁决**：park 条件只能是「有真实进展可能的那些源」——事件通道、`last_ready` 指的那条
子流发送环、取消令牌。写环腾空间这件事**不需要**单独唤醒：写泵会持续把环上字节搬到
传输端，而复用循环真正需要重试的时机总伴随一次子流环的提交（`TxReady`）或事件。

### 3.2 先搬出子流环、再判写环空间 ⇒ 静默丢帧

`drain_one_` 早期版本先把段字节 `move_items_to_buff` 到 scratch（**段的 drop 会提交
消费，字节从此离开子流发送环**），之后才判写环空间，装不下就 `return Ok(false)` 回顶部。
结果：这批字节既不在子流环里、也没有进写环——**永久丢失**。1024 条子流下写环经常接近
满，于是大面积丢帧，表现为对端读到 `Closing` 而载荷从未到达。

**裁决**：判空间必须在**动环之前**；而且判据不能是「整帧连续空间」——写环与传输环容量
互相钳制时那个条件可能永远不成立（实测：写环剩 1987、下一帧要 2010，写泵此刻在等传输
环）。最终形态是 `enqueue_frame_`：**分块**写入，按环当前能给的段用多少写多少，环满才
park；字节一旦离开子流环就必须全部进写环。

### 3.3 用不推进段偏移的写法写环 ⇒ 提交 0 字节

`enqueue_frame_` 的分块写入最初写成

```rust
let chunk = child.iter_slices_mut().expect("写段非空");
chunk[..take].write_copy_of_slice(&frame[..]);   // 错
```

`slice::write_copy_of_slice` 只是逐元素写内存，**不会推进 `SegmMut` 的已消费量**，
于是段 drop 时 `reclaim(0)` 提交 0 字节：写环永远空着，写泵永远读到 `readable=0`，
复用循环则一直认为「写入成功」。所有测试在 1×4 规模就挂死。

**裁决**：写环一律用 `abs_buff` 里被验证过的 `move_items_from_buff`（它推进已消费量并
在 drop 时提交）。诊断手段值得记下：写一个**同步可观测**的单测（写 9 字节后直接查
`producer_state` / `consumer_state`），比在四循环 + 事件通道里追日志快得多。

### 3.4 调试期用过的定位手段

- 由 `SMUX_TRACE` 门控的 `eprintln!` 追踪（四条循环各自打点 + 连接编号），定位完即删；
- `git worktree` 拉一份 HEAD 基线跑同一用例，确认「基线通过、新实现失败」；
- 把冒烟场景按 `dock 数 × 每 dock 条数` 参数化，二分出失败阈值（16×64 必挂、16×32 通过，
  后来发现 1×4 也挂——阈值只是掩盖了确定性的 bug）。

> 结论：**先造同步可观测的最小单测**，再上大场景；大场景的失败常常只是同一个确定性
> bug 的放大版。

## 4. 顺带修正的既有问题

1. `frame_.rs` 的帧头编码抽出**唯一**来源 `encode_header_into_`：`write_header_async_`
   与连接级写环的「整帧一次编码」都走它，避免两处各写一份字段顺序。`write_header_async_`
   自身在生产路径上已无调用者，删除（其测试改用编码函数，更直接）。
2. `K_MAX_FRAME_HEADER = 64` 作为帧头长度的**上界**，用于「帧总长 ≤ `max_packet_size`」
   的保守校验（自描述字段的精确宽度要编码后才知道）。
3. 上一轮文档里「中心循环持有一条帧暂存环」的说法与实现对齐（现在真的有了）。

## 5. 遗留

1. **`StageBuff` 的容量仍由配置实现者负责**：默认 64 KiB，超出 `max_packet_size` 的
   部署需要自己放大；连接不做二次校验（`MuxConnection::new` 只检查容量落在 ring 允许
   区间，否则 panic，因为那属于配置错误）。
2. **`signal_` 仍是无界 flume 通道**：本轮按裁决保持现有封装不动，事件通道的定容 /
   直用改造留下一轮。
3. **`ReadEvent_::Release` 的追踪打点已删**，若将来再查拆流竞态需要重新加。
4. **`memory` 层面的收益尚未实测**：本轮只保证语义与测试通过，读写泵带来的批量效应
   与那多出来的一次「环→环」拷贝，等实测数据再决定要不要做零拷贝直通。
