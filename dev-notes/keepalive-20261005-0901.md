# 保活与空闲超时（写法 B）：每连接一个 tick 循环

日期：2026-10-05 09:01
性质：**设计决策 + 施工单**（下个会话按此实现）。
依赖：`embedded-timers v0.4.0`（已由人类加入 `Cargo.toml`，git tag 依赖）。
关系：本文取代上一轮讨论里「用 delay 顶替 `std::time::Instant`」的说法——正确做法是
**注入 `Clock`**（§2.3）；并在 `outlook-concurrency` §12 登记为 **T6**。

---

## 0. 人类裁决（按原意记录）

> 1. 保活按**写法 B** 实现；
> 2. **每一个连接只有一个计数器**；
> 3. 这个计数器写成**第若干个循环**（一个独立的本地任务）；
> 4. **依靠它来激活其它可能已经静默的循环**；
> 5. 已为此在 `Cargo.toml` 引入 `embedded-timers`（`git = … tag = "v0.4.0"`）。

## 1. 现状与为什么是 B（因果链摘要）

**现状（本会话核对过）**：

- `FrameKind::Pulse` 只有**接收分支**（[session_.rs](../src/connection/session_.rs) 的
  `WindowUpdate | Pulse` 合并处理），`src` 里**没有任何 PULSE 发送点**；
- `max_channel_timeout` 只出现在文档、协商与 codec，**没有执行点**；
- `MuxError::IdleTimeout` 只定义、从不产生；
- `src` 里**没有任何定时器**（`TrDelay`/`sleep`/`timeout` 只在注释里）；
- `ChannelState_` 的 `base_: Instant` / `active_millis_` 与 7 处 `touch_()` 调用是
  **只写不读的死状态**（唯一读者带 `#[cfg(test)]`）——它恰好是写法 B 需要的量。

**为什么 A（每子流一个 delay）不值得**：`abs_art::TrDelay::delay` 是**关联函数**、返回
`impl Future`（不透明类型）⇒ **不可存储、不可重挂**；要"每子流一个 delay"只能：

1. 每条子流 `spawn_local` 一个计时任务 ⇒ N 子流 = N 个任务，每个都要 `'static`、各自与
   取消令牌竞争、各自撤销（N 份收尾逻辑，1024 子流下不可接受）；或
2. 自建时间轮（把 N 个 delay future 钉在循环本地 arena 里）⇒ 等于抄一遍 tokio timer wheel。

而循环现在**刻意只持注册表句柄 + 标量**（不持核心、不持作用域），spawn 计时任务还要把
作用域塞进循环，重新引入"循环保活核心/作用域"的收尾风险。

**B 的形状**：一个连接一个计时器、一处取消、天然限频、可复用 `active_millis_`/`touch_`
与注册表的惰性回收（`reap_wait_close_`）同构。**结论：B。**
A 只在「要把超时精度做到接近零误差，且愿为每子流常驻计时器」时才值得，本轮**非目标**。

## 2. `embedded-timers v0.4.0` 的真实能力（读的是本地 tag 源码）

### 2.1 它提供什么

| 项 | 说明 |
| --- | --- |
| `clock::Clock` | `type Instant: Instant`；`fn now(&self) -> Self::Instant`；`fn elapsed(&self, Instant) -> Duration`（有默认实现）。**按设计不可失败**、全部 `&self`（可共享）。 |
| `instant::Instant` | 单调时刻 trait：`Add/Sub<Duration>`、`Sub<Self, Output = Duration>`、`Ord`、`Copy`、`Debug`、`Hash`、`Send + Sync + 'static`（`Any`）等。crate 文档明确以 `std::time::Instant` 作为实现示例。 |
| `timer::Timer<'a, CLOCK>` | **一次性**软件定时器，持有 `&CLOCK`；`try_start(Duration)`（可覆盖已运行的）、`duration_left()`、`is_expired()`、`is_running()`、`try_wait() -> nb::Result<(), TimerError>`（就绪时**清空**计时）、`cancel()`。`TimerError::{NotRunning, Overflow}`。 |
| `delay::Delay<'a, CLOCK>` | **阻塞式** `delay(&mut self, Duration)`（内部靠 `embedded_hal::delay::DelayNs` + `nb` 忙等）。 |

### 2.2 它**不**提供什么（决定施工形状）

- **没有任何异步唤醒**：没有 `Future`、没有 waker 注册；`try_wait` 是 `nb` 风格轮询。
- 因此「到点唤醒」**仍必须由运行时提供**（`abs_art::TrDelay`，或另行注入的 async ticker）。
  `embedded-timers` 负责的是**时钟抽象 + 期限算术**，不是调度。
- `Delay` 会阻塞线程，**异步循环里禁止使用**（只用 `Clock`/`Instant`/`Timer`）。
- **零堆分配**：`src` 无 `Vec`/`Box`/`alloc::` ✓（符合本仓分配纪律）。
- 传递依赖（新增）：`embedded-hal 1.0.0`（只被 `Delay` 与文档示例用）、`nb 1.1.0`、
  `void 1.0.2`。

### 2.3 对「能不能不用 `std::time::Instant`」的正式答案

`embedded-timers` **不能**替我们去掉 `Instant`，但能把它**变成可注入的 trait**：
smux 自身只写 `CLOCK::Instant` 与 `Clock::now()`，具体类型由调用方的 `Clock` 实现给出
（可以是 `std::time::Instant`，也可以是假时钟）。收益：

1. `src`（除测试）不再出现 `std::time::Instant`；
2. 宽限期与空闲超时可以**用假时钟确定性验收**（今天只能靠看门狗掐时间）。

## 3. 共识形状（下个会话照此实现）

### 3.1 第 5 个循环：`timer_loop`

- **投递**：与四个循环同级，在 `MuxConnection::new` 里经同一个
  `TrLocalScope::spawn_local` 投递（注意：核心此时持有 `&S`，是唯一能 spawn 的地方）。
- **持有**：注册表句柄 + `Clock`（值）+ 异步等待源（ticker）+ `Timer<'_, CLOCK>` +
  取消令牌。**不持核心**（否则 conn 永不析构、四个循环与状态永久泄漏——与现有四循环同一条纪律）。
- **每轮动作**：
  1. `Timer::try_start(next)`（一次性，每轮重新 arm）→ `await` ticker 到期；
  2. 取注册表读锁扫 channel 身份，用 `Clock::now()` 与每子流「最后活动」算空闲时长；
  3. 对「接近超时」的投 `WriteEvent_::Control { PULSE }`：PULSE 帧**携带本端接收窗口**，
     天然顺带做窗口重同步（`connection/mod.rs` §7.1 的既定形状）——这一步**同时唤醒 mux 循环**；
  4. 对「确认超时」的置位 + 投事件，让**持有环半部的那个循环**去关环 / 拆流
     （timer 循环不碰环：环半部在 demux/mux 的本地表里）；
  5. 重新 arm 到「下一个感兴趣的期限」（或固定 tick，见 §5）。
- **「激活静默循环」的落点**：完全静默时，timer 循环是**唯一**还会醒来的任务；它通过既有
  的两条事件通道（或一个连接级 `NotifySlot_`，见 §5.5）把「有事要做」传给 demux/mux。
- **唤醒纪律**：不得在持有注册表守卫时 `wake`（见 §6 风险 2）；每个 park 点都必须与取消
  令牌竞争（`race_cancel_` / 手写 `poll_fn` 的既有模式）。

### 3.2 时间表示（顺手了结 `Instant` 问题）

| 项 | 现状 | 本方案 |
| --- | --- | --- |
| 每节点 | `base_: Instant`（`std::time::Instant::now()`）+ `active_millis_: AtomicU64` | **去掉 `base_`**；`active_millis_` 原样保留（`touch_` 继续在 7 个活动点写） |
| 连接级 | 无 | 一个 **epoch**（`CLOCK::Instant`），由 timer 循环/核心持有；「现在」= `Clock::now().duration_since(epoch)` 的毫秒数 |
| 宽限期索引 | `BTreeSet<(Instant, Dock, Dock)>` + `now + max_channel_wait_close` | 改为 `BTreeSet<(u64 毫秒, Dock, Dock)>`；`reap_wait_close_(now_millis)` |
| `std::time` | `owner_` / `registry_` 各一处 | `src`（除测试）**不再出现**；具体 `Instant` 类型只存在于调用方的 `Clock` 实现 |

热路径代价不变：每次活动仍是一次 `active_millis_` 原子写；epoch 只在扫描时读一次。

## 4. 施工顺序（每步可编译、可测）

1. **先解决依赖可构建**（§6 前置条件）＋ 在 `x_deps` 里加 `pub use embedded_timers;`
   （`src/lib.rs` 已有该模块，属**公开面**变更）。
2. **`Clock` 注入 + 假时钟**：在 `new`（或 `TrConnCfg`）注入 `Clock`；同时给测试提供假时钟
   （`TimespecInstant`，或自写一个按计数递增的 `Instant`）。
3. **`timer_loop` 骨架**：只做「每 tick 投一条事件」，先把取消/收尾验证干净
   （conn drop ⇒ 立刻退出、不泄漏）。
4. **`touch_`/`active_millis_` 盘活 + epoch 迁移**：`owner_` 去掉 `base_: Instant`；
   `registry_` 的到期索引改毫秒。
5. **PULSE**：扫描 → `WriteEvent_::Control` → mux 循环写出；限频/抖动规则见 §5.3。
6. **超时落地**：按 §5.1 的语义裁决（拆子流 / 终连接 / 如何通知应用）。
7. **用例**（假时钟，双运行时）：
   - 宽限期到期回收（把今天的看门狗式用例升级为确定性用例）；
   - 空闲超时触发，且**不早于** `max_channel_timeout`；
   - PULSE 按阈值发出、限频生效、不抖动集中；
   - **静默连接下 timer 循环仍能醒**（防「被饿死」的回归用例）；
   - `alloc_count` 增一条 tick 期的全局分配上界。

## 5. 开工前仍需裁决

1. **超时语义**：`IdleTimeout` 是**终止整条连接**还是**只拆该子流**？若只拆子流，应用如何
   被告知（现在只有 `is_tx_closed` / `Closing`，可能需要一个子流级错误回传面 = 公开 API）。
2. **异步等待源**：`TrDelay` 不在 `S: TrLocalScope` 上（见 §2.2）⇒ 三选一：
   (a) `new` 加一个 ticker 参数（**推荐**，不碰上游）；(b) `TrConnCfg` 加关联类型；
   (c) 请上游给 `TrLocalScope` 加 `delay`。**`embedded-timers` 给不了这一项**。
3. **PULSE 规则**：阈值（如 `timeout / 2`）、每 tick 最多处理多少条、是否抖动、是否只发
   最老的 K 条。
4. **`Clock` 注入形状**：`new` 的值化参数 vs `TrConnCfg::Clock`（两者都是公开 API 变更）。
5. **tick 唤醒落点**：复用两条事件通道，还是新增一个连接级 `NotifySlot_`（后者省一次
   `flume` 全局分配，但要多一条唤醒路径）。
6. **tick 频率**：固定 tick（实现简单、误差 = tick）vs 「最早到期」动态 arm（精度更好，
   但每次扫描后都要重算最小期限）。

即：`embedded-timers` 本体在本地 git cache 里（`Cargo.lock` 已锁到 `v0.4.0` = `c148f72`），
但它的三个传递依赖 **`embedded-hal 1.0.0` / `nb 1.1.0` / `void 1.0.2` 不在本地
registry cache**，而本沙箱的 `CARGO_HOME`（`/root/.cargo`）**只读**（`touch` 探测报
`Read-only file system`）。cargo 已经**联网下载成功**，只是写不进 cache。开工前三选一：

- **(a)** 放宽文件沙箱 / 提权，让 cargo 能写 `CARGO_HOME`（最小改动，推荐先试）；
- **(b)** 把 `CARGO_HOME` 指到**工作区内可写目录**并 `cargo fetch`（会重新拉取整个依赖图）；
- **(c)** 与上游确认能否把 `embedded-hal` 改为可选依赖（它只被阻塞式 `Delay` 与文档用到），
  或本仓自实现等价的 `Clock`/`Instant`/`Timer`（约百行、零外部依赖）——**这是设计变更，需裁决**。

另：`Cargo.toml` 的这次改动目前**未提交**（按 AGENTS §3，在它被处理前不动代码文件；本
session 只写文档）。

### 6.2 风险 1：tick 放大事件通道消息量

每条 PULSE 走 `WriteEvent_::Control` ⇒ 一次 `flume` 消息 = 一次**全局**分配
（audit §3.1 #9/#10 那两条「已承认的例外」）。tick 频率 × 在册子流数直接放大这块开销，
必须限频，并给 `alloc_count` 加一条 tick 期上界（否则"稳态读侧分配"这条基线会被悄悄改写）。

### 6.3 风险 2：在注册表锁内 `wake`

现存两处调用在持有注册表守卫时唤醒等待者：`notify_inbound_`（`rec.notify_()`）与
`mark_failed_`（`rec.notify_()` / `rec_.notify_establish_()`）。这**与本仓自订纪律不一致**
——`sync_::NotifySlot_` 的类型文档写的是「取 waker 后**释放锁**再 `wake`」（`wake` 可能同步
重入 `poll`，持自旋锁调用即单线程自死锁）。当前两个后端未观察到问题（它们的 `wake` 只入队、
不内联执行），但 **timer 循环会成为第三个这样的调用方**。建议实现保活时一并统一为
「锁内只置位 / 取 waker，锁外 `wake`」。

### 6.4 风险 3：静默时 timer 循环是唯一唤醒源

它自己必须在每个 park 点都能被 **ticker 到期** 与 **取消令牌** 唤醒；本仓有过「只 park 在
环上、导致别的唤醒被饿死」的踩坑记录（`session_` 模块文档「两个内侧循环各自的 park 点」），
这里是同一类陷阱，必须有用例钉住。

### 6.5 非目标

不做写法 A；不为每条子流起计时任务；本轮不改上游 `abs_art`（若最终选 §5.2(c) 另行讨论）。
