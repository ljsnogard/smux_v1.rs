# 流控落实：核对结论与**未决死锁**（flow-ctrl）

本文记录「按协议设计落实 smux_v1 流控 + 真实 socket 上证明有效」这一轮的实际进展。

**结论先行**：

- `src/flow_ctrl/` 的窗口算法本身是对的；问题全在**什么时候发通告**与**谁叫醒谁**。
- 本轮修掉 **7 个**缺陷（§1）。它们几乎都是同一个根因的不同侧面：这套「阈值通告 +
  事件唤醒」机制**缺少显式状态**——「对端还有没有额度」「待发送额度是否已变化」这些
  事实，现在是用「事件 + 环可读 + 指针」近似出来的，于是每修好一处就暴露下一处。
- **真实 socket 用例仍未通过**：阻塞点已收敛到最后一处（§2），而它指向的正是上述
  设计缺口，需要先定方案再动手。

## 0. 为什么此前没人发现

`K_CHANNEL_CAPACITY = 4096`，而所有既有用例的载荷只有 64 字节：**接收窗口永远用不
完**，`WINDOW_UPDATE`、额度耗尽、额度回补这三条路径一行都不会执行。现有全绿说明的
是「窗口用不完时一切正常」，不能说明流控有效。

真实 socket 的定向证据需要三个条件同时成立，本轮把它们固定成
`tests/common/mod.rs` 的 `FlowCtrlConfig`：

| 量 | 取值 | 作用 |
| --- | --- | --- |
| 子流环容量 `K_FLOW_CTRL_RING_CAPACITY` | 512 B | 就是窗口；`make_ring_buffs` 里**上钳**，保证一定被用尽 |
| 载荷 `K_FLOW_CTRL_PAYLOAD_LEN` | 64 KiB | 比窗口大 128 倍，窗口必然反复耗尽 / 回补 |
| 接收步长 `K_FLOW_CTRL_READ_STEP` | 64 B | 慢读，逼出「窗口在 0 与刻度之间往复」 |

## 1. 已修缺陷

### 1.1 `SendWindow::on_report` 把「窗口回补」当成过期通告丢掉

原判据 `absolute <= r0` ⇒ 忽略。但接收方**消费**数据会让窗口回补，而它此时可能还没
再收到新数据——通告就长成「`R` 不变、`W` 变大」，被判为重复而丢弃。窗口跌到 0 之后
的第一条回补通告**恰好总是这种形状**。

修：判据改为「`R` 更大，或 `R` 相同而 `W` 更大」。单测
`send_window_accepts_window_growth_with_same_recv_total`。

### 1.2 额度用尽时照样发 `FIN` ⇒ 静默丢数据

`WriteEvent_::TxClosed` 原先 `flush_entry_` 之后就无条件发 `FIN` 并摘表项。而
`flush_entry_` 在额度为 0 时是**静默返回**的，于是「应用写成功 → 对端读到 FIN →
载荷从未到达」，违反 README §5 第 2 条的承诺。

修：引入 `PendingFin_` 集合与 `finalize_entry_`；`FIN` 只在「发送环确实空了」时发
（`has_writable_` 判定），否则等额度 / 环推进后由主循环第 2.5 步继续。

### 1.3 额度为 0 时复用循环**纯空转**

复用循环 park 时把「最近通知的那条发送环可读」当唤醒理由。但额度为 0 时
`drain_one_` 一条也发不出去，于是「回到顶部 → drain 失败 → 立刻又就绪」无限循环。
实测把同 `LocalSet` 上的其它任务全部饿死，**连测试的超时看门狗都来不及触发**。

修：park 的就绪条件追加「该子流确实还有发送额度」（`ChannelOwner_::try_with_`）。

> 顺带结论：**CPU 空转会把超时保护一起吃掉**。以后凡是「用例挂住但看门狗没响」，
> 第一嫌疑是某个循环在忙等。

### 1.4 收到窗口通告不叫醒复用循环

读循环处理 `WINDOW_UPDATE` / `PULSE` 时只更新 `SendWindow`，不投任何事件；而复用循环
在额度为 0 时 park 在事件通道上，通告因此被「白收」。

修：更新成功后投一条 `WriteEvent_::TxReady`。注意**不能**走 `tx_queued_` 去重位——
它可能正被应用上一次写入置着（额度为 0 时写循环没机会清它），那样唤醒会被静默丢掉。

### 1.5 提醒时机：**分区机制**取代刻度列（协议设计的核心一条）

原实现是「1/4、1/2、3/4 三个刻度 + 单向越过」。它有两个毛病：

```rust
shrink_levels → [1/2, 1/4, 0]      // 0 不是刻度
expand_levels → [1/2, 3/4, 满]      // 缺 1/4，多了「满」
```

缺的 1/4 正是发送方的**首次解封点**——缺了它，首次放行必须等空闲涨过 1/2，而发送方
一次只发得出上次放行的量、空闲又被填回去，越等越高。

**按人类给出的新设计改为分区**（越接近瘫痪越密报），判据一律看**剩余容量**：

| 区间 | 行为 |
| --- | --- |
| 剩余 ≤ 容量/N（临界区） | **任何变化都提醒** |
| 容量/N < 剩余 ≤ 容量×(1−1/N)（中间区） | 按变动量门限提醒（防抖） |
| 剩余 > 容量×(1−1/N)（充裕区） | 不提醒；只有「跌出充裕区」那一次要报 |

- 分区边界由**同一个旋钮** [`TrFlowCtrlPolicy::critical_denominator`] 推出（缺省 4），
  不再有两个可能互相矛盾的参数；
- **进入更紧的分区无条件放行**（发送方最需要知道的信息，不能等门限）；
- `shrink_levels` / `expand_levels` / `K_REPORT_LEVEL_COUNT` **已删除**（人类裁决
  分区完全取代刻度列）；
- 临界区覆盖了「归零」与「从 0 抬起」，**旧实现那两个免门限特例因此不再需要**——
  这正是分区机制相对刻度列的价值。

顺带修掉两个实现缺陷：

- **临界边界算错了**：原写法拿「当前剩余」去除以分母（`212/4 = 53`），于是边界随窗口
  浮动、临界区几乎永远进不去。必须用**容量**。
- **「窗口没变」不该重发**：`current == last` 时任何分区都没有新信息。

单测：`default_policy_window_and_zone`、`recv_window_zone_boundaries`、
`recv_window_reports_every_change_in_critical_zone`、
`recv_window_silent_while_relaxed_but_reports_transition`、
`recv_window_silent_when_unchanged`、`recv_window_zero_and_refill_need_no_special_case`。

### 1.6 中间区的度量：**字节变动量**，不是帧数

中间区的防抖门限原先是「自上次提醒以来收到多少个数据帧」。这个口径有个致命偏斜：
**它只能靠收到数据帧推进**。于是窗口一旦归零（发送方停摆、一帧也发不出来），或者
应用只消费、发送方还没跟上时，变动量明明在涨、帧计数却纹丝不动，提醒被永久压住。

已改为**字节变动量**（收到 + 消费都算）：

```rust
fn min_advance_between_reports(&self, initial: Credit) -> Credit;   // 缺省 initial/N
```

它对「哪一侧在动」不敏感，任何真实进展都能推进它。绝对下限 `K_MIN_ADVANCE_FLOOR`
避免极小窗口下退化成 0（= 不限频）。两个附带修正：

- `on_data` 原先**先**加帧计数**再**判越权，于是违例帧也推进门限（对端可以靠灌违例
  帧把门限刷开）。现已改为只在**被接受之后**记账，且只记真实载荷字节。

### 1.7 发送侧：待发积压超过 3/4 才频繁提醒

`ChannelTx::notify_tx_ready_` 原先**每次写入**都投一条 `TxReady`（只靠 `tx_queued_`
去重位压频率）。但写循环每轮要在「排空」与「处理事件」之间分时，事件被灌满就会挤占
排空段。

已按人类设计改为与接收侧对称的规则：**待发积压 > 容量 × 3/4（即剩余不足 1/4）时
任何变化都通知**，并在进出临界区的边沿各补一次，避免写循环漏掉状态切换。临界水位
取自同一个 `critical_denominator`，在 `ChannelTx::new_` 时由调用方算好传入。

### 1.8 事件挤占排空段 ⇒ 复用循环从没进过排空

主循环原先「每处理一条事件就 `continue` 回顶部」。事件是**持续到来**的，于是只要事件
队列非空，第 2 步的**排空段永远轮不到**——实测复用循环一直在顶部打转、一帧也没发出去。

修：每轮只处理有上限的一批（`K_EVENT_BATCH = 32`），然后**必定**走一次排空。

## 2. ⛔ 仍未解决：发送方在第二轮窗口归零后停摆（**当前唯一阻塞**）

分区机制（§1.5–§1.7）落地之后，**接收侧已经完全正确**——实测能看到完整的窗口循环，
而且第一轮能一路放到 448 字节：

```text
should: cur=0   last=512  zone=Critical lastzone=Relaxed   ← 归零，临界区每变必报
should: cur=64  last=0    zone=Critical                    ← 从 0 抬起（无需任何特例）
should: cur=128 last=64   zone=Critical
should: cur=192 last=128  zone=Moderate                    ← 进入中间区（无条件放行）
should: cur=256 last=128  zone=Moderate act=128 minadv=128 ← 变动量达标
should: cur=320 last=256  zone=Moderate
should: cur=384 last=256  zone=Moderate act=128
should: cur=448 last=384  zone=Relaxed                     ← 回到充裕区
SENT take=512  →  SENT take=448                            ← 发送方按通告放行
```

**但第二轮不再前进**：接收侧把窗口从 448 一路报回 0、再抬到 384（上面那串在后半段
重复出现），而发送侧**始终没有新的 `SENT`**——`avail` 停在 0，`drain_one_` 只打印
`STUCK avail=0`。

也就是说：**接收方的提醒发出来了，发送方的 `SendWindow` 也收到了，但发送方没有被
叫醒去排空**。这与 §2.5（旧编号）是同一类问题：唤醒信息不够，`TxReady` 的投递条件
在发送侧收紧之后（§1.7 只在临界区频繁提醒）暴露出新的空档。

按嫌疑排序，下一轮从这三处入手：

1. **`WINDOW_UPDATE` 到达时的唤醒必须无条件**：读循环收到通告后投的那条 `TxReady`
   （§1.4）现在仍受「已入队」去重位影响——而该位可能正被应用上一次写入置着，于是
   这次唤醒被静默丢掉。应在**绕过去重位**的专用通道上投递，或直接给「额度从 0 变正」
   记一个必须被消费的待办位。
2. **`drain_one_` 开局就清去重位**：清位发生在真正判断「能不能发」**之前**，于是清位
   之后到失败返回之间进来的那次写入，其事件可能被吞。需要把清位挪到「确实取到了段」
   之后，或改成带序号的一对计数器。
3. **给「待发送 / 待唤醒」一个显式状态**：不要再拿「事件 + 环可读 + `last_ready` 指针」
   三样东西近似它。§1.3 / §1.4 / §1.7 / §1.8 与本节全是这个缺口的不同侧面。

## 3. 给下一轮的建议顺序

1. **先解决 §2**：它已是唯一阻塞点，且指向明确的建模缺口；
2. 去掉 `flow_ctrl_socket_{tokio,compio}` 的 `#[ignore]`，用真实 socket 验收；
3. 再加 inmem 版与跨进程 / 局域网那条；
4. **最后**才按 §4 拆信令循环——必须等这条链正确之后再拆，否则会把同一类唤醒问题
   复制进新循环。

## 4. 给信令循环的既定结论（本轮与人类确认）

- 信令循环是**一条真正的内部子流**，收发时填**真实的 dock 号**（库内固定常量，两端
  相同），因此**不触碰**「保留值不能当身份」这条不变量，也无需在帧校验里开特例。
- `ChannelRx` **不投瞬态数值**（消费增量）：它只**提醒**信令循环「去查看水位是否
  越档」，由信令循环自己读共享状态判定。`WriteEvent_::RxConsumed` 的 `amount_` 应据此
  去掉（**公开面不变**——它是 crate 内部枚举）。
- `min_frames_between_reports` **保留**：它是设计的一部分，作用是防抖（水位在刻度线
  附近浮动时不要反复报告），作用域收缩到**收缩方向**。
- 出帧仍走 `WriteEvent_::Control` 这条已做过分块阻塞写的车道，不做第二个写环生产者。

> **备注（本轮实测的硬结论）**：帧数门限靠**收到数据帧**推进，因此它只在「发送方还有
> 余量、会持续发帧」时可达。三种不可达情形都实测到了：窗口归零后完全停摆；窗口很小
> （512 B）时一次放行只够发一两帧；而唯一攒得满的情形正是不需要扩张通告的状态。故
> **归零无条件发、扩张一律免门限、收缩保留门限**。试过的中间方案（`last == 0` 时豁免、
> 用授权水位 `R + W` 判停摆）都失败并已回退——后者在整缓冲粒度上并不等价。
