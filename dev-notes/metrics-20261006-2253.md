## 2. 需求方六条约束与落地方式

| # | 约束 | 落地 |
| --- | --- | --- |
| 1 | metrics 自身是一个独立 mod | `src/metrics/`，`mod.rs` 只做导出控制（不用 `*`，逐项列出），逻辑分在 `sink_` / `debug_` |
| 2 | MuxConn 不承担灵活性代价：不做 `Arc` 分配、不做运行时替换 sink、不做 `dyn` 适配 | 「不上报」的形态是**零大小**的 `NoMetrics`（`type Metrics = NoMetrics;` + `metrics()` 回 `NoMetrics::silent()`）；`metrics()` 返回**确定的引用**，调用点没有判空；**没有**任何 `set_sink`；**没有** `impl TrMetricsSink for Arc<T>` 之类的便利适配。上报点是 `C::Metrics` 上的静态分派，会被单态化 |
| 3 | MuxConn 自己也需要一个 bench / debug 用的 metrics | `DebugMetrics`：`Arc` 包住的**一份独立计数**，`Clone + Default`（见 §12），挂在 `feature = "metrics"` 上 |
| 4 | 缓冲区水位不报 | trait 里**没有**任何水位 / 队列长度方法；相应地**取消了**草案里的 `MetricsSnapshot` 快照接口 |
| 5 | sink 的问题交给 metrics 实现方，MuxConn 不参与 | MuxConn 只做两件事：经 `config.metrics()` 借一个 `&C::Metrics`，建连时 `clone` 一份进内部共享量。存在哪、怎么共享、生命周期归谁，全由需求方决定（`metrics_e2e` 演示了「放 `static`」这一种） |
| 6 | `on_frame` 对 MuxConn 不是 `dyn` | 见 §3 的实证：缺省 sink 下调用点被完全消除；具体 sink 下是一次直接调用（是否内联由具体类型决定） |

## 3. 注入形状与实证

```rust
pub trait TrConnCfg: /* …既有约束不变… */ {
    /// 必需项：不上报就写 `= NoMetrics`。
    type Metrics: TrMetricsSink + Clone;

    /// 必需方法：返回**确定的引用**，不是 `Option`。
    fn metrics(&self) -> &Self::Metrics;
}
```

两个设计点各有其不可替代的理由：

1. **关联类型是必需项**（没有默认值）：每个 `TrConnCfg` 实现显式表态。不上报的写法是
   `type Metrics = NoMetrics;`。曾用过 `= NoMetrics` 默认值（免去 8 处实现的这一行），
   但该方案在 §11 被废弃。
2. **取用方法返回 `&Self::Metrics` 而不是 `Option<&…>`**（需求方 2026-10-06 的裁决）。
   「有没有 sink」是**编译期**由关联类型决定的**类型事实**，做成运行期状态只会让每一个
   上报调用点多一次判空分支——而那个分支在「不上报」的装配下本可以彻底不存在。

代价是 `metrics()` **没有默认实现可写**：Rust 不允许默认方法体假定
`Self::Metrics == NoMetrics`。因此它与 `runtime()` / `allocator()` / `policy()` 同形，
8 处实现各写两行：`type Metrics = NoMetrics;` 与 `fn metrics() -> &Self::Metrics { &NoMetrics }`
（零大小类型的常量引用被提升为 `'static`，不涉及分配，也不需要静态存储）。

> 曾考虑另一条路：让 `TrMetricsSink` 提供一个必需项（如 `const SILENT: &'static Self`）
> 以保住 `metrics()` 的默认实现。**未采纳**——那把「config 的缺省从哪来」这个负担推给了
> sink 实现方，而持有堆状态的 sink（`Arc<…>`）根本给不出静态实例，反而更别扭。

`Clone` 是硬要求而非风格：五个循环**不持有核心**（`connection` 模块文档 §2.2），
建连时必须把 sink 克隆一份进 `MuxLoopShared_` / `ByteLoopShared_`。

### 实测（`rustc 1.101.0-nightly`，`-O`）

用一个最小探针验证了三件事，结论如下（探针已删，形状与本仓一致）：

- 带 `#[cfg(feature = "metrics")]` 门控的默认关联类型**两种 cfg 都能编译**；
- 既有 `impl`（不写 `type Metrics`、不写 `metrics()`）**照旧编译**；
- 缺省 sink 下调用点被**完全消除**：生成的汇编里那个函数体只有 `retq`，没有任何
  `callq`；LLVM 甚至把它与显式的空函数合并成同一个符号
  （`record_via_default_cfg = record_explicit_nosink`）。

具体 sink 时是一次直接调用（`Arc<dyn …>` 才会退化成 `callq *24(%rcx)` 的间接调用
——那属于需求方自己选的代价，mux 不做这个选择）。

探针的核心形状（可复现：`rustc --edition 2024 --crate-type lib -O --emit=asm`）：

```rust
#![feature(associated_type_defaults)]

pub trait Sink: Send + Sync + 'static { fn on_frame(&self, _b: u32) {} }
pub struct NoSink;
impl Sink for NoSink { #[inline(always)] fn on_frame(&self, _b: u32) {} }

pub trait Cfg {
    type Metrics: Sink + Clone = NoSink;
    fn metrics(&self) -> Option<&Self::Metrics> { None }   // 缺省 = 不上报
    fn runtime(&self) -> u64;
}

/// 既有实现：不提 Metrics / metrics，仍然编译通过。
pub struct LegacyCfg;
impl Cfg for LegacyCfg {
    type Metrics = NoMetrics;                    // 也可以用默认值
    fn metrics(&self) -> &NoMetrics { NoMetrics::silent() }
    fn runtime(&self) -> u64 { 0 }
}

#[unsafe(no_mangle)]
pub fn hot_legacy(cfg: &LegacyCfg, bytes: u32) {
    if let Some(sink) = cfg.metrics() { sink.on_frame(bytes); }
    core::hint::black_box(cfg.runtime());
}
```

生成的汇编里 `hot_legacy` **没有任何 `callq`**：

```asm
hot_legacy:
	movq	$0, -8(%rsp)
	leaq	-8(%rsp), %rax
	retq
```

## 4. 指标裁剪（对照原始五类清单）

| 原始指标 | 结论 | 依据 |
| --- | --- | --- |
| 连接建立成功 / 失败 | ✅ **只到复用层** | 握手层（`handshake/agent.rs`）没有配置注入点，且配置是握手**之后**才交给 `MuxConnection::new` 的；把握手失败也计入要另加一条注入路径，收益不抵改动 |
| 连接关闭（正常 / 错误 / 对端关闭） | ✅ | 原因取自注册表的**锁外**快照 `fail_kind_`（`Drop` 不能取锁）；分 `Local` / `PeerClosed` / `Transport` / `ProtocolError` 四类 |
| 连接持续时间 | ✅ | `epoch_` + `now_millis_()` 的差 |
| 当前活跃连接数 | ⚠️ **由 sink 从事件累加** | 本 crate 没有进程级容器，连接对象自包含；这也正是「sink 的问题交给实现方」的一条推论 |
| 子流打开 | ✅ | 唯一建成点 `install_channel_`（两条环建好、半部已移交） |
| 子流关闭（正常 / 超时 / 建流超时） | ✅ | 正常收尾在 `maybe_release_` 的 `claim_release_`；超时两条路径在 `timer_` 里各自上报（它们**不经过** `maybe_release_`） |
| 子流持续时间 | ✅ | `ChannelState_` 新增 `created_millis_`（登记时写一次），关闭时相减 |
| 每子流发送 / 接收字节数 | ✅ | `on_frame` 带 dock 对，需求方据此自行按子流聚合**——因此不需要给 `SendWindow` 加访问器，也不需要额外回调** |
| 当前活跃子流数 | ⚠️ **由 sink 从事件累加** | 同「活跃连接数」 |
| 帧收发按类型 | ✅ | 8 种 `FrameKind`；写侧在编帧处、读侧在 `header.kind()` 派发前 |
| 帧字节数 | ✅（两侧口径**逐字节一致**） | 写侧 = 帧头实际编码长度 + 载荷；读侧 = 逐字节状态机**自己数出的**帧头长度（`FrameHeaderParser::consumed_len_`）+ 载荷。因此**同一批帧在两个方向的字节数之和相等**——端到端用例把它钉成了断言（见 §9） |
| 帧处理错误 / 协议错误 | ✅ | 收敛到 `fail_mux_loop_` 一处（13 个调用点各带 `kind`） |
| 流控阻塞事件 | ✅（判据已定义） | 「有数据待发但额度为 0」由复用循环在 `send_available_` 处判定 |
| 超时 | ✅ | `timer_scan_` 的认领点 |
| 重置次数 | ✅ | `on_reset(by_peer)`：本端发 RESET（发送成功后）与对端来 RESET 各一处 |
| 缓冲区水位 / 队列长度 | ❌ **不报**（约束 4） | 环对象在循环本地表里，使用者的 `ChannelTx` / `ChannelRx` 只公开 `write_all` / `read_exact` / `abort_reason`，拿不到 `ring_state()` |
| 重传次数 | ❌ **删除（恒 0）** | 协议跑在可靠有序字节流上，「同连接内不存在重排 / 重传」（`connection` 模块文档 §4.3） |
| 心跳延迟 | ❌ **不可测** | `PULSE` 没有请求 / 应答语义（收到的一方只刷存活时钟、**不回复**），RTT 在协议上不存在 |
| `HEADERS` / `RST` / `PING` | ❌ **改名** | 本协议 8 种帧：`Open` / `Accept` / `Reject` / `Close` / `Data` / `Datagram` / `WindowUpdate` / `Pulse`；`RST` 是 `Close` 上的 flag |

### 4.1 两个 `ConnCloseReason` / `ChannelCloseReason` 的取值取舍

- `ConnCloseReason` 里**没有** `Cancelled`：取消令牌收尾**不**在注册表上留失败标志，
  语义上就是正常关闭，归入 `Local`（`session_::fail_mux_loop_` 的文档说明了这一点）。
- `ChannelCloseReason` 里**没有** `LocalReset` / `PeerReset`：RESET 是一个**事件**
  （可能发生多次、也可能只在一个方向），由 `on_reset(by_peer)` 单独表达。枚举里重复
  一份会产生永远不可达的取值，因此删掉。

## 6. 已知缺口

**连接级失败时，在册子流不会有各自的关闭回调**：`ChannelRegistry_::mark_failed_`
只置失败位、唤醒等待者、取消五个循环，**不逐条释放身份**。因此
`ChannelCloseReason::ConnFailed` 目前只在文档层面表达；需求方要从 `on_conn_closed`
推断在册子流一并终结。若将来需要精确口径，在失败路径补一次全表遍历即可（成本只在
失败路径上）。

线上总长相等）与 `frames_sent == frames_recv`。读侧若只填载荷长度，这两条必然失败
——这正是 §9 那次改动的验收点。

## 8. 遗留

1. `on_frame` 的粒度是**每帧一次调用**。4 KiB 帧、高吞吐下这是每帧一次虚 / 直接调用
   （取决于需求方选的 sink 类型）。是否需要「循环本地累加 + 批量 flush」，等真实
   bench 数据出来再定。
2. `Arc` 走全局分配器：若需求方把 sink 放进 `Arc`，那次分配发生在**需求方**的代码里，
   不违反本仓「每一处堆分配都走注入分配器」的纪律（mux 只做 `clone`）。若需求方希望
   连构造也走注入分配器，用 `mm_ptr::Shared<T, A>` 作为 `Metrics` 即可。
3. `MuxCore::drop` 里的时钟读（`now_millis_()`）现在是**无条件**的：去掉 `Option` 短路
   之后，即使 sink 是静默的 `NoMetrics`，这次读也会发生。它落在收尾路径、每条连接
   只发生一次，因此可以接受；换成「按需才读」等于把判空重新引回调用点，与本次裁决
   相悖。读时刻的前提仍是 `TrConnCfg::runtime` 的契约（交出**建连时抓住**的运行时值）；
   compio 的连接是 `!Send`、不可能跨线程丢弃，tokio 的 `Runtime` 是 `Handle`。
   两种装配下的端到端用例都覆盖了这条路径。

## 9. 一次未采纳的方案：用环状态差值测帧头长度

**建议（需求方 2026-10-06）**：解析前后各取一次 `TrBuffRead` 的 `data_size()`，差值即
帧头读了多少字节。

**为什么不可行**（查证过 buffex 源码）：

- `read_header_async_` 是**逐字节**推进的（`Demand::exactly(1)`），环空时会 park——
  而外侧读泵正是在那一刻往**同一个环**里填字节。于是「前后 `data_size()` 之差」量的是
  「期间消费 − 期间写入」，最坏可以为负；
- `buffex` 的环状态（`RingState` / `IoPos`）只有**物理**读写指针 `rp` / `wp`
  （都在 `[0, capacity)` 内环绕）与 `data_size()` / `free_size()` 两个瞬时量，
  **没有单调累计量**——因此「改用消费量之差」这条退路也不存在。

**采纳的替代**：让**逐字节状态机自己数**。它零歧义——字节本来就是它一个个吃掉的，而
`consume_byte_` 的文档里早已写明「消费不变量」：只要还需要更多输入就必定消费该字节
（包括让它完成或判定非法的那个字节），出结论之后的重复喂入不再消费。

**计数的生命周期**（需求方随后指出的修正，已落实）：`consumed_` 只表达**本轮解析**的量，
并且**回到解析开头（`State_::Start`）时重新起算**——帧首字节计为 `1`，其余状态在本轮内
累加。第一版把它写成「自建立以来累计」，那是错的：解析器一旦被复用，第一帧之后的每一帧
都会拿到偏大的长度（含此前所有帧的字节）。现在 `Start` 分支显式重置该计数，单元测试同时
钉住「新一轮从 1 起算」与「出结论后不再增长」。

改动很小：`FrameHeaderParser` 加一个 `usize` 字段、入口处一次 `saturating_add`、一个
访问器；`read_header_async_` 的返回类型从 `FrameHeader` 变成 `(FrameHeader, usize)`
（`pub(crate)`，调用点两处，其中一处是测试辅助）。

**证据**：端到端用例断言 `frame_bytes_sent == frame_bytes_recv`——读侧若仍按载荷长度
上报，这条必然失败（写侧含帧头）；另有单元测试
`consumed_len_counts_exactly_the_header_bytes_` 直接钉住计数语义与幂等性。

## 10. 一次返工：`metrics()` 去掉 `Option`（需求方裁决）

**初版形状**：

```rust
fn metrics(&self) -> Option<&Self::Metrics> {
    Option::None          // 缺省 = 不上报
}
```

它的唯一好处是**带默认实现**，因此 8 处既有 `impl TrConnCfg` 一个字都不用改。

**为什么被否**：`C::Metrics` 是**编译期**确定的类型，「有没有 sink」是**类型事实**，
不是运行期状态。做成 `Option` 会让每一个上报调用点多一次判空分支——即使缺省装配下
编译器能把整句消除（实测确实如此），**配了 sink 的装配仍然每次都要判一次**。

**返工后的形状**：

```rust
fn metrics(&self) -> &Self::Metrics;      // 必需方法
```

- 调用点变成 `shared.metrics_().on_frame(..)`：**没有判空分支**——缺省时 `NoMetrics`
  的空实现让整句消失，配了 sink 时是一次直接调用；
- 共享量的字段从 `Option<M>` 变成 `M`：缺省时它是零大小的 `NoMetrics`，**结构体尺寸
  不变**；
- 代价一：`metrics()` 失去默认实现（Rust 不允许默认体假定 `Self::Metrics == NoMetrics`），
  8 处实现各加一行 `NoMetrics::silent()`；
- 代价二：`MuxCore::drop` 里的时钟读从「有 sink 才读」变为**无条件读一次**
  （见 §8.3）。

**未采纳的替代**：让 `TrMetricsSink` 提供 `const SILENT: &'static Self` 以保住默认实现
——那把「config 的缺省从哪来」推给了 sink 实现方，而持有堆状态的 sink（`Arc<…>`）
给不出静态实例。

**实测**（`rustc --edition 2024 -O --emit=asm`，同一个**真实** sink 的两版调用点）：

```asm
; 返工后：metrics() 返回 &M
hot_direct:
	movl	%esi, %eax
	lock		addq	%rax, (%rdi)
	retq

; 返工前：metrics() 返回 Option<&M>
hot_option:
	cmpl	$1, (%rdi)          ; ← 每帧一次的判空
	jne	.LBB1_2
	movl	%esi, %eax
	lock		addq	%rax, 8(%rdi)
.LBB1_2:
	retq
```

对照组里那条 `cmpl` / `jne` 就是「每次都让 CPU 猜有没有」，`8(%rdi)` 的偏移则是
`Option` 判别式挤出的空间。返工后两者都不在了。

## 11. 一次适配：`Metrics` 去掉默认值 + `DefaultConnCfg` 增加 `M` 参数（需求方裁决）

**改了什么**（需求方 2026-10-06 亲自落地；本文件补齐测试侧与文档侧）：

1. `TrConnCfg::Metrics` **去掉默认值**：`type Metrics: TrMetricsSink + Clone;`。随之
   `#![feature(associated_type_defaults)]` 也从 `lib.rs` 移除——本 crate 不再需要它。
2. `DefaultConnCfg` 增加**第 3 个**泛型参数：
   `<W, R, M = NoMetrics, P = DefaultPolicy, Rt = DefaultRt_>`，并新增字段 `metrics_: M`；
   其 `TrConnCfg::Metrics = M`，`metrics()` 返回 `&self.metrics_`。
   `new` / `new_with_rt` 用 `M::default()` 造出它。

**受影响的编译目标与修法**（本次适配已全部修好）：

| 目标 | 问题 | 修法 |
| --- | --- | --- |
| `src/connection/test_support_.rs`（2 处 impl） | 缺 `type Metrics` | 各加 `type Metrics = NoMetrics;` |
| `tests/common/config_.rs`（2 处） | 同上 | 同上 |
| `tests/inmem_mux.rs`（1 处） | 同上 | 同上 |
| `tests/alloc_count.rs`（2 处） | 同上 | 同上 |
| `examples/active_passive.rs` | `DefaultConnCfg<Tx, Rx, DefaultPolicy, Rt>` 把 `DefaultPolicy` 顶到 `M` 位 | 改成 `<Tx, Rx, NoMetrics, DefaultPolicy, Rt>` |
| `README.md` 的示例 | 同上 | 同上 |
| `src/connection/config_.rs` 的 `Debug` impl | 仍是 4 参形态（`M` 位错位） | 改成 `<W, R, M, P, Rt>` 并输出 `metrics_` |

**关于「`M` 不能 `Default` 就没意义」的澄清**（需求方 2026-10-06 提问，本文档先前的
「已知缺口」提法**错误、已撤回**）：

- `DefaultConnCfg` 的字段（含 `metrics_: M`）全是私有的，外部只能经 `new` / `new_with_rt`
  构造；这两个入口没有 sink 参数，所以**必须**要求 `M: Default`——否则无从得到初值。
  该约束放在**构造器**上（而不是 `TrConnCfg` impl 上）正是为此。
- 因此 `M` 只可能是「Default 型 sink」，有意义的现实取值就是零大小的 `NoMetrics`。
- 想挂**能被自己读到**的采集器，正解是**写自己的配置类型**（`tests/metrics_e2e.rs` 的
  `MetricsCfg` 就是范例，只多十行）——这与 §3 的既定分工一致：sink 存哪、怎么共享
  属于需求方。
- 所以 `M` 参数的意义是**开放性**：`type Metrics` 是必需项，`DefaultConnCfg` 必须声明它；
  参数化让这个声明保持开放，同时不破坏既有的 `DefaultConnCfg<W, R>` 写法。它不是
  「挂 sink 的入口」，也**不需要**再加 `new_with_metrics` 之类的 API（先前那条建议已撤回：
  它会把「sink 存哪」这件事又拉回 mux 自己的类型里）。

## 12. 两次返工：内置采集器的形态（`&'static` → 零大小 → `Arc`）

内置采集器一共试过三种形态，因果链记在这里：

| 形态 | `Clone` | `Default` | 每份独立 | 代价 |
| --- | --- | --- | --- | --- |
| ① `DebugMetrics(&'static DebugCounters)` | ✓（复制指针） | ✗ | ✓ | 调用方必须自己准备 `static`；`Default` 不成立 ⇒ `M` 参数形同虚设（见 §11） |
| ② 零大小 unit struct + 进程级静态原子 | ✓（空操作） | ✓ | ✗ | **全局单例**：多连接、多测试共享同一份计数 |
| ③ **`DebugMetrics(Arc<Counters_>)`（当前）** | ✓（引用计数 +1） | ✓ | ✓ | 构造时一次 `Arc::new`（走全局分配器） |

两次推动力都来自需求方：

1. **①→②**：「`&'static` 没必要」——那个引用只是为了绕开「`M: Clone` 而 `DebugCounters`
   含原子、不可 `Clone`」，而代价（要求调用方准备静态存储、失去 `Default`）全由调用方承担。
2. **②→③**：「为什么不把那些 static 移回成员、用 `Arc` 包住？反正它只是 debug 用的」
   ——② 为了「零分配」牺牲了「每份独立」，而**零分配是我自己加的目标、不是需求**，
   「每份独立」才是实用的那一条。

③ 的代价是构造时一次全局分配，且它可能由 mux 的代码触发（`DefaultConnCfg::new` 里的
`M::default()`）。这是**刻意的例外**：本类型是给调试与基准用的便利件，不是生产数据面的
一环；生产路径要精确控制分配，就自己实现 `TrMetricsSink`。

当前形态的三点性质（都有用例钉住）：

- **每份独立**：`default()` 造一份新计数 → 单元用例与 e2e 各自独立，断言可精确到数值；
- **`Clone` 共享**：`clone()` 与本体指向同一份 → 配置持一份句柄、调用方另持一份，
  两边读到的就是同一批计数；
- **`Default` 成立**：`tests/metrics_e2e.rs` 里有一条**编译期断言**
  （`DebugMetrics: TrMetricsSink + Clone + Default`）钉住「`M` 参数真的可用」。

**热路径没有额外成本**：上报调用点是「一次指针解引用 + 一次 `Relaxed` 原子加」，与 ② 的
全局静态形态没有可测差别——引用计数只在 `clone()`（建连时两次）动。

**取舍边界**：`&'static` 形态并不「错」，它只是不该当**内置**形态；当 sink 需要跨动态库 /
跨进程共享同一份计数时，它仍是正确选择。

**顺带**：`NoMetrics::silent()` 也一并删掉了——`&NoMetrics` 的常量借用本来就会被提升为
`'static`，那层包装是多余的。
