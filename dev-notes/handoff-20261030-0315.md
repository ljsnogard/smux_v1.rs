### 3.1 `metrics_e2e`：帧长口径不一致（发送 24 / 接收 84）

> `Datagram`，全部控制帧漏报。修法是在 `main_loop` 的两个控制帧写点

> 失败信息也会打印「帧种类 × 方向」表。

- **断言位置**：`smux_v1/tests/metrics_e2e.rs:318`——
  `assert_eq!(snap.frame_bytes_sent, snap.frame_bytes_recv, ...)`；下一行还有
  `frames_sent == frames_recv` 的条数断言。

- **已知线索**：

### 3.2 `thread_safety`：三个用例全部挂起

> **结论（R18）**：根因假设**成立**——主线程建连后不再驱动 `LocalSet`，`main_loop`
> 没人 poll，工作线程的 `bind_async` 请求永远没有消费者。
>
> 但「主线程后台 `run_until(pending)`」**不可行**：`LocalScope` 是 `!Send`（`Rc<LocalSet>`
> 绑定创建它的线程），挪不到后台线程。可行的最小改法是**把整段场景移进
> `block_on(scope.run_until(..))`**，并把阻塞的 `thread::join()` 换成
> `futures::channel::oneshot` 异步回传——`block_on` 在等待场景 future 时会持续 poll
> 本地队列，`main_loop` 因此被驱动。三例修复后合计 0.11 s 通过，无需 `#[ignore]`，
> 也不需要 compio 替代验证。
>
> 工作线程的 `block_on` 保留：它正是「句柄跨线程 + 各自运行时」的被测对象本身。
>
> **修好壳之后暴露的第二个根因**：跨线程并发访问 `Tcs_` 让
> `sw-scope::WeakSlot::try_sharing` 的竞态显形——CAS 失败后读 `data_state()` 不是
> 原子的，另一线程刚把最后一个 `Sharing` 放回 `Created` 时升级被误报为
> `Err(Created)`；`Tcs_::is_abandoned_` 据此把 `bind` 答成 `Cancelled`
> （实测约 1/3 概率 `[Bound, Other(Cancelled)]`）。已在 **sw-scope `4d624c5`** 修复
> （`Created` 状态重试 + 回归用例），smux_v1 无公开 API / 协议改动。修好后
> `thread_safety` 连跑 20 次全过。

- **现象**：三个用例都超过 60 s 无结果（`timeout 200` 内没有任何 `ok`/`FAILED`）；
  单跑 `mux_auto_dock_allocation_is_atomic_tokio_`（`--test-threads=1`）在
  `timeout 300` 内同样没有结果、到点被杀——**已排除「三例并发互相干扰」**，
  每个用例本身就会停住。
- **结构**：主线程建连：
  `tokio_rt.block_on(async { let scope = art_rt.local_scope(); scope.run_until(connect_pair_(..)).await; (a, b, scope) })`
  → 主线程的 `block_on` 返回后**不再驱动** `scope`；
  工作线程各自 `new_tokio_rt_()` + `block_on(bind_async(..))`。
- **根因假设（未验证）**：`bind_async` 走 `MainRequest_` → 请求队列 → `main_loop`；
  而 `main_loop` 是主线程 `LocalSet` 里的本地任务。主线程建连后不再 `run_until`，
  请求没有任何消费者 → 工作线程永久等待。也就是说这些用例**当前欠一个「持续驱动
  本地队列」的宿主**，不是产品逻辑挂死。
- **下一步（按代价从低到高）**：
  1. 在主线程留一个后台驱动：`std::thread::spawn(|| tokio_rt.block_on(async { scope.run_until(core::future::pending::<()>()).await }))`，
     工作线程完成后再用取消/`shutdown` 收回；先只改一个用例验证假设；
  2. 若 `run_until(pending)` 不能与「另一个线程的 `block_on` 同时使用同一个 `LocalSet`」
     共存，则这组用例在现架构下**不可测**——改为 `#[ignore]` + 文件头写明原因，并把
     「绑定独占性」的验证移到 compio 单线程（两个 `Task` 在同一 scope 内竞争）。
  3. **验收**：三例要么通过，要么显式 `#[ignore]` 且在 `thread_safety.rs` 与
     `sw-scope-20261028-2130.md` §7 写明「为什么不可测、替代验证在哪」。
- **注意**：`tokio` 的 `LocalSet` + `Handle` 模型决定了「连接的循环必须在建连线程上被
  持续 poll」；这与「句柄可跨线程」并不矛盾（跨线程的只是句柄），但**测试壳必须提供
  那个持续 poll 的宿主**。

## 5. P2：已知偏离、死代码与待拍板

### 5.1 `main_loop` 不是「完全同步」（设计稿 §6.3 的偏离）

`main_step_` / `handle_request_` / `tick_` 里仍有：

- `release_done_channels_` / `reap_retired_` / `reserve_channel_` / `take_pending_inbound_`
  等注册表异步取锁；

### 5.5 `block_on` 审计（R18）

需求：业务实现代码与测试代码里的 `block_on` 都应考虑改 `await` / 异步函数；smux_v1
不应存在**必须以同步代码写成**的阻塞点。R18 逐处核对后的结论：

| 位置 | 性质 | 处置 |
| --- | --- | --- |
| `smux_v1/src`（生产路径） | **零** `block_on` / `thread::park` / `sleep` / 同步通道 `recv` | 无需改 |
| 库内单测（`tcs_` / `control_state_` / `scope_` / `parser_` / `time`） | `futures::executor::block_on` 驱动一个 async 辅助函数 | 保留：它们测的是 async 辅助本身，单测没有运行时上下文；换成 async 测试只会把同一个阻塞挪进测试框架 |
| `main_loop::tests_` 的 `block_on_ready_` | 手写单次 poll（Pending 即失败） | 保留：它是**非阻塞**的断言辅助，不是阻塞点 |
| `multi_art_test_!` 宏展开 | 生成 `#[test]` 内的后端 `block_on`（smol 无隐式上下文） | 保留：测试用例的**外部驱动源** |
| `smoke_smol` / `cross_thread_smol` | `smol::block_on` 作为外部驱动源 | 保留：smol 没有隐式运行时上下文 |
| `thread_safety` 主线程 | `block_on(scope.run_until(场景))` 作**宿主** | 保留：这正是「谁驱动本地队列」的被测前提 |
| `thread_safety` 工作线程 | 各自 `block_on(bind_async)` | 保留：**被测对象本身**（句柄跨线程 + 各自运行时） |
| `thread_safety` 的 `thread::join()` | 阻塞汇合，停摆主线程的 `LocalSet` | **已删除**（R18 改 oneshot 异步回传） |

结论：生产路径不存在阻塞点；被删掉的唯一「同步压异步」是 `thread_safety` 的阻塞
`join()`。其余 `block_on` 要么是测试的外部驱动源，要么正是被测对象，改成 `await`
会失去测试意义。
