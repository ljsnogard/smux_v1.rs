# 子流级可等待收尾：`TrBuffFlush` 与 `TrChannelRx::close_async`

日期：2026-10-17（承接 `flush-contract-20261015-2340.md`）

## 1. 起因

`abs_smux` 的最新提交（`70ea9e3` "Add `TrBuffFlush` for channelTx"）改了子流契约：

```rust
pub trait TrChannelTx<C> where C: TrMuxConfig,
    Self: TrBuffFlush<C::Data> + TrProducerState + TrChannelHalf<C> {}

pub trait TrChannelRx<C> where C: TrMuxConfig,
    Self: TrBuffRead<C::Data> + TrConsumerState + TrChannelHalf<C>,
{
    type CloseAsync<'f>: TrMayCancel<'f, MayCancelOutput = Result<(), Self::Err>>;
    fn close_async(&mut self) -> Self::CloseAsync<'_>;
}
```

即：发送半边从「只有 try 写」抬到**带冲 / 封口**（`TrBuffFlush`），接收半边多出一个
**异步关闭**入口。`smux_v1` 那一轮只改了一半（`impl<C> TrChannelRx` 漏了泛型参数、
`TrBuffFlush` 漏关联类型、`close_async` 里是 `todo!()`、`ring_.close()` 的 `()` 与
`Result` 不匹配），编译不过。

本轮把它补完，并**给这些入口实现真正的语义**。

## 2. 裁决（人类）

问了两点，答复都是推荐项：

1. **语义强度**：等**真正上线**。`flush_async` 等发送环排空；`close_async`（发送）等
   `CLOSE(FIN)` 已写进传输；`close_async`（接收）等 `CLOSE(RESET)` 已写进传输。否决了
   「同步动作 + 立即就绪」的轻量做法——那样调用方无法用 `await` 确认收尾已经生效。
2. **`Drop` 与显式 `close` 的关系**：**复用**同一套收尾实现，保证两者语义不可能漂移。

## 3. 机制

### 3.1 完成判据落在共享状态字上

| 等待 | 判据 | 已有的位 / 新增 |
| --- | --- | --- |
| `flush_async` | 发送环 `data_size() == 0` | 直接读环（`RingState`） |
| `close_async`（Tx） | 本端 `FIN` 已上线 | 复用既有 `LOCAL_FIN_SENT`（它只在排空后置位） |
| `close_async`（Rx） | 本端 `RESET` 已上线 | **新增** `LOCAL_RESET_FLUSHED` |

`LOCAL_RESET_SENT` 的语义**不改**：它表示「由谁去发这条帧」的认领（去重用），置位在
写出**之前**。新位把「认领」与「完成」分开，正是因为 `close_async` 的完成点需要后者。

### 3.2 零分配唤醒：每条子流两个内联通知槽

`ChannelState_` 新增两个 `NotifySlot_`（`tx_progress_` / `rx_progress_`），语义与建流
通知槽同构（持久位 + 单 waker 槽）：半部是**独占**的（既非 `Clone`，等待又取
`&mut self`），因此每条子流每个方向至多一个等待者，符合 `NotifySlot_` 的前提。

唤醒点（写循环与终局路径）：

| 位置 | 动作 |
| --- | --- |
| `drain_one_` 每写出一段数据 | `notify_tx_progress_`（排空是**渐进**的，没有别的时刻能覆盖「最后一段离开环」） |
| `finalize_entry_` 发出 `FIN` | `notify_tx_progress_` |
| `WriteEvent_::RxClosed` 分支：发完 `RESET` | `set_local_reset_flushed_` + `notify_rx_progress_` |
| 读循环处理 `CLOSE(RESET)` | `notify_tx_progress_` |
| 读循环处理 `CLOSE(FIN)` | `notify_rx_progress_` |
| `WriteEvent_::LocalAbort`（空闲超时拆流） | `notify_both_progress_` |
| `timer_` 的 `Abort`（认领中止后） | `notify_both_progress_` |
| `maybe_release_`（身份释放） | `notify_both_progress_` |
| `mark_failed_`（连接级失败，逐条遍历 bindings） | `notify_both_progress_`（顺序：**先**发布 `ConnFailed` 通知，**再**唤醒） |

等待者在醒来后**复检**，因此不需要「精确事件」——只需保证任何改变终局的事实都喊一次。

### 3.3 终局必须让等待返回，而不是永久挂起

两个方向的等待判据都把「不可能再前进」当作**终局**：

- 发送：对端 `RESET`（授权放弃已提交字节）、`abort_reason()` 非空（空闲超时 / 连接级
  失败 / 连接关闭）、发送环消费端已关闭 → `Err(ProducerError::Closing)`；封口等待在这
  些情况下只要 `FIN` 已发或对端已 `RESET` 就报 `Ok`。
- 接收：`abort_reason()` 非空 → `Err(ConsumerError::Closing)`；对端 `FIN` 或接收环写端
  已关闭 → `Ok`（接收方向本来就到头了）。

### 3.4 幂等：封口只投递一次

`drop` 与 `close` 复用 `seal_tx_` / `seal_rx_`，而「排空 + 发 `FIN`」/「发 `RESET`」的
**事件投递**用 `set_app_tx_closed_` / `set_app_rx_closed_` 的**首次置位**去重（两方法
改为返回 `bool`）。少了这层去重，第二条 `TxClosed` 会在写循环的表项已经被摘掉之后被重新
登记进「欠一条 `FIN`」集合——见 §4。

## 4. 顺手修掉的既有缺口：僵尸收尾条目

`finalize_entry_` 的 `has_writable_` 用 `table.get_mut(&pair)?` 表达「表里没有」，
与「环给不出结论」共用同一个 `None`。于是**表项已被别的路径摘掉**（典型：应用先收到
对端 `RESET`，写循环 `table.remove` + `pending_fin.remove`，之后应用才 discard / 封口
发送半边）时，那条 `TxClosed` 会把 pair 重新插进 `pending_fin`，而它永远排不了空、也
永远发不出 `FIN`：**每轮扫描都要探测一次的僵尸条目**。

修法：`finalize_entry_` 第 0 步先判 `table.contains_key(&pair)`，没有就
`pending_fin.remove(&pair)` 并返回 `Ok(false)`。此后 `has_writable_` 的 `None` 只剩
「环给不出结论」一档（注释已同步）。

## 7. 遗留

- 契约里**没有**暴露的仍有两处：收尾接口的错误类型来自 `abs_buff`
  （`ProducerError` / `ConsumerError`），以及 `TrChannelHalf` 与
  `TrProducerState` / `TrConsumerState` 对关闭态的两套投影。前者让业务层若要点名错误
  类型仍会依赖 `abs_buff`；后者只是同义表达，未感到不便。
- `flush_async` 的完成点是「环排空」，**不**等于「字节已到达对端设备」：后者不在
  `abs_smux` 契约里（传输写半边自己的 `flush_async` 才管那一层）。
- 本轮的等待 future 由 `gen_may_cancel_future` 生成；内部的 `wait_tx_progress_` /
  `wait_rx_progress_` 用 `poll_fn` + `race_cancel_` 手写复检循环。若将来要复用到
  telegraph 的收尾上，值得把这两个 helper 提到共用位置。
