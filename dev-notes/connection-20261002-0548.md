### 5.1 Q4 裁决的已知残留风险与必须遵守的实现契约

Q4 选的是「提交前通知 + park 兜底」，**不是**健全方案。必须把风险与契约写在代码旁：

- **残留漏洞**（真实可构造）：两条子流 A、B 各持有一个已借出但未提交的写段；两者
  都发了事件；写循环醒了、扫了一遍（都还没提交），于是 park 到**最后通知的**
  B 环上。之后 A 提交（A 的事件已被消费掉、A 的环没有被 park），B 一直不提交 ⇒
  **A 的数据永久发不出去**。
- **为什么在目标场景下大概率不触发**：单线程执行器下，应用从拿到段到 drop 提交
  之间**不经过 await 点**就不会把控制权交回调度器；冒烟测试的
  `write_channel_all_` / `try_write_all_` 正是这种形态。
- **实现必须遵守的契约**（把概率压到最低，且出问题时可见）：
  1. 「刚通知」按**最近一次收到事件的那条环**解释，且写循环在**每次醒来后先全扫
     一遍本地表**，再决定 park 到哪条环；
  2. 写循环**只在表内确实有环可 park** 时才 park；表为空时 park 在事件通道上；
  3. 每条子流的「已入队」位由**应用侧写路径置位、写循环在开始排空前清零**（顺序
     与 §11.4 一致：先清位、再读数据），因此重复事件无害；
  4. 该漏洞作为**已知限制**写进 `session_.rs` 与模块文档；若后续出现「channel
     卡住」类问题，**第一嫌疑就是它**，届时再升级为「包裹段提交后通知」（Q4 的
     建议方案），改动点集中在 `channel_.rs` 的段类型。

### 5.2 Q7 裁决带来的连带设计（与 §2 表中 2.7 行的初判不同）

> 本节描述的是**事件通道移交半部**的形态；§17 已确定把「移交载体」改为「句柄直接
> 持有连接智能指针」，届时本节的通道部分失效，但「循环本地持有半部、可自由 park」
> 这条结论不变。

因为会话侧半部交循环本地持有，所以：

- **环不再经过 `SyncCell_`**：循环可以直接在环上 `read_async` / `write_async`
  （park 是被允许的），也**不需要**每帧一次 copy；
- 两个循环各自维护一张**按 dock 对索引的本地表**，节点用调用方注入的分配器分配
  （沿用 `ChannelRegistry_` 的侵入式单链表写法），表项 = `Shared<ChannelOwner_>`
  + 会话侧环半部；
- 移交通道必须承载**带类型的环半部** ⇒ 事件通道类型变成连接的内部泛型类型；
  读循环与写循环各一条通道（写循环通道带 `AttachTx` / 控制帧 / `TxReady` /
  `RxConsumed` / `Release`；读循环通道带 `AttachRx`）；
- `ChannelOwner_` 因此**只承载标量共享状态**（`FlowCtrl`、活跃时间、各类标志），
  环半部不在里面 —— 这也顺带消掉了 §11.3 里「半部藏在共享实体的锁后面」那条硬
  约束的冲突。
- **策略 `P` 的访问**：`RecvWindow::should_report<P>` 需要 `&P`，而 `C` 的
  `policy()` 只返回引用。做法是在共享上下文里存 `C` 本身，用
  `SyncCell_::with_(|c| …)` 的**短闭包**（不 await）在构造 `FlowCtrl` 与判定
  `should_report` 时就地取用；多线程配置下给 spawn 的那个 `impl` 补
  `C: Send + Sync` 的**实现级 bound**（不改公开 trait）。

## 6. 立项时已核对的硬事实（备查）

> 本节是**开工时**核对的上游/本地事实，是后面各轮决策的依据。少数条目描述的是当时
> 的本地状态，已在该条内注明后续变化。

1. **环的 park 是单槽单位**：`buffex/src/ring/half_.rs` 的 `RingHalf_` 单槽 +
   `RingState` 的 `CONSUMER_STNDBY` / `PRODUCER_STNDBY`；`advance_write` /
   `advance_read` / `close_*` 只在兴趣位有效且登记被认领时 `wake()`。⇒ 一个写循环
   无法同时 park N 条环（§2.2）。
2. **段的提交点在段 drop**：`try_write` 只借出区间、不推进 wp；`advance_write`
   在段回收时执行。⇒ 「进入时通知」是提交前通知（§2.2）。
3. **`abs_art` 的 spawn 要 `'static`**，且 `TrJoinHandle` 无 `abort`、只有 `detach`
   ⇒ 循环必须自持状态、spawn 后 detach、靠取消令牌退出（§2.3 / §2.7）。
4. **`atomic_sync` 只有 preemptive（同步自旋）mutex**，没有 async mutex；
   cooperative rwlock 自带等待队列但需要 `alloc`。⇒ 「跨 await 持锁」在本项目里
   没有现成原语，共享单元的短闭包里不能 await。（**后续**：手搓的 `SyncCell_` 已在
   §13 被 `atomic_sync` 的读写锁取代，但「闭包内不得 await」这条契约不变。）
5. **`TrBuffSegmView` / `TrBuffSegmMut` 公开、`SegmMut::new` 是 public const**；
   `TrBuffWrite::WriteAsync<'f>: TrMayCancel`；本项目已有
   `gen_may_cancel_future` 生成具名 future。⇒ 「包裹段 + 包裹 write_async」可行
   （§2.2）。
6. **`read_header_async_` 只解析帧头**，载荷由调用方按 `payload_len` 读；每帧都
   必须带非保留值的 dock 对；`max_packet_size` 默认 4096（`BasicOpts::DEFAULT`；
   `max_channel_count` / `max_dock_chan_count` 默认 `1<<28`；
   `max_channel_timeout` 默认 30s）。
7. **`ChannelRegistry_` 的当时状态**：dock 链 + 每 dock 的 `remote_dock` 单链表、
   `inbound_waker_`、配额计数、两个循环令牌、`FailKind_`；**没有** owner 挂载、
   没有按 dock 对查询、没有重复检测、没有入向待决队列、没有建流响应槽。
   （**后续**：这些缺口已由 §2 表 2.5 行与 §14 / §15 两轮升级补齐；该结构现在是
   `mux_connection::registry_` 的三张 BTreeMap + 一本到期索引。）
8. **握手交付物**：`HandshakeDelivery { opts, tx, rx }`；`MuxConnection::new` 收
   `HandshakeDelivery<W, R>` 与 `C`，目前只把它俩存成字段（`Rx`/`Tx` 由连接独占）。
9. **基线验证**（**开工时**实测）：`cargo test --all-targets` = 58 passed + 2 ignored。
   （当前验证矩阵见 §16.4。）

### 7.2 顺带落地的基础设施

- `flow_ctrl::ReportThresholds_`（`pub(crate)`）：把策略里的「通告阈值 / 最小帧间隔」
  在连接建立时展开一次，读写循环因此不需要持有 `C` / `P`；`RecvWindow::should_report`
  改为委托给 `should_report_with_`。
- `MuxError::cast_`：把 `MuxError<(), ()>`（注册表等只有类别、没有载荷的路径）搬成
  目标错误类型。
- `ChannelRegistry_` 升级：节点挂 `Shared<ChannelOwner_>`、入向待决表
  （`Pending` → `HandedOut` + 对端窗口快照）、`Duplicate` 检测、`find_channel_`、
  `allocator_()`；`mark_failed_` 现在会唤醒**所有**等待中的 API future
  （dock 入向等待者 + 每条主动子流的建流等待者）。
- `ChannelOwner_` / `ChannelState_`（`owner_.rs`）：`FlowCtrl` + 建流状态 + 活跃时间 +
  拆流记账，全部经 `SyncCell_` 短闭包访问（**闭包内不 `await`**）。

### 7.3 实施阶段查出的三个真实缺陷（值得记下）

1. **通告的窗口快照没有记账** ⇒ 对端第一帧被误判为 `FlowCtrl::PeerViolation`。
   `RecvWindow` 的越权判定以「最近一次通告」为准；建流时只用策略算了个数写进
   `OPEN`，却没有调用 `report()` 把它记进去。修法：建 `FlowCtrl` 之后立刻
   `recv_window_mut().report()`（两处：主动方 `open_channel_async`、被动方
   `accept_async`）。
2. **只读不消费地看待环段** ⇒ 同一段数据被反复上线（对端读到重复载荷）。
   写循环最初用 `segm.as_segm_ref().iter_slices()` **只读**段再写网络，段的已消费量
   没有推进，drop 提交时环的读指针不动。修法：改成 `move_items_to_buff` 把字节
   **搬进循环自有的暂存**（`scratch: Vec<u8>`，每条连接分配一次），搬出即消费。
3. **在「排空数据」里用了会 park 的 `read_async`** ⇒ 多子流直接死锁。
   `drain_one_` 原本用 `read_async(Demand::no_more_than(..))`；`no_more_than` 的最小
   需求是 0，但 park 的判定按「至少 1」算，于是空环上它会 park——而这一步一旦
   park，事件通道里的事件就再也送不进来。修法：`drain_one_` 改用**非阻塞的
   `try_read`**；等待新数据只由写循环第 2 步（与事件通道竞争）负责。

### 7.4 Q4 兜底的实现 refinement（与原裁决的差异，需知悉）

原裁决是「park 到刚通知的那条环兜底」。实现时发现：**只 park 在环上会在多子流下
死锁**——写循环睡在 A 环上，B 子流入队的 `TxClosed` 排在事件队列里没人取，而 B 的
对端正等它的 `FIN`。因此第 2 步改成「**同时轮询环与该环的数据 + 事件通道**」：
事件先到就处理事件并回到循环顶部（顶部会先非阻塞排空事件），环先到就回到顶部正式
取走数据。这仍然满足「覆盖提交前通知的竞态」，同时消掉了死锁。

## 8. 后续复查：冒烟测试「无法完成」的真正原因（**已结案**）

## 9. 后续复查：`bind_async` 的 dock 绑定独占性（**已结案**）

> 人类指示：「`bind_async` 的实现完全没有尊重设计协议——一个 dock 被绑定之后，后续
> 再对同一个 dock 绑定应该在返回结果上报错而不是允许。调查它是否约等于百分百允许
> 绑定不检测，并写测试钉住这个原则。」

**调查结论**：修复前确实是「除保留值外 100% 允许」。当时只有两道检查——保留值
`is_special()`，以及 `reserve_dock_(dock, DockUse_::Channel)`；后者只是**用途种类**
标记，同种类重复登记幂等放行，且 `use_` 会被 `release_channel_` 在子流清零时抹掉，
连持久状态都不是 ⇒ 同一个 dock 反复 `bind_async` 永远成功。

**修法**：绑定独占性必须是**独立且持久**的状态，因此给 dock 条目加 `bound_` 并计入
判空（绑定期间不可被 prune），新增 `bind_dock_` / `unbind_dock_`，由 `DockBinding` 的
`Drop` 解绑。语义是「**绑定期间独占、drop 即解绑**」——已由该 binding 建出的
`ChannelTx` / `ChannelRx` 不借用 binding，解绑不会动它们。

> **§15 的连带修订**：`DockUse_` 与 `reserve_dock_` / `release_dock_` 后来在统一身份
> 表里**被整体删除**（用途种类改由 `DockBinding_` 的变体表达），`bound_` 保留在
> `DockCtx_` 里。因此本节不再描述 `reserve_dock_`。

**钉住原则的测试**（反向验证过：短路 `bound_` 检查后三条全部失败，说明它们不是恒真）：

| 层 | 用例 | 断言 |
| --- | --- | --- |
| 注册表单测 | `registry_::tests_::dock_binding_is_exclusive_and_persistent` | 同 dock 二次绑定 `DockInUse`；不同 dock 互不影响；**子流清零后绑定仍有效**；解绑后可重绑 |
| 集成（tokio） | `inmem_mux::mux_bind_is_exclusive_tokio_` | 经公开 `TrConnection::bind_async`：二次绑定 `DockInUse`；解绑后重绑成功；对端同名 dock 不受影响 |
| 集成（compio） | `inmem_mux::mux_bind_is_exclusive_compio_` | 同上 |

**连带影响**：`DockBinding` 新增 `Drop`；`MuxError::DockInUse` 的文案从「已被 channel
或 telegraph 占用」改为「已被绑定或已作其他用途占用」；模块文档 §4.1 增补「绑定层
独占」一段。

## 13. 用 `atomic_sync` 的读写锁替换手搓 `SyncCell_`（2026-10-02）

> 人类指示：既然已直接依赖 `atomic_sync`（含 cooperative rwlock），就应该用它的
> 读写锁管理 dock 绑定等并发状态，不再手搓 `SyncCell_`。裁决：**注册表用
> cooperative，其余用 preemptive**。

### 13.1 选型与理由

| 位置 | 锁 | 为什么 |
| --- | --- | --- |
| `mux_connection::registry_` 的 `ChannelRegistry_` | `rwlock::cooperative::CooperativeRwLockOwned` | 每连接 1 把；保留 `read_async` / `write_async`，便于后续把需要跨 `await` 持锁的路径迁进来 |
| `owner_` 的 `ChannelOwner_`（每条子流） | `rwlock::preemptive::SpinningRwLockOwned` | **零内部堆分配**、可内联进 `Shared`；cooperative 内部是 `Arc<RwCore>`，每子流一把会引入一次隐蔽的全局分配，违反「堆分配一律经 `allocator_api`」的纪律（准确表述见 §14.1） |
| `sync_` 的 `CancelToken_` | `rwlock::preemptive::SpinningRwLockOwned` | 需要 `Send + Sync`，且同样不该引入隐蔽分配 |

`SyncCell_` / `SyncAtomicCell_` / `CellImpl_` / `with_spin_lock_` 已全部删除。

### 13.2 访问方式与重入契约

三处都提供「短闭包」辅助（`with_` / `with_mut_`），内部只取**同步快路径**
`try_read` / `try_write`：

- 临界区**不得 `await`、不得重入**（与旧 `SyncCell_` 的契约一致）；
- 取不到锁时由 `sync_::on_lock_contended_()` 统一处理：**单线程配置直接 panic**
  （那里没有别的执行者，取不到锁必然是重入 bug——与旧 `RefCell` 的 fail-fast
  行为一致），**多线程配置自旋等待**（可能是另一线程短暂持锁）。

这样既保住了旧单元「单线程下嵌套访问立刻炸」的可观测性，又能在多线程下正确串行。

### 13.3 顺带清理

- 删掉真正无用的 `ChannelState_::peer_report_` 字段（只写不读；被动方的窗口通告
  实际由 `FlowCtrl::send_window_mut().on_report(...)` 就地应用），`ChannelState_::new_`
  随之从两参降为一参。
- 删掉测试专用的 `CancelToken_::is_cancelled_`，测试改用
  `TrCancellationToken::is_cancelled`。
- `sync_` / `owner_` / `signal_` / `frame_` 的**无差别 `#![allow(dead_code)]`
  已撤掉**：缺省配置下全 crate 零 `allow` 也零告警。剩余 allow 都收窄到明确范围：
  - `registry_` / `session_` / `signal_`：`#![cfg_attr(feature = "multi-thread",
    allow(dead_code))]`（多线程驱动仍是 `todo!()`）；
  - `registry_` 内 6 项「仅测试 / 待 telegraph」的成员逐个标注；
  - `frame_::K_VAL_TYPE_MASK` 单独标注（协议常量，当前解码不用掩码）；
  - `telegraph/endpoint_.rs` 保留（整条 telegraph 支线未实现）；
  - `ring_.rs` 保留原有单行标注。

## 14. 索引结构改为 `BTreeMap` + 分配纪律澄清（2026-10-02）

> 人类指示（本轮）：
> 1. 「注册和管理多个子流，应当用 `BTreeMap` 来存储和查找对应的管理结构……按我的
>    预计，应该是要用两个或者三个 `BTreeMap`，一个用来保存 `dock_binding`，一个
>    用来建立 `remote_dock` 和 `local_dock` 的索引关系。」
> 2. 「我看到你在某些会话的思维链中强调，smux_v1 不分配堆上内存。这应该是一个
>    误解。正确的理解是，不能随意地依靠 `vec` 等等的堆上数据结构来解决问题。」
> 3. 「参考 `buffex_compio_adapt` / `buffex_tokio_adapt` 的做法，为整个
>    `mux_connection` 所有必须用到堆分配的场合和数据类型，抽取出来成为一个
>    `TrMaxAllocConfig`，并且一律使用 `allocator_api` 完成堆上内存分配。」

### 14.1 澄清：分配纪律的准确表述（修订 §13.1 的措辞）

§13.1 表格里写的「违反『`make_buff` 是唯一分配入口』」是被**误读**出来的纪律。
准确表述是：

- 本 crate **会**做堆分配，**不是**「不分配堆上内存」；
- 每一处堆分配都必须走**调用方注入的分配器**（`allocator_api`），不得隐式落到
  全局分配器；
- 不得为了省事随手用 `Vec` / `String` 之类的全局堆结构绕开设计；
- 因此 §13.1 里「选 `preemptive` 是因为零内部堆分配」的理由依然成立，但**理由
  改写**为「它不引入不受 `allocator_api` 控制的隐蔽分配」，而不是「本 crate 不该分配」。

`crate::connection` 模块文档 §5 已按此重写。

### 14.2 三张索引表（`mux_connection::registry_`）

旧实现：`docks_` 单链表 + 每个 `DockNode_` 再挂 `head_` 子流单链表，
`find_*` / `prune_*` / `remove_*` 全是 O(n) 线性扫描，节点用 `Owned::new(_, alloc)`
手工构造 / 释放。新实现：

| 结构 | 键 | 值 | 服务的查询 |
| --- | --- | --- | --- |
| `docks_` | `Dock`（local） | `DockCtx_`：`use_` / `bound_` / `chan_count_` / `inbound_waker_` | `bind_dock_` / `unbind_dock_` / `reserve_dock_` / 入向唤醒 |
| `channels_` | `(Dock /*local*/, Dock /*remote*/)` | `ChanCtx_`：`owner_` / `inbound_` | 按 dock 对 O(log n) 定位；**唯一事实源** |
| `remote_index_` | `(Dock /*remote*/, Dock /*local*/)` | —（`BTreeSet`） | 按 remote 反查 local |

三个关键判断：

1. **主键只能是 dock 对。** `remote_dock` 单独不能作主键：发起方会把发往同一个
   对端监听 dock 的多条并发子流用不同 `local_dock` 区分（模块文档 §4.1），同一个
   `remote_dock` 会对应多条在册子流。`local_dock` 单独也不行：响应方的监听 dock
   被多条子流共用。只有 `(local, remote)` 有序对恒唯一。
2. **不需要第 4 张「按 local 枚举」表。** `channels_` 的键是有序对，
   `(local, unspecified)..=(local, wildcard)` 恰好覆盖本 dock 的全部子流；`0` /
   `u32::MAX` 是协议保留值、永不作为子流 `remote_dock`，可以安全当区间哨兵。
3. **`remote_index_` 当前没有协议路径依赖它**（每帧都同时带两个 dock），人类仍
   选择保留（「两个或者三个」选了三个）。实现上以 `(remote, local)` 为键序提供
   O(log n + k) 的 `for_each_local_of_remote_`（用回调而不是返回集合：既不引入堆
   分配，也不让索引守卫逃出锁外）；增删与主表严格同步，由单测
   `assert_index_consistent_` 钉住。

### 14.3 循环本地表也改成 `BTreeMap`（`session_`）

`ReadEntry_` / `WriteEntry_` 去掉了 `local_dock_` / `remote_dock_` / `next_` 三个
字段（dock 对已是表的键），四个手写链表辅助函数删除。附带收益：

- `drain_once_` 原本先把全部 dock 对收集进 `Vec` 再轮转（每次轮转一次堆分配，正是
  人类指出的「随意依靠 `Vec`」）——改为「上一个键之后的第一个键」推进
  （`range((Excluded(last), Unbounded))`，O(log n)/步），**零分配**，也不在
  `await` 期间持有对表的借用；
- 重复 `Attach` 现在是覆盖（旧链表会留下陈旧条目）。

### 14.4 `allocator_api` 的落地与 feature 门

三张表都用 `BTreeMap::new_in(alloc.clone())` / `BTreeSet::new_in(...)`，分配器即
调用方注入的 `C::Alloc`。本轮**不引入** `TrMaxAllocConfig`（人类裁决：先做
`BTreeMap`，新 trait 下一轮整体引入，避免公开 API 改两遍）。

`BTreeMap` 的分配器参数在当前 nightly（1.100.0, 2026-09-04）上还有独立 feature 门
`btreemap_alloc`（与 `allocator_api` 不同门），已在 `lib.rs` 一并打开并注明原因。

## 15. 统一身份表 + 拆流宽限期（`WaitClose`）（2026-10-02）

> 人类指示（本轮）：
> 1. 「以 `(local, remote)` 对作为键的那个 `BTreeMap`，其值类型应该是一个
>    `dock_binding`。持有 `dock_binding` 的，要么是一个 channel，要么是一个
>    telegraph，还有一种是 listener。这个表应该体现出这个设计，这样就可以把
>    `mux_connection` 的几种子流归一化管理。」
> 2. 「TCP 流关闭后端口在一段时间内不可被分配，以等待网络报文过期。我们的流控
>    设计里也有 `max_channel_timeout`。是否要设一个 WAIT_CLOSE 表暂存这些已关闭
>    但仍不能直接拿出来用的 `local_dock`？抑或这就是 `docks_` 的作用？」

### 15.1 先纠正一个前提：三种子流的身份元数不同

查 `abs_smux::conn`（`ba91f49`）：

| 种类 | 身份 | 证据 |
| --- | --- | --- |
| channel | `(local, remote)` 两个具体值 | `open_channel_async(remote_dock, …)` |
| telegraph | **只有 local**；`remote` 是逐次操作的实参 | `send_async(remote_dock, …)` / `recv_async(remote_dock, …)` |
| listener | **只有 local**；`remote` 天然 wildcard | `listen_async()` / `income_async()` |

所以 `(local, remote)` 这个键天然只能表达 channel。要让三者共用一张表，必须给
后两者的键补一个**哨兵 remote**。协议恰好给了现成的哨兵：`unspecified()=0` 与
`wildcard()=MAX` 是**双方保留值、永不作为真实子流的 `remote_dock`**（§4）。

人类裁决：**采用哨兵 remote**（备选的 `enum DockKey_` 会丢掉 `(local, *)` 的
区间枚举能力）。落地为：

| 身份 | 键 | `DockBinding_` 变体 |
| --- | --- | --- |
| channel | `(local, 具体值)` | `Channel(ChanCtx_)` |
| telegraph | `(local, unspecified)` | `Telegraph(TgCtx_)` |
| listener | `(local, wildcard)` | `Listener(LsnCtx_)` |
| 已关闭、宽限期内 | `(local, 具体值)` | `WaitClose(WaitCloseCtx_)` |

键序天然是「telegraph(0) < channel < listener(MAX)」，带来三个直接收益：

1. 「按 `local_dock` 枚举**具体子流**」= 一次开区间 `range`（`channel_range_`），
   两个哨兵行自然排除；
2. 「channel 与 telegraph 不得共用 local_dock」= 查一次 `(local, unspecified)`，
   原来的 `DockUse_` 用途枚举**整个删除**；
3. listener 与 channel 是不同键，**可以共存**于同一 `local_dock`（这正是监听 +
   接流的常态）。

`docks_` 保留，但收窄成纯 dock 级簿记：`bound_`（绑定独占）+ `chan_count_`
（活跃 channel 计数）。身份种类不再由它表达。

### 15.2 `docks_` 不是 WAIT_CLOSE，但 WAIT_CLOSE 确实必要

**先答「是不是」**：不是。`docks_` 装的是**活跃** dock 级簿记，判空即剪，没有
定时器，键只有 local。

**再答 TCP 那个理由**：不成立。本协议跑在**可靠、有序**的字节流上，同一连接内
没有重排 / 重传，`CLOSE(L,R)` 一定排在新 `OPEN(L,R)` 之前（所有出向帧走同一个
FIFO 写事件队列），对端也按序处理，因此身份复用不会把旧报文投给新化身。

**但排查时发现一处真实缺陷**，它才是 WAIT_CLOSE 的真实动机：

1. app drop `TxRing_` → `WriteEvent_::TxClosed`（`halves_.rs`）；
2. app drop `RxRing_` → `WriteEvent_::RxClosed`；
3. 写循环 `maybe_release_` 判定 `is_done_`（`owner_.rs`：app 两个半边都丢弃即
   算收尾）→ `release_channel_` + 发 `ReadEvent_::Release`；
4. 读循环排空该事件 → 读本地表条目被移除；
5. 对端仍在发数据（它那侧 app 还没关，尚未处理我们的 `CLOSE`）→ 读循环查不到
   pair → 走 `MalformedFrame` → `mark_failed_` → **整条连接被杀**。

两个方向是**各自有序的独立字节流**，所以「按序」救不了它；窗口约 1 个 RTT。

人类裁决：**落地为统一表第 4 变体、pair 级**，宽限期用**新增的独立协商参数**
（不复用 `max_channel_timeout`——后者是活跃子流的空闲超时，语义正交）。

### 15.3 落地内容

**握手层（公开 API 变更，人类已批准）**

- `BasicOpts` 新增 `max_channel_wait_close: Duration`，缺省 5 秒（理由：宽限期
  只需覆盖「对端处理我们 `CLOSE` 的时间」≈ 1 RTT + 调度余量，越小则 tombstone
  越少；可协商）；
- 新增第 5 个基础协商键 `NegotiationKey::MaxChannelWaitClose = 0x04`，
  `K_BASIC_KEY_COUNT` 4 → 5；`ACCEPT` / `CONFIRM` 因此必须补全 **5** 项；
  保留段由 `0x04..=0x0B` 收窄为 `0x05..=0x0B`；
- 文档同步：`handshake/mod.rs` §2/§6.1/§6.3/§7.1–§7.4、`opts.rs` 模块文档与
  `codec_.rs` 槽位数说明。

**连接层**

- `registry_`：`channels_` → `bindings_`（四变体统一表）；`DockUse_` 删除；
  `release_channel_` 不再删键，而是改写为 `WaitClose` 并登记到期索引
  `wait_close_expiry_`（`(Instant, local, remote)` 有序集合）；

  （`MalformedFrame`）」；
- listener 身份：`listen_async` 登记 `(local, wildcard)`（幂等），
  `ChannelListener::drop` 释放；入向等待者从 `DockCtx_` 移进 `LsnCtx_`；

  `release_channel_` / `is_wait_close_` 三处顺带调用（tombstone 只可能由
  release 产生，因此这些点足以自我限制规模）。

**文档**：`crate::connection` 新增 §4.3（统一身份表 + 宽限期），§9 模块表更新。

### 15.4 顺带查出的第二个脆弱点：握手的「立即拒绝」路径

## 16. 分层 RPC 探针：API 形状实测（2026-10-02）

> 人类指示：「编写一个冒烟测试，模拟客户端和服务端两端，分别建立连接 / 等待连接、
> 握手成功、开辟若干 channel 进行通信。这几个过程不能全写在一个方法里，而应该像
> 实际服务器或客户端 SDK 那样，在不同的 OSI 层次、不同的阶段调用不同的函数……
> 我预计现有的 `DockBinding` 和 `MuxConnection` 的生命周期限制，会妨碍使用者将
> 不同层次需要操作的对象分发到不同的函数中使用。……在 doc comment 中强调，这是一个
> 有可能随 API 演进而变化的测试，而不是对设计的确认与行为验证。」

产物：`tests/layered_rpc.rs`（L4 传输 / L5 复用 / L6 会话 / L7 业务四层，客户端与
服务端各一条「一次绑定、循环 accept / 并发调用」的路径；tokio + compio 各一条用例）。
文件头已按指示写明它是 **API 形状探针**，不是设计确认、不是行为验证，会随 API 演进。

> **后续**：本节各项的结论已在 §17 重新审视——人类裁定把 `MuxConnection` 重构为
> 对 `MuxCore` 的智能指针薄封装、句柄改为持有该指针，F2 / F3 / F5 随之消失。本节
> 保留为「旧 API 下实测到了什么」的记录。

### 16.1 人类预判成立的部分（**F2 / F3 已由 §17 的目标设计解决**）

| 编号 | 结论 | 影响 |
| --- | --- | --- |
| F1 ✅ | `MuxConnection` 无生命周期参数，可作为返回值跨层传递 | 这一层没有摩擦 |
| F2 ⛔ | `DockBinding<'f>` 借用连接 → 无法与 `MuxConnection` 同处一个结构体（自引用），调用方必须一路显式传 `&MuxConnection` | 「RPC 会话对象」这种自然封装写不出来 |
| F3 ⛔ | `ChannelListener<'s,'f>` 可变借用 `DockBinding` → 不能从持有 binding 的函数返回，也不能与 binding 同处一个结构体 | 服务端 `bind → listen → income → accept` 四步**必须同处一个函数**，「建 listener」与「accept 循环」拆不开 |
| F4 ⚠️ | `income_async(&mut self)` 的**输出**是 `ChannelHandle<'s,'f,…>`，不含 `&mut self` 的借用 | 类型系统**不**阻止同时持有多个未决句柄；「同一 dock 串行化」只是协议约定（已用 `probe_two_pending_handles_` 钉在编译期） |

结论：**唯一能跨函数自由传递的对象是两个 owned 的 channel 半部**。分层的可行形状
因此被限定为「每个角色一个函数走完自己的借用链，靠 owned 半部把业务层接出去」。

### 16.2 人类没预判到、但实测撞上的三点

| 编号 | 结论 |
| --- | --- |
| F5 ⛔ | 已建立 channel 的**具体类型无法命名**：`TxRing_` / `RxRing_` 未对外导出（`connection::channel_half` 私有），`ChannelTx<TxRing_<…>>` 写不出来。下游只能 `impl Trait` 出层，或走关联类型投影 `<DockBinding<'f,…> as TrDockBinding>::Tx`（本文件两种都验证过）。「把 channel 存进 session 表」因此很别扭 |
| F6 ⛔ | `TrChannelTx` 的 supertrait 只有 `TrBuffTryWrite` + `TrChannelHalf`，**不含**异步的 `TrBuffWrite`。按 trait 编程拿不到 `.await` 读写，必须自己补 `+ TrBuffWrite<u8>`，也就等于业务层仍要直接依赖 `abs_buff` |
| F7 ⚠️ | 建流帧的「开场消息 / 欢迎信息 / 拒绝理由」当前**无处可取**（读循环只存窗口通告）。RPC 框架无法把第一个请求搭在 `OPEN` 上，必须多走一次数据往返 |

### 16.3 F8：探针撞出的**真实缺陷**——关闭顺序会吃掉尚未发出的数据

本文件第一版按函数参数逆序自然析构（`rx` 先于 `tx`），结果服务端刚写好的响应被
自己吃掉，客户端只读到 `Closing`。根因在 `session_` 的 `RxClosed` 分支（丢弃
`ChannelRx` 触发），它依次做三件事：

1. `table.remove(&pair)` —— 写循环丢掉发送环读端，**环里尚未发出的数据一起丢弃**；
2. 向读循环发 `ReadEvent_::Release` —— 摘掉读表项；
3. 回 `CLOSE(RESET)`。

两个后果都与模块文档 §7「每个方向的结束是独立的」相抵触：

- **丢弃接收半边会连带毁掉发送方向**：`ChannelTx` 仍然活着、`is_tx_closed()` 仍报
  `false`，但写循环已经不再为它服务，应用之后写进去的数据**永远发不出去**（静默）；
- **第 2 步会把在途帧变成「未知子流」**：对端在收到我们 `RESET` 之前发出的帧到达时，
  该 dock 对在注册表里仍是活跃 `Channel`（不是 `WaitClose` 宽限态），于是
  `is_wait_close_` 为假 → `MalformedFrame` → **整条连接被杀**。这与 §15 修掉的那处
  竞态同源，只是入口不同（§15 修的是 `release_channel_` 路径，这里是
  `RxClosed` → `ReadEvent_::Release` 路径）。

**规避方式**（本文件采用并写入 `close_gracefully_` 文档）：收尾顺序必须是
「先丢发送半边（`TxClosed` 分支是**先 flush 再 FIN**）→ 等对端 `FIN` → 最后丢接收
半边」。写反了**不会有任何编译错误**，症状是「响应偶尔丢失 / 连接偶发断开」。

**建议的修复方向**（本轮未实施，留待裁决）：`RxClosed` 至少应做到 (a) 先 flush
发送方向的残留数据再拆发送侧，或 (b) 不要立即 `table.remove(&pair)`，而是把该

## 17. 正式设计：`MuxCore` 演员 + `MuxConnection` 智能指针（2026-10-02）

> 人类裁决（本轮）：
> 1. 「第一要务是要将 API 重构为支持像这种 RPC 框架会对 smux 的用法。」
> 2. 「**正式确定**：将 `MuxConnection` 现有的数据成员移入一个叫 `MuxCore` 的类型里，
>    然后将 `MuxConnection` 重构为对 **一个 `MuxCore` 的智能指针**的薄封装。」
> 3. 「`MuxCore` 将在一个线程（或者 thread local runtime）里运行若干个 local spawn，
>    分别用来处理 IO 和所有 channel / listener / telegraph 等对 `MuxCore` 的需求，
>    例如提醒 mux core 某 Channel 中的数据水位有变化、listener accept 或者 reject 了
>    某个连接请求之类的。大体来说 `MuxCore` 是一个 **actor**，但我们不使用 actor
>    框架，而是依赖**一个或者多个读写锁**来串行化所有对 `MuxCore` 的请求。」
> 4. 「这是一个重大的设计变化，但我的估计不会影响具体的线格式等等的逻辑。需要你
>    根据这个新变化，**清理所有旧文档**，并在文档中描述这个新设计和部分关键代码。
>    这些关键代码**必须能够支持 layered_rpc 测试**，使用户能够自由地分层分阶段处理
>    mux 不同层次的需求，不容易受生命周期参数限制表达。」
> 5. 「先不修 F8 那个 bug。」

本节是这次变更的**权威设计记录**。§17.2–§17.5 是设计本体与关键代码，
§17.6 是它对 §16 各项摩擦的逐条结论，§17.7 是迁移清单，§17.8 是当时尚未裁决的
开放项。

> **落地结果见 §18**（2026-10-02 同一轮）：§17.7 的迁移清单已全部执行，§17.8 的
> 五个开放项与 §17.9 的「`Rt` 是否需要实证」都在 §18.1 裁定。本节保留为设计依据。

### 17.1 一句话概括

**把「谁借用谁」换成「谁持有谁的一份智能指针」。**

旧模型里，句柄是**借用的视图**：`DockBinding<'f>` 借 `MuxConnection`、
`ChannelListener<'s,'f>` 可变借 `DockBinding`、`ChannelHandle` 再借 listener。
于是一条链上所有对象的生命周期被绑死在一起，无法分发到不同函数、不同结构体。

新模型里，句柄是**各自独立的持有者**：每个句柄持有一份 `MuxConnection`
（= 指向 `MuxCore` 的智能指针，克隆廉价）。生命周期参数从公开类型上**全部消失**，
借用关系退化为「一次调用期间的 `&mut self` 独占」。

### 17.2 架构总览

```text
                      ┌──────────────────────────────────────────┐
   MuxConnection<C,Rt>│ 薄封装：Shared<MuxCore<C>, C::Alloc>      │  Clone 廉价
   （公开、可克隆）    │        + PhantomData<Rt>                 │
                      └────────────────┬─────────────────────────┘
                                       │ 强引用（引用计数）
                      ┌────────────────▼─────────────────────────┐
   MuxCore<C>         │ config_ / opts_                          │  actor 状态
   （公开、被共享）    │ reg_: ChannelRegistry_<C::Alloc>         │  ← 协作式读写锁 #1
                      │ wake_: CoreWake_                         │  ← 自旋读写锁 #2
                      │ control_: ControlQueue_                  │
                      └───────┬───────────────────────┬──────────┘
                              │ spawn_local           │ spawn_local
                      ┌───────▼───────┐       ┌───────▼───────┐
                      │ 读循环         │       │ 写循环         │
                      │ 解复用 / 投递  │       │ 调度 / 成帧    │
                      └───────────────┘       └───────────────┘
```

要点：

1. **`MuxCore` 是 actor**：连接的全部共享状态都在它里面；对共享状态的**修改**一律
   经读写锁串行化（**不用** actor 框架）。注意：锁规定的是「共享状态怎么被保护」，
   **不规定**「需求怎么被投递」——见下面「需求的投递方式」一节。
2. **`MuxConnection` 只是智能指针**：`Clone` 即多一份强引用。用户可以随便把它塞进
   结构体、传进函数、跨层分发。
3. **若干 `local spawn`**：读循环、写循环（后续还有保活定时任务）都是
   `Rt::spawn_local` 出来的，`detach()` 后靠取消令牌收尾（**§2.2 的收尾方式不变**）。
4. **`R` / `W` 从公开类型上消失**：它们在 `MuxConnection::new` 里被移进两个循环，
   之后不再出现在任何签名里。公开类型从 `MuxConnection<R, W, C, Rt>` 简化为
   `MuxConnection<C, Rt>`。
   > **后续修订（2026-10-02 晚）**：这一条的**方向被推翻**——`R` / `W` 回到公开类型
   > 上（`MuxConnection<C, S, R, W>`），理由见 §18.7：把**错误类型**放在那里才是真
   > 正的坏味道（错误是次要信息且常常不可命名），而传输类型既好命名又是主要信息。

#### 需求的投递方式：按需选择，**不是设计纪律**

> 人类修正（本轮）：「水位变化、收尾、accept/reject，是否要全部竞争锁，这个可以
> 根据实际情况考虑，**不是设计上的纪律**。毕竟如果锁竞争太多也是性能浪费，尤其是
> 水位变化这种非常适合通过 Flume 一次性发送也不影响其他状态的，没有必要抢锁。」

候选判据（供实现参考，不是纪律）：

| 需求 | 发起方与频率 | 必须立刻改共享状态？ | 倾向 |
| --- | --- | --- | --- |
| 水位置位 | `ChannelTx` 每次写入，**极高频** | 不必——写循环自己去环里取数 | **通道一次性投递**（载荷只有身份） |
| 水位回落 | `ChannelRx` 每次消费，**高频** | 要（回补接收窗口并择机公告） | 待实测：可先投通道提示，由写循环持锁自查 |
| 建流 / accept / reject | 应用面，**每条子流数次**（不是低频） | 要（登记身份、建环、挂共享状态） | **锁**（短临界区；`count` 上与子流数同阶，必须按份额算竞争） |
| 绑定 / 解绑 / listen | 应用面，**每个 dock 一次**（在册数 O(端口数)） | 要 | **锁**（调用次数低，但在册对象与 listen 的持续工作随子流数增长） |
| 发送 / 接收方向收尾 | 半部 drop，低频 | 要（排空后发 `FIN` / 发 `RESET`） | 锁或通道皆可；与水位同序更省心 |
| 循环唤醒 | 循环内部 / 需求方 | —（只写等待者槽） | 小锁或原子 + `Waker` |

> **频率口径更正（后续讨论）**：上面两行的「低频」原先只按**调用次数**看，漏了
> **在册对象数**与**路径的持续工作**两条：`bind_async` / `listen_async` 是
> **(连接, dock) 级**的应用面对象（一个服务端在 16 个 dock 上监听就有 16 份，且长期
> 持有），而 listen 这条路径**每建立一条子流都要改一次身份表**（读循环登记入向 +
> listener 的 `income_async` + accept/reject + 拆流）。也就是说**身份表不是一个可以
> 当作「低频、几乎无争用」的入口**。完整的触点表与线程布局见
> [`outlook-concurrency-20261002-2322.md`](outlook-concurrency-20261002-2322.md) §5.3。

三条不变量（**这才是纪律**）：

1. 无论走哪种投递方式，**最终修改共享状态都必须串行化**，不得有两个写入者同时改
   同一份状态；
2. 每条需求都要有**明确的顺序保证**（例如「先登记等待者、再复检需求」，否则丢唤醒）；
3. **高频路径优先免锁**，低频路径优先简单。

**对「去掉 flume」的修正**：`flume` 通道不一定要全部拆掉——它本来就是
「多生产者 → 单消费者、消息可重建」的合适工具，正好匹配「只带身份的提示」。要改的
是**「每条连接两条无界通道」这个具体形态**：换成**定容**通道后只在建通道时分配
一次。但即使定容，`flume` 仍不支持 `allocator_api`，内部依旧是**全局分配**——所以
这只是**减少**违规，不是消除；是否值得自建队列（归 `TrMaxAllocConfig`）取决于实测的
分配次数与竞争数据，不预设结论。

### 17.3 关键代码（一）：`MuxCore` 与智能指针

```rust
/// 复用连接的**演员核心**：连接的全部共享状态与全部「需求」入口。
///
/// 它不持有 `Rx` / `Tx`——那两个半边在 `MuxConnection::new` 里就被移进读 / 写循环，
/// 因此 `R` / `W` 不出现在本类型的参数里。`Rt` 也不需要：`abs_art` 的 spawn 是
/// 无 `self` 的关联函数，核心只负责状态，不负责投递。
///
/// # 串行化
///
/// 内部有**两把读写锁**，临界区一律是短闭包、**不跨 `await`、不可重入**：
///
/// | 锁 | 保护的东西 |
/// | --- | --- |
/// | `reg_` 自带的协作式读写锁 | 身份索引 / 配额 / 宽限态 / 失败标志 / 循环取消令牌 |
/// | `wake_` 的自旋读写锁 | 两个循环的等待者槽 + 「有无待处理需求」标志 |
///
/// 两把锁分开是为了让「高频水位通知」不必与「身份索引查询」互斥；若实测无争用，
/// 合并成一把也成立（人类裁决允许「一个或者多个」）。
///
/// 再说一遍：锁只管**共享状态怎么被保护**，不管**需求怎么被投递**。下文 `note_*`
/// 系列写成同步调用只是**候选**，水位这类高频提示完全可以直接走定容通道——
/// 见「需求的投递方式」一节。
pub struct MuxCore<C>
where
    C: TrMuxConfig,
{
    /// 资源策略：环存储工厂、分配器、流控策略。
    config_: C,

    /// 协商结果：配额、拆流宽限期、保活超时、单帧上限。
    opts_: BasicOpts,

    /// 建流时通告的初始接收窗口与通告阈值快照（原 `LoopShared_` 的三个标量）。
    flow_snapshot_: FlowSnapshot_,

    /// 身份索引 + 配额 + 宽限态 + 失败标志 + 两个循环的取消令牌。
    reg_: ChannelRegistry_<C::Alloc>,

    /// 两个循环的等待者槽与需求标志。
    wake_: CoreWake_,

    /// 待写出的控制帧队列（取代旧设计的写向 `flume` 通道）。
    control_: ControlQueue_,
}

/// 对 `MuxCore` 的**需求**入口。应用面句柄与两个循环都只能经这些方法触碰核心。
///
/// 命名沿用 `_` 后缀：这些是 crate 内部接口，公开面只有 `abs_smux` 的 trait。
impl<C> MuxCore<C>
where
    C: TrMuxConfig,
{
    //-- 应用面：会话身份（原 `bind_dock_` / `reserve_listener_` / …）--
    pub(crate) fn bind_dock_(&self, local: Dock) -> Result<(), MuxError<(), ()>>;
    pub(crate) fn unbind_dock_(&self, local: Dock);
    pub(crate) fn reserve_listener_(&self, local: Dock) -> Result<(), MuxError<(), ()>>;
    pub(crate) fn release_listener_(&self, local: Dock);
    pub(crate) fn reserve_telegraph_(&self, local: Dock) -> Result<(), MuxError<(), ()>>;
    pub(crate) fn release_telegraph_(&self, local: Dock);

    //-- 应用面：建流 / 收流（每次调用都在锁内改状态，并唤醒对应循环）--
    pub(crate) fn open_channel_(
        &self,
        local_dock: Dock,
        remote_dock: Dock,
    ) -> Result<ChannelPair_<C>, MuxError<(), ()>>;
    pub(crate) fn accept_inbound_(&self, local_dock: Dock, remote_dock: Dock)
        -> Result<ChannelPair_<C>, MuxError<(), ()>>;
    pub(crate) fn reject_inbound_(&self, local_dock: Dock, remote_dock: Dock);
    pub(crate) fn take_pending_inbound_(&self, local_dock: Dock) -> Option<Dock>;

    //-- 应用面：**水位与关闭通知**（是否走同步调用由实测决定，见「需求的投递方式」）--
    /// 发送环水位升高：应用刚写进数据，写循环可以取数了。
    pub(crate) fn note_tx_ready_(&self, local_dock: Dock, remote_dock: Dock);
    /// 接收环水位降低：应用刚消费了数据，接收窗口可以回补、并择机公告。
    pub(crate) fn note_rx_consumed_(&self, local_dock: Dock, remote_dock: Dock, amount: Credit);
    /// 应用丢弃了发送半边：排空后发 `FIN`。
    pub(crate) fn note_tx_closed_(&self, local_dock: Dock, remote_dock: Dock);
    /// 应用丢弃了接收半边：发 `RESET`（**F8 的语义问题见 §16.3，本轮不动**）。
    pub(crate) fn note_rx_closed_(&self, local_dock: Dock, remote_dock: Dock);

    //-- 循环面 --
    /// 登记本循环的等待者；返回后调用方必须**重新检查**需求，避免丢唤醒。
    pub(crate) fn register_loop_waker_(&self, which: LoopId_, waker: &Waker);
    /// 取走一条待写出的控制帧。
    pub(crate) fn take_control_frame_(&self) -> Option<ControlFrame_>;
    /// 记下连接级失败并触发两个循环的取消令牌（语义同旧 `mark_failed_`）。
```

### 17.4 关键代码（二）：句柄全部「持有」而非「借用」

四个公开句柄的形状统一成「智能指针 + 身份」：

```rust
/// 在某个 `local_dock` 上派生的会话对象。
///
/// **不借用连接**：自己持有一份强引用，因此可以存进结构体、可以从函数返回、
/// 可以与连接对象同处一个结构体（旧模型下那是自引用，见 §16.1 F2）。
pub struct DockBinding<C, Rt>
where
    C: TrMuxConfig,
{
    conn_: MuxConnection<C, Rt>,
    local_dock_: Dock,
}

/// 某 `local_dock` 上的入向子流监听器。
///
/// **不借用 `DockBinding`**：`listen_async(&mut self)` 的 `&mut` 只在调用期间存在，
/// 返回值是独立对象。因此「建 listener」与「accept 循环」可以拆成两个函数
/// （旧模型下写不出，见 §16.1 F3）。
pub struct ChannelListener<C, Rt>
where
    C: TrMuxConfig,
{
    conn_: MuxConnection<C, Rt>,
    local_dock_: Dock,
}

/// 一个入向建流请求的待决句柄。
pub struct ChannelHandle<C, Rt>
where
    C: TrMuxConfig,
{
    conn_: MuxConnection<C, Rt>,
    local_dock_: Dock,
    remote_dock_: Dock,
}

/// 数据报端点。
pub struct Telegraph<C, Rt>
where
    C: TrMuxConfig,
{
    conn_: MuxConnection<C, Rt>,
    local_dock_: Dock,
}
```

配套的 `Drop` 语义不变，只是改从自己持有的指针调核心：`DockBinding::drop` →
`core_.unbind_dock_(local)`；`ChannelListener::drop` → `release_listener_`；
`Telegraph::drop` → `release_telegraph_`。

**关联类型上的生命周期随之消失**（这是「不受生命周期参数限制表达」的关键）：

```rust
    type Rx = ChannelRx<C, Rt>;

    fn listen_async(&mut self) -> Self::ListenAsync<'_>;
    fn open_telegraph_async(&mut self) -> Self::OpenTelegraphAsync<'_>;
    fn open_channel_async<'f, M>(&'f mut self, remote_dock: Dock, message: &'f mut M)
        -> Self::OpenChannelAsync<'f, M>;
}

impl<C, Rt> TrChannelListener for ChannelListener<C, Rt>
where
    C: TrMuxConfig,
{
    type ChannelHandle = ChannelHandle<C, Rt>;   // ← 无生命周期参数
    type IncomeAsync<'f> = MuxIncomeAsync<'f, C, Rt> where Self: 'f;
    fn income_async(&mut self) -> Self::IncomeAsync<'_>;
}
```

### 17.5 关键代码（三）：channel 半部与「水位通知」直达核心

旧设计里，应用写数据后经一条 `flume` 通道通知写循环。新设计下这一步**有两种候选**
——直接调核心（下面代码所示）或继续走**定容通道**；选哪个由实测的锁竞争与分配次数
决定（见「需求的投递方式」）。下面给的是同步调用那一版：

```rust
/// 应用侧**发送**环半部。
///
/// 除了 `buffex` 的写端，它还持有连接指针：应用一写数据就**直接**调用
/// `note_tx_ready_`（旧设计是往 `flume` 通道投一条消息）。两种投递方式下这个类型的
/// 形状一样，差别只在「调用」还是「投递」：**先按实测数据选，不预设**。
pub struct ChannelTxHalf<C, Rt>
where
    C: TrMuxConfig,
{
    ring_: BufferedTx<C::Buff, C::Alloc>,
    conn_: MuxConnection<C, Rt>,
    local_dock_: Dock,
    remote_dock_: Dock,
}

/// 子流发送半边。**具名、可写进结构体字段**（旧模型里内层包装类型未导出，
/// 下游写不出这个类型，见 §16.2 F5）。
pub struct ChannelTx<C, Rt>(ChannelTxHalf<C, Rt>) where C: TrMuxConfig;

/// 子流接收半边；应用消费数据后直接调 `note_rx_consumed_`。
pub struct ChannelRx<C, Rt>(ChannelRxHalf<C, Rt>) where C: TrMuxConfig;
```

`channel_half` 模块因此**导出**两个 ring 包装类型（旧设计把它们标成
「模块私有」，只为了让 `ChannelTx` 的泛型 arity 保持不变——那个理由在新设计里
不再成立，因为公开类型本来就要带 `C, Rt`）。

### 17.6 这套形状对 §16 各项摩擦的结论

| 编号 | 旧结论 | 新设计下的结论 |
| --- | --- | --- |
| F1 ✅ | `MuxConnection` 可跨函数传 | 不变；且 `Clone` 后可以**多处**持有 |
| F2 ⛔ | `DockBinding` 借用连接 → 不能同处一个结构体 | **解决**：`DockBinding` 自己持有指针 |
| F3 ⛔ | `ChannelListener` 借用 `DockBinding` → 四步必须同函数 | **解决**：输出 owned，`bind` / `listen` / `income` / `accept` 可拆成四个函数 |
| F4 ⚠️ | 句柄不借用 listener，串行化靠约定 | 不变（现在是显式的：句柄各自独立） |
| F5 ⛔ | channel 具体类型无法命名 | **解决**：半部包装具名导出，`ChannelTx<C, Rt>` 可写进字段 |
| F6 ⛔ | `abs_smux` 只承诺 try 语义 | **不变**（上游 trait 决定的）；文档明确写出「要 `.await` 需自行补 `+ TrBuffWrite<u8>`」 |

```text
async fn server_listen_(conn: &Mux<Rt>, dock: Dock) -> ChannelListener<C, Rt>;

// 新模型下 ✅：绑定与连接同处一个结构体也不再是自引用。
struct RpcServer<C, Rt> {
```

### 17.7 迁移清单（按依赖顺序）

1. **`MuxCore` 落地**：把 `MuxConnection` 的字段（`config_` / `opts_` / `reg_` /
   `w_events_` / `r_events_`）与 `session_::LoopShared_` 的三个标量搬进 `MuxCore`；
   `MuxConnection` 变成 `Shared<MuxCore<C>, C::Alloc>` 的薄封装。
2. **句柄去生命周期**：四个句柄改为持有 `MuxConnection`；`types_::SessionMark_`
   整个删除；各处 `'s` / `'f` 参数从公开类型上摘掉。
3. **半部具名化**：`TxRing_` / `RxRing_` 改名为公开类型并从 `channel_half` 导出；
   `ChannelTx` / `ChannelRx` 改为 `<C, Rt>` 参数。
4. **需求的投递方式逐个定**：建流 / 绑定 / accept 走锁（注意「低频」的口径更正：
   身份表的写入次数与子流数同阶，见上文更正块）；高频的水位变化优先
   走**通道一次性投递**，不走锁。`signal_` 模块因此**保留**，只是把无界通道换成
   定容通道。四条 `note_*` 里哪些真的需要 `MuxCore` 同步调用，由实测的竞争与分配

5. **循环改为从核心拉取**：两个循环持有 `MuxConnection` 克隆，park 用
   `MuxCore::register_loop_waker_`；**唤醒登记必须先于需求复检**（沿用既有的
   「先登记、再复检」纪律，否则会丢唤醒）。
6. **测试**：`tests/layered_rpc.rs` 的分层函数签名按 §17.6 展开成「四个函数」的
   形状（本轮它已经用注释标出了这两处写不出来的位置）；`common` 与两个 smoke
   目标的类型别名同步 `MuxConnection<C, Rt>`。**线格式、握手、流控、注册表内部
   逻辑都不动**（人类判断成立：这次变更不触及线格式）。

### 17.9 未决问题：`Rt` 能否从公开类型上消失？——**需要实证**

> 人类指示（本轮）：「不要在 `MuxConnection` 上暴露 `Rt`，甚至 `MuxCore` 如果可能，
> 也应该可以不暴露。但这个设想现在缺乏实证支持——`abs_art` 目前支持的三个异步
> 运行时，能不能以及如何在实际上支持 `spawn_local` 还是未知之数。所以在这个设计
> 完全落实之前，要通过**实际测试**来判断，要不要通过 `abs_art` 来完成整个对
> `spawn_local` 的抽象，还是靠 `smux_v1` 自行设计 trait 来对 `spawn_local` 进行
> 抽象。」

**目标形状**：`MuxConnection<C>` / `MuxCore<C>`，公开类型上不带 `Rt`。

> **注**：以下三项是**当时**（`abs_art@083454a`）的状态。`local_scope` 落地后三条
> 全部改变——smol 的执行器改由作用域持有、tokio 改走方法版 `spawn_local`（不再有
> panic 陷阱）、`detach` 的存活契约写进 trait 文档。保留原文作为「为什么要推动
> 值化」的证据链。

#### 已查明的事实（读 `abs_art@083454a` 源码，**尚未在本 crate 实测**）

`abs_art` 的工作区有 `abs_art{,-tokio,-compio,-smol,-bridge}`，即**三个后端**。
`TrSpawnLocal` 只声明 `fn spawn_local<F>(future: F) -> Self::JoinHandle<F::Output>`，
`TrJoinHandle::detach(self)` 的文档里已经写明了三者的差异：

| 后端 | `spawn_local` 的实现方式 | `detach()` 之后任务还能推进吗 |
| --- | --- | --- |
| tokio | `tokio::task::spawn_local`；**必须在 `LocalSet` 上下文内**调用，否则 panic | ✅ 能（tokio 的 drop 即 detach，本地队列由调用方的 `LocalSet` 驱动） |
| compio | compio 的线程本地队列（`spawn_local` 与 `spawn` 行为一致，只放宽了 `Send`） | ✅ 能（`JoinHandle::detach` 是原生方法） |
| smol | **没有原生 `spawn_local`**；`abs_art` 每次调用**新建一个 `LocalExecutor`**，执行器**随 `JoinHandle` 存活**，句柄 poll 时驱动它 | ❌ **不能**：detach 消费句柄 → 执行器被销毁 → 本地任务等同被取消 |

**第二条与第三条事实对本 crate 是硬冲突。**

1. smux 的两个循环是「`spawn_local` 后**立即 `detach()`**，靠取消令牌自行退出」
   （§17.2 要点 3、模块文档 §2.4）。**在 smol 上，`detach()` 会把两个循环当场取消，
   连接根本无法工作。** `abs_art` 自己在 `TrJoinHandle::detach` 的「已知限制」里
   写明了这一点：「smol 后端的 `spawn_local` 任务……detach 消费句柄后执行器被销毁，
   本地任务无法继续推进（等同取消）」。
2. tokio 的 `spawn_local` 需要一个**环境条件**（处于 `LocalSet` 上下文）。纯类型
   参数 `Rt: TrSpawnLocal` **表达不了**这个前置条件——类型对了、调用点错了，运行期
   直接 panic。而 smux 的 `MuxConnection::new` 恰恰是「调用方调用、内部 spawn」，
   这个前置条件要么写进文档靠约定，要么做成**值**（spawner）来携带。

#### 两条候选路线

**路线 A：继续用 `abs_art` 做抽象**

- 优点：本 crate 不新增公开 trait；三个后端适配已就位；`Rt` 是一个类型参数，
  将来若要去掉，只需在 `new` 上做文章。
- 必须先解决：smol 的 `spawn_local + detach` 语义（要么上游把执行器改成不随句柄
  销毁，要么 smux 在 smol 上退回 `spawn` + `Send` 约束——而 `Send` 约束会与
  `!Send` 的传输实现冲突，见 §17.9 的待验证项）；以及 tokio「必须在 `LocalSet`
  上下文内」这条前置条件如何表达与检查。

**路线 B：`smux_v1` 自建 spawn 抽象**

- 定义自己的 trait（例如 `TrMuxSpawn`），契约里**显式写明**：
  1. 投递的任务**在 detach 之后必须继续运行**，直到自己退出；
  2. 收尾一律靠取消令牌，**不依赖句柄的 drop 语义**（这正是三个后端语义分裂的地方）；
  3. 调用所需的环境条件由实现自行表达——例如把 spawn 能力做成**值**
     （`fn spawner(&self) -> impl TrMuxSpawn`），而不是纯类型参数。
- 优点：契约由本 crate 说了算，三个后端的差异在**适配层**消化；`Rt` 可以彻底不出现在
  公开类型上（甚至可以用值参数取代类型参数，顺带把「必须在 `LocalSet` 上下文内」
  这类条件编码进去）。
- 代价：多一层适配；`smux_v1` 要自己维护（或要求使用者提供）三个后端的适配实现。

**在实验完成之前**：`Rt` **保持现状**（留在公开类型上），并在文档里标注为
「**待实证的临时形状**」，不得据此写死下游用法。

#### 必须做完的实证清单

1. **跨后端 `spawn_local` + `detach` 存活实验**（最高优先级）：在 tokio / compio /
   smol 上各 `spawn_local` 一个「自增计数器 + 周期性 tick」的任务，**立即 detach**，
   随后观察它是否继续推进。smol 那一路**预期失败**——这条实验的价值是把预期变成
   证据，而不是继续靠读代码推断。
2. **tokio 上下文实验**：在 `LocalSet` 之外调用 `spawn_local`，确认 panic 的形态，
   判断能否在 `new` 里做一次廉价的自检（或必须靠文档约定）。
3. **`TrDelay` 是否同病**：保活（§7.1）依赖 `abs_art` 的定时原语。若定时任务也是
   「detach 后不推进」，那么它与循环是同一类问题，必须一并解决。
4. **值参数化可行性**：若走路线 B，验证「把 spawn 能力做成值」是否真能让
   `MuxConnection` 不带 `Rt`，以及这个值本身会不会把 `Send` 约束漏进类型、
   破坏 `!Send` 传输的使用。
5. **`Send` 回退的代价**：若 smol 只能支持 `spawn`（要求 `F: Send`），验证
   smux 的循环 future 在 `!Send` 传输（如 compio 的 socket）下是否根本无法满足——
   这决定 smol 是「需要上游修」还是「只能不支持」。

#### 结论（**已由 `abs_art` 的落地解决**）

`abs_art` 随后采纳了本节列出的**路线 A 的加强版**：把「本地队列」**值化**为
`TrLocalScope` 的实现值（各后端的 `LocalScope`），并把「谁驱动队列」一并交给这个
值——见 `abs_art/dev-notes/local_scope-20261002-1307.md`。三个后端的 `detach` 语义
由此统一（契约写进 trait 文档），tokio 的「必须在 `LocalSet` 上下文内」也从文档
约定变成「拿不到值就 spawn 不了」。

因此本节的实验清单**不必再由本 crate 完成**：tokio / smol 的 `detach` 存活问题在
`abs_art` 侧已用「执行器归作用域所有」修掉，`abs_art-smoke` 的三后端矩阵成为防回归
的绿测试。本 crate 本轮据此把 `Rt` 从公开类型上彻底删除（§18）。

| `types_.rs` | `SessionMark_` / `MuxMark_` 整个删除（借用关系不再需要编码进类型） |
| `test_support_.rs`（新，`#[cfg(test)]`） | 单元测试专用：无循环连接构造 `new_test_`、空作用域 `NullScope_`、测试策略 `TestMuxConfig_` |
| `Cargo.toml` | 删除 `[features] multi-thread`；dev-deps 注释改为作用域值 |
| `tests/` | `common` 的场景函数改为「作用域作为第一个参数」（`S: TrLocalScope + Clone`）；四个测试目标各自取得并驱动作用域；`layered_rpc` 把服务端拆成 `bind_and_listen` + `serve` 两个函数，并新增 `RpcServer_`（连接 + binding + listener 同处一个结构体）与 `HalfHolder_`（半部作为具名字段）两处旧模型写不出的形状 |
| `tests/inmem_mux.rs` | 新增两个收尾用例：`dropping_connection_stops_both_loops_tokio_`（两侧同时丢弃）与 `dropping_one_side_stops_its_loops_tokio_`（**只丢一侧、对端活着且空闲**）。两者都用**析构探针**包住四个传输半边，且探针把 future 包成**忽略取消令牌**的形态（`IgnoresCancel_`），以模拟「只做转发、不在取消时唤醒 park」的传输适配层 |

### 18.3 最终形状（关键代码）

```rust
// 公开：薄封装。Clone 廉价，可任意分发；不带任何生命周期参数。
// 参数是**传输**类型 R / W（不是它们的错误类型），错误由 R::Err / W::Err 派生。
pub struct MuxConnection<C, S, R, W> where C: TrMuxConfig {
    core_: Shared<MuxCore<C, S>, C::Alloc>,
    _mark_: PhantomData<fn() -> (R, W)>,
}

// 内部：演员核心。注意这里**没有**建流展开的三个标量（它们归 LoopShared_）。
pub(crate) struct MuxCore<C, S> where C: TrMuxConfig {
    config_: C, opts_: HandshakeOpts, scope_: S,
    reg_: ChannelRegistry_<C::Alloc>,
    w_events_: EventSender_<WriteEvent_<C::Buff, C::Alloc>>,
    r_events_: EventSender_<ReadEvent_<C::Buff, C::Alloc>>,
}
impl<C, S> Drop for MuxCore<C, S> where C: TrMuxConfig {
    fn drop(&mut self) { self.reg_.cancel_loops_(); }   // ← 收尾的唯一入口
}

impl<C, S, R, W> MuxConnection<C, S, R, W> where C: TrMuxConfig {
    // 这里的 R / W 就是类型参数本身：传输类型决定 Self，错误类型由它派生。
    pub fn new(scope: &S, delivery: HandshakeDelivery<W, R>, config: C) -> Self
    where
        S: TrLocalScope + Clone,
        R: TrBuffRead<u8> + 'static,
        W: TrBuffWrite<u8> + 'static,
    { /* 建核心 → scope.spawn_local(读循环).detach() → spawn_local(写循环).detach() */ }
}
```

收尾链条（**本架构最容易被写坏的一处**）：

```text
最后一个应用面对象被丢弃      （连接 / binding / listener / handle / telegraph / 半部）
   ⇒ MuxCore 析构 ⇒ Drop 取消两个令牌
   ⇒ 循环在下一个 park 点醒来并退出 ⇒ 传输半边被 drop、连接真正关闭
```

若循环改成持核心强引用，第二步永远不会发生：任务、传输与整个连接状态永久泄漏。
这条不变量由两个用例钉住，并**反向验证过**：把 `cancel_loops_()` 注释掉后
`dropping_connection_stops_both_loops_tokio_` 如期失败（四个析构标志全为假）。
`dropping_one_side_stops_its_loops_tokio_` 是更严格的那条——对端活着且空闲，因此
被丢弃那一侧**不能**靠「对端先关掉环」顺带被唤醒。

### 18.4 实施中查出的问题

1. **核心里的三个标量是冗余的**。按 §17.3 的字段表把「初始接收窗口 / 通告阈值 /
   单帧上限」搬进核心后，编译器报了三处 `never read`：它们只有循环读，而循环拿的是
   `LoopShared_`。**裁决：核心不存这三个标量**，`LoopShared_` 是它们唯一的家
   （同时核心里 `scope_` 的 `never read` 也提示了一个更好的写法——投递也走核心里的
   那一份作用域，于是「谁提供队列」在核心上只有一处，且不需要 `#[allow(dead_code)]`）。
2. **取消被记成了连接失败**。`mark_failed_` 原先无条件把错误投影进注册表，而循环
   退出时收到的最后一个错误正是「取消」。对一条已经析构的连接留下失败标志虽无害，
   但语义错。**修法**：新增 `fail_loop_`，`cancel.is_cancelled()` 为真时不记失败。
3. **`Owned` 没有 `resize`**。旧代码在 `drain_one_` 里按段长 `scratch.resize(take, 0)`；
   换成定长 `Owned<[u8], _>` 后无处可 resize。**修法**：暂存按 `K_MAX_DATA_CHUNK`
   预分配一次，并在借段处显式判 `take > scratch.len()`（`Demand::no_more_than` 保证
   它不会发生，真发生即 `MalformedFrame`）——不引入静默截断。

4. **「取消能否唤醒 park」不是本 crate 能假定的事**。`may_cancel_with` 只把令牌交给
   内层 future（内层在被 poll 时才检查 `is_cancelled`），**是否在取消时唤醒 park 中
   的 future 取决于那一层的实现**：`buffex` 的环半部会把 `cancellation()` 存进自己
   的 park 状态并在取消时唤醒（`ring/half_.rs` 的 `cancel_sig`），而一个只做转发的
   传输适配层不会。若把「丢弃连接即关闭连接」建立在这条隐含契约上，某个传输实现就能
   让循环永远收不了尾（任务与传输泄漏）。**修法**：新增 `race_cancel_`，把循环里每一
   次可能长期 park 的 await 都与 `cancellation()`（它保证登记 waker）竞争——收尾因此
   与传输实现无关。收尾用例里的探针**故意忽略取消令牌**，正是为了让这条独立性可测。

顺带修正的既有小问题：`Owned::new_slice` 的初始化闭包要求返回 `()`（原写法返回
`&mut u8`），以及 `gen_may_cancel_future` 生成的 future 类型需要显式补第二个生命周期
参数（`MuxBindAsync<'f, 'f, …>`）；`TrBuffRead::ReadAsync` 只承诺 `TrMayCancel` 而
不承诺 `Future`，包装它时要经 `IntoFuture` 投影。

### 18.5 遗留（**当前**清单）

0. **入向待决仍是全局身份表的一部分**：`reserve_inbound_` / `take_pending_inbound_`
   仍在 `channels_` 上做；人类已裁决改为 **per listener 队列**（设计与待办清单见
   [`outlook-concurrency-20261002-2322.md`](outlook-concurrency-20261002-2322.md) §5.3）。
1. **`signal_` 仍是无限通道**：无界 + 每条子流至多一条水位事件 ⇒ 队列天然有界，
   但每条消息仍可能分配、且 `flume` 不支持 `allocator_api`。换定容需要「队列满 ⇒
   置连接级全扫标志」的兜底机制，**留待实测的竞争与分配数据再定**。
2. **telegraph 整条支线仍未实现**（`send_async` / `recv_async` 仍是 `todo!()`），
   身份登记已就位。
3. **保活超时（`IdleTimeout`）未实现**：只记录活跃时间与处理收到的 `PULSE`。
4. **`RxClosed` 的语义缺陷（§16.3 F8）本轮明确不修**（人类指示），收尾顺序仍需
   遵守「先丢发送半边」的规避写法。
5. **`TrMaxAllocConfig` 未引入**：当前每处分配都走调用方注入的 `C::Alloc`
   （含新换的 `Owned` 暂存），但「环存储 / 环容器 / 帧暂存 / 控制帧载荷」还没有
   各自的关联类型；注册表内层锁与 `flume` 仍是记录在案的全局分配例外。
6. **`MuxCore` 保持 crate 内部**：若将来要把「高级用法」（直接对核心下单）开放给
   用户，需要另行讨论公开面（§17.8 第 4 项的答案仍是「暂不开放」）。

## 18.7 追加修订：公开泛型参数改为「传输类型」，错误类型改为派生（2026-10-02 晚）

> 人类指示：「`MuxError` 和 `MuxConnection` 上面的 `RE` `WE` 是反直觉的设计，不应该让
> 错误类型出现在高层泛型参数上，因为它们是次要信息，产生 `RW` 和 `WE` 的类型本身才是
> 重要信息，也即我们要通过 `R` 和 `W` 来推断得到 `RE` 和 `WE`，而不是被 `RE` 和 `WE`
> 牵着走，这是坏味道。」

（本节编号挂在 §18 之下，但它修订的是 §18.1 的 Q11 与 §17.2 第 4 条。）

### 18.7.1 为什么原裁决是坏的

1. **错误是次要信息**：`MuxConnection<C, S, io::Error, io::Error>` 里读不出「这条连接
   建在什么传输上」——两个不同传输只要错误类型相同就完全同型。
2. **错误类型常常不可命名**：它可能是私有类型，或只以
   `<T as TrBuffTryRead<u8>>::Err` 这样的投影存在。原形状因此逼调用方在**每一个**类型
   别名里写投影：`tests/common/mod.rs` 上一轮就出现了
   `<R as TrBuffTryRead<u8>>::Err` 这种连接别名——坏味道的直接证据。
3. **参数应当是「你手里有什么」**：调用方手里是两个传输半边 `Rx` / `Tx`；错误类型是
   他们从没见过的东西。

### 18.7.2 落地形状（含一次走错的岔路）

**第一版尝试（已废弃）**：把引擎枚举保留为「载荷参数化」，另外提供一个以传输参数化的
**类型别名** `pub type MuxError<R, W> = MuxError_<R::Err, W::Err>;`，让公开名字变成别名。
它能让 `MuxError<Rx, Tx>` 这种**类型标注**写出来，但实测在**模式匹配**上失败：

```text
error[E0284]: type annotations needed
   --> tests/common/mod.rs
    |            Result::Err(MuxError::DockInUse)
    |                        ^^^^^^^^ cannot infer type for type parameter `R` declared on the type alias `MuxError`
    |    = note: cannot satisfy `<_ as TrBuffTryRead>::Err == _`
```

原因是编译器必须**反向求解投影**（从 `MuxError_<R::Err, W::Err>` 反推 `R`）。「参数不可
命名」的问题只是从连接搬到了错误类型上，**并没有解决**——而这正是人类指示的核心
（「不应阻止开发者主动为 `MuxError` 写代码」）。因此别名方案作废。

**最终形状**：让**枚举自己**以传输为参数，载荷变体写成投影：

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| `MuxConnection` / 四个句柄 / 两个半部 | `<C, S, R, W>`（当时叫 `RE` / `WE`） | `<C, S, R, W>`，语义改为**传输类型** |
| `MuxError` | `MuxError<RE, WE>`（参数是**载荷**） | `MuxError<R, W>`（参数是**传输**），变体 `Rx(<R as TrBuffTryRead<u8>>::Err)`、`Tx(<W as TrBuffTryWrite<u8>>::Err)` |
| `TrConnection::Err` | `MuxError<R::Err, W::Err>` | `MuxError<R, W>` |
| trait impl 的 bound | `RE: core::error::Error` | `R: TrBuffTryRead<u8>`、`W: TrBuffTryWrite<u8>` |
| `MuxConnection::new` | `new<R, W>`（方法级泛型）+ `R::Err = RE` 等式约束 | **直接使用类型参数**：无方法级泛型、无等式约束 |
| `Debug` | `derive` | **手写**：派生会给 `R` / `W` 本身加 `Debug` 约束，而真正需要的是**载荷**可打印 |
| `MuxCore<C, S>` | — | 不变（核心既不含传输、也不含错误） |

**内部单边形式**：连接内部有些层只碰一个方向（帧解析只会产生读侧载荷）。这些地方不能
「顺手借」另一侧的传输类型，因此新增一个 crate 内部的**占位半边**
`NoHalfway_`（不可构造，其载荷 `NoHalfwayErr_` 也不可构造），于是：

```rust
type MuxReadErr_<R>  = MuxError<R, NoHalfway_>;   // 只可能出读侧载荷
type MuxWriteErr_<W> = MuxError<NoHalfway_, W>;   // 只可能出写侧载荷
```

这让「另一侧不可能出错」变成**类型上的事实**，而不是一句注释。`wire_io_` 的
`CursorError` 保持原样（仍用 `()` 占位，因为握手模块也用它），映射在连接层完成：
`map_read_cursor_err_` / `map_write_cursor_err_` 把 `()` 翻译成 `NoHalfwayErr_`。

正面副作用：`new` 的签名变短；测试别名从「投影堆」变成
`SmokeConn<R, W, S> = MuxConnection<SmokeMuxConfig, S, R, W>`；`MuxError` 的 `match`
可以正常推断（doctest 与 `tests/layered_rpc.rs` 的 F9 探针都钉住了这一点）。

代价：传输类型重新出现在公开类型上——即 **§17.2 第 4 条被推翻**。裁决理由是「错误类型
不可命名」这条**硬约束**强于「传输在类型上不可见」这条美学；而 §17.2 的原始动机（句柄
不被运行时参数绑住）不受影响——`S` 仍是值的类型，且传输不参与任何行为。

### 18.7.3 验证（实测）

「开发者能对错误写代码」这条不靠声明、靠两个可执行的钉子：
- `error_.rs` 的 **doctest**（`cargo test --doc`）里直接 `match MuxError::Rx(_)`；
- `tests/layered_rpc.rs` 的 **F9 探针**：用项目自己的 `WireRx` / `WireTx` 写分类函数，
  并演示它同样吃 `<Mux<S> as TrConnection>::Err`（编译期检查）。

```bash

cargo clippy --all-targets       # 零告警
cargo doc --no-deps              # 零 rustdoc 警告
```

## 19 跟随 `abs_smux` 建流语义更新：缓冲在最终裁决时由调用方给出（2026-10-03）

### 19.1 上游改了什么

`abs_smux` 这一轮更新（`c5789e3` / `f43f356`）把「子流要用的缓冲」从**建连时的配置**
挪到了**建流最终裁决时的调用方**：

| 位置 | 旧 | 新 |
| --- | --- | --- |
| 模块 | 全部在 `conn` | 新增 `chan`（IO facade）：`TrChannelHalf` / `TrChannelTx` / `TrChannelRx` / `TrChannelHandle` |
| `TrDock` | `abs_smux::conn` | `abs_smux::dock`（并新增 `Dock::value()`） |
| `TrChannelHandle::accept_async` | `accept_async(&mut welcome)` → `(Tx, Rx)` | `accept_async(&mut welcome, prepare: P)`，`P: TrPrepareChannelBuff` → `(Tx, Rx)` |
| 缓冲来源 | 由实现（本 crate 的配置）按 `channel_capacity` 造 | **调用方**：`prepare(self) -> ChannelBuff<B> { tx_buff, rx_buff }`（`B: BorrowMut<[MaybeUninit<u8>]>`，`|| (b, b)` 有 blanket impl） |
| `TrDockBinding::open_channel_async` | → `(Tx, Rx)` | → `Self::ChannelHandle`（**半建立**句柄） |
| `Listener` / `Telegraph` / `DockBinding` 关联类型 | GAT（带 `'f`） | 不再是 GAT |
| 半边的 bound | `TrBuffTryWrite` / `TrBuffTryRead` | **`TrBuffWrite` / `TrBuffRead`**（约束更多的那个） |
| `TrPrepareChannelBuff::Buff` | `BorrowMut<[MaybeUninit<u8>]>` | **补上能力约束**：`+ Send + Sync + 'static`（缓冲要跨线程、要活到连接结束）。这是为了让实现方能把它装箱成自己的载具，见 §19.4.3 |

对称化后，**两侧都走两段**：`open_channel_async` / `income_async` 产出半建立句柄 →
`accept_async(welcome, prepare)` 才最终裁决。

> 最后一行的能力约束是**第三轮**补的：缓冲的**类型**由使用环境按 channel 决定，连接
> 不该管，因此实现方需要「能装箱」的资格；`Send + Sync + 'static` 本来就是复用连接的
> 语义要求。**上游不需要任何等式/关联类型**——那一版（第二轮试过）能用，但会把「一条
> 连接一种缓冲类型」重新强加给使用环境，已被否决（§19.4）。

### 19.2 本 crate 的调整：`OPEN` 一律延后到 `accept_async`

这不是风格选择，而是**语义强制**：`OPEN` 要通告本端**接收窗口**，而窗口值取决于调用方
给出的**接收缓冲容量**——在拿到缓冲之前发 `OPEN` 只能撒谎。于是：

- **主动方** `open_channel_async`：只做本地两件事——登记身份（dock 对唯一性 + 配额）与
  把开场消息搬进句柄（`Vec`，冷路径一次分配），**不发任何帧**；返回一个「尚未在线上
  露面」的句柄。
- **被动方读循环**：读到入向 `OPEN` 只 `reserve_inbound_`，**不再抢先回一条 `OPEN`**
  （旧形状在读循环里回，因为那时容量由配置统一定死）。
- **`accept_async` 成为唯一提交点**：按调用方给的容量建两条环 → 登记 owner → `Attach`
  两个会话侧半部 → 主动方发 `OPEN` 后等对端 `OPEN` + `ACCEPT`，被动方发自己的
  `OPEN` + `ACCEPT` 后立即完成。
- **丢弃未裁决的句柄 = 放弃建立**，按角色收尾（见 19.3）。

连带简化：**连接不再需要任何连接级窗口快照**。`LoopShared_` 从「注册表句柄 + 三个
标量」缩成「注册表句柄 + 单帧上限」，`MuxCore` / `CoreBundle_::build_` 里的
`initial_window` / `thresholds` 计算全部删除；**通告阈值改为逐条子流**
（`ChannelState_::thresholds_`，建流时按该子流接收缓冲容量算），写循环从 owner 取它。
`Cargo.toml` 的 `abs_smux` 临时指向 `path = "../abs_smux"`（上游修改尚未推分支）。

### 19.3 两种「未裁决就丢弃」的收尾（新增寄存器入口）

| 角色 | 线上痕迹 | 收尾 | 为什么 |
| --- | --- | --- | --- |
| **发起方** | **无**（`OPEN` 还没发） | `unreserve_channel_`：**立即**归还身份与配额，不留宽限期 | 对端不知道这条子流存在、不可能有在途帧；若走 `release_channel_`，同一 dock 对会被白白占住一整个 `max_channel_wait_close` |
| **响应方** | 对端 `OPEN` 已到 | 先补一条空理由的 `REJECT`，再 `release_channel_`（进宽限期） | 不发 `REJECT` 的话，对端的 `accept_async` 会**永远悬着** |

三点说明：

1. `unreserve_channel_` 是新增的 crate 内部入口（`pub(crate)`，非公开 API）：就是
   `release_channel_` 去掉宽限期那一半——`bindings_.remove` + 反向索引 + 两个计数 +
   `prune_dock_`。
2. `reject_async` 按同一张表分流：发起方句柄拒绝 = 纯本地撤销（对端不知情，发
   `REJECT` 反而会让它困惑）；响应方句柄拒绝 = 带理由载荷发 `REJECT`。
3. `ChannelHandle` 因此新增 `Drop`（旧形状没有）：`settled_` 标记防止接受成功后又被
   drop 掉身份。

### 19.4 ✅ 缓冲归属：从「等式约束」到「连接不该管缓冲类型」（2026-10-03 第二/三轮）

这一节记录两次走偏与最终结论。**最终结论**：问题不在上游 trait 的表达力，而在本 crate
把**环存储类型**当成了连接级策略（`TrMuxConfig::Buff`）——而客观需求是**由使用环境按
channel 自行决定缓冲用什么承载**。连接侧需要的只是「一个固定的类型让循环/事件/半部能
编译」，这个类型应当是**类型擦除的载具**，而不是某个被声明的具体类型。

#### 19.4.1 第一次尝试：让上游加等式（能用，但把约束放错了地方）

第一轮曾提出给 `TrChannelHandle` 加 `type Buff` 并要求
`P: TrPrepareChannelBuff<Buff = Self::Buff>`。它确实解开了「直接用调用方存储建环」的
类型问题（实测：本 crate 随即不再需要 `make_buff`，全量测试通过），但代价是
**一条连接只能有一种缓冲类型**——等于把「缓冲用什么承载」又交回给连接统一规定，与客观
需求相反。因此这一版被否决。

#### 19.4.2 中间一问：把约束写成 `Buff: BorrowMut<[MaybeUninit<Self::Data>]>` 够不够

不够。那是一个**约束**而不是**等式**：它只说 `P::Buff` 满足什么 trait，没有说它**等于**
连接的环类型；而且在 `Self::Data = u8`（本 crate 就是）时已被
`TrPrepareChannelBuff` 自身的 `type Buff: BorrowMut<[MaybeUninit<u8>]>` 蕴含。实测在该
约束下直接使用调用方存储，墙原封不动：

```text
error[E0308]: mismatched types
   |  let _typed_rx: BufferedRx<C::Buff, C::Alloc> = probe_r;
   |                 -------------------------------   ^^^^^^^ expected `TrMuxConfig::Buff`,
   |                                                           found `TrPrepareChannelBuff::Buff`
```

#### 19.4.3 最终形态：连接侧类型擦除 + 上游只补**能力**约束

两侧各改一处，都不涉及「类型相等」：

**(1) 上游（`abs_smux`）**：只把缓冲的**能力**写清楚——它必须能跨线程共享、并且活到连接
结束（环由两个 `spawn_local` 的循环持有）：

```diff
 pub trait TrPrepareChannelBuff {
-    type Buff: BorrowMut<[MaybeUninit<u8>]>;
+    type Buff: BorrowMut<[MaybeUninit<u8>]> + Send + Sync + 'static;
     fn prepare(self) -> ChannelBuff<Self::Buff>;
 }
```

（连带：`|| (b, b)` 的 blanket impl 的 `B` 也要带同样约束。）这条约束**语义上本来就必须
成立**，只是之前没写出来；写出来之后，实现方才有资格把调用方给的存储**装箱**成自己的
统一载具。

**(2) 本 crate**：新增类型擦除载具 `MuxChanBuff`（环只需要
`BorrowMut<[MaybeUninit<u8>]>`，因此任意存储都能装进去）：

```rust
#[doc(hidden)]
pub struct MuxChanBuff { inner_: Box<dyn BorrowMut<[MaybeUninit<u8>]> + Send + Sync> }
```

- `TrMuxConfig` **删掉** `type Buff`（回到「分配器 + 流控策略」两项）；
- 两个循环的本地表、两条事件通道、两个半部的环端类型一律用 `MuxChanBuff`；
- `accept_async` 把 `prepare` 给的两块存储装箱（容量在建环前读出，用于算接收窗口与环
  大小），此后连接侧与「承载者具体是什么」再无关系；
- 为什么需要这层 newtype：`Box<T>` 只为 `T` 自身实现 `BorrowMut<T>`，
  `Box<dyn BorrowMut<[MaybeUninit<u8>]>>` **不是** `BorrowMut<[MaybeUninit<u8>]>`；载具
  显式把 `borrow` / `borrow_mut` 转发给内部 trait object。
- 为什么是 `pub` + `#[doc(hidden)]`：它会出现在
  `ChannelTx` / `ChannelRx` 的 `TrBuffTryWrite` / `TrBuffTryRead` 关联类型里（那些 GAT
  就是环自己的段类型），因此不能是 crate 私有；但它不是给使用者手工构造的类型（入口是
  `prepare` 的返回值），故隐藏。**这是本轮唯一的公开 API 变化。**

代价：每条子流每方向一次装箱（冷路径），环每次取切片一次虚调用。换来的是连接对缓冲类型
一无所知。既不需要上游的等式，也不需要把整个环端异步接口擦除。

#### 19.4.4 验收：同一条连接上混用不同承载者

新增 `mux_mixed_carrier_{tokio,compio}_`（`tests/inmem_mux.rs` +
`common::run_mixed_carrier_scenario_`）：**同一条连接**的两条子流分别用
`Owned<[MaybeUninit<u8>], CoreAlloc>`（容量 4096）与 `Box<[MaybeUninit<u8>]>`
（容量 8192，类型与容量都不同），两侧的承载者还各自不同；两条子流都要双向收发 + 半关闭
成功。在 19.4.1 的等式方案下这个用例**编译不过**——这正是「缓冲由使用环境决定」的可执行
判据。

### 19.4.5 顺带清理：通道内部不再泛型于缓冲类型

载具固定成 [`MuxChanBuff`](crate::connection::MuxChanBuff) 之后，连接**内部**的
`B` 参数已经没有第二种取值（实测：`session_` / `signal_` / `halves_` 里只出现
`MuxChanBuff`；真正的多样性只存在于**传输**角色——测试里的 `TestBuff` / `WireBuff` /
`SmokeBuff` 是用 `buffex` 环当网络传输）。于是把内部这一层去泛型：

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| `WriteEvent_` / `ReadEvent_` | `<B, A>` + `B: BorrowMut<…> + Send + Sync` | `<A>` |
| `read_loop_async_` / `write_loop_async_` | `<R, B, A, K>` / `<W, B, A, K>` | `<R, A, K>` / `<W, A, K>` |
| `ReadTable_` / `WriteTable_` / 表条目 | `<B, A>` | `<A>` |
| `drain_read_events_` / `handle_write_event_` / `maybe_release_` / `flush_entry_` / `drain_once_` / `drain_one_` | 带 `B` | 去 `B` |
| 半部与事件里的环端类型 | `BufferedTx<MuxChanBuff, A>` 等逐处书写 | 统一用别名 `ChanRingTx_<A>` / `ChanRingRx_<A>` |

`session_` 里的 `B` 从 41 处降到 0；`BorrowMut` / `MaybeUninit` 的约束也从循环与事件
签名上消失。

**泛型别名保留**：`BufferedTx<B, A>` / `BufferedRx<B, A>` / `BufferedChannel<B, A>`
仍然是泛型的——它们是与 `buffex` 对接的桥，`B` 由**使用者**决定（内存环、池化缓冲、
静态区都可以），用于「把 `buffex` 环当传输用」这一正当场景（测试里的
`make_passive_ring_` 就是）。连接内部的通道与它无关，因此不复用那份泛型。

### 19.6 `TrAcceptBuff`：把「接受哪种缓冲」交给实现声明（第三轮，已落地）

分工（人类裁决）：`TrPrepareChannelRing<B, T>` 只描述「用户交出指向**自己分配的内存**的
智能指针」（`ChannelBuff<B, T>`，**无容量入参**——分配多少是用户的权限，连接只管校验后
拒绝）；**实现**通过 `TrAcceptBuff` 声明「我能接受哪一种」；`accept_async` 的约束接在它
上面。这样「一条连接只能用一种环存储」落在实现身上，而不是写进抽象层的类型定义里。

#### 19.6.1 纯参数标记（`TrAcceptBuff<B, T> {}`）为什么不够

它能把**调用点**检查住（调用方的 `B` 从 `prepare` 推断、再拿 `Self: TrAcceptBuff<B, T>`
对），但**实现侧用不上**：impl 里 `B` 是刚性类型参数，而 trait 声明里的
`Self: TrAcceptBuff<B, T>` 只是**被假设成立**的约束，编译器不会把它反解成等式
`B = C::Buff`。于是 smux 里「用 `B` 型缓冲建 `C::Buff` 型环」直接报：

```text
error[E0308]: arguments to this method are incorrect
   |  fn accept_async<'f, Wb, P, B>(
   |                                - found this type parameter
   |  self.accept_buff_(tx_buff, rx_buff)
   |       ^^^^^^^^^^^^
note: expected associated type, found type parameter `B`
```

#### 19.6.2 两处最小修正（都已验证）

1. **类型要由实现声明成关联类型**（可规范化），而不是交给调用点推断：

   ```rust
   pub trait TrAcceptBuff<T> {
       /// 本连接能接受的**那一种**缓冲智能指针（由实现声明）。
       type Buff: BorrowMut<[MaybeUninit<T>]>;
   }
   ```

   连接的 `accept_async` 约束写成可规范化的投影：

   ```rust
   P: TrPrepareChannelRing<<Self as TrAcceptBuff<Self::Data>>::Buff, Self::Data>
   ```

   smux 侧：`impl<..> TrAcceptBuff<u8> for ChannelHandle<..> { type Buff = C::Buff; }`
   （**无** where 子句 ⇒ 投影可被规范化到 `C::Buff`）。

2. **声明必须是 `TrChannelHandle` 的 supertrait，而不是 where 约束**：

   ```rust
   pub trait TrChannelHandle
   where
       Self: TrChannelHalf + TrAcceptBuff<<Self as TrChannelHalf>::Data>,
   { ... }
   ```

   原因：where 子句里出现具体 `Self` 类型会触发 **rustc issue #152409**（"the where-bound
   … shadows this definition"：impl 里 GAT 的定义被遮蔽，构造 future 时被判类型不符）。
   supertrait 形式不引入 where-bound，因此绕开该缺陷。

   连带：GAT 的 where 子句里 `P` 不再要求 `'f`（future 已经把「准备 + 接受」放在方法体里
   同步做完，不再持有 `P`）。

#### 19.6.3 验收

- **零装箱**：环、事件、两个半部全部按 `C::Buff` 静态参数化；无 `dyn`、无装箱。
- **调用点检查有效**（实测）：连接声明 `Owned<[MaybeUninit<u8>], CoreAlloc>` 时，传一个
  返回 `Box<[MaybeUninit<u8>]>` 的闭包：

  ```text
  error[E0271]: expected `{closure}` to return `(Owned<[MaybeUninit<u8>], CoreAlloc>, …)`,
                but it returns `(Box<[MaybeUninit<u8>]>, Box<[MaybeUninit<u8>]>)`
     |  .accept_async(&mut welcome, || { … })
     |   ------------               -- this closure
     |   required by a bound introduced by this call
  ```

- **大小由用户决定、连接只拒绝**：`accept_buff_` 先量容量，低于环的下限就返回
  `MuxError::RingRejected`（新增变体），并按角色收尾（响应方补 `REJECT`，发起方撤销登记）；
  因为 `OPEN` 已推迟到 `accept_async`，拒绝发生在发出任何帧之前。
- 全量：`cargo check/clippy --all-targets` 零告警、`cargo doc --no-deps` 零警告、
  74 单测 + 10 inmem + 2 layered + 2+2 smoke、5 doctest 全绿。

### 19.7 更正：`unspecified` / `wildcard` 是「不能作身份」，不是「不能出现在帧里」

人类裁决（本轮更正）：朝 `wildcard` / `unspecified` dock **发送 telegraph 是允许的**，
收不收是对端自己的策略——此前本 crate 把「任何一帧的 dock 取保留值即违例」写进了
`connection` 模块文档 §4 与 `frame_.rs`，那是**把身份和地址混为一谈**。

更正后的规则：

| 帧种类 | dock 的角色 | 保留值 |
| --- | --- | --- |
| `OPEN` / `ACCEPT` / `REJECT` / `CLOSE` / `PULSE` / `WINDOW_UPDATE` / 数据帧 | dock 对 = **子流身份** | local / remote 取 `unspecified` / `wildcard` 即违例（`MuxError::ReservedDock`） |
| `DATAGRAM`（telegraph） | remote dock = **目的地址** | 取 `wildcard` / `unspecified` **合法**；local dock 来自已绑定 telegraph，天然真实 |

对错误类型拆分的影响：`ReservedDock` 只应出现在**拿 dock 做身份**的面——
`BindError`（`bind_async` 选定并校验 local dock）与 `OpenChannelError`（调用方给的
remote dock 是身份的一半）；**telegraph 的面不带它**（发到保留值是合法的）。

遗留（本轮不动，telegraph 尚未实现）：`frame_.rs` 里「出帧不得带保留值」的检查目前对
所有帧一视同仁，接 `DATAGRAM` 写路径时必须按帧种类放宽；读侧收到 `DATAGRAM` 时也要接受
保留值的 remote dock。（现状：`send_async` 未实现，读循环对 `DATAGRAM` 收到即忽略。）

### 19.8 错误类型拆分：连接级 `MuxError` + 每个子对象自己的错误类型

人类裁决：`abs_smux` 给每个子对象留了 `type Err` 槽位（`TrConnection`、
`TrDockBinding`、`TrChannelListener`、`TrChannelHandle`、`TrTelegraph`），因此
**不该把所有失败塞进一个 `MuxError`**；同时 `MuxError` 保留——它本身要表达的东西
（连接级失败）不属于任何单个 API 面，删除它同样是错的。

最终形状：

- `MuxError<R, W>` **收窄**为连接级失败：`Rx` / `Tx` / `Transport{write}` /
  `Cancelled` / `PeerClosed` / `Closed` / `IdleTimeout` / `MalformedFrame` /
  `UnsupportedField` / `FrameTooLarge` / `ReservedDock` / `FlowCtrl`——正是读写循环与
  帧编解码**真正会构造**的那些（其余变体在 `MuxError` 里的唯一存在理由只是给面转发）。
- 每个子对象一个公开错误类型，只列本面会报的失败，并把连接级失败包在 `Mux(..)` 里：
  `BindError`（`bind_async`）、`BindingError`（`listen` / `open_telegraph` /
  `open_channel` **共用**——`TrDockBinding` 只有一个 `Err` 槽）、`ListenerError`
  （`income`）、`HandleError`（`accept` / `reject`）、`TelegraphError`（`send` / `recv`）。
  统一手写 `Debug` / `Display`（`derive(Debug)` 会给 `R` / `W` 加约束），
  `Error::source()` 指回内层 `MuxError`，`From<MuxError>` 让 `?` 直通；生成逻辑收在
  `face_error_impls!` 里，每个面只给一张「变体 → 中文说明」表。
  > **后续（2026-10-03）**：`face_error_impls!` 已删除，全部错误类型改用
  > `thiserror`（`#[derive(thiserror::Error)]`；面包内层用
  > `#[error(transparent)] + #[from]`，与旧宏生成的 `Display` / `source` /
  > `From<MuxError>` 逐项等价）。文案逐字未变，回归由 `connection::error_` 的
  > 单测钉住。
- 注册表的 `bind_dock_` / `reserve_*` 改返回 crate 内部的 `ReserveErr_`
  （`DockInUse` / `Duplicate` / `WaitClose` / `DockChanLimit` / `ChanLimit`），由各面
  映射进自己的枚举（`binding_` 的 `map_reserve_err_`）；`MuxError::cast_` 因此删除。
  `FailKind_` 同步收窄为循环能产生的种类。
- `ReservedDock` 的归属按 19.7 的更正：`BindError`（local dock）与 `BindingError`
  （`open_channel` 的 remote dock，身份的一半）；telegraph 的面不带它。
- 连带代价：面错误类型的 `Default`-less `Error::source()` 需要内层 `'static`，因此
  五个面的 trait impl 与相关 step fn 补了 `R: 'static` / `W: 'static`（连接本来也
  只以 `'static` 传输构造，无实际收窄）。

验收：`mux_ring_rejected_{tokio,compio}`（新增，中文注释按纪律写）——响应方给容量
`1` 的缓冲裁决（环下限 `2`）必须得到 `HandleError::RingRejected`，主动方得到
`HandleError::Refused`，且**同一条连接**上随后正常建流成功（拒绝路径没有弄脏连接与
注册表）。全量：check / clippy `--all-targets` 零告警、doc 零警告、74 单测 + 12 inmem +
2 layered + 2+2 smoke + 5 doctest 全绿。

> 待业务反馈：各面变体的**具体形状**（哪些失败真的会出现、要不要合并）以真实使用为准，
> 本轮只做「按面拆开」这一步。

### 19.9 跟随上游「allocator 进 accept」的重构（进行中）

上游 `abs_smux` 已把「为用户内存准备指针」改成「调用方在 `accept_async` 里交出**分配器**」
（`fn accept_async<'f, W, A>(&'f mut self, welcome, alloc: A) where A: Allocator`），
`TrAcceptBuff` 整个消失，`TrMuxConfig` 上移成上游概念（`Data` / `Dock`），公开类型收敛到
`<C, S>`（配置 + 本地作用域）。

人类裁决（本轮）：**把承载 ring 内存的智能指针里的 `A` 参数擦除成 `dyn Allocator`**。

#### 19.9.1 落地内容

- 上游 `chan.rs`：`A` 的约束补成 `'static + Allocator + Send + Sync`。理由：擦除要求把
  分配器**拥有**进载体；用借来的分配器分配的环内存活不过这次调用，而半部类型里没有生命
  周期位置表达这一点（`A: 'f` 不足以支撑「内存活得比调用久」）。`Send + Sync` 是因为半部
  随连接跨任务移动。
- `ring_.rs` 新增 `MuxChanBuff`：`ptr_ + cap_ + layout_ + Arc<dyn Allocator + Send + Sync>`。
  `pair_from_alloc_(alloc, capacity)` 一次造 Tx / Rx 两块并**共享**同一份擦除分配器
  （因此不要求 `A: Clone`）；实现 `Borrow` / `BorrowMut<[MaybeUninit<u8>]>`（环要求）与
  `Drop`（按 vtable `deallocate`）。先在一次性探针工程里验证过 `dyn Allocator` 的对象安全
  与装箱 bound，才写进仓库。
- `TrConnCfg`：新增 `const RING_CAPACITY`（容量不再由调用方按次决定——接口上只剩分配器）
  与 `fn make_ring_buffs<A>(alloc, capacity) -> Result<(Buff, Buff), AllocError>`（默认走
  `MuxChanBuff`，环境也可以声明零开销的自有 `Buff`）；`Buff` 的 bound 补 `Send + Sync + 'static`。
  `DefaultConnCfg` 收敛为 `<W, R, P>`，`Buff = MuxChanBuff`。
- `accept_async` 收 `alloc: A`，在方法体里同步完成「造内存 + 建环 + 移交」；原
  `accept_buff_` 改为 `accept_alloc_`（容量不足或分配失败 ⇒ `HandleError::RingRejected`）。
