# 流控：卡死真因、修法与验收转绿（flow-ctrl）

> **本文件取代**已删除的 `flow-ctrl-20261004-1241.md` 与 `connection-20261122-0000.md`。
> 前者的 §2「三个嫌疑」经本轮实测**不是**卡死原因（见 §4）。
> 本轮结束时两个真实 socket 的流控验收用例（tokio / compio）**已去掉 `#[ignore]` 并转绿**。

## 结论先行

1. 人类要求的两条微调：**「取消 >3/4 静默」已落实**（§1.1）；**「信令循环侧主动扫描」
   按人类裁决暂缓**（§5，附「为什么字面形状做不到」）。
2. 真实 socket 流控验收的卡死有两个真因，**都不是**唤醒/去重位问题：
   - **§2（已修）** 复用循环搬出读段时只搬「当前物理段」，读指针靠近环末端时会把一条
     **正常**数据帧判成 `MalformedFrame`，`fail_mux_loop_` **终止发送方的复用循环**；
   - **§3（已修）** 接收侧「已消费量」按 `data_size` **采样差值**记账，被并发写入掩盖，
     额度被永久漏记；环已读空而窗口仍为 0，两端互等。
3. 治 §3 采用了人类选定的 **C 方案**：判定权交给**持有接收环写端**的解复用循环。
   一路上的两个施工要点（事件方向、`park` 不得吃掉事件）见 §3.1/§3.2。
4. 还剩一条**独立**的未决项：`CLOSE(RESET)` 会顺手拆掉对端的**接收**方向，从而丢弃
   本端仍在途的最后一个窗口（§3.3）。它不影响本轮验收形态，但属于承诺面漏洞。

## 1. 本轮输入与落实

### 1.1 取消「剩余 > 3/4 不提醒」（已落实）

接收侧的提醒政策**不再随水位放松**，只分两档：

| 区间 | 行为 |
| --- | --- |
| 剩余 ≤ `容量/N`（临界区） | 任何变化都提醒（不受变动量门限约束） |
| 剩余 > `容量/N` | 自上次提醒以来累计**变动量** ≥ `min_advance` 才提醒（防抖） |

改动落点：`RecvWindow::should_report_with_` 删掉「充裕区不提醒」分支与「进入更紧分区」
特例；`Zone_` 由三变体收敛为 `Normal / Critical`；`last_level_`、`tighter_than_`、
`report_in_zone_`、`ReportThresholds_::relaxed_above_` 全部删除（在「窗口没变 ⇒ 没新
信息」这条判据下它们都是冗余状态）；公开 trait `TrFlowCtrlPolicy::critical_denominator`
的文档契约同步收窄为「只决定临界区上界」，`min_advance_between_reports` 的适用范围由
「中间区」改为「临界区之外」。

**为什么必须取消**：一旦本端停止更新通告，对端的可用额度就永远停在旧快照上，连「本端
消费掉多少」都传不过去。实测里 `available == 0` 与「环里有数据」可以长期共存。

### 1.2 主动扫描（按裁决暂缓，理由见 §5）

## 2. 卡死真因一：搬出读段时只搬了「当前物理段」（已修）

`drain_one_` 原来这样搬数据：

```rust
let take = segm.least_count();          // 逻辑长度
let mut child = segm.as_segm_ref();     // ← 只给出「当前物理段」
let moved = unsafe { child.move_items_to_buff(uninit) };
if moved != take { return Err(MuxError::MalformedFrame); }
```

`create_read_segm_` 在**读指针靠近环末端**时会构造一个横跨「环尾 + 环首」的**两段**
逻辑读段，`least_count()` 是**逻辑**长度；而 `as_segm_ref()` 只暴露第一段。于是
`moved = take − 首段长 < take`，一致性检查把一条正常数据帧判成帧格式错误：

```text
DBG-FLOW TXREADY (Dock(20481),Dock(1))
DBG-FLOW TXREADY (Dock(20481),Dock(1))
DBG-FLOW FAIL MalformedFrame          ← 复用循环就此退出
```

**修法**：直接对读段本身调用 `move_items_to_buff`——`ReclSliceRef` 的实现会自己按物理
段循环，直到搬够 `take`（`ChildReclaim` 在子段 drop 时把已搬量累加回父段的 `offset_`）。

> 教训：**逻辑段与物理段是两个概念**。`ChannelRx::read_exact` 里同款写法是安全的（它按
> `child.least_count()` 夹住 `dst` 并在外层循环补齐），但**不能**照抄到「一次搬完」的场合。

## 3. 卡死真因二：消费量按水位采样记账（已修，方案 C）

原写法（`ChannelRx`）：

```rust
let now = self.ring_.ring_state().data_size();
let delta = self.last_data_.saturating_sub(now);   // ← 净水位差值
self.last_data_ = now;
if delta > 0 { /* 投 RxConsumed */ }
```

`data_size` 是**净**水位：只要两次采样之间既有读出又有写入，差值就退化成 0，那一次消费
被永久漏记。稳态恰好是这个形状——对端每拿到一份「+64 的额度」就写回等量字节，正好把应用
刚读掉的顶回去。实测终局：

```text
DBG-FLOW WU pair=(20481,1) r=1792 w=0 ok=true avail=0
DBG-FLOW NOTECONSUMED (1,20481) now=0 last=0 delta=0     ← 接收环已读空
DBG-FLOW PARK 22                                          ← 两端都在睡
```

即**接收环 `data_size == 0`，而通告窗口仍是 0**，差了整整一个容量的额度被漏记。

### 3.1 修法：判定权归持有接收环**写端**的解复用循环

「累计已消费量」= `RecvWindow` 记账的累计已收 `R` − 环内实际积压 `buffered`。解复用循环
是接收环**唯一的写入方**，两个量都在同一个任务里读，因此这个差值**精确**。落实成三件事：

1. **事件方向翻转**：`WriteEvent_::RxConsumed`（带 `amount_`）**删除**，
   新增 `ReadEvent_::RxConsumed`（**裸通知**，不带增量）——应用侧只投「去看看」，
   判定与出通告都在解复用循环里完成（通告仍走 `WriteEvent_::Control` 交给复用循环写出）。
   这与旧日志 §4「`ChannelRx` 不投瞬态数值」的既定结论一致。
2. **应用侧去重位**：`ChannelOwner_` 新增锁外的 `rx_consumed_`（与 `tx_queued_` 同构），
   保证每条子流至多一条待处理通知。消费方必须**先清位、再读环内积压**（顺序不可反），
   这样清位之后发生的消费会重新置位并投递，不会丢。
3. **解复用循环的 park 同时等读事件通道**：`RxConsumed` 到来时连接读环完全可能长期为空
   （对端正等额度、没有新帧），只 park 在环上会让通知一直排在一条睡着的循环后面。
   新增 `park_read_wake_`：把「取消 / 读事件 / 连接读环」三个 future 都在闭包**外面**
   `pin` 好再 poll。

   > 三个 future 必须在闭包外 pin：环的 park future 在 drop 时**撤回**自己的唤醒登记
   > （`buffex::ring` 的等待槽是**单槽信箱**），「就地建 future、poll 一次、丢掉」等于
   > 只问一句「此刻可读吗」，留不下任何唤醒。这也是 §5 里「主动扫描」按字面做不到的
   > 同一个原因。

### 3.2 施工中的坑：park **取出**的事件不能被丢掉

`park_read_wake_` 的第一版把事件从通道里取出来之后当成「有个事件」的信号就丢了。
`flume` 的异步接收是**消费**语义，丢掉即静默吞掉这条 `Attach`：

```text
DBG2[0x…58b8] DISPATCH Data pair=(Dock(1), Dock(8193)) known=false tablelen=0
DBG2[0x…58b8] NOENTRY -> is_wait_close (Dock(1), Dock(8193))
```

附加事件被 park 吃掉 ⇒ 本地表没有表项 ⇒ 随后到达的数据帧掉进「未知子流」分支 ⇒ 卡在
注册表锁上（0% CPU 的死锁）。**被 `mux_min_stage_inmem`（1 字节帧暂存）稳定复现**，
这正说明那条用例的价值。

修法：`ReadWake_` 带出事件本身（`Event(ReadEvent_<..>)`），循环**就地**用
`handle_read_event_` 处理；成批排空 `drain_read_events_` 与它共用同一个单事件处理函数。
这与复用循环里 `taken` + `handle_write_event_` 的形状完全同构。

### 3.3 未决：`CLOSE(RESET)` 会拆掉对端的**接收**方向

修完 §3 之后验收用例不再死锁，改为**读少一个窗口**：

```text
DBG3 CLOSE reset=true pair=(Dock(1), Dock(20481))
DBG3 READ-FAIL after 65024 bytes: Closing        ← 65536 − 512
```

原因是一条**正常用法**：应用写完载荷、`drop(tx)` 之后，作用域结束顺带丢掉了 `rx` 半边 ⇒
本端发 `CLOSE(RESET)`；而对端收到 `RESET` 时会

- `entry.writer_.close()`（关掉**自己的接收环写端**）——于是本端仍在途的最后一个窗口
  被丢弃；
- 本端复用循环在 `RxClosed` 分支里还 `table.remove(&pair)`——把**发送方向**尚未排空的
  表项一起摘掉。

这与 README §5「写进环的字节是承诺要送达的」相冲突：只丢 `rx` 不该让已经承诺的字节消失。
两种修法：

| 方案 | 做法 | 影响面 |
| --- | --- | --- |
| **半 RESET** | 对端处理 `CLOSE(RESET)` 时**只**置 `peer_reset_`、**不**关接收环写端（接收方向仍由 `FIN` 收尾）；本端 `RxClosed` 不再 `table.remove`，改走既有的 `pending_fin` 排空后再发 `FIN` | 改协议帧语义：`FIN` = 我不再发（关对端接收），`RESET` = 我不再收（关对端发送），两者正交 |
| **测试侧持有 `rx`** | 场景文档本来就只声明「丢发送半边」，因此让 `a_side` 把 `rx` 交还调用方持有到 `join!` 结束 | 不改库；但「写完后立刻丢两半」这一正常用法仍会丢最后一个窗口 |

**本轮裁决（人类）**：**先不动**，采用「测试侧持有 `rx`」走通验收
（`tests/common/mod.rs` 的 `run_flow_ctrl_socket_scenario_` 已加注释说明）；
**半 RESET 记为后续项**，语义与改法留档于此，不动协议帧语义。

## 4. 对旧日志「三个嫌疑」的实测否证

仪器化后的完整链路（`WINDOW_UPDATE` → `SendWindow::on_report` → 投 `TxReady` → 复用
循环醒来）实测**全部正常**：

```text
DBG-FLOW WU pair=(20481,1) r=512  w=64  ok=true avail=64
DBG-FLOW TXREADY (20481,1)
DBG-FLOW PASS 7 last_ready=Some((Dock(20481), Dock(1)))
DBG-FLOW SENT pair=(20481,1) take=64 avail_was=64
```

- 通告**都**被接受（`ok=true`）并算出正确的 `avail`；
- 读循环投的那条 `TxReady` **不经过「已入队」去重位**，逐条都送达并唤醒复用循环；
- 因此「唤醒被去重位静默丢掉」「`drain_one_` 清位吞掉写入」在本用例里**不是**观测到的
  事实；「待发送/待唤醒缺显式状态」也**不是**本轮的必要修法——真凶是 §2 与 §3。

## 5. 主动扫描：暂缓（附「字面形状做不到」的原因）

人类要求的形状是「一轮事件处理中没有收到任何水位提醒，就主动扫描所有子流缓冲区并搬出
数据」。**搬出**本来就由复用循环第 2 步 `drain_once_` 全表遍历完成；缺的是**唤醒**：

- 子流环的唤醒登记只有 `park_async` 一个入口，且它的 future 在 **drop 时撤回登记**
  （`buffex::ring::half_` 的 `ConsumerParkFuture::drop` → `withdraw_`，等待槽是单槽
  信箱）。因此「在 park 闭包里对每条环 poll 一次 `read_async` 再丢掉」只会得到「此刻
  是否可读」，**留不下任何唤醒**——与第 2 步已经做过的事重复，等于空转。
- 要让全表扫描真正兜住唤醒，只有两条路：
  1. **跨 poll 持有 N 个环 future**：这些 future 借用本地表里的读端半部，要存下来就得
     自引用/重排本地表（本模块刻意避免的结构）；
  2. **给「待发送」一个显式状态**：应用侧**无条件**置位一个「可能有数据待搬」的位
     （去重位只用来合并风暴），复用循环被叫醒后全表扫描，扫描完再清位并复检。

人类裁决：**暂不做，留作后续加固项**（`tx` 侧目前没有观测到丢唤醒；等出现新证据再做）。
§3 验收已经通过，本条不再是任何验收的阻塞点。
