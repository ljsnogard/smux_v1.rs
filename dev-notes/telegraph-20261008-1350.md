# telegraph 并发验收暴露的两个真 bug：写侧半帧、收尾唤醒缺口

> 主题：`connection::telegraph` 的**发送原子性**与**接收侧收尾唤醒**。
> 触发场景：`smux_v1_sock_demo` 新增的「同一连接上 channel + telegraph 并发」验收项
> （见 `smux_v1_sock_demo/dev-notes/mix-telegraph-20261008-1348.md`）。
> 两个 bug 都是**间歇性**的、只在「大负载 + 数据报并发」下出现，且**症状都不指向自己**：
> 一个表现为对端报「帧格式非法」，另一个表现为应用侧永久 park。

---

## 0. 怎么被发现的

给 demo 加完混合项后：

| 配置 | 结果 |
| --- | --- |
| 小负载（1 子流 × 64 KiB，telegraph 8 帧） | 稳定通过 |
| 大负载（8 子流 × 8 MiB，telegraph 16 帧），`tokio/compio` | **约 1/3 ~ 1/4 失败** |
| 同大负载，**不开**混合项的基线 | 4/4、3/3 稳定通过 |

失败时的证据（由 demo 的 metrics 采集）：

1. 一端报 `复用帧包含未知或非法的字段`（`kind=None`，即帧首字节不是合法种类）→
   **帧流错位**；
2. 同一时刻另一端的 telegraph 侧报 `第 1 帧第 169 字节与确定性载荷不符` →
   数据报**内容被污染**；
3. 另一端则表现为 `run_phase` 永不返回（超时被杀）。

---

## 1. Bug 1：`write_frame_to_stage_` 会往写环里留下**半个帧**

### 1.1 根因（三个叠加的缺口）

`session_.rs` 的 `write_frame_to_stage_` 负责把一条 telegraph 的「帧头 + 载荷」写进连接
写环，它的文档写着「要求整帧放得下才动手，否则整帧推迟」——但实现只覆盖了**总空间**：

```rust
if ring_space_(tx_stage).unwrap_or(0) < total { return Err(Closed); }  // 只判总量
let writable = tx_stage.try_write(&Demand::at_least(total))...;         // ← 两片视图
let mut dst = writable.as_segm_mut();                                   // ← 只取当前物理片
// 写帧头（写不完就 return Err，但帧头已经写了一部分）
// 然后再去借载荷段（借不出也 return Err，此时帧头同样已经写出去了）
```

1. **借段顺序错了**：帧头**先**写进写环，载荷段**后**借。后者失败（源环关闭 / 借不出）时
   直接 `Err`，而写环里已经躺着一段没有载荷的帧头；
2. **跨物理片没处理**：`try_write` 返回的是覆盖「当前可写区」的两片视图（`ReclSliceMut`
   内含 `pieces`），而 `as_segm_mut()` 只把**当前那一片**交出来。当 `wp → 环尾` 的那一片
   小于 `total` 时，帧头 + 载荷写不完，`put == 0` 就 `Err`——同样留下残片；
3. **载荷搬运不完整**：`move_items_to_segm` 只搬「源片与目标片都能容纳」的量，
   `moved != take` 时也 `Err`，还是半帧。

「整帧推迟到下一轮」这个意图是对的，但它要求**在写出第一个字节之前**就把所有可能失败的
事情做完；实现把最容易失败的「借载荷段 + 跨片搬运」放在了写帧头之后。

### 1.2 为什么大负载才触发

写环容量 64 KiB、telegraph 单帧只有几百字节，所以「总量不足」几乎不会发生——但
**「第一片不足」与「借段失败」**在写环频繁接近满 / 回绕时概率显著上升：小负载下写环几乎
总是空的、`wp` 也很少贴着环尾；8 × 8 MiB 的并发流量让它一直处于「快要满 + 反复回绕」的
状态。混合项只是把这种状态**稳定地**带进了验收。

### 1.3 修法

```rust
// ① 先把载荷段借到手：一切可能失败的借段都发生在写第一个字节之前
let mut payload_segm = entry.reader_.try_read(&read_demand)...;  // 失败 → 写环未动
// ② 帧头：段级循环，写满当前片就换下一片（跨片由循环承担）
while !head_left.is_empty() { ... tx_stage.try_write(&Demand::at_least(1)) ... }
// ③ 载荷：同样段级循环；每轮按**剩余长度**用 take_segm_ref 精确裁剪源段再搬
while left > 0 { ... let piece = src.take_segm_ref(&Demand::exactly(left))...; dst.move_items_from_segm(&mut piece) }
```

- 借段前移之后，**提前返回时写环一个字节都没写**；
- 段级循环让「整帧」不再要求「落在同一物理片里」：写环总空间已判够、且本循环是它唯一的
  写入者，因此循环必然推到底，跨片不再产生残帧；
- 载荷的精确裁剪保留了旧修复（`move_items_to_segm` 是整段搬运，不裁剪会把下一条报文的
  载荷一起吃进这一帧）。

代价：帧头与载荷现在可能分多次借段（多次原子操作），不再是「一次借段写完」。telegraph
帧小、条数少，这点开销可忽略；换来的是**构造上不可能留下半帧**。

## 2. Bug 2：接收侧收尾**唤不醒** park 中的接收者

### 2.1 根因

`telegraph::recver_` 的 `recv_async` 循环里，park 的是**接收队列的持久通知位**：

```rust
if let Some((_, len)) = rx.ctx_holder_.in_().try_pop_() { ... }
if let Some(reason) = fail_kind_() { return Err(...) }                 // 只有「连接级失败」兜底
if rx.ring_rx_.ring_state().is_producer_closed() { return Err(RxClosed) }
let wait = poll_fn(|cx| rx.ctx_holder_.in_().poll_wait_(cx));          // ← park 在队列通知上
race_cancel_(&cancel, wait).await
```

而连接**正常收尾**时只做了 `TgRecvCtx_::close_()` 里的 `writer_.close()`：关闭接收环写端
**不会**置位队列通知位。于是：

- 环确实关了、`is_producer_closed()` 也确实是 `true`，
- 但正 park 在队列通知上的接收者**没有任何人被叫醒**去看它；
- `fail_kind_()` 只在连接被判失败时置位，**正常收尾**恰恰不置位。

症状就是「一端已经正常收尾并退出，另一端 `run_phase` 永不返回」。

> 这与 channel 的接收侧不同：`ChannelRx` park 在**环**上，环关闭会唤醒环的 park。
> telegraph 的接收侧 park 在**队列**上，所以「关环」必须额外带一次队列通知。

### 2.2 修法

```rust
pub(crate) fn close_(&mut self) {
    self.writer_.close();
    self.owner_.in_().notify_();   // 「不会再有报文了」也是一次队列状态变化
}
```

`close_()` 的两个调用点（循环退出守卫、身份自查摘表）因此都覆盖到了。

## 4. 教训

1. **「原子性」的注释必须逐条对着失败路径审**：`write_frame_to_stage_` 的文档写了
   「整帧放得下才动手」，但实现只判了总量、没判跨片，也没把「借载荷段」放到写之前——
   注释描述的是**意图**，不是**不变量**。
2. **同名字段/同一动作在两侧语义相反**（承接本目录 `telegraph-20261007-1630.md` §3.1 的
   教训）：这次的「帧流错位」与「内容错位」是**同一个**半帧在两侧的不同表现——写侧多写了
   半帧，读侧就会在载荷中间找到「帧首」。
3. **唤醒条件要写全**：park 在 A 上、状态却由 B 改变时，**B 的每一次不可逆变化**都要带上
   对 A 的通知；「关环」与「连接失败」是两条不同的收尾路径，只覆盖一条就会留下一个只在
   正常收尾时出现的死等。
