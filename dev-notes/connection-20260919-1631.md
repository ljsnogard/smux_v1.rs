## 【设计约定】运行时：可以 spawn，但必须经 `abs_art`（不用 `abs_art-bridge`）

- `smux_v1` **允许** spawn / delay / join，目的是让实现简洁易懂；但**必须经由
  `abs_art`**（`no_std` 的能力位抽象：`Runtime<CAPS>` + `TrSpawnSend` /
  `TrSpawnLocal` / `TrDelay` / `TrJoinHandle`，见 `abs_art/abs_art/src/{caps.rs,runtime.rs}`）。
- **不依赖 `abs_art-bridge`**：bridge 的规则是「必须且只能启用一个后端」，会把
  后端选择传染给所有下游；直接依赖 `abs_art` 则由**最终二进制**决定后端。
- 因此 `MuxConnection` **内部自行 spawn** 读 / 写两个循环，并在内部持有
  `JoinHandle`。**`drive_async` 是错误的设计**——最终用户不应知道它的存在；对外
  只有 `abs_smux` 的 `TrConnection` / `TrDockBinding` 这套 trait。
- 生命周期：连接关闭时 abort 内部任务；设备/网络错误经内部注册表回传给被动端，
  避免被动端等待一个已经死掉的循环。
- **线程模型优先级**：`smux_v1` **首先保证单线程运行**（**compio 是首要适配目标**）；
  多线程是**额外的 feature**，且**不一定在近期执行**。因此适配 tokio 时，必要时
  可以**全部选用 `spawn_local`**（不要求 `Send`），不必为了 `Send` 牺牲实现的简单性。
- 注：socket / buffex 主动端的缺陷与方案不在本文件展开，见
  `buffex/dev-notes/circ_buff-20260919-1849.md`。

## 【设计约定】`MuxConnection` 的运行时参数与共享状态（方案 A 落地）

**前提**：`abs_art` 已升级到 **0.3.0**（方案 A：`TrSpawnSend` / `TrSpawnLocal` 的
`spawn<F>` / `spawn_local<F>` 为**方法级泛型**，`JoinHandle<T>` 仍按输出参数化），
`smux_v1` 已依赖 `abs_art` 的 `dev/0.3.0` 分支，且**不依赖 `abs_art-bridge`**。
实验依据见 `abs_art_backend_exp/dev-notes/abs_art-20260919-2021.md` 与
`abs_art-20260919-2039.md`。

### 1. 运行时类型参数 `Rt`

- `MuxConnection<R, W, C>` → **`MuxConnection<R, W, C, Rt>`**；`DockBinding` 持有
  `&MuxConnection<..>`，因此同样带上 `Rt`。
- `Rt` 必须是**结构体类型参数**，不能只做 `new` 的方法级泛型。（当初的理由是
  「`<Rt as …>::JoinHandle<()>` 要存成字段」；**该理由已被 §8.1 推翻**——句柄不再
  入字段。但结构体参数这一条仍然成立，理由换成：`Rt` 要跟着 `MuxConnection`
  一路出现在 `DockBinding` / `Listener` / `Telegraph` 等派生类型的签名里。）
- 约束按目标切换：缺省（**单线程、compio 首要**）`Rt: TrSpawnLocal`；
  `multi-thread` feature 下换 `Rt: TrSpawnSend`；若保留空闲超时再加 `Rt: TrDelay`。
- **后端由最终二进制选择**（`abs_art_tokio::Runtime<{…}>` / `abs_art_compio::Runtime<{…}>`），
  smux_v1 内部不出现任何后端名；同一二进制可同时用两个后端（实验 `app_multi_backend` 已证）。

### 2. 共享状态用 `mm_ptr::Shared`（人类决策）

`JoinHandle<T>` 带 `where T: 'static`，且 `spawn` 出去的 future 必须 `'static`，
所以**两个循环不能借用 `MuxConnection`**，必须自己拥有所需状态：

- `Rx` / `Tx` 分别移进对应的内部循环；
- 子流注册表、配额、控制帧队列、窗口等改为**共享句柄
  `mm_ptr::Shared<T, A>`**（与 `buffex` 内部同款，走调用方注入的分配器，单线程与
  多线程两种模型都能用）；
- 新建 `connection/sync_.rs` 承载这一层（目前尚不存在）。

### 3. 任务生命周期与错误回传

- ~~连接 `Drop` 时如何停止两个任务：需确认 `TrJoinHandle` 是否提供 `abort` /
  `detach`。~~ **已确认并改设计**：`TrJoinHandle` **没有 `abort`**，只有
  `detach`；且三个后端对「drop 句柄」的语义不一致（tokio = detach、compio / smol
  = 取消）。因此收尾改为「**取消令牌 + 连接已失败标志**，spawn 后当场 `detach()`」，
  句柄不入字段。推导见 §8.1。
- 循环出错（对端关闭 / 帧非法 / 流控违例）必须让 `bind_async` / `income_async` /
  子流收发**感知并被唤醒**，不能永远 park：需要一个「连接已失败」的共享标志 +
  唤醒机制，与 `sync_` 层一并设计。

### 4. 接线与测试

- 冒烟测试要传 `Rt`：dev-dependencies 增加 `abs_art-tokio` / `abs_art-compio`
  （`abs_art-bridge`(backend-compio) 仍留给握手测试）。
- `MuxConnection::new(delivery, config)` 的调用点随之调整。`new` **不需要运行时值**——
  `abs_art` 的 spawn 方法是**无 `self`** 的关联函数，`Rt` 纯类型即可。

### 5. 落地顺序

1. ~~把 `Rt` 加进 `MuxConnection` / `DockBinding` 与各 impl，并定 `multi-thread`
   的 bound 切换~~（**已完成**，见 §8.2）；
2. ~~接线测试（dev-dep 与调用点）~~（**已完成**：dev-deps 加了
   `abs_art-tokio` / `abs_art-compio`，冒烟测试传入各自的 `Runtime` 标记类型）；
3. 新建 `connection/sync_.rs`：`mm_ptr::Shared` 共享句柄 + 唤醒 + 「连接已失败」标志

### 3.1 `TrMuxConfig`

「环存储类型 `B`、分配器 `A`、流控策略 `P`」在整个连接里是同一组，因此打包：

```rust
pub trait TrMuxConfig {
    type Buff: BorrowMut<[MaybeUninit<u8>]> + Send + Sync;
    type Alloc: AllocatorClone + Send + Sync;
    type Policy: TrFlowCtrlPolicy;
    fn allocator(&self) -> Self::Alloc;
    fn policy(&self) -> &Self::Policy;
    fn channel_capacity(&self) -> usize;
}
```

公开类型因此只有 `MuxConnection<R, W, C>` 三个参数，而不是五个。

### 3.2 帧字段编码（本轮定稿，见 §7）

`head = (flags << 4) | kind`，其余字段 `header = (val_type << 4) | field_id`：

- 帧首字节（位置固定）：低 4 位 `kind`（`0x01..=0x09`，`0x00` 与 `0x0A..=0x0F`
  保留）、高 4 位 `flags`（`FIN` / `RESET` / `ACK` / `NO_PAYLOAD`）；
- `field_id`（低 4 位）：`LocalDock = 0x00` / `RemoteDock = 0x01` /
  `PayloadLen = 0x02` / `WindowUpdate = 0x03` / `ReasonCode = 0x04`，
  `0x05..=0x0F` 保留；
- `val_type`（高 3 位）：复用握手的 `NegotiationValType`，1/2/3/4/8 字节大端；
  发送方取能容纳数值的**最小**宽度，接收方接受任意足够宽的编码；
- dock 字段只接受 1/2/4 字节宽度（`BeU24` / `BeU64` 非法），其余字段不限宽度；
- `PayloadLen` 必需且**必须最后出现**：它是字段序列的定界符（见 §7.2）。

### 3.3 会话派生类型的生命周期占位

`ChannelListener` / `ChannelHandle` / `Telegraph` 用类型别名
`SessionMark_<'s, 'f, R, W, C> = PhantomData<(&'s &'f (), fn() -> (R, W, C))>`。
`&'s &'f ()` 把 `'f: 's` 编码进类型：它们派生自「借用了连接的会话」，因此连接
借用的生命周期必须覆盖类型自身。这样 `Self: 'i` 就能推出宏生成类型所需的
`'f: 'i`，无需在每个 impl 里手写 `'f: 's`。

### 3.4 数据面的错误

子流半边是 `buffex` 端半部的薄包装，`Err` 直接就是 `ConsumerError` /
`ProducerError`（已实现 `TrTaggedError<ReadErrTag/WriteErrTag>`），不再包一层
`MuxError`。控制面统一用 `MuxError<RE, WE>`。

## 5. 调度决策与冒烟测试（同日追加）

### 5.1 控制帧与数据帧的公平性

**决策：控制帧优先级更高。** 先排空控制帧队列（`ACCEPT` / `REJECT` / `CLOSE` /
`WINDOW_UPDATE` / `PING`），再考虑数据帧。判据不确定时一律按「控制帧优先」处理。

理由：控制帧数量少，而且直接决定子流能否推进（`ACCEPT` 决定建流、`WINDOW_UPDATE`
决定对端能不能继续发）；让它们先走实现最简单，也不会造成饿死。这条判据留给中心
循环的写路径（`connection/mod.rs` §2）。

### 5.2 多个复用子流之间的公平性

**决策：按「对端发送窗口」定优先级——窗口越大，优先级越高。** 发送窗口为 0 的
子流本轮直接跳过。这样慢子流不会占住调度，带宽天然让给「对端还有余量」的子流；
判据是单调的、无需维护额外的时间片状态，实现与理解成本都低。已写入
`connection/session_.rs` 的写会话文档。

> 注：这是**发送侧**的调度判据，与 `flow_ctrl` 的窗口计算解耦——调度只读
> `SendWindow::available()`，不改窗口。

### 5.3 冒烟测试先行（TDD）

按「先写冒烟测试、再写逻辑」的安排，本轮新增集成测试（见 §5.3）：

- 两个真实异步运行时：**tokio** 与 **compio**；
- 通过 UNIX domain socket 建连，在其上完成握手协商 → 构造复用连接；
- 两端各向对端的 **16 个 dock** 发起 **1024 条并发 channel**，收发数据并校验；
- 连接层当前全是 `todo!()`，因此测试先以 `#[ignore]` 标记，实现落地后移除。

### 5.4 运行时适配

`smux_v1` 说的是 `abs_buff::TrBuffRead<u8>` / `TrBuffWrite<u8>`。设备侧适配器均已
就绪：tokio 用 `abs_buff_tokio_adapt`，compio 用 `abs_buff_compio_adapt`（后者为
本轮新增的独立 crate，提供 `TrInput` / `TrOutput` 与 `TrBuffRead` / `TrBuffWrite`
两套适配）。

需要注意的是**传输的组装方式**：把设备接进 `buffex` 环的「主动设备模式」在真实
socket 上不可用（compio 半边 `!Send`、tokio 侧握手实测 hang）。当前采用的传输形态
是「**全被动环 + 调用方驱动的 async 泵**」，可运行实现见 `tests/common/mod.rs`；
完整根因与方案见 `buffex/dev-notes/circ_buff-20260919-1849.md`。

## 6. 子流身份：dock 对即身份（人类决策）

**决策：`(local_dock, remote_dock)` 有序对就是子流身份。协议中不存在双方共识的或
任何一方分配的 channel id，也不需要——只需本方自己能从 dock 对里认出「是哪一条」
即可。**

推论（因此是协议约束，不是实现细节）：

1. **同一个 `(local_dock, remote_dock)` 上，同一时刻至多一条活动子流。** 发起方
   若把多条并发子流发往同一个 `remote_dock`，必须为它们分配**互不相同**的
   `local_dock`（临时 dock，类比 TCP 临时端口）；响应方在自己的 `local_dock` 上
   用请求帧里的 `remote_dock` 区分不同连接。
2. `max_dock_chan_count` 约束的是**单个 `local_dock`** 上的活动子流数（所以「一个
   dock 服务多条连接」是合法的），`max_channel_count` 约束整条连接上的总数。
3. **线格式不变**：帧头仍然只有 `LocalDock` / `RemoteDock` 两个 dock 字段，不加
   channel id。早期记录的「dock 身份歧义」至此关闭。

不引入 channel id 的理由：dock 已经是端口语义，再加一层 id 会让线格式、建流状态机
与两侧映射表各多一份需要同步维护的状态，而这些恰恰是最容易出错的地方。

落地位置：`connection/mod.rs` §4.1、`frame_.rs` 模块文档、`channel_.rs` 的
`DockBinding` / `ChannelHandle` 文档。

## 7. `frame_` 线格式决策（本轮实现时定稿）

实现 `frame_` 时发现骨架文档对「`Kind` / `Flags` 如何编码」自相矛盾：模块文档说
「发送方取能容纳数值的最小宽度」，而私有模块 `frame_` 里 `FieldId::accepts_val_type_` 的文档却说
「非 dock 字段一律只允许 `BeU16` / `BeU32`」。本节记录因此形成的四项决策与两处遗留。

### 7.1 帧首合并 `kind` 与 `flags`（人类决策）

- **骨架原状**：`FieldId::Kind = 0x00`、`FieldId::Flags = 0x01`，是两个独立的自描述
  字段，各占「1 个头字节 + 值字节」；按原字段文档（非 dock 字段只允许 2/4 字节）
  合计 6 字节，按最小宽度也要 4 字节。
- **决策**：合并成位置固定的帧首字节 `head = (flags << 4) | kind`（`kind` 低 4 位、
  `flags` 高 4 位）。
- **理由**：两者是**每帧必有**的定长信息，合并后只占 1 字节。
- **代价**（已知并接受）：`flags` 只有 4 位且恰好用满，没有扩展位；`kind` 不再是
  「自描述、可换序」的字段，而是位置绑定。
- **落点**：`compose_frame_head_` / `flags_from_frame_head_` /
  `K_KIND_MASK` / `K_FLAGS_MASK` / `K_FLAGS_SHIFT`；`FieldId` 删去 `Kind` / `Flags`
  并**重编号**为 `LocalDock = 0x00` … `ReasonCode = 0x04`（线格式尚未发布，无兼容
  负担，密集编号可避免「0x00/0x01 为何空缺」的疑问）。

### 7.2 `PayloadLen` 同时充当字段序列的定界符

帧首不再自描述 `kind`，字段序列就需要一个结束标记；沿用「读到 `PayloadLen` 即头
结束」的规则，于是 **`PayloadLen` 必须最后出现**。这对发送方是**硬约束**：字节流上
无法回退，若把它放在中间，接收方会把后续头字段当作载荷，整帧错位。
**未采纳**「帧头加长度前缀」：省下的正是这一字节，却要多维护一个两端必须同步一致的
字段。已用单测 `payload_len_terminates_the_header` 把该约定固定下来。

### 7.4 宽度策略：dock 限 1/2/4，其余按最小宽度（人类决策）

`accepts_val_type_` 原文把非 dock 字段限制为 `BeU16` / `BeU32`，会带来两个问题：
`ReasonCode` 白占 3 字节；`payload_len` 一旦超过 `u32::MAX`（`max_packet_size` 目前
**没有**上限）就无法编码。因此定为：

- 发送方取能容纳数值的**最小**宽度，接收方接受任意足够宽的编码（与握手一致）；
- dock 字段额外限制为 1 / 2 / 4 字节：`Dock<u32>` 的数值语义是规范的，3 / 8 字节
  没有对应类型（`Dock::value()` 返回 `u32`，也取不到这种值）。

### 7.5 遗留一：`ReasonCode` 只校验不保存

`abs_smux` 的 `TrChannelHandle::reject_async(reason: &mut R)` 把拒绝理由当作**载荷**
传递，因此数值型 `ReasonCode` 字段在当前 API 下**没有消费者**，`FrameHeader` 也没有
对应槽位（骨架设计即如此）。当前做法：发送侧不产出该字段；接收侧校验（只允许出现在
`REJECT` 上、取值必须能装进 `u8`）后丢弃。**待定**：删掉该字段，或给 `FrameHeader`
加槽位并让 `reject_async` 的理由走上线格式的数值通道。

### 7.6 遗留二：`flags::K_NO_PAYLOAD` 与 `PayloadLen == 0` 重复（**已关闭**）

该位表达的信息已被必需的 `PayloadLen == 0` 完整表达，而 `flags` 现在只剩 4 位。
**已关闭**：该位已删除，位 3 改作 `flags::K_TOTAL_RESET`（窗口通告的「累计量已重置」
变体，见 §11.2.3）。

### 7.7 重构：共享字节游标 `wire_io_`

`frame_` 需要与握手完全相同的一套「读满 / 写全」逻辑——其中包括把借出的
`MaybeUninit<u8>` 段搬进 `[u8]` 的 `unsafe`。为避免把这段 `unsafe` 抄第二份，抽成
crate 内部模块 `src/wire_io_.rs`：

- `ReadCursor::{read_byte_async_, read_async_}`、`write_all_async_`；
- 错误类型保持中立（`CursorError<RE, WE>`）：握手侧映射为 `WireError`，复用侧映射为
  `MuxError`，两边调用点都能继续直接用 `?`；
- 握手侧原有的 `FrameCursor` 与本地 `write_all_` 删除，改用共享实现；随之删掉不再
  需要的 `Demand` / `TrBuffSegmMut` / `TrBuffSegmRef` / `TrMayCancel` 导入。
- **验证**：重构后 22 个握手单测与 4 个文档测试重跑全绿，证明行为未变。

### 7.8 上游：`abs_smux::dock::Dock::value()`

帧编解码必须把 dock 还原成数值，而 `Dock<T>` 的字段私有、原本没有任何取值入口
（`Dock::new` 只能反向构造，`Dock` 也没有 `Deref`）。因此在 `abs_smux` 增加
`pub const fn value(&self) -> T`，本地联调走临时 `[patch]`（见 §2）。

## 8. 运行时参数 `Rt` 落地（本轮）

### 8.1 停止两个循环：取消令牌 + 当场 `detach`（人类决策）

约定 §3 留了一个待确认问题：「连接 `Drop` 时如何停止两个任务？需确认
`TrJoinHandle` 是否提供 `abort` / `detach`。」核查 `abs_art` 0.3.0 的结论是**原设计
不成立**：

- `TrJoinHandle<T>` **没有 `abort`**；只有 `detach(self)`，以及它自身是
  `Future<Output = Result<T, JoinErr>>`（可 await join）；
- 三个后端对「**drop 句柄**」的语义**不一致**（`abs_art/src/runtime.rs` 的文档写明）：
  - tokio：drop = detach，任务继续在后台跑；
  - compio：drop 会 `cancel(true)`，任务被取消；
  - smol：drop 会 `set_canceled()`，任务被取消；且 `spawn_local` 的任务随句柄存亡。

也就是说「持有句柄 → 关闭时 abort」这条路没有 API 可走，而「持有句柄 → drop」会让
同一份 smux 代码在 tokio 与 compio 上有**不同的关闭语义**。因此改为：

- `MuxConnection` 只持有**取消令牌 + 「连接已失败」共享标志**（随 `sync_` 落地）；
- spawn 之后**立即 `detach()`**：句柄不入字段；
- 循环在**每个 await 点**经 `may_cancel_with(令牌)` 检查取消与失败标志，自行退出；
- 连接 `Drop` 时置位即可；设备 / 网络错误经失败标志回传给被动端。

**顺带的好结果**：既然句柄不入字段，`Rt::JoinHandle` 就不必出现在任何类型签名里，
于是不需要为它取名，也就不需要额外引入「公开 trait 别名」来统一
`TrSpawnLocal::JoinHandle` 与 `TrSpawnSend::JoinHandle`（约定 §1 里
「`<Rt as …>::JoinHandle<()>` 要存成字段」这条理由随之作废；`Rt` 仍然必须是结构体
参数，理由换成：它要跟着连接出现在所有派生类型的签名里）。

### 8.2 `Rt` 参数化怎么落地（人类决策：两份 `#[cfg]` 的 impl）

- **改了哪些类型**：`MuxConnection<R, W, C>` → `<R, W, C, Rt>`、
  `DockBinding<'f, …>`、`SessionMark_<'s, 'f, …>`，以及由它派生的
  `ChannelListener` / `ChannelHandle` / `Telegraph` 与全部 trait impl 的关联类型
  （含 `gen_may_cancel_future` 生成的 `MuxBindAsync` / `MuxSendAsync` 等）。
  共 `channel_.rs` 50 处、`telegraph_.rs` 10 处插入 `Rt`。**`ChannelTx` / `ChannelRx`
  不必改**——它们只带 `<H>`（`buffex` 端半部）一个参数。
- **字段占位**：`MuxConnection` 加 `rt_: PhantomData<fn() -> Rt>`。用 `fn() -> Rt`
  而不是 `PhantomData<Rt>`：前者对 `Rt` 只要求 `Sized`，不会把 `Rt: Send` 之类的
  约束传染给连接对象（连接是否需要 `Send`，由缺省 / `multi-thread` 模型各自决定）。
- **bound 切换**：按人类决策，**不新增公开项**，把「会 spawn 的那个 `impl`」写成两份
  `#[cfg]`：缺省 `Rt: TrSpawnLocal`、`multi-thread` 下 `Rt: TrSpawnSend`。其余 impl
  不带任何 `Rt` 约束，因此 `Rt` 只在真正 spawn 的那一步收窄。两份 impl 里只有
  `new` 一个方法，多线程版文档指向缺省版以避免语义漂移。
- **测试接线**：dev-deps 增加 `abs_art-tokio` / `abs_art-compio`（与 `abs_art` 同一个
  gitee `dev/0.3.0` 源，保证是同一套 trait）；两个冒烟测试各自定义
  `SmokeRt = Runtime<{ SPAWN_SEND | SPAWN_LOCAL }>`——同时声明两种能力，同一份测试

  cfg 选择的 bound 别名 `TrSmokeRuntime`，与 `smux_v1` 的 feature 对齐。
- **纯签名改动、行为不变**：`new` 仍是 `todo!()`，34 个单测与 4 个文档测试在两种
  feature 配置下都仍然全绿（见 §4）。

### 8.3 顺带修掉的两处过时内容

## 9. 子流半边的关闭态：直接读环的两端（本轮）

### 9.1 问题

`TrChannelHalf` 要求每个半边都能回答 `is_tx_closed` / `is_rx_closed`，而一条子流
的**两个方向各有一条环**（发送环：应用端是 [`ChannelTx`] 的生产端、另一端在写会话；
接收环：会话端是生产端、应用端是 [`ChannelRx`] 的消费端）。于是「本半边的**另一个
方向**是否已关闭」看起来必须靠一份跨半边的共享状态，也就是说：

- 要么给半边再加一个共享句柄参数（`ChannelTx<H, S>`）——但那会打破「薄包装 / 只带
  `<H>`」的定位，也把 `sync_`（第 6 步）提前拖进来；
- 要么把这两个方法留成 `todo!()`，等 `sync_`。

### 9.2 决策：环自己就是那份共享状态

`buffex` 的每条环**本来就维护两个方向的关闭位**，而且两端互相可见：

| 方法 | 语义 |
| --- | --- |
| `Producer::is_producer_closed()` | 本端（生产端）是否已关闭 |
| `Producer::is_consumer_closed()` | 对端（消费端）是否已关闭 |
| `Consumer::is_consumer_closed()` | 本端（消费端）是否已关闭 |
| `Consumer::is_producer_closed()` | 对端（生产端）是否已关闭 |

因此不需要第二份状态——**环就是那两个端共享的那点状态**，映射关系是：

| 半边方法 | 读的是 | 含义 |
| --- | --- | --- |
| `ChannelTx::is_tx_closed()` | `producer.is_producer_closed()` | 应用端不再发送（丢弃 `ChannelTx` 即置位，`buffex` 在半部 drop 时提交该事件） |
| `ChannelTx::is_rx_closed()` | `producer.is_consumer_closed()` | 写会话已关闭发送环的消费端，即会话拆掉了这条子流 |
| `ChannelRx::is_rx_closed()` | `consumer.is_consumer_closed()` | 应用端不再接收 |
| `ChannelRx::is_tx_closed()` | `consumer.is_producer_closed()` | 会话已关闭接收环的生产端，即对端不再发送（EOF） |

骨架里两句 `todo!()` 备注其实已经指向这个设计：「读发送方向关闭标志」= 读本端
标志，「（由会话标记）」= 读**另一端**的标志——而「另一端」正是会话持有的那个半部。
会话通过关闭 / 丢弃自己那一端来表达 FIN、RESET 与拆流，应用侧立刻可见。

### 9.3 代价与实现约束

- `is_producer_closed` / `is_consumer_closed` 是 `buffex` 半部的 **inherent 方法**，
  不是 `abs_buff` 的 trait 方法，因此 `TrChannelHalf` 的 impl **只能落在具体类型**
  `ChannelTx<BufferedTx<B, A>>` / `ChannelRx<BufferedRx<B, A>>` 上，泛型 `H` 上
  无法调用。`TrBuffWrite` / `TrBuffTryWrite` / `TrBuffRead` / `TrBuffTryRead` 的转发
  impl 仍然是泛型 `H`（它们只用到 trait 方法）。
  （上游已**删除** `abs_buff` 的 `is_stuffed_closing` / `is_drained_closing`；替代是
  `TrConsumerState` / `TrProducerState` 与 `RingState` 上的关闭标志，见 §12.3。）
- 关闭入口不新增 API：丢弃半边即半关闭；`buffex::ring` 提供**同步**的
  `RingWriter::close()` / `RingReader::close()`（= `close_producer` / `close_consumer`，
  幂等，并唤醒 park 中的对端），本 crate 原样转发。
- 构造入口 `ChannelTx::new_` / `ChannelRx::new_` 为 `pub(crate)`：对外仍只由
  `abs_smux` 的 trait 产出这两个半边。

### 9.4 单测（3 个，全部跑在内存环上）

- `halves_report_docks_and_delegate_try_io`：dock 对如实上报；`try_write` / `try_read`
  原样转发（写入 5 字节读回逐字节相等）；
- `close_flags_track_both_ends_independently`：四个标志的初值全假；关生产端后两半边
  的 `is_tx_closed` 变真而 `is_rx_closed` 仍假；再关消费端后 `is_rx_closed` 也变真
  ——证明两个方向互不影响、且状态由环共享；
- `send_close_keeps_buffered_data_then_eof`：关写端不丢已缓存数据；排空后继续读返回
  `ConsumerError::Closing`（EOF 语义）。

## 10. 共享状态层 `sync_`（本轮）

### 10.1 先记三条核对事实（含一条我先前读错的更正）

1. **`mm_ptr::Shared<T, A>` 的 `Send` / `Sync` 是*有条件*的**：
   ```rust
   unsafe impl<T, A> Send for Shared<T, A> where T: ?Sized + Send + Sync, A: AllocatorClone {}
   unsafe impl<T, A> Sync for Shared<T, A> where T: ?Sized + Send + Sync, A: AllocatorClone {}
   ```
   （`Owned<T, A>` 同理：`Send` 要 `T: Send + A: Send`，`Sync` 要 `T: Sync`。）
   我一度读成「无条件 `Send + Sync`」并据此断言「非原子容器不可行」——**该结论错误，
   已作废**。正确结论正好相反：`Shared<RefCell<_>, A>` 自身即 `!Send + !Sync`，
   §6「缺省配置连接为 `!Send`」的实现路径是通的。
2. **`abs_cancel` 0.2.0 只提供两个常量令牌**（`CancelledToken` 恒已取消、
   `NonCancellableToken` 永不取消），**没有可主动触发的令牌**；`TrCancellationToken`
   自身要求 `Send + Sync`。所以「可触发令牌」必须由本 crate 补（见 10.3）。
3. **分配是既定手段**：根对象、dock 节点、子流节点都按需用调用方注入的分配器分配，
   这正是「不隐式分配、不隐藏内存预算」的落点。

### 10.2 `SyncCell_`：按 feature 分叉的内部可变性

| 配置 | 内部容器 | 效果 |
| --- | --- | --- |
| 缺省 | `core::cell::RefCell` | `Shared<RefCell<_>, A>` 为 `!Send + !Sync` → 连接 `!Send`（§6 的承诺） |
| `multi-thread` | `atomic_sync::SpinningMutex` | 共享状态可跨线程；配合 `Rt: TrSpawnSend` |

对外只有 `with_` / `with_mut_` 两个方法（闭包内不得重入、不得 `await`）。
自旋锁的获取只可能因「等待期间令牌被取消」失败，这里固定传
`NonCancellableToken`，因此失败分支不可达（代码里用 `unreachable!` 显式标注）。

### 10.3 `CancelToken_`：补上「可触发」的那一种

`abs_cancel` 缺可触发令牌，而第 7 步的读写循环必须能被唤醒退出（buffex 的
park 点只会被环事件唤醒，连接被 drop 时没有任何环事件）。因此本 crate 实现：

- 内部状态 = `bool + Option<Waker>`，放在 **`SyncAtomicCell_`**（两种配置都用原子锁）
  ——因为 `TrCancellationToken: Send + Sync`，这里不能用按 feature 分叉的
  `SyncCell_`；
- `cancel_()` 幂等，**先取出 waker、释放锁之后再 `wake()`**（避免唤醒路径重入本层
  造成自锁）；
- `cancellation()` 的 future **先登记再检查**，避免「检查完、还没登记」之间丢信号；
- **单等待者**：本 crate 每个等待点天然至多一个等待者，且读写循环各自持有一个
  令牌、一次只 `await` 一处，因此一个槽就够（同一令牌并发两个 `cancellation()`
  会互相覆盖，已写进文档）。

### 10.4 「连接已失败」＝ 标志 + 取消令牌

- 共享状态里存 `FailKind_`：`MuxError<RE, WE>` 的**载荷无关投影**（底层错误值
  `RE` / `WE` 只存在于循环那一侧，无法跨到 API 面）。具体的变体集合已按 §11.1
  重新定稿并**尚未实现**：实现前 `FailKind_` 对 `Rx` / `Tx` 的投影是临时形态，
  实现时连同 `MuxError` 一起改；
- **首个原因生效**：后续失败不覆盖，保证调用方看到的是根因；
- `mark_failed_` 同时 `cancel_loops_()`：两个循环的令牌一起触发，所有挂在
  `may_cancel_with(令牌)` 上的 await 立即醒来 —— 这就是「不能永远 park」的落实。

### 10.5 `WakerSlot_` 与索引

- `WakerSlot_`：单等待者槽，`register_` / `take_` / `is_registered_`。约定是
  **持锁登记、取出后释放锁再唤醒**；每个 dock 节点带一个「入向事件」槽供
  `income_async` 使用（第 8 步接线）。
- `ChannelRegistry_<A>`：`Shared<SyncCell_<RegistryInner_<A>>, A>` 持有的
  **dock 链 + 每 dock 的子流链**（单链表，节点按需分配、释放即归还）。索引不用
  哈希表也不预分配：`max_channel_count` 的协商缺省值是 `1<<28`，预分配不可行，
  而链式索引让内存随实际并发走。
- 配额语义与 `MuxError` 对齐：`DockInUse`（channel / telegraph 互斥，双向都拒绝）、
  `DockChanLimit`（单 dock）、`ChanLimit`（整条连接）。
- 节点释放规则：dock 节点在「无子流、无显式占用、无等待者」时被摘除并归还内存。
- **`# Panics`**：分配节点失败时 panic（与标准库容器 OOM 行为一致）。要给调用方
  一个可处理的 `AllocError` 分支，需要给 `MuxError` 增补变体——同样属公开 API
  变更，待定。

## 11. 架构修订（人类提议，**各项均已定稿**）

各项提议（`MuxError` 变体、保活 `PULSE`、`ChannelOwner`、信号通道、子流建立三步与保留
dock）连同我核对到的事实一并记录在本节；结论与落地状态见各小节标题。**协议部分（§11.2）与架构部分（§11.3 / §11.4）要写进
`frame_.rs` / `connection/mod.rs` 的 doc comment**，落地顺序见 §11.6。

### 11.1 `MuxError`：区分「对端主动关闭」与「传输中断」（人类决策，**已实现**）

**问题**：现在的 `PeerClosed` 写作「对端在帧中途关闭了连接」，而且 §10.4 把底层
`Rx` / `Tx` 统一投影成 `Transport → PeerClosed` 回传，于是三件事被混成一种错误：
对端**优雅关闭**、**网络错误**导致的中断、以及**帧中途截断**。

**提议的变体集合**（待确认）：

| 变体 | 含义 |
| --- | --- |
| `Rx(RE)` / `Tx(WE)` | **本次操作直接遇到的**底层读写错误（载荷保留，仅循环侧可见） |
| `Transport { write: bool }` | 连接因底层传输失败而中断（载荷无法跨到 API 侧，只保留方向） |
| `PeerClosed` | **对端主动关闭**该连接 / 子流（收到 `CLOSE`/`FIN`，或对端读端正常收尾） |
| `Closed` | 本方已关闭该子流 / 子流已拆 |
| `IdleTimeout` | 保活超时（见 §11.2）：`max_channel_timeout` 内既无数据也无保活应答 |
| `ReservedDock` | `wildcard` / `unspecified` 是保留取值，不能作为子流 dock（§11.7） |
| 其余 | `MalformedFrame` / `UnsupportedField` / `FrameTooLarge` / `DockInUse` / `DockChanLimit` / `ChanLimit` / `Refused` / `Duplicate` / `FlowCtrl` / `Cancelled` 保留 |

**连带改动**：`sync_::FailKind_` 随之细分（`Transport { write }` 无损方向），
`mark_failed_` 的投影不再是「一律 PeerClosed」。此外**分配失败**是否也要一个变体
（现在按 OOM panic）仍在待定清单里。

### 11.2 保活：一种 `PULSE` 帧 + 接收窗口通告（人类决策，**已定稿**：选 (b) + 只用一种帧）

**语义**（按提议整理、已定稿）：

1. 保活报文**与具体 channel 相关**，必须带 `LocalDock` + `RemoteDock`
   —— 第 3 步曾把 `PING` / `PONG` 定为「连接级帧」，该决定（原 §7.3）已删除；
2. 它同时是**发送方本地接收窗口**的通告；
3. 触发条件是**闲置**：`MuxConnection` 发现某 channel 无 IO 活动、即将超过
   `max_channel_timeout` 时主动发出；
4. **只用一种帧 `PULSE`**（0x08），`PING` / `PONG` 两种帧取消，0x09 起保留。
   收到 `PULSE` 的一方**只**刷新该子流的活跃时间、并按载荷更新对端发送窗口，
   **不立即回复**——两个方向各自按自己的空闲计时发 `PULSE`。这条「不立即回」是
   单帧方案能成立的前提：若收到就回，两条 `PULSE` 会互相触发成死循环。于是没有
   「请求 / 应答」之分，双方处理栈完全同一份（这正是取消两种帧的目的）；
5. `max_channel_timeout` 内既无数据也无任何方向的 `PULSE` ⇒ 该子流超时，报
   `MuxError::IdleTimeout`。

**线格式**（已实现）：窗口通告统一为**绝对值**，`OPEN` / `PULSE` / `WINDOW_UPDATE`
共用一个字段 `FieldId::RecvWindow`（0x03），其余帧禁止携带；`ACCEPT` 不再需要窗口
字段（被动方的窗口已由它自己的 `OPEN` 通告，见 §11.7）。

````text
PULSE 帧头（示例：local=1, remote=2, recv_window=4096, 无载荷）
88 00 01 01 02 13 10 00 02 00
^  ^-----^ ^-----^ ^--------^ ^--^
|  LocalDock RemoteDock RecvWindow PayloadLen
+-- head = (flags << 4) | kind，0x88 = NO_PAYLOAD<<4 | PULSE
````

#### 11.2.1 通告时机与频率（人类决策，**已定稿**）

本端接收窗口 `W`（= 本端还能再收多少字节）相对容量 `cap` 的取值触发通告：

| 方向 | 触发点 | 语义 |
| --- | --- | --- |
| 开场 | 建流时（`OPEN`） | 通告**最大接收窗口**（= `cap`），此后不再有更大的值 |
| 收缩 | `W` 跌破 `1/2` | 缓冲被填起来了，压制对端 |
| 收缩 | `W` 跌破 `1/4` | |
| 收缩 | `W` 降到 `0` | 对端必须停 |
| 扩张 | `W` 升过 `1/2` | 应用消费了，放行 |
| 扩张 | `W` 升过 `3/4` | |
| 扩张 | `W` 回到满 | |

**频率限制（已定稿：默认开启）**：两次通告之间至少经过若干个数据帧（或若干字节），
避免窗口在阈值附近来回抖动导致「同一个事件反复发」。因为通告携带的是「截至某个已收
字节数的窗口」快照（见下），**延迟通告不会造成越权**——发送方按上一次通告算出的额度
本身就受限于那次的真实窗口，最多是把对端多压一会儿。

#### 11.2.2 通告的表示法：`(R, W)` 两个数（人类决策，**已实现**）

只说「剩余窗口 W」是不够的，必须同时给出它对应的**已收字节数**。推导如下：

设本端容量 `cap`、累计已消费 `C`、累计已收 `R`，则本端物理剩余

```text
W = cap − (R − C)
```

在途字节数 = `已发 S − 已收 R`。发送方**正确的可用额度**应是

```text
可用 = cap + C − S = W − (S − R)
```

也就是说：**只用 W 时，发送方只能取「可用 = W」，会把已经在途、接收方还没计入 `R`
的那 `S − R` 个字节重复算一遍**，于是越权发送，接收环可能溢出。带上 `R` 就能精确
减掉在途量。

- **帧字段**：`OPEN` / `PULSE` / `WINDOW_UPDATE` 携带两个值——`R`（累计已收字节数，
  单调不减；为避免 4 GiB 回绕逻辑用 `u64`，线格式本来就允许 `BeU64`）与 `W`（当前
  接收窗口绝对值，`u32` 足够：它不超过容量）。
- **发送方**：记录最近一次通告 `(R₀, W₀)`，之后 `可用 = W₀ − (S − R₀)`，下钳 `0`；
  `S` 随发送递增，因此两次通告之间额度自然递减到 0，不会越权。
- **落地**：线格式上是两个字段 `FieldId::RecvTotal`（`R`，`u64`）与
  `FieldId::RecvWindow`（`W`，`u32`），在 `OPEN` / `PULSE` / `WINDOW_UPDATE` 上必需且
  必须成对；`flow_ctrl::WindowReport` 承载这一对值，`SendWindow::on_report` 幂等
  （`R` 不比已记录的更大就忽略，因此保活重复携带同一快照是安全的）。
- **已否决的备选**：只发「累计授权量 `T = cap + C`」（发送方 `可用 = T − S`）。单值、
  天然幂等，但授权不能撤回，**「收缩触发点」就没有意义了**，与 §11.2.1 的决策冲突。

#### 11.2.3 累计已收量 `R` 的宽度与「已重置」变体（人类决策，**已实现**）

- **宽度规格**：`FieldId::RecvTotal` 允许 **2 / 4 / 8** 三种（`BeU16` / `BeU32` /
  `BeU64`），发送方取能容纳当前值的最小者——小值常驻 2 字节，控制帧保持紧凑。
  1 字节规格被排除：一次突发就要重置，得不偿失。
- **重置变体**：累计量涨到当前规格之前，接收方发一帧带
  `flags::K_TOTAL_RESET` 的通告，其中 `RecvTotal` 携带**重置前**的累计量（上一个
  epoch 的绝对总量）。对端据此 rebase：`绝对已收 = epoch 起点 + 帧内累计量`，
  此后帧内累计量从 `0` 重新计数。这样窄规格也能干净地重新开始，不必改用更宽字段。
- **何时重置**：由 [`TrFlowCtrlPolicy::recv_total_epoch`](`crate::flow_ctrl`)
  决定（缺省 4 字节 = `u32::MAX`；选 `u16::MAX` 更紧凑、重置更频繁；选 `u64::MAX`
  实际不重置）。重置是**编码前提**，因此 `should_report` 为它**绕过最小帧间隔**
  （阈值通告的频率限制只管阈值通告）。
- **合法性**：`K_TOTAL_RESET` 只允许出现在 `PULSE` / `WINDOW_UPDATE` 上；`OPEN` 时
  还没有 epoch，其余帧不带窗口通告，带上即 `MalformedFrame`（读写两侧都校验）。
- **顺带关闭的旧待办**：`flags::K_NO_PAYLOAD` 与必需的 `PayloadLen == 0` 语义重复，
  原 §7.6 一直挂着「删除或改作它用」；现在**删除**它，位 3 改作 `K_TOTAL_RESET`。
- **发送方 rebase 的推导**：设对端宣告重置时其绝对累计量为 `B`（新的 epoch 起点），
  我方在那一刻的已发总量为 `S_b`，在途 `S_b − B`。重置后我方 `S` 继续单调递增，
  `绝对已收 = B + (epoch 内 R)`，于是 `在途 = S − (B + R)`，
  `可用 = W − 在途` —— 与重置前同一公式，只是 `R` 多了一个 epoch 起点。

### 11.3 `ChannelOwner`：每子流的共享实体（人类提议，**已定稿**：按 11.3 末的所有权切分）

**目标**：放弃「读会话 / 写会话各自管住全部通道」的形态，改为**每条子流一个堆上实体**，
与 `MuxConnection` 通过信号通道协作。

**我核对到的三条硬约束**（必须进设计）：

1. **段借用**：`TrBuffTryRead` / `TrBuffTryWrite` 借出的段，其生命周期绑定在**环半部
   自身**上。因此 `ChannelTx` / `ChannelRx` 必须**直接持有**自己的环半部，不能把它放进
   共享实体、再通过锁去访问（段不能比锁守卫活得久）。⇒ `ChannelOwner` 承载的是
   **共享状态**（身份、收发窗口、活跃时间、关闭标记、信号句柄），环半部仍由两个半边与
   `MuxConnection` 分别独占。
2. **环的内存本来就是智能指针管的**：`buffex` 的两个半部通过 `CoreRef` 共享同一个核心，
   存储 `B = Owned<[MaybeUninit<u8>], A>` 由注入分配器分配；而 `mm_ptr::{Shared, Weak,
   Owned}` 都实现了 `abs_mm::res_man` 的 `TrBoxed` / `TrStrongShared` / `TrWeakShared` /
   `TrUnique`（已核对），所以「以智能指针抽象注册」这条完全可行——注册可以表达成
   「交出会话侧半部 + 一个 `Shared<ChannelOwner>`（或 `Weak`，让 app 全丢时可回收）」。
3. **`abs_mm` 没有通知 / 事件抽象**，`abs_sync` 只有 trait、没有具体实现（后端要让
   使用者选）⇒ 信号通道必须自建（见 §11.4），不能指望现成件。

**建议形态**（待确认）：

```rust
// 子流共享实体：堆上、Shared 持有，不对外暴露
struct ChannelOwner<B, A> {
    local_dock_: Dock,
    remote_dock_: Dock,
    /// 收发窗口、活跃时间、关闭标记
    state_: SyncCell_<ChannelState_>,
    /// 上行信号（接收窗口有更新 / 请求保活）
    upstream_: SignalSink_,
}

// 对外半边：各自独占环半部 + 共享同一个 owner
pub struct ChannelTx<H> { half_: H, owner_: Shared<ChannelOwner<..>, A> }
pub struct ChannelRx<H> { half_: H, owner_: Shared<ChannelOwner<..>, A> }
```

**注册流程**：建流时先由库内建 `ChannelOwner`（两个环都由此刻建立、内存走注入分配器），
然后「注册」给 `MuxConnection`：交出**会话侧**两个半部（tx 环的 `Consumer`、rx 环的
`Producer`），`MuxConnection` 把它们放进自己的会话本地表、并把 owner 记进注册表；
最后把两个 app 侧半边包成 `ChannelTx` / `ChannelRx` 返回。

**关闭态**：`ChannelTx` 仍按值独占生产端，**丢弃即半关闭**；会话侧由 `buffex` 的
EOF 唤醒（已核对：被动消费端在生产者关闭时**总是**唤醒）⇒ **下行方向不需要单独的
信号通道**。这也是免掉「每条子流两份关闭标记」的原因。

### 11.4 信号通道：**一条被所有 ChannelOwner 共享的 MPSC 通道**（人类决策，已定稿）

**通道形态**：每条连接**一条**上行通知通道，**多生产者（所有 ChannelOwner）→ 单消费者
（MuxConnection）**。`MuxConnection` 在建流注册时把这条通道的**生产端句柄**交给
`ChannelOwner`；owner 在应用读过（接收方向）环里的数据之后，用它发一条通知，
**由 `MuxConnection` 自行决定去查看对应环的接收空间大小、并按自身策略决定何时向对端
发窗口更新**。

**实现底座（人类决策，**已定稿并落地**）**：用 [`flume`](https://docs.rs/flume) 的
`flume::bounded(capacity)`。选型经过「自研定容环 → `asyncband::mpsc` → `flume`」三轮
（前两轮的实现与对比均已删除，理由见 §11.4.1）：`Sender: Clone` 即多生产者、
`Receiver` 只交给我方一处即单消费者，`try_send` 非阻塞（满时 `TrySendError::Full`）、
`recv_async` 自带消费者唤醒，正好对应下面的契约；代价是它 **std-only**，因此本 crate
不再 `#![no_std]`（见 §12.5）。

**消息内容**：只带**子流身份**（`(local_dock, remote_dock)`，8 字节），不带字节数、
更不带数据本体——窗口是状态，`MuxConnection` 拿到身份后直接读 owner 的窗口记账
（`RecvWindow` 的累计消费量）或环的 `free_size()` 即可，两者都比「随手报一个数」
可信。是否要在消息里附带消费量作为**提示**（而非依据），留待实现时按需再加。

**为什么必须是「可达 + 不丢」而不是「尽力而为」**：漏掉一条通知意味着对端的发送窗口
永久少一截，最终会把那条子流卡死。因此通道虽然是**定容**的，但用两个机制保证不丢：

1. **每条通道一个「已入队」位**（放在 owner 的共享状态里）：只有 0→1 时才真正入队，
   **每条通道在队列里至多占一条**。于是「丢掉的只会是重复项」，而重复项本来无害。
2. **队列满 ⇒ 置连接级「需要全扫」标志**：该标志只表示「有通道的消费没被队列记录」，
   消费者看到它就沿注册表扫一遍所有通道（慢路径，只在压力下出现）。这样即使队列容量
   小于并发通道数，也不会丢更新。

**消费者协议（关键顺序）**：取出一个身份后**先把「已入队」位清零、再去读累计消费量**：

```text
loop {
    let (local, remote) = channel.next_async().await?;   // 或扫表分支
    owner.queued_ = false;                 // 1) 先清位
    let consumed = owner.take_consumed();  // 2) 再取累计
    if consumed > 0 { 按策略发 WINDOW_UPDATE }
}
```

顺序不能反：若先读累计再清位，生产者在「读完、未清位」之间累加的字节会因为「位仍是 1」
而不入队，从而永久丢失。反过来（先清位再读）最多多发一条通知，不会丢。

**实现底座**：`abs_mm` 没有通知 / 事件抽象，`abs_sync` 只有 trait、没有具体实现（后端要
使用者选）⇒ 通道自建：

- 队列本体是**定容环形缓冲**（容量取内部常量，例如 64/256），元素是 dock 对；
- **互斥用 §10 的 `SyncCell_`**：缺省配置（单线程）就是 `RefCell` —— 此时「多生产者」
  本就同线程，语义完全正确；开启 `multi-thread` 后换成原子自旋锁，临界区只有一次入队 /
  出队。**不引入无锁 MPSC**：无锁环形队列要 per-slot 序号 + 内存序，收益与复杂度不成
  比例，等真有性能数据再说（记为可后续优化项）；
- 消费者 park 用 §10 的 `WakerSlot_`：生产者**释放锁之后**再唤醒消费者，避免唤醒路径
  重入本层；
- 通道只在**连接**上分配一次；每个 owner 只多持一个句柄（`Shared`），不按通道分配内存。

**下行方向（MuxConnection → owner）不需要通道**：对端 `FIN` / `RST` / 拆流一律用
「关闭接收环的生产端」表达，`buffex` 会唤醒挂在读端的应用（已核对：被动消费端在生产者
关闭时**总是**唤醒）；对端窗口更新只影响会话自身的调度，应用侧从不阻塞在窗口上——
owner 的共享状态随时可读，不需要唤醒。

#### 11.4.1 选型的三轮演进（结论：`flume`）

| 轮次 | 方案 | 结论与理由 |
| --- | --- | --- |
| 1 | **自研定容环**（`SyncCell_` + `WakerSlot_`，走注入分配器） | 能满足契约并保住 `no_std`，但要自己维护环形队列、唤醒与清位顺序（约 180 行）；只作过一轮对照实现 |
| 2 | **`asyncband::mpsc`** | 核对发现它是 **std-only**（内部包 `std::sync::mpsc`）且走全局分配器；做了一轮「双实现对比」（两套都过同一组 4 个单测），但收益不足以抵消把本 crate 拖进 `std` 的代价 |
| 3 | **`flume::bounded`**（最终） | API 与本模块契约一一对应（`Sender: Clone` 多生产者、`try_send` 满时 `Full`、`recv_async` 自带唤醒、`Receiver` 单消费者），零配置依赖、上游维护活跃；代价是本 crate 放弃 `#![no_std]` |

两套早期实现与它们的测试**已删除**；现在只有 `flume` 一套实现（4 个单测：定容 + FIFO、
空通道异步取会 park 且被唤醒、有积压时立即就绪、多生产者克隆）。但 **`TrSignalSender_` /
`TrSignalReceiver_` 两个内部 trait 保留**——中心循环只依赖这两个 trait，将来若要换回
`no_std` 实现（或做注入分配器版本），替换点只有一处。

### 11.7 子流建立：对称三步 + 保留 dock（人类决策，**已实现**）

**保留 dock**：`wildcard`（全 1）与 `unspecified`（全 0）由**双方共同保留**，不能
作为正常子流的 dock。线上出现即 `MuxError::ReservedDock`；发送侧同样拒绝构造这种
帧头。因此旧设计里「连接级帧用 `unspecified` 当哨兵」的做法一并消失。

**对称三步**（两侧同一状态机）：

```text
主动方 A                                        被动方 B（ChannelListener）
   | -- OPEN(开场消息, A 的接收窗口) -------------> |
   | <-- OPEN(载荷为空, B 的接收窗口) ------------- |   B 收到 OPEN 后先回一条 OPEN
   | <-- ACCEPT(欢迎信息) ----------------------- |   再发 ACCEPT
```

- `OPEN` **双方都发**，两条都必需携带 `RecvWindow`；主动方那条带开场消息，被动方
  那条载荷为空、作用就是通告自己的接收窗口；
- `ACCEPT` 只有被动方发，载荷为欢迎信息，**不再带窗口字段**（窗口已在其 `OPEN` 里
  通告过）；
- 于是两侧都是「发 `OPEN` → 收对端 `OPEN` →（被动方多发一个 `ACCEPT`）→ 建立」，
  谁都不会先看到对方的数据；
- 建流阶段就交换了窗口，因此连接**不再假定**两端用同一条规则算出相同初窗——窗口以
  通告值为准（`flow_ctrl` 的模块文档已同步）。

## 12. 上游 API 迁移（本轮）

本轮上游集中发了多处破坏性改动，`smux_v1` 的既有实现（`frame_` / `flow_ctrl` /
`channel_` / `sync_` / 握手 / 集成测试）**全部**需要跟着改。下面按「上游改了什么 →
我们怎么改 → 为什么这么改」记录，便于下次上游再动时快速定位。

### 12.1 触发：上游的四项破坏性改动

| 上游 | 旧 | 新 |
| --- | --- | --- |
| `buffex` | `circular_buff`（含 `builder::CircularBuffBuilder`、`Producer` / `Consumer` 半部、`SpscPair`） | `ring`（`Ring` / `RingReader` / `RingWriter`；`Producer` / `Consumer` 退化为 park 钩子） |
| `abs_mm` | `mem_alloc::TrMalloc`、`mem_alloc::CoreAlloc` | 删除；改用 `core::alloc::{Allocator, AllocatorClone}`，`CoreAlloc` 提到 crate 根 |
| `abs_async_iter` | `NextAsync` 输出 `Result<Item, Err>`，但条目流把「读完」放在 `Ok(None)` 里 | 明确为 `Result<Item, Err>`：**`Err` 本身就表示「不能再产出」** |
| 适配 crate | `abs_buff_tokio_adapt` / `abs_buff_compio_adapt` 的 `CompioReadAsBuff` 等 | 改名 `buffex_{tokio,compio}_adapt`；设备级类型 tokio 侧经 `x_deps` 重导出，compio 侧根导出 |
| `mm_ptr` | `dev/0.1.3` | `dev/0.2.0`（适配 crate 固定该分支；`Owned` / `Shared` 的 `allocator_api` 适配在此版本） |

### 12.2 环：`circular_buff` → `ring`（新增 `connection/ring_.rs`）

上游不再有构建器，构造方式是「**环本体持有缓冲与 park 原语**，再切出两个半部」：

```rust
let ring = Ring::try_new(buffer)?;              // B: BorrowMut<[MaybeUninit<u8>]>，容量 [2, 2^28-1]
let shared = Shared::new(ring, alloc);          // 环独占在这个共享句柄里
// SAFETY: 无第二句柄、无 Weak 升级路径；两半各持一个强引用
let (tx, rx) = unsafe { Ring::split_unchecked(shared) };
```

- 别名固定为 `BufferedTx<B, A> = RingWriter<Shared<Ring<B>, A>, B, u8>`、
  `BufferedRx<B, A> = RingReader<Shared<Ring<B>, A>, B, u8>`、
  `BufferedChannel<B, A> = (BufferedTx, BufferedRx)`；
- 唯一的构建入口是 `ring_::new_buffered_channel_`；单测与集成测试各自建环，
  单测经 `ring_::test_support_::make_test_channel_` 复用同一份构造逻辑；
- `ring` 模块被移到 `ring_.rs`，`connection/mod.rs` 只做逐项重导出（符合
  「`mod.rs` 不存放实际逻辑」的纪律）。

### 12.3 关闭语义：`is_*_closing` 删除

- `abs_buff` 的 `is_drained_closing` / `is_stuffed_closing` **已删除**，且它们本就不是
  我们要的「方向关闭」语义；
- 新判据：半部 `ring_state()` → `is_producer_closed()` / `is_consumer_closed()`
  （`Ring` / `RingState` 上是 inherent 方法，所以 `TrChannelHalf` 的 impl 仍只能落在
  具体类型上）；
- 关闭入口变成**同步**的 `RingWriter::close()` / `RingReader::close()`（幂等、会唤醒
  park 中的对端），旧的 `close_async()` 不存在；
- EOF 语义：写端关闭后**先交付已提交数据**，排空后再读返回 `ConsumerError::Closing`
  ——单测从「断言 `is_drained_closing()`」改为「断言错误变体是 `Closing`」。

### 12.4 分配器：`TrMalloc` → `AllocatorClone`

- `#![feature(allocator_api)]` 重新启用（`lib.rs`），分配器 bound 统一写成
  `A: AllocatorClone (+ Send + Sync)`；`TrMuxConfig::Alloc` 的 bound 同步改（**公开
  关联类型的约束变化**，属上游强制的连带改动）；
- `mm_ptr` 升到 `dev/0.2.0`：适配 crate 固定该分支，两个版本并存会让
  `Owned` / `Shared` 变成不同类型；
- `CoreAlloc` 统一从 `mm_ptr::x_deps::abs_mm::CoreAlloc` 取（`mem_alloc` 已无）。

### 12.5 平台：放弃 `#![no_std]`

信号通道选 `flume`（§11.4.1 第 3 轮），它是 **std-only**，因此 `lib.rs` 的
`#![no_std]` 被移除，只保留 `#[cfg(test)] extern crate std;`。这条是**已知的代价**：
若将来需要 `no_std`，替换点只有 `signal_.rs` 一处（它背后的两个内部 trait 保留着），
但届时中心循环、`sync_` 的 cfg 分叉与分配器约定都要一并复核。

### 12.6 迭代器契约：`Result<Item, Err>` 与「读侧失败优先分类」

`TrAsyncIterator` 现在把「条目读完」也用 `Err` 表达（没有 `Option`）。这条改动在
协商路径上引出一个**必须显式处理**的语义问题，值得记下完整因果链：

1. 条目流 `EntryStream_` 的 `Item = NegotiationEntry`、`Err = StreamEnd_`，因此
   `next_entry_async_` 的返回类型从 `Result<Option<Entry>, StreamEnd_>` 收窄成
   `Result<Entry, StreamEnd_>`，并新增 `StreamEnd_::Ended` 表示「正常读完」；
2. 协商器（`AcceptAllEntries` / `CapPacketSize`）因此**无法**区分「读完」与「读侧失败」，
   统一按「不再拒绝」返回 `true`；
3. 区分只能由调用方做：`FrameReader::take_error_` 里有底层错误就是失败。于是把
   「读侧失败」的判定**提到 `!accepted` 分支之前**——否则 CRC 失败会在协商器返回
   `true` 之后被当成「协商通过」，接着因为基础项不完整而误报 `Inconsistent`
   （`checksum_failure_is_not_reported_as_rejected` 这条既有单测正是抓住了它）；
4. 该顺序同时保证 §9 的分类：读侧失败按失败分类（**不得回 `REJECT`**），只有真正的
   中途拒绝才会发 `REJECT` 并返回 `Rejected`。
