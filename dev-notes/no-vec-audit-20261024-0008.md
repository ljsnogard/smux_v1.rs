# no-vec：`smux_v1/src` 的 `Vec` 清单、必要性与替代算法

- 仓库/分支：`smux_v1`，`feat/no-vec`
- 基线提交：`d2f848e`（本文所有行号以此提交为准）
- 审计范围：`smux_v1/smux_v1/src/**/*.rs`
- 本轮目标：**只做标记与分析，不改源码**；先把每一处 `Vec` 的用途、是否真的分配、
  能否零堆替代与代价写清楚，再逐项决定重构顺序。

> **2026-10-24 修订（重要）**：初版把“控制帧载荷必须缓冲”写成“协议/API 约束”，
> 并把 `Vec` 当成难以替代的实现。这个表述过强，已撤回。**`Vec` 本身没有不可替代性**：
> 它只是“当前所有权边界 + 帧头长度先于载荷 + 写循环独占 Tx”三者夹出来的一个实现
> 选择。真正需要保留的至多是“一段由连接拥有的暂存”，而不是 `Vec`、更不是堆分配。
> 详见 §3.1.1 与 §3.1.5。

> 对应；`Vec` 审计的原则（先标记、再决定替代）仍有效。

## 0. 结论先行

1. **数据面已经是零分配**：稳态收发路径没有 `Vec`；`frame_.rs` 的帧头走
   `[u8; K_MAX_FRAME_HEADER]` 栈上缓冲，载荷直接从子流环搬进传输环。实测稳态
   搬运的**注入分配为 0**（见 §5.1）。
2. **生产路径中真正会分配堆内存的 `Vec` 只有三处语义**：
   - 控制帧载荷 `ControlFrame_::payload_`（`OPEN` / `REJECT` 的非空载荷）；
   - 把它读出来的 `read_available_into_vec_`；
   - 把开场消息暂存在待决句柄里的 `ChannelHandle::message_`。
   这三处其实是**同一条载荷链**，应作为一个整体设计，不应拆成三次局部修补。
3. 另外两处需要单独讨论：
   - `session_.rs` 解复用循环里每次自查产生的 `gone: Vec<Dock>`（临时分配）；
   - `registry_.rs` 的 `reusable_docks_: VecDeque<Dock, A>`（持久但动态增长，
     已走注入分配器，仍是堆内存）。
4. `Vec` 的空构造点（`Vec::new()`）本身**不分配**；它们会随着载荷类型改造一起消失，
   不应单独按“分配点”优化。
5. 其余 `Vec` 全部位于 `#[cfg(test)]` 或文档注释中，不影响生产分配面。
6. **载荷链里的 `Vec` 不是不可替代的**：`OPEN`/`REJECT` 的字节最终要成为一段
   可写出的连续载荷，但这段载荷可以由连接级复用缓冲、内联缓冲或控制环提供，
   `Vec` 只是当前最省事的容器。见 §3.1.1 / §3.1.5。

## 2. 生产路径逐项标记

### 2.1 P1：`ControlFrame_::payload_`

| 位置 | 代码 | 说明 |
| --- | --- | --- |
| `src/connection/signal_.rs:94` | `payload_: Vec<u8>,` | 写循环事件里的控制帧载荷 |
| `src/connection/signal_.rs:117` | `payload: Vec<u8>,` | `with_window_` 构造参数 |
| `src/connection/signal_.rs:106` | `payload_: Vec::new(),` | Z：空载荷，不分配 |
| `src/connection/signal_.rs:72` | 文档 | 明确写了“冷路径例外” |

**承载的帧**：`OPEN`（开场消息）、`REJECT`（拒绝理由）；`CLOSE` / `PULSE` /
`WINDOW_UPDATE` / `ACCEPT` 目前都传 `Vec::new()`，不分配。

**分配时机**：`send_open_` 把 `ChannelHandle::message_` move 进来；`reject_async`
把 `read_available_into_vec_` 的结果 move 进来。随后经 `flume` 无界事件队列交给
写循环，写完即随事件 drop。

**频率**：每条子流建流一次（`OPEN`），拒绝时一次（`REJECT`）。属于控制面冷路径，
但**不是零分配**，且走的是全局分配器。

### 2.2 P2：`read_available_into_vec_`

| 位置 | 代码 |
| --- | --- |
| `src/connection/util_.rs:18` | `pub(crate) async fn read_available_into_vec_<M, K>(...) -> Vec<u8>` |
| `src/connection/util_.rs:23` | `let mut out: Vec<u8> = Vec::new();` |
| `src/connection/channel_handle/handle_.rs:653` | `reject_async` 的理由载荷调用点 |
| `src/connection/dock_binding/binding_.rs:278` | `open_channel_async` 的开场消息调用点 |

**算法**：循环 `read_async(Demand::at_least(1))`，每拿到一段就
`out.resize(base + want, 0)`，再用 `move_items_to_buff` 写入新尾部；因此：
- 可能发生多次 `realloc` + 整段拷贝（取决于源一次给出多少字节）；
- 每次 `resize` 会把新区域先填 0，再被覆盖，存在一次多余写入；
- 读取上限是 `max_packet_size`（默认 4096，可协商）。
- 源为空时 `Vec::new()` 不分配；源非空时至少一次分配。

**为什么必须缓冲**：控制帧头里的 `payload_len` 必须先于载荷写出，而源是
`TrBuffRead`（不知道总长）；`OPEN` 的载荷还要跨 `open_channel_async` →
`accept_async` 存活。所以“不缓冲、直接流式写出”在现行协议与 API 下不可行（详见
§3.1）。

| 位置 | 代码 | 说明 |
| --- | --- | --- |
| `src/connection/channel_handle/handle_.rs:84` | `message_: Vec<u8>,` | 发起方暂存开场消息，直到 `accept_async` |

## 3. 必要性与替代算法

### 3.1 控制帧载荷链（P1 + P2 + P3）

#### 3.1.1 不可替代性判定：`Vec` 不是必需的

先把结论说清楚：**`Vec` 没有不可替代性**。它现在出现，是因为三件事同时成立：

| 约束 | 是不是协议要求 | 它真正强制了什么 | 能否消除 |
| --- | --- | --- | --- |
| 帧头里的 `PayloadLen` 在载荷之前 | **是**（当前线格式） | 写出第一个载荷字节之前必须知道总长 | 不改帧格式就消不掉；但它只强制“先知道长度”，不强制 `Vec` |
| 源 `M: TrBuffRead<u8>` 不暴露总长 | 否（是 trait 接口） | 读完整段之前无法写帧头 | 可加“已知长度”快路径（如 `&[u8]`/`len()`），或让连接先收完再写 |
| 载荷要跨 `open_channel_async → accept_async` 存活 | 否（是 API 生命周期） | 必须有某个对象在 `await` 之间持有字节 | 可改 `ChannelHandle` 的生命周期/所有权，或改用连接级暂存 |
| `WriteEvent_::Control` 经 `flume` 无界队列 | 否（是事件通道实现） | 事件必须是 `'static`，不能带 `&mut M` | 可改控制环/借用式握手/直接写 Tx |
| 写循环独占 `C::ConnTx` | 否（是当前架构） | API 侧不能直接写传输 | 可让 API 持有控制写入句柄，或把 Tx 放进共享控制环 |
| `enqueue_frame_parts_` 接收 `&[u8]` | 否（是当前写函数签名） | 载荷必须是一段连续切片 | 可改成分段/流式写入，但帧头长度问题仍在 |

因此，在当前**代码结构**下真正剩下的只是：

> **一段“已经知道长度、由某个执行者拥有、可被写循环连续取出”的载荷暂存。**

这段暂存可以是：
- 连接级预分配的复用缓冲/控制环（每连接一次分配，之后零分配）；
- 内联在 `ControlFrame_` / `ChannelHandle` 里的定长小缓冲；
- 调用方提供的缓冲（API 变更）；
- 甚至直接是写循环持有的 Tx（如果 API 能直接驱动它）。

但**不必是 `Vec`，也不必是每次操作一次堆分配**。

再把两条路径分开看：

- **入向 `OPEN` / `REJECT` 已经没有 `Vec`**：解复用循环在
  `session_.rs:982` 用 `Owned::new_slice(shared.max_packet_size_, ..., alloc)` 建了一块
  **连接级复用缓冲**，每帧读进同一块 `payload`，再就地解析。这正是“从连接级 Rx
  就地解析”的现成形态，只是它目前服务读方向。
- **出向的 `Vec` 在 API 侧**：`open_channel_async` 拿到的是调用方的
  `&mut M`（`TrBuffRead`），`accept_async` 返回的 `ChannelHandle` 不带生命周期参数，
  而真正拥有 `C::ConnTx` 的是 mux loop。于是 API 侧无法“把 M 直接接到 Tx 上”：
  - `open_channel_async` 返回后，`&mut M` 的借用已经结束，句柄不能继续持有它；
  - 即使能持有，`WriteEvent_` 走 `flume`，事件要求 `'static`，不能把 `&mut M` 放进去；
  - 即使能把 M 交给写循环，帧头长度仍未知，而 Tx 是 `TrBuffWrite`（不可回填/不可 seek），
    不能先写占位符再补长度。
- **`REJECT` 理论上更接近“就地写”**：`reject_async` 自己持有 `&mut reason`，如果
  它同时持有 Tx（或一个控制写入句柄），可以在读完一段后直接写；但当前它没有 Tx，
  只能把载荷交给写循环。因此它同样受“所有权 + 事件通道”限制，而不是受协议限制。

所以，如果目标是“**完全不复制、直接从源写到 Tx**”，需要改的是下面之一（都属于
架构/API 变更，必须讨论）：

1. `open_channel_async` 接收**拥有所有权**的 `M`（或 `&'static [u8]` 之类），
   `ChannelHandle` 持有它到 `accept_async`；如果 `M` 还能报告长度（如切片），
   写循环可直接“先写头、再流式写载荷”，零拷贝。
2. `ChannelHandle` 增加生命周期参数，借用调用方缓冲到 `accept_async`；公开类型会变。
3. 给 API 一个**控制写入句柄**（共享 Tx 或连接级控制环），让它自己写控制帧；
   这需要解决 Tx 的多写者串行化，以及长度已知/可回填的问题。
4. 改线格式：允许“长度后置”或控制载荷分片；这会破坏与现有对端的兼容性。

如果不想改 API/协议，那么“复制进连接级暂存”是合理的；但暂存可以是**预分配的、
复用的、按连接计费的**，而不是每次 `Vec::new()`。下一节的 A0/A2 就是这两个方向。

#### 3.1.2 方案对比

> 方案按“是否还使用 `Vec` / 是否每次操作分配”分层；A0/A2 是重点。

| 方案 | 每次操作堆分配 | 保持语义 | 公开 API | 代价 / 风险 |
| --- | --- | --- | --- | --- |
| **A0. 连接级控制载荷池/控制环** | **0**（池在连接构造时一次分配） | 是 | 不变 | 在 `MuxCore` 或循环侧建固定数量的 `Owned<[u8], A>` 槽（或一条定容控制环），`open/reject` 借槽、读入、事件携带槽句柄，写循环写完归还；需要定容策略、槽耗尽背压/取消归还；固定内存 `槽数 × max_packet_size`；不消除复制，只消除每次堆分配 |
| **A1. 注入分配器的 `Vec<u8, A>`** | 每次仍有（但走 `C::Alloc`） | 是 | 不变 | 最小改动；`ControlFrame_` 需泛型化；载荷仍按需增长、可能 realloc；只是把“隐式全局分配”变成“可记账分配”，不满足零堆目标 |
| **A2. 小缓冲优化（SBO）** | 小载荷 0；大载荷走 A0/A1 | 是 | 不变 | `Payload_` 内联 `[u8; K]`（K=64/128），超过 K 回落连接级槽或 `Vec<u8, A>`；`ControlFrame_` / `WriteEvent_` 尺寸增加 K+tag，`flume` 节点随之变大；需要初始化细节和实测选 K |
| **A3. 硬内联上限，无堆** | 0 | **否**（超限需报错/截断） | 可能变（新错误/限制） | 真正零堆，但 `max_packet_size` 默认 4096，开场消息/拒绝理由可能超过 K；改变可观察行为，须按 AGENTS §1 先讨论 |
| **A4. 连接级固定槽池/arena** | 0（每次操作） | 是（在容量内） | 不变或新增配置 | 与 A0 同族；若不做槽归还/复用，只是一次性 arena；固定内存可能很大（4 KiB × pending 数）；槽耗尽需背压/报错 |
| **A5. 调用方提供缓冲区** | 0 | 是（但 API 变） | **变**（需讨论） | 例如 `open_channel_async(..., buf: &mut [u8]) -> len`；句柄不能借用调用方缓冲跨 `await`，要么复制、要么把句柄生命周期绑到缓冲，公开类型会复杂化 |
| **A6. 协议/写路径改造，直接流式** | 0 | 否 | 可能变 | 需要预写长度或改成“先占位后回填”，字节流传输不可回填；或改帧格式允许多段控制载荷；`REJECT` 还要跨越事件通道，收益低、风险高 |

#### 3.1.3 实测代价

用现有 `tests/alloc_count.rs` 的计数分配器，把 8 条子流的开场消息从空改为
256 字节（临时改动，已恢复），实测：

| 场景 | 每子流全局分配 | 每子流全局字节 |
| --- | --- | --- |
| 空消息（基线） | 24 次 | 1920 B |
| 256 B 开场消息 | 26 次 | 2240 B |
| **增量** | **+2 次** | **+320 B** |

256 B 就出现 2 次分配，至少说明这条路径并非固定 1 次分配；逐段 `resize` 会带来
额外的扩容/拷贝。默认上限 4096，最坏情况下分配次数还会更多。稳态搬运（不涉及 OPEN）
的注入分配仍为 0，证明这条链只影响控制面。

> 注意：把消息直接加到 4096 会超过“帧总长 ≤ max_packet_size”的限制；实测该用例
> 会挂起，因此 A0/A3/A4 选容量时必须算上帧头（`K_MAX_FRAME_HEADER`）。

#### 3.1.4 建议

- **首选 A0（连接级控制载荷池/控制环）**：它最贴合“Tx/Rx 本身带缓存”的思路。
  在连接构造时从注入分配器一次性准备固定数量的载荷槽（或一条定容控制环），
  `open_channel_async` / `reject_async` 借一个槽、读入、把槽句柄放进
  `WriteEvent_::Control`，写循环写完归还。**每次 OPEN/REJECT 不再发生堆分配**，
  公开 API 不变。代价是固定内存与槽耗尽策略（等待/背压/错误），以及槽在
  取消、Drop、连接收尾时的归还路径。
- **叠加 A2（SBO）**：`Payload_` 先尝试内联 `[u8; K_INLINE]`，只有超过 K 才去借
  A0 的槽。这样短开场消息/短拒绝理由连池都不碰，长载荷也不产生每次堆分配。
  备选内核：
  ```text
  enum Payload_<A> {
      Empty,
      Inline { buf: [u8; K_INLINE], len: u16 },
      Pooled(Slot_<A>),   // 连接级槽，Drop 归还
  }
  ```
- **A1 只作为过渡**：如果 A0 的槽管理暂时太重，先把 `Vec<u8>` 换成
  `Vec<u8, C::Alloc>`，让分配可记账；它不满足“每次操作零堆”的最终目标。
- **不采用 A3/A5/A6**，除非先有明确的产品约束（开场消息最大长度）并完成 API 讨论。
- `K_INLINE` 需用真实业务消息长度分布选值；建议先测 64 与 128 两种，并记录
  `size_of::<WriteEvent_<CoreAlloc>>()` 的变化。若事件尺寸增长导致 `flume` 节点
  成本不可接受，可只对 `ControlFrame_` 使用 `Payload_`，或退回 A1。

#### 3.1.5 为什么不能“直接把源接到连接级 Tx”？

“从连接级 Tx/Rx 就地解析”在读方向已经成立，在写方向还差三块拼图：

| 缺口 | 现状 | 直接写 Tx 需要什么 |
| --- | --- | --- |
| Tx 所有权 | `C::ConnTx` 被 move 进 `mux_loop_async_`，API 只有一个 `MuxConnection` 智能指针 | 共享控制写入端（锁/队列），或把 Tx 的控制写权限借给 API future |
| 事件通道 | `WriteEvent_` 走 `flume::unbounded`，事件必须 `'static` | 控制环/借用式握手，或事件只携带“槽句柄”而不是字节 |
| 长度先于载荷 | `PayloadLen` 是帧头最后一个字段，源 `TrBuffRead` 不报总长 | 已知长度的源（切片/`len()`），或允许回填/长度后置的帧格式 |
| Tx 不可回填 | `C::ConnTx: TrBuffWrite<u8>` 只有顺序写，没有 seek/patch | 先知道长度；或给 Tx 增加“预留+回填”能力（会收窄传输类型） |
| 写函数签名 | `enqueue_frame_parts_(tx, head: &[u8], payload: &[u8])` | 改成流式/分段接口；但长度问题仍在 |

因此，**在不改 API/架构的前提下**，最小可行的“去 Vec”不是“让源直接写 Tx”，
而是“把源读进一个连接级拥有的槽/环，再让写循环从槽里写”。这仍然有一次复制，
但没有每次操作的 `Vec`/堆分配。若要把这一次复制也消掉，就必须改上面至少一项：
源的所有权/长度、Tx 的共享方式，或帧格式。三者都不是纯内部重构，需先讨论。

### 3.2 `gone` 与 `tg_live`（P4）

#### 3.2.1 必要性

`collect` 不是算法需要，只是借用检查的绕行：不能在 `tg_table.keys()` 的迭代器
还活着时 `remove`。三种替代都能表达同一个语义。

#### 3.2.2 方案对比

| 方案 | 每轮分配 | 仍需注册表扫描 | 复杂度 | 备注 |
| --- | --- | --- | --- | --- |
| **C1. `tg_table.retain` + 现有 `tg_live`** | 0（删除 `gone`） | 是（`BTreeSet` + 读锁） | 最低 | 只解决 `Vec`；`tg_live` 仍是全局堆，仍有 O(T log T)/轮 |
| **C2. `TgRec_` 增加 released 原子位 + 注册表脏位，`retain` 按位清理** | 0 | 否（只在有释放时 O(T)） | 中 | `release_telegraph_` 从 `bindings_` 取出 `TgOwner_` 后置位；注册表置“有 telegraph 释放”原子位；解复用 drain 后 `swap(false)`，需要时 `retain` 检查每个 owner 的位。**推荐** |
| **C3. 新增 `ReadEvent_::TgRelease`，事件驱动摘表** | 每次释放一条事件（`flume` 全局分配） | 否 | 中高 | 与 channel 的 `Release` 对称；但注册表目前不持有 `r_events` 发送端，需要调整构造顺序或把 sender 注入注册表；还要证明 `TgAttach`/`TgRelease` 的投递顺序。释放是冷路径，这条事件分配可接受 |

#### 3.2.3 建议

- 先做 **C1** 作为“去掉 `gone` Vec”的最小改动（`tg_table.retain` 内直接
  `entry.close_()`，返回 `false` 删除）。语义与现有按键升序 collect 后再 remove 一致。
- 目标做 **C2**：它同时删掉 `tg_live` 的全局 `BTreeSet`、每轮注册表读锁和 O(T log T)
  扫描，且不引入新事件。新增成本只是 `TgRec_` 里一个 `AtomicBool` 和注册表里一个
  `AtomicBool`。
- C3 可作为后续“事件驱动化”的统一方向，但本轮不必为它改构造顺序。

### 3.3 `reusable_docks_`（P5）

#### 3.3.1 必要性

池是必要的（避免 dock 号耗尽）；`VecDeque` 只是实现选择。它已经是注入分配器，
问题在于“动态增长 + 独立缓冲”。

#### 3.3.2 方案对比

| 方案 | 堆分配 | 容量上限 | 顺序 | 代价 |
| --- | --- | --- | --- | --- |
| **B1. 侵入式空闲链表（推荐）** | 0 | 无 | 可保持 FIFO（head/tail + `next_free`） | 在 `DockCtx_` 里加 `next_free: Option<Dock>`、`in_pool: bool`，注册表加 head/tail/len；push/pop O(1)；池项必须保留在 `docks_` 里（多一个 map 节点，数十字节量级），以换取零独立缓冲；`prune_dock_` 必须把 `in_pool` 视为非空；`bind_dock_` 留下的陈旧池项仍在链上，出队时按现有逻辑丢弃 |
| **B2. 定容环形数组** | 0 | `K_POOL_CAP` | FIFO | 注册表内联 `[Dock; K_POOL_CAP]`（`4 × K_POOL_CAP` 字节）；无堆、无 map 保留；但池满时要有策略（丢弃归还 / 回退游标 / 报错），且固定内存对多连接场景不友好 |
| **B3. 预分配 `VecDeque::with_capacity_in(K, A)`** | 1 次（每连接） | 软上限 | FIFO | 最简单；初始 K 个槽；超过 K 仍可增长（realloc）；仍有一个堆缓冲，但不满足零堆目标 |
| **B4. 去掉池，仅游标** | 0 | `[1024, wildcard)` | — | 长期运行会耗尽候选；不可接受 |

#### 3.3.3 建议

- 目标 **B1**：它消除独立缓冲，且保留 FIFO 语义；需要把 `DockCtx_::is_empty_`
  扩展为“未绑定、无子流、不欠归还、**不在池**”，并给 `assert_index_consistent_`
  增加“链表长度 = 池项数、无环、无重复”的断言。
- 如果担心池项保留 map 节点的内存，选 **B2**，但必须先定义池满策略和 `K_POOL_CAP`
  的配置归属（常量还是 `TrMaxAllocConfig`）。
- **B3** 只作为过渡：先消除首次 push 的 realloc，不满足最终目标。

### 3.4 空构造点（Z）

`Vec::new()` 不分配；它们会随 `Payload_`/`Vec<u8, A>` 的替换自动消失。重构时
**不要**为了“消灭 `Vec::new()` 字样”单独引入新类型；先把 P1/P3 的载荷类型定下来，

## 4. 汇总与建议顺序

| 优先级 | 项 | 改动 | 预期分配变化 | 公开 API | 风险 |
| --- | --- | --- | --- | --- | --- |
| S0 | P1+P2+P3 载荷链 | A0（连接级槽/控制环）+ A2（SBO）；A1 仅作过渡 | 非空 OPEN/REJECT：每次堆分配 → 0；小载荷不进池 | 不变 | 中：槽生命周期/背压、`ControlFrame_` 泛型化、事件尺寸 |
| S1 | P4 `gone` | C1 `retain` | 删除每次自查的临时 `Vec` | 不变 | 低 |
| S1 | P4 伴随 `tg_live` | C2 released 位 + 脏位 | 删除全局 `BTreeSet` 与每轮 O(T log T) 扫描 | 不变 | 中：`TgRec_`/注册表各加一个原子位，需补测试 |
| S2 | P5 `VecDeque` | B1 侵入式 FIFO 链表 | 每连接少一个动态缓冲；push/pop 零分配 | 不变 | 中：池不变量、`prune_dock_`、陈旧项处理 |
| S3 | T 测试 `Vec` | 可选清理 | 仅测试 | 不变 | 低，但收益也低 |
| — | Z/D | 随 P1/P3 自然收敛 / 不动 | — | — | — |

**建议讨论顺序**：先定 P1+P2+P3 的载荷类型（尤其是 `K_INLINE` 与 `max_packet_size`
的关系），再定 P4 用 C1 还是 C2，最后定 P5 用 B1 还是 B2。三项都可在不改公开 API
的前提下完成；任何“硬上限/调用方缓冲/协议改帧”的方案都必须先按 AGENTS §1 讨论。

实测（空开场消息，8 条子流）：

```text
[alloc] 建流 ×8        全局 211 次 / 17408 B    注入 93 次 / 200944 B
[alloc] 稳态搬运       全局 992 次 / 77824 B    注入 0 次 / 0 B
[alloc] 拆流 + EOF     全局 70 次 / 5888 B      注入 2 次 / 384 B
```

把开场消息临时改为 256 B 后：

```text

[alloc] 稳态搬运       全局 992 次 / 77824 B    注入 0 次
```

这组数字说明：数据面已零注入分配；控制面载荷的 `Vec` 成本可被计数，适合作为
A0/A2 的验收基线。

### 5.2 重构后应补的用例

1. **小载荷 SBO**：非空短消息（如 16 B）OPEN/REJECT，全局分配为 0；大载荷
   （> `K_INLINE` 且 ≤ `max_packet_size - K_MAX_FRAME_HEADER`）回落到注入分配，
   全局分配仍为 0。
2. **载荷完整性**：SBO 的 `Inline` 与 `Heap` 两条路径都要做端到端比对（字节一致、
   `payload_len` 正确、CRC/帧解析不受影响）。
3. **telegraph 释放**：开/关 N 个 telegraph 后，`tg_table` 中不残留条目，接收端
   `recv_async` 能读到关闭；C2 下还要断言“没有释放时不做全表 retain”。
4. **自动 dock 复用**：反复 `bind_async(unspecified)` / drop，池命中、无重复、
   无泄漏；B1 下断言池长度与链表一致、无环。
5. **分配计数**：在 `tests/alloc_count.rs` 增加上述区间，沿用现有
   `CountingGlobal` / `CountingAlloc`，并注意脚手架 `Vec` 在武装前分配。

### 5.3 测试超时

按项目纪律，单测/定向测试设置不超过 1 分钟超时；全量测试不超过 5 分钟。本文的
基线命令是单 target，正常在秒级完成。
