# 迁移 `gen_mcf2` / `abs_cancel` v0.2：编译修复与 `CancelAgnostic` 移除实验

> 范围：`smux_v1` 的 `src/handshake/agent.rs`、`src/handshake/codec_.rs`、`src/handshake/mod.rs`、`src/lib.rs`。
> 上游：`abs_buff`（`dev/0.3.0`）改为经 `gen_mcf2::gen_may_cancel_future` 提供宏；
> `abs_async_iter` / `abs_cancel`（`dev/0.2.0`）为 `abs_cancel` v0.2。

---

## 0. 结论速览

1. 本次编译错误**全部来自迁移提交 `eb81873`（"Migrate to `gen_mcf2` and `abs_cancel` v0.2"）未改干净的写法**，而不是核心协议逻辑有问题。共 4 类：`E0277` / `E0308`（残留 `Clone` 约束）、`E0309`（令牌生命周期）、`E0382`（令牌被 move）、`E0446`（可见性）。
2. **`CancelAgnostic` 在新宏下已不再需要，可以删除。** 旧宏会改写输出类型里的用户生命周期，新宏逐字保留输出类型；因此 `NextAsync` 现在可以直接由 `#[gen_may_cancel_future]` 生成的具名类型充当。实验已通过：`cargo check` / `clippy` 无警告，14 个单测 + 2 个文档测试全绿。
3. 取消令牌传播已全面改为 `child_token()`：全 crate 不再有任何 `TrCancellationToken: Clone` 约束，也没有对令牌的 `.clone()`。
4. 删除 `CancelAgnostic` 是**净收益**（去掉一个手写适配层，`NextAsync` 由不透明类型变成可命名的 `pub(crate)` 类型），但也带来两点需要知道的代价：每个 step future 都要生成一套类型机（模板代码变多），且生成的 step 函数形参里那个令牌目前是**语义惰性**的（见 §3.5、§6）。

---

## 1. 根因

### 1.1 上游两个变更

**(a) `gen_mcf_macro` → `gen_mcf2`。** 两个宏都导出同名属性 `gen_may_cancel_future`，但展开策略不同。与本次问题直接相关的一条差异：

| 维度 | `gen_mcf_macro`（旧） | `gen_mcf2`（新） |
| --- | --- | --- |
| 输出类型里的用户生命周期 | 由 `transform_output_lifetimes` 统一改写成「最后一个生命周期」`last_lt`（即取消令牌的借用生命周期） | **原样保留**；只在生成类型上追加 `'lt_fut__` |

旧宏的改写逻辑见 `gen_mcf_macro.rs/src/lib.rs:1017-1125`（`transform_output_lifetimes`），调用点在 `lib.rs:337`。新宏则把 `syn::ReturnType` 直接抄进 `{Prefix}Async` / `{Prefix}Future` 的 `Output`，见 `gen_mcf2/src/elements_.rs:140,173,205,249,275`（`model.output_ty_`）。

**(b) `abs_cancel` v0.1 → v0.2。** `TrCancellationToken` 去掉了 `Clone` 超 trait，新增关联类型与 `child_token(&self)`：

```rust
pub trait TrCancellationToken where Self: Send + Sync {
    type Cancellation: Future;
    type ChildToken: TrCancellationToken + Sized;
    fn is_cancelled(&self) -> bool;
    fn can_be_cancelled(&self) -> bool;
    fn child_token(&self) -> Self::ChildToken;   // 取代 clone
    fn cancellation(self) -> Self::Cancellation;
}
```

同时 `TrMayCancel::may_cancel_with` 改成**按值**接收令牌（`cancel: C`，约束 `C: 'a + TrCancellationToken`），而不再是 `&'a mut C`。后一条是 `negotiate_async` 生命周期报错的直接来源。

### 1.2 受影响的代码面

迁移提交把两处状态机与读状态的令牌都从「`&'f mut K` 借用」改成了「`K` 按值 + `child_token()`」，但漏掉了三件事：

- `impl TrAsyncIterator for &mut FrameReader` 上仍留着 `K: TrCancellationToken + Clone`；
- 把 `cancel` 按值传进子函数之后，仍有调用点在 move 之后继续借用它；
- `AcceptAllEntries` 被提为 `pub`，但它对应的生成类型没有同步放宽可见性。

## 2. 编译错误逐条修复

> 全部修复都只调整「受上游更新影响的写法」，协议语义、帧格式、状态机流程均未改动。

### 2.1 `E0277` / `E0308`：残留的 `Clone` 约束

`impl<'s, 'f, R, K> TrAsyncIterator for &'s mut FrameReader<'f, R, K>` 的约束写着 `K: TrCancellationToken + Clone`。v0.2 的 `Clone` 已不是 trait 超集，于是实参 `cancel.child_token()` 的类型 `<K as TrCancellationToken>::ChildToken` **无法证明**满足该 impl 的 `Clone`，一连串「`&mut FrameReader<'_, R, _>: TrAsyncIterator` 不满足」与 `negotiate_async` 的 `E0308` 都是它的连锁反应。

修复：删除 `+ Clone`（`src/handshake/codec_.rs`）。该 impl 及其调用链只使用 `child_token()`，本就不需要 `Clone`——这是迁移时的漏改。

### 2.2 `E0309`：`negotiate_async` 的令牌生命周期

```rust
async fn negotiate_async<'m, D, I, K>(
    negotiator: &'m mut D, entries: I, cancel: K,
) -> bool
where
    D: TrNegotiator,
    I: TrAsyncIterator<Item = D::Entry<'m>> + 'm,
    K: TrCancellationToken,          // ← 需要 + 'm
```

`D::ShouldAcceptAsync<'m, I>: TrMayCancel<'m>`，而 v0.2 的 `may_cancel_with<C>` 要求 `C: 'm`。令牌由「借用 `&'m mut K`」改为「按值 `K`」之后，这个 outlives 义务就必须显式写出。

修复：`K: TrCancellationToken + 'm`。实测在 `handshake_invite_async_` / `listen_handshake_async_` 的调用点（实参类型是 `<K as TrCancellationToken>::ChildToken`）该约束可被满足，没有引入新的限定。

### 2.3 `E0382`：令牌被 move 后仍被借用

`write_frame_async_` 现在按值收令牌，但两处「先把令牌 move 进去写帧、后面还要读下一帧」的调用点仍按旧写法传 `cancel`：

- `handshake_invite_async_`：写 `CONFIRM` 后又 `begin_async_` 读空 `CONFRM`；
- `listen_handshake_async_`：写 `ACCEPT` 后又 `begin_async_` 读 `CONFIRM`。

修复：这两处改为 `cancel.child_token()`。其余调用点都是「传完即 `return`」，保持按值移交更直白，其中发起方 `Inconsistent` 分支原来写了 `cancel.child_token()` 却配 `<W, K, R::Err>` 的 turbofish（`E0308`），一并改回按值 `cancel`。

**约定**：令牌的「最后一次使用」按值移交；之后还要继续使用的，一律交 `child_token()` 子令牌。

### 2.4 `E0446`：公开的 `AcceptAllEntries` 泄漏私有生成类型

迁移提交把 `AcceptAllEntries` 从 `#[cfg(test)] pub(crate)` 提为 `pub struct`（模块路径 `smux_v1::handshake::agent::AcceptAllEntries`），但宏调用仍是 `#[gen_may_cancel_future(AcceptAll)]`，生成的 `AcceptAllAsync` 与输入函数同为私有，于是它的 `impl TrNegotiator` 里 `type ShouldAcceptAsync = AcceptAllAsync<...>` 触发「private type in public interface」。

修复：`#[gen_may_cancel_future(AcceptAll, pub)]`。这与同一文件里 `HandshakeInvite` / `ListenHandshake`、以及测试里的 `CapPacketSizeAccept` 的写法一致。

### 2.5 顺带清理（同属迁移遗留）

- `src/lib.rs`：删除 `#![feature(unboxed_closures)]` 与 `#![feature(min_specialization)]`。这两个 nightly feature 是旧宏的 `impl AsyncFnOnce` 方案遗留；新宏改用「`impl Trait` in assoc type 的私有工厂 trait」，只需 `#![feature(impl_trait_in_assoc_type)]`（`gen_mcf2/README.md` 已说明）。**注意 `impl_trait_in_assoc_type` 仍然必需**——宏生成的工厂 impl 里仍有 `type MadeFuture = impl Future<...>`；实验性删除它会得到 `E0658`。
- `agent.rs` / `mod.rs`：把迁移提交重命名后仍指向旧名的文档链接 `[`HandshakeEndpoint`]` 全部改为 `[`HandshakeDelivery`]`，消除 3 条 `cargo doc` 链接告警。
- `agent.rs` 测试模块：删掉未使用的 `TrMayCancel` 导入。

## 3. `CancelAgnostic` 移除实验

### 3.1 它当初为什么存在

`TrAsyncIterator::next_async` 的签名要求返回类型同时满足：

```rust
type NextAsync<'f>: TrMayCancel<'f, MayCancelOutput = Result<Option<Self::Item>, Self::Err>>
where Self: 'f;
```

`Item` 是固定类型 `NegotiationEntry<'s>`（`'s` 是 `&'s mut FrameReader` 的外层借用）。若用旧宏生成 step future，宏会把输出类型里的 `'s` 改写成 may-cancel 借用生命周期 `'g`，使 `MayCancelOutput` 变成 `Result<Option<NegotiationEntry<'g>>, _>`，与 GAT 要求固定 `Item` 冲突（旧代码注释记录为实测 `E0271`）。因此只能手写一个适配层 `CancelAgnostic<F>`：包住任意 future，`may_cancel_with` 直接返回自身。

### 3.2 新宏为什么可行

新宏**逐字保留输出类型**（§1.1）。把 step 逻辑写成模块级 `async fn` 并显式声明 `'s`、让它只出现在返回类型里，宏就会把 `'s` 原样带到 `MayCancelOutput`；`'s` 只作为 `PhantomData<&'s ()>` 标记字段出现在生成类型中。于是 `NextAsync` 可以直接写成具名类型。

实测展开（`cargo rustc --lib -- -Zunpretty=expanded`，节选）：

```rust
pub(crate) struct NextEntryAsync<'s, 'f, 'r, 'lt_fut__, R, K>(
    &'r mut FrameReader<'f, R, K>,
    PhantomData<&'lt_fut__ ()>,
    PhantomData<&'s ()>,
) where 'f: 's, R: TrBuffRead<u8> + 'f, K: TrCancellationToken + 'f,
        's: 'lt_fut__, 'f: 'lt_fut__, 'r: 'lt_fut__;

impl<...> TrMayCancel<'lt_fut__> for NextEntryAsync<'s, 'f, 'r, 'lt_fut__, R, K> {
    type MayCancelFuture<'lt_mcf__, TyTok__> =
        NextEntryFuture<'s, 'f, 'r, 'lt_mcf__, R, K, TyTok__> where ...;
    type MayCancelOutput = Result<Option<NegotiationEntry<'s>>, StreamEnd_>;   // 's 原样保留
    ...
}

impl<'s, 'f, R, K> TrAsyncIterator for &'s mut FrameReader<'f, R, K>
where R: TrBuffRead<u8> + 'f, K: TrCancellationToken + 'f {
    type Item = NegotiationEntry<'s>;
    type Err = StreamEnd_;
    type NextAsync<'g> = NextEntryAsync<'s, 'f, 'g, 'g, R, K> where Self: 'g;
    fn next_async(&mut self) -> Self::NextAsync<'_> { NextEntryAsync::new(&mut **self) }
}
```

### 3.3 生命周期对齐

step 函数需要三个生命周期，生成类型的泛型顺序是「用户生命周期按声明序 → `'lt_fut__` → 类型参数」：

| step fn 里的角色 | 声明 | 生成类型里的槽位 | 别名 `NextAsync<'g>` 的实参 |
| --- | --- | --- | --- |
| 条目对外生命周期（`Item`） | `'s` | `'s` | `'s`（来自 impl） |
| 读缓冲借用 | `'f` | `'f` | `'f`（来自 impl） |
| 本次读取对 reader 的借用 | `'r` | `'r` | `'g`（= `&mut self` 的借用） |
| may-cancel 借用 | 无（宏追加） | `'lt_fut__` | `'g` |

变形的根源是 `Item` 必须固定为 `NegotiationEntry<'s>`，而 future 实际持有的是对 `self` 的**再借用** `'g`；两者靠 `'f: 's` 上的协变（`NegotiationEntry<'f>` 收窄成 `<'s>`）打通。因此 step fn 的 where 子句里必须显式写出 `'f: 's`。

### 3.4 实验结果

删除 `pub(crate) struct CancelAgnostic<F>` 及其两个 impl，代之以：

```rust
#[gen_may_cancel_future(NextEntry, pub(crate))]
async fn next_entry_async_<'s, 'f, 'r, R, K, C>(
    reader: &'r mut FrameReader<'f, R, K>,
    _cancel: C,
) -> Result<Option<NegotiationEntry<'s>>, StreamEnd_>
where
    'f: 's,
    R: TrBuffRead<u8> + 'f,
    K: TrCancellationToken + 'f,
    C: TrCancellationToken,
{ /* 原来的 async 块逐行搬入 */ }
```

`cargo check --all-targets`、`cargo clippy --all-targets` 无警告；14 个单测与 2 个文档测试全通过；`cargo doc --no-deps` 无告警。**结论：可以移除。**

### 3.5 语义等价性与取消路径

- `may_cancel_with(token)` 的**可观测行为不变**。旧 `CancelAgnostic` 忽略令牌；新生成的 `NextEntryFuture` 把令牌收下并原样交给 step 函数，而 step 函数把它命名为 `_cancel` 不使用。二者在「本层是否响应这个令牌」上完全一致。
- 读侧取消本来就**不靠这个令牌**：`FrameReader` 在 `begin_async_` 时收下一枚子令牌存放在 `cancel_`，之后每次 `read_async` 都用 `self.cancel_.child_token()` 施加取消；`negotiate_async` 交给协商器的那枚令牌是**同一个握手令牌的另一个子令牌**。因此设计器沿用的公开约定（"取消发生在帧中途时判定 `HandshakeError::Cancelled`"）不受影响。
- 唯一差别是令牌存活时间略变长（从 `may_cancel_with` 立即丢弃，变为随 future 存活到首次 poll 并传入 step 函数），对本协议无影响。

### 3.6 保留意见：什么时候仍然要手写适配层

`CancelAgnostic` 被删掉是因为**全 crate 只有这一处**需要「把任意 future 补成 `TrMayCancel`」，而它正好可以改写成宏能处理的 `async fn`。这不代表该模式本身过时：

- 若将来需要适配的对象不是「一个可写成 `async fn` 的步骤」，而是**外部传入的既有 future**（例如把 `TrBuffRead::read_async` 的返回 future 直接塞进某个需要 `TrMayCancel` 的槽位），则没有对应的 `async fn` 可标注，仍需手写适配层；
- 生成方案的模板代码量明显更大（每处多出一个 `{Prefix}Async`、`{Prefix}Future` 与工厂 trait/impl），单文件 step 数量很多时，手写一个泛型 `CancelAgnostic` 更省。

因此结论是「本处的 `CancelAgnostic` 可以且应该移除」，而非「该适配模式应被废弃」。

## 4. 取消令牌传播审计

迁移遗留的 `Clone` 用法已清零：

- 不再有 `TrCancellationToken` 的 `Clone` 约束（`codec_.rs` / `agent.rs` 全部为 `K: TrCancellationToken [+ 'f / + 'm]`）；
- 需要「保留父令牌、同时把取消能力交给子操作」的位置一律 `child_token()`：`FrameCursor::read_async_`、`write_all_`、`write_frame_`、`FrameReader::begin_async_` / `next_entry_async_`、`write_frame_async_`、`negotiate_async`、`accept_all_async_`，以及两处状态机的各次子调用；
- 剩余 `.clone()` 只作用于协议数据（`NegotiationBasicEntry`）与 CRC 增量状态（`CrcDigest`），与取消无关。

## 6. 风险与遗留

1. **`next_entry_async_` 的 `_cancel` 是惰性形参。** 它满足 `gen_mcf2` 的语法约定（末位按值令牌），但本层不消费它。这与 `CancelAgnostic` 时代一致，也是 `FrameReader` 自持令牌这一设计的必然结果；但按 `AGENTS.md` 纪律 4 的字面要求，实现「不应假定调用者不会通过取消令牌发送主动取消」，此处严格说是靠 `FrameReader::cancel_` 这条另一路径来满足的。若将来把「读侧令牌」统一为由调用者逐次传入（而非状态机自持），则这个惰性形参会自然变成真实信号——那是设计调整，不在本次「不改核心逻辑」的范围内。
2. **取消路径缺少测试覆盖。** 现有 14 个测试没有覆盖「帧中途取消 → `HandshakeError::Cancelled`」。工作区内目前只有 `NonCancellableToken` / `CancelledToken`，没有可翻转的测试令牌，补这条用例需要引入测试令牌与阻塞读的桩。
3. `AcceptAllEntries` 的公开化是迁移提交已作出的决定；本笔记只补齐了它要求的生成可见性，不改变该决定。
