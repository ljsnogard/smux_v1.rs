## 2. 三个决策点

### 2.1 谁来驱动本地队列：`smol::block_on(scope.run_until(..))`

- tokio 壳用 `#[tokio::test]`（运行时自带执行体）；
- compio 壳用 `#[compio::test]`（thread-local `Runtime` 自己驱动）；
- **smol 没有隐式运行时上下文**：`abs_art-smol` 的本地队列是本线程 `thread_local!` 里的
  `Rc<LocalExecutor<'static>>`（`local_scope.rs` 的模块文档原话是「队列归本线程，且是
  `!Send`」）。因此壳写成普通 `#[test]`，用 `smol::block_on` 当**外部阻塞驱动源**，把
  `scope.run_until(scenario)` 跑起来——这也正是 `abs_art-smol` 文档给出的标准用法。

### 2.2 怎么拆读写半边：`smol::io::split`

`async-net` 2.0 的 `UnixStream` **没有** `into_split`（tokio 与 compio 都有），因此 smol
版用 `futures_lite::io::split`（即 `smol::io::split`）拆成 `ReadHalf` / `WriteHalf`：
它内部用一把 `Arc<Mutex<T>>` 共享同一条流，只在 `poll_read` / `poll_write` 期间持锁、
临界区极短，语义上与 `into_split` 等价——两个半边仍指向同一条全双工连接。

### 2.3 `buffex_smol_adapt` 的「按需驱动」正好贴合这条链路

连接层把五个循环投进本地作用域，传输侧是**调用方 await 的四条泵**
（`pump_input_` / `pump_output_`，见 `tests/common/pump_.rs`）。`buffex_smol_adapt` 的
设备适配层不 spawn 任何任务、搬运挂在调用方的 poll 上，因此这里**不需要**给适配器准备
任何执行体，装配与 tokio 侧逐字同构——这正是它上一轮放弃 `smol::spawn` 换来的好处
（因果见 `../../buffex_smol_adapt/dev-notes/smol_adapt-20261006-2130.md` §3）。

## 3. 三 feature 互斥

与原有两条一样，`test-smol-runtime` 只打开 bridge 的**一个** backend
（`abs_art-bridge/backend-smol`），因此「裸名 `Runtime` 是谁」仍有唯一解。跑 smol 装配
必须显式关掉缺省（否则 compio 与 smol 两个 backend 同时进入并集，bridge 的守护会让
manifest 解析失败）：

```bash
cargo test --test smoke_smol --no-default-features --features test-smol-runtime
```

`just test-smol` 就是这条；它已接进 `just test` 的串行链（排在 `test-tokio` 之前）。

## 4. 实测结果（2026-10-06）

三个装配各自的四条冒烟用例全部通过：

| 装配 | 命令 | 结果 |
| --- | --- | --- |
| compio（缺省） | `cargo test --test smoke_compio` | 4 passed（9.84 s） |
| tokio | `cargo test --test smoke_tokio --no-default-features --features test-tokio-runtime` | 4 passed（6.88 s） |
| **smol** | `cargo test --test smoke_smol --no-default-features --features test-smol-runtime` | **4 passed（7.25 s）** |

四条用例是 `smoke_socket` / `small_socket` / `flow_ctrl_socket` /
`flow_ctrl_isolation_socket`；后两条带 20 秒看门狗（smol 侧用 `smol::Timer` +
`futures::future::select` 竞速），它们顺带把「窗口用尽 → 回补」这条路径在 smol 上也验了
一遍。

**结论**：`buffex_smol_adapt`（设备级适配 + 调用方驱动的泵 + 全被动 `buffex::ring` 环）
与连接层的对接没有问题——类型层面（`tests/smoke_common.inc` 里的
`assert_smol_adapters_fit_`）与运行层面（真实 UNIX domain socket、16 dock × 1024 条子流
的冒烟）都成立。
