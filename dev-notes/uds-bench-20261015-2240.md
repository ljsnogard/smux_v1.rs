# smux_v1_uds_bench：三后端 × 两环境的 UDS 性能测试

日期：2026-10-15（`smux_v1_uds_bench` 立项当轮）

## 1. 要做的事

在 `smux_v1` 项目里加一个性能测试项目：用 **compio / smol / tokio** 三个后端各实现一个
基于 UNIX domain socket 的 C/S 结构，客户端依次发起 **2 / 4 / 8 / 16** 个并发客户端，
向同一个服务端发数据，测**平均带宽**与**每个发送任务完成时间的方差**；对照组是
「用 `smux_v1` 的复用 channel 代替真实 UDS stream，完成完全相同的任务」。

## 2. 关键决策与因果

### 2.1 两条路径都走适配器 —— 否则差值无法归因

`raw` 路径本可以直接读写 socket 的 `AsyncRead` / `AsyncWrite`。若真那样做，`raw ↔ smux`
的差值会同时包含「环形缓冲 vs 直连设备」与「N 条真 socket vs 1 条 socket 上的复用子流」
两项。因此两条路径都用 `buffex_*_adapt` 的环，**唯一差别只剩传输形态**。

### 2.2 墙钟取「所有发送任务发完」，服务端收齐只作参考量

最初把墙钟定为「服务端收齐最后一条流」，问题有两个：

1. 它受环容量、`--chunk`、适配器排空策略支配——「换个大环」会凭空改变带宽读数；
2. 两条路径的排空路径长度不同（smux 还要等 `FIN` 走完子流 → 复用 → 传输三层），
   于是「协议开销」被算进了带宽差。

改成「栅栏释放 → 最后一个发送任务写完最后一字节」之后，两条路径的口径严格一致；
服务端收齐（`drained_secs`）仍写进报告，作为「数据确实走完了」的参考。

### 2.3 真并发的证据量：并发因子

只报方差会漏掉「所有任务都很慢且完全同步」这种形态，因此报告里同时给
`并发因子 = Σ(任务时长) / 墙钟`：串行时趋近 `1.0`，N 个任务真同时推进时趋近 `N`。
实测（release，tokio）：raw N=16 的并发因子 16.00，smux N=16 约 12，说明复用路径上
确实存在收尾拖尾（复用循环要按窗口轮转，比 N 条独立 socket 更容易串起来）。

### 2.4 两种环境：单跑器与多跑器

初版只在**单线程**里跑全部用例，说服力不足。现在把「用例」与「跑器线程」分开：

```text
--runners 1     全部用例依次在同一个线程、同一个运行时上跑完（干净基线）
--runners N > 1 N 个工作线程，各自持有自己的运行时与本地作用域，从共享队列取用例并列跑
```

**为什么不能把一个用例拆到多个线程**：`smux_v1` 的连接内部循环（解复用 / 复用 / 计时）
是 `spawn_local` 投出去的 `!Send` 任务，一条连接只能属于一个线程。并列只能来自
「多个用例分布到多个线程」——这也正是真实应用里多连接并存的形态。

## 3. 三个后端的运行时就绪条件（踩过的坑）

这一节是本轮最值钱的部分：三个后端的「能跑起来」条件各不相同，而且**症状都是静默挂起**。

### 3.1 tokio：写侧必须用自驱动适配器，且它必须活在一个显式作用域里

> **后续（`2026-10`，见 `dev-notes/flush-contract-*.md`）**：本节第 1 条"必须用
> `try_new_local`"已经**不再成立**——`abs_buff` 补了 `TrBuffTryFlush` / `TrBuffFlush`，
> `smux_v1` 现在握手每帧后 `flush_async`、连接退出时 `close`，因此按需形态 `try_new`
> 也能把帧推出去。仍然成立的是第 2 条：**用例必须活在一个连续被驱动的作用域里**
> （连接循环与（若用）自驱动泵都挂在本地队列上）。

- 现象：握手永远完不成——服务端在 `listen` 里等 `INVITE`，客户端在 `invite` 里等
  `ACCEPT`，两边都停在自己的读上，**没有任何报错**。
- 根因：`buffex_tokio_adapt::BuffWrite::try_new`（按需形态）只把「环 → 设备」推进放在
  调用方的 `write_async` / `flush_async` 上；而 `smux_v1` 的复用循环把帧提交进环之后
  就走了，于是字节永远留在环里。
- 修法：
  1. 写侧改用 `try_new_local`（自驱动：构造时把泵投到本线程 `LocalSet`）；
  2. **并且**让整格用例活在一个**显式作用域**里——泵是 `LocalSet` 上的任务，
     本地队列必须被持续驱动。

为此引入了 `Drive` trait：`with_scope` 把「跑这一格」交给后端自己驱动，
`drive` 负责建运行时。三后端的 `with_scope` 形态因此一致，用例逻辑逐字相同。

### 3.2 compio：`CURRENT_RUNTIME` 是 thread-local，取运行时值之前必须先有它

- 现象：`取运行时值时调用点不在所选后端的运行时上下文内`（facade 的守护 panic）。
- 根因：`Runtime::current()` 读的是 `scoped_thread_local!` 里的当前运行时；
  `#[compio::main]` 之外没有任何东西会设置它。
- 修法：`Drive::drive` 里先 `compio::runtime::Runtime::new()`，再在它里面取运行时值。
  每个跑器线程一个 compio 运行时实例。

### 3.3 smol：没有隐式运行时上下文

本地队列在本线程 `thread_local!` 里的 `LocalExecutor`，必须由调用方驱动；
`smol::block_on(scope.run_until(..))` 同时驱动队列与用例。
UNIX socket 类型要用 `async_net::unix::{UnixListener, UnixStream}`
（`smol::net` 不导出它们）。

### 3.4 拨号重试是必需的

两端在同一个进程里并发起步，客户端可能比服务端的 `bind` 早一步（拿到 `ENOENT`）。
真实 C/S 也有同样的先后竞态，因此客户端做「重试 + 退避」（20 ms × 100 次）。

### 3.5 一格一个 socket 路径

路径里含进程号、用例号与轮次（`smux_v1_uds_bench_<pid>/case<n>_r<m>.sock`），
多跑器线程之间也不会互踩；`run_case_task` 自己按需建目录（集成测试不走 `run_matrix`）。

## 4. 一个真实 bug：JSONL 首字段多了一个逗号

现象：`{,"runtime":"tokio""mode":"raw",...}` —— 既不是合法 JSON，也缺分隔符。

根因：`push_field_*` 的最后一个实参语义是「**要不要在前面补逗号**」，而调用点把它读成了
「是不是最后一个字段」：首字段传了 `true`，第二字段也传了 `false`。

修法：把语义写成明确的「首字段 `false`、其余 `true`」，并把这条纪律写进函数文档；
同时补两条回归断言（首字段形状 + 相邻字段之间的分隔符），
以及一个**黑盒验证**：跑一格小用例后用 `json.loads` 逐行解析 JSONL。

> 教训：手写 JSON 序列化时，「分隔符由调用点决定」这种设计极易被误读。
> 更稳的写法是让 `push_field_*` 自己维护「是否已写过字段」的状态。

## 5. 结果怎么读

- `results/summary.md`：三后端 × 两环境的总表（由 `scripts/merge_results.py` 合并）；
- 每格的 `bench-<后端>-summary.md`：逐格表、`raw ↔ smux` 对照、结论、失败清单；
- `bench-<后端>.jsonl`：原始记录（一行一个用例，字段见 `report::CaseResult::to_json_line`）。

## 6. 遗留

- `smux_v1` 的连接在**多跑器**下每条连接仍只跑在一个线程上（API 使然）；
  若将来出现 `Send` 的连接形态，本 bench 的 `Drive` 抽象可以直接复用。
- `--no-verify` 目前只跳过 CRC 核对；长度核对仍在（空转的用例会立刻暴露）。
- 报告里的 `drained_secs` 只给了墙钟侧的一段，未做逐任务的服务端完成时刻采集
  （`hub::TaskTime` 留了 `server_end_ns` 字段的位置，将来要加不必改结构体）。
