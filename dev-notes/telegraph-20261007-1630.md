# telegraph（数据报）落地：语义裁决与实现记要

> 主题：`connection` 模块的 telegraph 数据报通道。
> 本文记录**已定稿的语义**、**最终实现形状**，以及实现过程中撞到的两个真 bug
> （都在收发链路上，且都被真实 socket 与进程内直连两条路径验证过）。
> 弃用的中间结论已按「文档先清理」删掉，只留最终链条。

---

## 1. 本轮定稿的语义（用户裁决）

telegraph 按 **UDP 的行为**执行：

1. **一次提交 = 一条报文 = 一条 `DATAGRAM` 帧**。报文边界就是调用者一次 Send 时通过
   `Demand` 实际提交的量；`MuxConnection` 尽力多给、可跨段，但不超过最大帧长度。
2. **长度在发送前已知**：报文长度由提交那一刻确定，帧头的 `PayloadLen` 直接照搬，
   因此接收端**不需要**任何长度前缀，也**不截断**。
3. **接收端整条丢弃**：接收环（或长度队列）装不下整条报文时**丢弃该条**，不写半条、
   不重传、不阻塞；丢弃计入 metrics（`on_datagram_dropped`）。
4. **不参与流控**：没有接收窗口、没有 `WINDOW_UPDATE`、没有信用回补，计时循环也不为
   telegraph 建任何时钟。
5. **`remote_dock` 是地址不是身份，且逐次给出**：`open_telegraph_async` **只**指定
   **本端** `local_dock`（它就来自 binding），**不收对端地址**；对端地址是
   `send_async(remote_dock, demand)` 的实参——同一条 telegraph 可以对不同目的地发报文，
   就像 UDP 的 `sendto`。对端据此索引自己的端点（帧头的 `remote_dock` = 对端的
   `local_dock`），与协议文档 §4 一致。
6. **身份由两个半边共同持有**：tx / rx 各持一份守卫，最后一份被丢弃时才释放身份。

### 1.1 被推翻的中间结论（保留因果，避免重犯）

- **截断标志**：曾计划「长度前标配一个截断标志、能填多少填多少」。**否决**——用户裁决
  「缓存不够就整个报文丢弃」，半条会破坏「`recv_async` 返回的长度就是下一条报文长度」
  的契约。
- **环内长度前缀**：曾计划在环里塞 `[len][payload]` 记录。**否决**——报文长度在发送前
  已知，帧头已经承载它；环里只存**纯载荷字节**，边界记在两个**长度队列**里。

## 3. 两个真 bug（均已修复并被两条路径验证）

### 3.1 对端地址没贯通到编码处（路由失配 + 帧流错位）

- **现象**：接收侧 `frame_parser_` 报 `UnsupportedField`（帧首字节不是合法 kind），
  且 `Datagram` 派发分支的命中计数为 0。
- **根因（两个叠加的设计错误）**：

  1. 我一开始把对端地址**硬编码**成了 `Dock::unspecified()`，对端按自己的 `local_dock`
     （如 11）索引不到端点，于是**静默丢弃**；而丢帧时**没有消费帧头之后的载荷**，
     解析器从载荷中间继续找帧首字节 —— 帧流整体错位。
  2. 随后又把它改成「`open_telegraph_async` 时固定对端地址」——**方向仍然不对**：数据报
     的远端是**地址**不是身份，同一端点可以对不同目的地发报文，因此它属于
     `send_async` 的实参（UDP `sendto`），不属于端点。

- **修复**：`send_async(remote_dock, demand)` 逐次给地址；地址与长度一起按 FIFO 记进
  发送条目队列（槽位把 `(dock, len)` 打包进一个 `usize`，保住「一条 release/acquire 链」
  的可见性），循环从队头取出地址用于编码帧头。
- **教训**：这类「某字段在两侧语义不同」的错误不会报协议错，只表现为「对端收不到
  + 后续帧错位」，**必须用「发送帧头 / 接收帧头」两侧对照打印**才能一眼看见。

### 3.2 `move_items_to_segm` 是整段搬运，必须先把源段裁剪到本条长度

- **现象**：接收侧载荷长度对不上（5 字节的那条之后读到 `0xab`，即 200 字节报文的
  填充字节）；发送侧自检查显示 `搬移量 205 != 5`。
- **根因**：`TrBuffSegmMut::move_items_to_segm` 的语义是**整段搬运**——它循环搬完
  源段里**全部**剩余数据，`take` 只影响 `dst` 的容量判断，**不是**「只搬这么多」。
  环里排着后续报文的载荷时，它会把下一条的开头也搬进这一帧。
- **修复**：先用 `take_segm_ref(Demand::exactly(left))` 把源段**裁剪**到本条报文的
  剩余长度，再搬；`self` 的剩余量随之减少，多搬在构造上不再可能。

  ```rust
  let mut piece = src.as_segm_ref();
  let ask = Demand::exactly(left);
  let Option::Some(mut piece) = piece.take_segm_ref(&ask) else { … };
  let take = core::cmp::min(left, piece.least_count());
  let moved = piece.move_items_to_segm(&mut dst);
  ```

- **教训**：`tr y_read` 借出的段常常比你要的多；凡是要「按长度切分」，必须在**源段**
  上收口，而不是在搬移调用的返回值上收口。

### 3.3 顺带修掉的健壮性问题

- **`write_frame_to_stage_` 的原子性**：帧头一旦写出就无法回退，因此要求写环当前至少有
  `帧头 + 载荷` 的空间才动手，否则整帧推迟到下一轮（不消费发送环、不出队长记录）。
- **超长报文**：单条报文超过 `max_packet_size` 时**整条丢弃并计入同一个丢弃计数器**，
  不能把连接判失败、也不能留在队头把后面的报文堵死。
- **未提交量的算法**：`send_async` 用「环内可读量 − 长度队列字节数」；它成立的前提是
  **两项同步递减**（循环每成功送出一条就 `try_pop_`），所以 `try_pop_` 必须紧邻写出成功
  之后。

## 4.1 prepare 契约的合并（去重）

`TrPrepareTelegraphRing` / `TelegraphRingAlloc` 一开始被我另立了一份，理由只是「channel 与
telegraph 是两条路径」。实际比对（去掉文档注释后逐字对比）显示两份的泛型约束、字段、
`new` / `destruct` **完全一致**，没有任何语义差异——「一个端点需要两块环内存」这件事与
「它是 channel 还是 telegraph」无关。

因此合并为一套，命名取中性的、**没有旧名残留**：

```rust
// chan.rs —— channel 与 telegraph 共用的唯一一套
pub struct RingBuffAlloc<B, T> { pub tx_buff: B, pub rx_buff: B, … }
pub trait TrPrepareRing<B, T> { fn prepare(self) -> RingBuffAlloc<B, T>; }
```

`TrDockBinding::open_telegraph_async` 与 `TrChannelHandle::accept_async` 收的是**同一个**
`TrPrepareRing`——为 channel 写好的 prepare 类型可以直接复用到 telegraph 上。

### 改名过程中记下的一个坑（避免重犯）

过渡方案本来可以把旧名留成**类型别名**（`pub type ChannelBuffAlloc<B,T> = RingBuffAlloc<B,T>;`
与 `pub use TrPrepareRing as TrPrepareChannelRing;`），让既有调用点零改动。这里有两件事值得记：

- **别名不能用「父 trait + blanket impl」实现**：那会让下游既有的
  `impl TrPrepareChannelRing for X` 与 blanket impl 撞车（冲突实现）。trait 别名必须是
  `pub use Trait as OldName;`，它才是**同一个** trait，`impl` 零冲突。
- **但最终没有保留别名**：项目还在「下游尚未形成」的阶段，留两个名字只会让后续每一处
  文档、示例与错误信息都要回答「该用哪个」。用户拍板趁早换成唯一命名——因此现在
  `ChannelBuffAlloc` / `TrPrepareChannelRing` 在整个仓库里**不存在**。

## 5. 遗留与既有缺陷

1. **「身份释放后可重开同一 `local_dock`」尚未单独写用例**。语义由
   [`TgIdentityGuard_`] 的「最后一份强引用」保证：`Telegraph::split` 会把身份守卫
   克隆成两份交给 tx / rx，任一份先丢都不释放；两份都丢掉时由最后那份投递
   `ReleaseTelegraph`。注意这里**不需要** `DockBinding` 存活——`bind_async` 交出的
   `DockBinding` 只负责「本端 dock 的绑定独占」，telegraph 自身的可用性由
   `MuxConnection` 智能指针 + 身份守卫保证（与 channel 的两个半边同形）。
2. 上游 `abs_smux` 的改动推到 `dev/0.1.0` 后，把 `Cargo.toml` 换回 git spec 并更新
   `Cargo.lock`。
3. **`use` 导入规范有 4 处既有违规**（本次改动前就在）：`src/connection/mod.rs:542`
   与 `src/lib.rs:60` 的重复 crate 根、`tests/inmem_mux.rs:34`（`core`）与
   `:61`（`abs_smux`）。本次新引入的那一处已手工合并
   （`tests/common/closure_.rs` 的 `abs_smux`）。其余 4 处未动：修复它们是独立的一件事，
   且按项目纪律 `--fix` 前要先建立可回退点。
4. **`tests/inmem_mux.rs` 的 `current_rt_()` 只分派 tokio / compio**（既有代码
   `git show HEAD` 即如此）：在 `--no-default-features --features test-smol-runtime`
   下 **`--all-targets` 编译不过**（它会在 `not(test-tokio-runtime)` 分支里取
   `abs_art_compio::current()`）。历史记录里 smol 只单独跑过 `smoke_smol`，因此这条
   一直没暴露。本次新增的 `telegraph_socket_smol_` 走的是 smol 专属 target（编译与
   运行都通过），未触碰该缺陷。
