## 0. 结论摘要

1. **相对旧版 `aa3e402`，当前版本不是“全面下降”，而是“低并发下降、高并发持平或略升”**：
   - tokio：N=2 **−17%**，N=4 −2%，N=8 **+2%**，N=16 **+2.5%**；
   - compio：N=2 **−36%**，N=4 −26%，N=8 −23%，N=16 −14%。
   - raw 对照组几乎不变（×0.98–1.00），排除机器/链路漂移。
2. **根因已定位到控制通道的忙等自旋**：`MpmcChanCfg_::FAST_SPIN = 512`。新版把两条 `Attach` inbox 和 `main_loop` 请求队列改成 `mpmc_chan`，而这三个 `RecvFuture` 在 **每次 poll 空队列时先做 512 次无锁尝试 + `spin_loop`**；mux/demux 又在**每轮循环里重建**这些 park future。低并发时循环频繁 park，自旋成本占用户态周期 **30%（tokio N=2）/ 44%（compio N=2）**；旧版对应路径为 0%。
3. **补丁已落地（R23）**：把连接控制通道的 `FAST_SPIN` 从 512 改为 0 后，同一台机器上：
   - tokio N=2：62.0 → **91.8 MiB/s（+48%）**；N=16：65.0 → **71.7（+10%）**；
   - compio N=2：49.1 → **86.2（+76%）**；N=16：63.8 → **85.3（+34%）**；
   - smol N=2：43.5 → **55.7（+28%）**；N=16：48.2 → **55.1（+14%）**；
   - 所有已测 N 均已**超过旧版 12–30%**；`task_cv` 与并发因子同时改善。
4. **内存不是问题**：新版峰值 RSS 在 N=16 反而低约 10%；N=8 基本持平（约 69 MiB）。heaptrack 显示分配次数从 **103,590 → 552（−99.5%）**，峰值堆 +5.5%；进程退出时的未释放量主要是 detached 任务仍持有的环，不足以判定泄漏。
5. **平稳性**：聚合带宽的 run-to-run CV 新版不差（0.1%–2.6%）；但新版的**单子流完成时间方差**在 N≥4 变差（compio N=16：30.0% → 34.7%），并发因子下降；补丁把这两项恢复到旧版水平甚至更好。

### 3.2 热点分类（`perf record` 自耗时，占用户态周期）

| 用例 | smux 业务 | `mpmc_chan` 轮询 | memmove/memcpy | runtime/框架 | 锁/自旋 |
| --- | ---: | ---: | ---: | ---: | ---: |
| tokio N=2 old | 81.9% | 0% | 9.9% | 4.6% | 0.7% |
| tokio N=2 cur | 55.7% | **30.2%** | 7.7% | 2.8% | 0.1% |
| compio N=2 old | 78.4% | 0% | 13.9% | 3.3% | 0.7% |
| compio N=2 cur | 45.0% | **43.6%** | 7.3% | 1.4% | 0.1% |
| compio N=16 cur | 56.3% | **28.0%** | 10.5% | 1.5% | 0.2% |

`mpmc_chan` 项的热点符号分别是：

- `RecvFuture<WriteAttach_<...>>::poll`：compio N=2 占 **19.6%**；
- `RecvFuture<ReadAttach_<...>>::poll`：**13.6%**；
- `RecvFuture<MainLoopRequest_<...>>::poll`：**10.0%**。

旧版对应位置是单条 `EventReceiver_` 事件通道，poll 为空时直接 park，没有这段自旋。

### 3.3 机制

`mpmc-chan` 的 `recv_async_` 快路径失败后，会按 `Cfg::FAST_SPIN` 做有界自旋：

```text
try_pop_fast_() 失败
  → for _ in 0..FAST_SPIN { try_pop_fast_(); spin_loop(); }
  → 真正注册等待节点并 park
```

连接侧的 `MpmcChanCfg_` 把 `FAST_SPIN` 设成 **512**（原本是给“数据面、随时可能有元素”的通道调低延迟用的）。但：

- 两条 `Attach` inbox 与 `main_loop` 请求队列都是**低频控制通道**；
- mux 的 `attach_fut` 在 **`loop` 内每轮新建**（`session_/mux_.rs:424`），demux 的 attach future 同理（`session_/demux_read_.rs:152`）；
- 每轮被 hint / public TX / 数据进展唤醒后，都会重新走一遍空队列的 512 次自旋。

低并发时循环“发一帧 → park”的节奏最明显，所以 tokio N=2 和 compio N=2 受害最重；高并发时循环更忙、park 比例下降，但 compio 仍保留 14–23% 的损失。

## 6. 优化建议

### P0（已落地，R23）

```diff
// smux_v1/src/connection/chan_cfg_.rs
-    const FAST_SPIN: usize = 512usize;
+    /// 控制通道是低频 inbox；512 次自旋会在每次 park 时白烧 CPU。
+    /// 实测降到 0 后 tokio N=2 +48%、compio N=2 +76%，且 N=16 也 +10–34%。
+    const FAST_SPIN: usize = 0usize;
```

- 这是**私有配置常量**，不改公开 API；
- 落地后已跑：`smux_v1 --lib` 366/366、`smux_v1_uds_bench` 单测与 `paths_clean` 全过；
- 若担心“刚好到达”的微延迟，可再试 8/16/32；当前数据表明 0 已经优于 512。

### P1（进一步收回 park 成本）

1. **拆分控制/数据通道配置**：`CtrlChanCfg_`（`FAST_SPIN=0`）用于 attach 与 main request；若以后有真正的数据面 mpmc 通道，再保留较大自旋。
2. **复用 park future**：mux 的 `attach_fut`、demux 的 attach future、main 的 request future 都是每轮 `pin!` 重建；改成循环外持有、完成后再 re-arm，可减少等待节点/唤醒注册的反复建立。
3. 给控制通道加**轻量通知**（原子位 + waker），彻底不走 mpmc 的等待队列；这是比调参更彻底的方案，但改动面更大，建议在 P0 验证后再评估。

### P1（控制面路径）

`WINDOW_UPDATE` 现在由 demux 判定、main_loop 组帧、mux 从公共 TX ring 搬出，比旧版多一跳。P0 修复后它已不是瓶颈（opt 全面超过旧版），所以**不建议现在为此改架构**；若后续 N=2 仍要压延迟，可考虑：

- main_loop 对同一子流的多条通告做合并/批量；
- 单条通告时允许 demux 走一条预分配的快速路径（注意保持“取快照”与“帧写得出去”的原子性）。

### P2（数据面）

`memmove` 占 7–14% 用户态周期。可评估：

- 帧头与载荷是否还能减少一次中间拷贝；
- 大 chunk 下 `enqueue_frame_parts_` 的分段写入是否可合并；
- 但这是次要点，优先级低于 P0。

### 内存

- 分配次数从 10 万降到 552 是明显收益，保持；
- 增加一个“连接 drop → 驱动作用域到静止 → live heap 回到基线”的测试，确认 heaptrack 的退出未释放量不是泄漏；
- 峰值堆 +5.5% 可接受；若在意，可检查 `sw_scope` 的池是否按连接长期保留。

## 7. 持续检测方案（本机已具备）

工具已安装：`perf`、`heaptrack`、`hyperfine`、`valgrind`、`sysstat`、`bpftrace`、`rustfilt`、`python3-psutil/matplotlib`、`gnuplot`。注意：

- `perf` 可用（`perf_event_paranoid=2`，但容器有 `CAP_PERFMON`；实测软/硬件计数正常）；
- tracefs 是只读挂载，`bpftrace` 的 tracepoint/kprobe 会受限；用 `perf sched`/`perf stat` 替代；
- `cache-misses`/`stalled-cycles-*` 在该 VM 不支持；可用 `LLC-loads`/`LLC-load-misses`、`cycles`、`instructions`、`IPC`。

建议每轮改动至少跑：

```bash
# 1) 交替 A/B（旧/新或基线/候选），每个点取中位数
python3 .tmp/ab/run_ab.py

# 2) CPU 成本
perf stat -j -e cycles,instructions,LLC-loads,LLC-load-misses,task-clock -- \
  target/release/bench_tokio --cases 2 --modes smux --bytes 64M --repeat 1 --runners 1 --out /tmp/x

# 3) 热点（带符号构建）
CARGO_PROFILE_RELEASE_DEBUG=1 RUSTFLAGS='-C force-frame-pointers=yes' \
  cargo build --release --bin bench_tokio
perf record -e cycles:u -F 999 -g --call-graph fp -- ./target/release/bench_tokio ...
perf report --stdio --no-children --sort symbol

# 4) 内存曲线
python3 .tmp/ab/observe.py /tmp/mem.csv -- ./target/release/bench_tokio ...

# 5) 堆分配点
heaptrack -o /tmp/heap ./target/release/bench_tokio ...
heaptrack_print -f /tmp/heap.zst.gz
```

CI 闸门建议：

- 带宽中位数回退 > 3% 失败；
- `cycles/B` 上涨 > 5% 失败；
- `task_cv` 上涨 > 2 个百分点失败；
- 峰值 RSS 上涨 > 10% 或出现单调增长失败；
- 每个提交保存 `(commit, backend, N, bw, cycles/B, IPC, task_cv, maxRSS)` 的 CSV，画趋势图。
